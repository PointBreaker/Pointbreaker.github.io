页错误处理

页错误不是 bug，而是机会。通过捕获页错误并更新页表，内核可以实现惰性分配、写时复制、按需分页等强大机制——提升性能、简化编程模型。

授课：rtm (Robert Morris) 日期：2025-02-13 难度：较高

虚拟内存的多个视角

视角说明
隔离每个进程有自己的地址空间——页表的原始目的
间接层页表给内核提供了"做酷事情"的机会

已有的"酷事情"

  • 共享 Trampoline 页（用户/内核切换）
  • Guard page（无 PT$E_{U}$，检测栈溢出）
  • Super pages（减少 TLB miss）

核心思想：在页错误时修改页表

页错误是一种 trap（类似系统调用）。xv6 默认 panic，但你可以：

  1. 检查错误原因和地址
  2. 分配物理页并更新页表
  3. 重新执行触发错误的指令

页错误 + 页表更新 = 强大的抽象工具！

惰性/按需页分配（Lazy/On-Demand Allocation）

问题：sbrk() 的浪费

sbrk() 是 UNIX 的传统 API，用于扩展堆。但它预先分配内存：

  • 应用可能申请大块内存但只使用一小部分
  • 如果内存紧张，sbrk() 可能阻塞等待内核回收页面

现代方案：惰性分配

计划：
  1. sbrk() 只增加 p->sz（地址空间大小），不实际分配
  2. 应用访问内存时触发 page fault
  3. 内核在 page fault 处理中分配物理页、安装 PTE
  4. 重新执行触发错误的指令

好处：
  - 未使用的内存不分配 → 节省内存
  - 分配开销分散到多次 page fault，而非集中在 sbrk()

Demo：xv6 的 sbrklazy()

// user/lazy.c
int main() {
    // buf 预留 10 页的空间，但不实际分配
    sbrklazy(buf, 10 * PGSIZE);
    // 只使用 3 页
    buf[0] = 'a';       // 第 1 次 page fault
    buf[4096] = 'b';    // 第 2 次 page fault
    buf[8192] = 'c';    // 第 3 次 page fault
    // 只触发 3 次 fault，分配 3 个物理页
}

vmfault() 实现

// kernel/trap.c
void vmfault(uint64 va, struct proc *p) {
    // 1. 检查 va 是否在 p->sz 范围内

        panic("vmfault: invalid va");

             (uint64)mem, PT$E_{W}$ | PT$E_{R}$ | PT$E_{U}$);

copyin/copyout 的复杂性

如果应用把 buf 传给 read()/write()，内核需要写入 buf 的物理页：

  • buf 可能还没有物理页（未触发 page fault）
  • copyin()/copyout() 需要先调用 vmfault() 确保 buf 有物理页
  • 物理地址在内核直接映射中，内核可以直接写入

对 lazy 应用来说，这一切都是透明的——它不知道发生了 page fault。

一个零页：按需填零（Zero Fill on Demand）

问题：大量零初始化内存

应用程序常有大量必须为零的内存（全局数组、BSS 段）。exec() 必须为 BSS 段分配页并清零——浪费时间和内存。

解决方案：共享零页

计划：
  1. memset 一个物理页为零
  2. 需要零页时，把零页映射为只读（无 PT$E_{W}$）
  3. 应用尝试写入 → page fault
  4. 分配新页、清零、映射为 R/W

好处：
  - 多个进程共享同一个零页
  - 只有真正写入的页才需要分配

Demo：vmfault0

void vmfault0(uint64 va, struct proc *p) {
    pt$e_{t}$ *pte = walk(p->pagetable, va, 0);

    if (是写错误 && 当前是零页) {

        memset(mem, 0, PGSIZE);
        mappages(p->pagetable, ..., mem, PT$E_{W}$ | PT$E_{R}$ | PT$E_{U}$);
    } else {
        // 第一次 fault：映射零页为只读
        mappages(p->pagetable, ..., zer$o_{page}$, PT$E_{R}$ | PT$E_{U}$);
    }
}

写时复制（Copy-On-Write）Fork

观察：fork + exec 的浪费

fork()    → 复制父进程所有内存（可能很大）
exec()    → 丢弃刚复制的内存，加载新程序
→ 复制白做了！

解决方案：COW Fork

计划：
  1. fork() 不复制物理页，而是共享
  2. 父/子进程的 PTE 设为只读（使用 RSW 位标记 COW）
  3. 任一进程尝试写入 → page fault
  4. 分配新页、复制内容、映射为 R/W
  5. 需要维护物理页的引用计数

PTE 格式（RSW 位）：
  [10 保留（含 2 位 RSW）| 44 PPN | 10 标志]
  RSW = Reserved for Software，xv6 用来标记 COW

COW 的挑战

  • 引用计数——知道何时真正释放页
  • 多个进程共享同一物理页——fork 后 exec 时如何处理？
  • 在真实 OS 中很复杂（参见 Linux 的 COW 实现）

按需分页（Demand Paging）

问题：exec 加载整个文件

exec() 从磁盘加载整个可执行文件到内存——可能很大，且可能只用了一部分。

解决方案：按需加载

计划：
  1. exec() 只分配 PTE，标记为"按需"（不加载实际内容）
  2. 应用访问某页 → page fault
  3. 从磁盘读取该页到内存、安装 PTE
  4. 需要 VMA（Virtual Memory Area）结构记录每页在磁盘的位置

VMA：Virtual Memory Area

struct vma {
    uint64 start;       // 起始虚拟地址
    uint64 end;         // 结束虚拟地址
    int prot;           // 读/写/执行权限
    struct file *f;     // 对应的文件
    uint64 offset;      // 文件中的偏移
};

虚拟内存大于物理内存

问题：应用需要比物理内存更多的内存

128 MB RAM 的机器如何运行需要 512 MB 的程序？

解决方案：换页（Paging）

计划：
  1. 把不常用的页换出到磁盘
  2. 需要时再换入
  3. 不写回未修改的页（D=dirty 位帮助识别）
  4. 替换策略：LRU（Least Recently Used）
     - A（Accessed）位帮助实现 LRU

工作集（Working Set）：
  - 如果活跃页能放入物理内存 → 工作正常
  - 如果工作集 > 物理内存 → 抖动（thrashing）

应用可以影响替换策略：

  • madvise()：告诉内核预期的访问模式
  • mlock()：锁定页面不被换出

内存映射文件（Memory-Mapped Files）

思想：用 load/store 访问文件

  • 内核按需从磁盘加载页（类似 demand paging）
  • 内存满时，把不常用的文件页换出
  • 修改过的页（dirty）写回磁盘

本课要点

页错误 = 机会

页错误不是 bug，而是更新页表、实现高级抽象的入口。

惰性分配节省内存

只在真正使用时分配物理页——未使用的地址空间不占物理内存。

COW 优化 fork

共享物理页、标记只读——写入时才复制，避免 fork+exec 的浪费。

mmap 简化文件访问

把文件映射到地址空间，用 load/store 直接访问——无需显式 read/write。
