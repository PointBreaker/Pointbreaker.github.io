GPU 架构与性能

理解 GPU 硬件是理解为什么深度学习代码这样写的关键。为什么 matmul 那么快？为什么 memory-bound 操作这么慢？为什么 kernel fusion 能加速？这一课从硬件层面回答这些问题。

授课：Tatsu Hashimoto 预计用时：80 分钟 难度：中等

GPU 架构概览

CPU vs GPU

特性CPUGPU
核心数~16-64 复杂核心~1000s 简单核心
优化目标低延迟（latency）高吞吐（throughput）
适合任务串行、分支密集并行、计算密集
内存低延迟，大容量高带宽，较大容量

A100 GPU 架构

A100 SM (Streaming Multiprocessor) 结构:
├── 108 个 SM
├── 每个 SM 包含:
│   ├── 64 FP32 CUDA cores (INT32 也可)
│   ├── 4 个 Tensor Cores (第三代)
│   │   └── 每个每时钟 256 FP16 FMA = 512 FLOPs
│   ├── 192 KB L1 cache / Shared Memory (可配置)
│   └── 寄存器文件 (256 KB)
├── 40 MB L2 cache (共享)
└── 80 GB HBM2e (高带宽内存)
    带宽: 2 TB/s

H100 GPU 架构（新一代）

H100 SM (Streaming Multiprocessor) 结构:
├── 132 个 SM (SXM5) / 144 个 SM (NVSwitch)
├── 每个 SM 包含:
│   ├── 128 FP32 CUDA cores
│   ├── 4 个 Tensor Cores (第四代)
│   │   └── 支持 FP8, FP16, BF16, TF32
│   ├── 228 KB L1 cache / Shared Memory
│   └── 寄存器文件 (256 KB)
├── 50 MB L2 cache
└── 80 GB HBM3
    带宽: 3.35 TB/s

GPU 内存层次

从慢到快，从大到小

层次大小带宽延迟访问者
HBM (Global Memory)80 GB3.35 TB/s~500 cycles所有 thread
L2 Cache50 MB~10 TB/s~30 cycles所有 thread
L1 Cache / Shared Memory228 KB/SM~19 TB/s~3 cycles同 block
Registers256 KB/SM~160 TB/s0 cycle单个 thread

仓库 vs 工厂类比（Horace He）：

HBM = 仓库：容量大，但搬运慢（带宽有限）

SRAM = 工厂车间：容量小，但搬运快（带宽极高）

Registers = 工人手：容量极小，但最快

优化目标：最小化从"仓库"（HBM）搬运数据的次数。

内存带宽 vs 计算速度

H100 (SXM5) 关键数字:
  计算峰值 (bf16): 989 TFLOP/s
  内存带宽:       3.35 TB/s
  Ridge point:    989e12 / 3.35e12 $≈$ 295 FLOP/byte

  这意味着: 每从 HBM 读 1 字节数据，需要做 295 次浮点运算
  才能"掩盖"内存延迟，达到 compute-bound。

GPU 执行模型

Thread, Block, Grid

# GPU 编程的基本抽象
Grid
 └── Thread Block (CTA)  ← 在单个 SM 上执行
      └── Warp (32 threads)  ← 以 SIMD 方式执行
           └── Thread        ← 基本执行单位

# 为什么是 Warp？
# 32 个线程以 lockstep 执行同一条指令
# 这是 GPU SIMD (Single Instruction, Multiple Thread) 的基础

SIMT 执行模型

SIMT = Single Instruction, Multiple Thread

# Warp 中的 32 个线程同时执行同一条指令
# 但操作不同的数据

# 例如: 向量加法
# Thread 0: a[0] + b[0] → c[0]
# Thread 1: a[1] + b[1] → c[1]
# ...
# Thread 31: a[31] + b[31] → c[31]
# 这 32 个加法在同一时钟周期完成！

分支发散（Branch Divergence）：如果 warp 中的一些线程走 if 分支，一些走 else 分支，GPU 会串行执行两个分支。这会导致性能下降。

# 坏: 分支发散
if threadIdx.x % 2 == 0:
    d$o_{A}$()  # 16 个线程执行
else:
    d$o_{B}$()  # 16 个线程执行
# 实际执行时间 = time(A) + time(B)

# 好: 无分支
# 让所有线程走相同路径

Occupancy

Occupancy = 活跃 warp 数 / 最大支持 warp 数

高 occupancy 意味着 SM 有更多的 warp 可以调度——当一个 warp 等待内存时，SM 可以切换到另一个 warp。

# 影响 occupancy 的因素:
# 1. 每个 thread 使用的寄存器数
# 2. 每个 block 使用的 shared memory
# 3. block 大小

# 经验法则:
# - 目标 occupancy > 50%
# - block size 应该是 warp size (32) 的倍数
# - 通常 block size = 128 或 256

Roofline Model

概念

Roofline model 直观地展示一个操作的性能上限：

性能 (FLOP/s)
    ↑
    │        ┌──────── 计算上限 (compute ceiling)
    │       /
    │      /  ← 斜率 = 内存带宽
    │     /
    │    /
    │───/───────────────→ 算术强度 (FLOP/byte)
    │  ridge point
  • 低算术强度：在斜线上 → memory-bound，性能 = 带宽 $\times$ 算术强度
  • 高算术强度：在平顶下 → compute-bound，性能 = 计算峰值

常见操作的 Roofline 位置

操作算术强度瓶颈
Element-wise (add, mul)~0.5 FLOP/byteMemory-bound
LayerNorm~1 FLOP/byteMemory-bound
Softmax~1 FLOP/byteMemory-bound
MatMul (B=1)~1 FLOP/byteMemory-bound
MatMul (B=1024)~512 FLOP/byteCompute-bound
Large MatMul>> 295 FLOP/byteCompute-bound

优化策略

Memory-bound 操作的优化：

  • Kernel fusion：合并多个操作，减少 HBM 读写
  • 提高精度：用 bf16 替代 fp32，减少传输量
  • 减少 batch/sequence：推理时 B=1 是 memory-bound 的根源

Compute-bound 操作的优化：

  • Tensor Cores：确保使用 Tensor Core（维度对齐）
  • FlashAttention：减少不必要的计算
  • 混合精度：用低精度 Tensor Core

Tensor Cores

什么是 Tensor Core？

Tensor Core 是 GPU 上的专用硬件单元，专门做矩阵乘法：

# 一个 Tensor Core 每个时钟周期执行:
# D = A $\times$ B + C
# 其中 A, B, C, D 是小矩阵 (如 1$6 \times 1$6)

# H100 第四代 Tensor Core:
# - 支持 FP8, FP16, BF16, TF32, FP64
# - 每个 SM 有 4 个 Tensor Core
# - 每个 Tensor Core 每时钟 256 FP16 FMA = 512 FLOPs

使用 Tensor Core 的条件

  • 数据类型：FP16, BF16, TF32, FP8（不支持 FP32！）
  • 矩阵维度：通常需要是 8 或 16 的倍数
  • 内存布局：需要满足对齐要求

TF32：两全其美

# TF32 (TensorFloat-32): A100 引入
# 1 位符号 + 8 位指数 + 10 位尾数 = 19 bits
# 范围和 FP32 一样（8 位指数），精度稍低（10 vs 23 尾数）
# 但用 Tensor Core 加速！

# 使用方式: PyTorch 默认开启
# torch.backends.cuda.matmul.allo$w_{tf32}$ = True

内存访问模式

Coalesced Access（合并访问）

GPU 内存访问以 32/128 字节的 "sector" 为单位。如果 warp 中的线程访问连续地址，可以合并为一个内存事务：

# Good: Coalesced (连续访问)
# Thread 0 → address 0
# Thread 1 → address 4
# Thread 2 → address 8
# ... → 一个 128B 事务搞定

# Bad: Strided (跨步访问)
# Thread 0 → address 0
# Thread 1 → address 1024
# Thread 2 → address 2048
# ... → 32 个独立事务！

Shared Memory Bank Conflicts

Shared memory 被分为 32 个 bank，每个 bank 宽 4 字节：

# 如果 warp 中多个线程访问同一 bank 的不同地址
# 会发生 bank conflict，串行化访问

# Good: 无 conflict
# Thread 0 → bank 0
# Thread 1 → bank 1
# ...

# Bad: 2-way bank conflict
# Thread 0 → bank 0, address 0
# Thread 16 → bank 0, address 1024
# 这两个访问会被串行化

GPU 编程范式

CUDA C++

// 最底层，最灵活，最复杂
__global__ void vecto$r_{add}$(float *a, float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

// 启动 kernel
vecto$r_{add}$<<<nu$m_{blocks}$, bloc$k_{size}$>>>($d_{a}$, $d_{b}$, $d_{b}$, n);
