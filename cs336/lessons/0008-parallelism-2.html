ZeRO 优化器与 FSDP

上一课讲了四种基本并行策略。这一课深入 Data Parallelism 的内存优化——ZeRO 优化器如何通过分片消除冗余存储，以及 PyTorch 的 FSDP 如何实现这些思想。

授课：Tatsu Hashimoto 预计用时：80 分钟 难度：困难

Data Parallelism 的内存问题

DDP 的冗余

在标准 Data Parallelism 中，每个 GPU 都存了完整副本：

# 每个 GPU 存储（70B 模型, fp32 + AdamW）:
参数:     $4 \times 7$0B = 280 GB
梯度:     $4 \times 7$0B = 280 GB
优化器 m: $4 \times 7$0B = 280 GB
优化器 v: $4 \times 7$0B = 280 GB
─────────────────────────────
总计:     1120 GB  ← 远超单卡 80 GB！

# 问题: 8 个 GPU 各存一份 → $8 \times 1$120 GB = 8960 GB
# 其中 7/8 是冗余的！

核心洞察：在 DDP 中，每个 GPU 最终得到的是相同的梯度（All-Reduce 后），然后用相同的梯度更新参数。这意味着每个 GPU 的优化器状态在每一步都是相同的——完全冗余！

ZeRO：消除冗余

ZeRO 的三阶段

ZeRO（Zero Redundancy Optimizer, Rajbhandari et al. 2020）通过分片消除冗余：

Stage分片什么内存节省通信
Stage 1优化器状态 (m, v)1/4 内存无额外
Stage 2+ 梯度1/4 内存Reduce-Scatter
Stage 3+ 参数1/N 内存All-Gather

ZeRO Stage 1：分片优化器状态

# 标准 DDP:
# 每个 GPU 存完整的 m 和 v（各 4P bytes）

# ZeRO Stage 1:
# 把 m 和 v 均分到 N 个 GPU
# GPU i 只存 m[i*N/N : (i+1)*N/N] 和 v[...]

# 每个 GPU 内存:
# 参数: 4P（完整）
# 梯度: 4P（完整）
# 优化器: 8P/N（分片）
# 总计: 8P + 8P/N bytes

# 8 GPU: 8P + P = 9P（vs 标准 16P）→ 节省 44%

ZeRO Stage 2：+ 分片梯度

# ZeRO Stage 2:
# 梯度也分片——每个 GPU 只存自己负责的那部分参数的梯度

# 关键: All-Reduce → Reduce-Scatter
# Reduce-Scatter 让每个 GPU 只得到自己那部分的聚合梯度

# 每个 GPU 内存:
# 参数: 4P（完整）
# 梯度: 4P/N（分片）
# 优化器: 8P/N（分片）
# 总计: 4P + 12P/N bytes

# 8 GPU: 4P + 1.5P = 5.5P → 节省 66%

ZeRO Stage 3：+ 分片参数

# ZeRO Stage 3:
# 参数也分片——每个 GPU 只存 1/N 的参数

# 前向/反向计算时:
# 1. All-Gather 获取完整参数
# 2. 计算
# 3. 丢弃非本地的参数分片

# 每个 GPU 内存:
# 参数: 4P/N（分片）
# 梯度: 4P/N（分片）
# 优化器: 8P/N（分片）
# 总计: 16P/N bytes

# 8 GPU: 2P → 节省 87.5%！

ZeRO Stage 3 的代价：每次前向/反向都需要 All-Gather 获取完整参数。通信量 = 4P bytes（每层）。

但通信可以和计算 overlap——在计算第 i 层时，同时 All-Gather 第 i+1 层的参数。

ZeRO 内存总结

# 70B 模型, 8 GPU, fp32 + AdamW

标准 DDP:     16P = 1120 GB/GPU  ← 放不下
ZeRO Stage 1: 9P  = 630 GB/GPU   ← 还是放不下
ZeRO Stage 2: 5.5P = 385 GB/GPU  ← 还是放不下
ZeRO Stage 3: 2P  = 140 GB/GPU   ← 还是放不下（但接近了！）

# 加上 bf16 混合精度:
# 参数 bf16: 2P/N
# 主参数 fp32: 4P/N
# 梯度 bf16: 2P/N
# 优化器 fp32: 8P/N
# 总计: 16P/N bytes

# 8 GPU: 2P = 140 GB → 还是超
# 16 GPU: P = 70 GB → 放得下！

FSDP：PyTorch 的 ZeRO 实现

什么是 FSDP？

FSDP (Fully Sharded Data Parallel) 是 PyTorch 1.11+ 内置的 ZeRO Stage 3 实现。

from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

# 包装模型
model = FSDP(
    model,
    shardin$g_{strategy}$=ShardingStrategy.FUL$L_{SHARD}$,  # ZeRO Stage 3
    cp$u_{offload}$=CPUOffload(offloa$d_{params}$=False),
    aut$o_{wrap}$_policy=transforme$r_{auto}$_wra$p_{policy}$,
)

FSDP 的工作流程

# FSDP 的前向传播（以一层为例）:

# 1. All-Gather: 从所有 GPU 收集完整参数
#    GPU 0 有 W[0:N/4], GPU 1 有 W[N/4:N/2], ...
#    → 所有 GPU 得到完整 W

# 2. 前向计算: Y = X @ W
#    每个 GPU 用不同的数据片（data parallel）

# 3. 释放: 丢弃非本地的参数分片
#    只保留本地的 W[rank*N/N : (rank+1)*N/N]

# 4. 反向传播时:
#    - All-Gather 参数（再次）
#    - 计算梯度
#    - Reduce-Scatter 梯度（每个 GPU 得到自己那部分的聚合梯度）
#    - 更新本地参数分片

FSDP 的通信量

# 每层前向: All-Gather 参数 = 4P bytes
# 每层反向: All-Gather 参数 + Reduce-Scatter 梯度 = 8P bytes
# 总计: 12P bytes per layer per step

# 对比 DDP:
# 每步: All-Reduce 梯度 = 8P bytes（与层数无关）

# FSDP 通信更多，但内存更少
# 适合: 模型太大，DDP 放不下时

FSDP 策略对比

策略描述内存通信
FUL$L_{SHARD}$ZeRO Stage 3，全分片最低最高
SHAR$D_{GRAD}$_OPZeRO Stage 2，只分片梯度+优化器中中
N$O_{SHARD}$标准 DDP，不分片最高最低
HYBRI$D_{SHARD}$节点内分片，节点间复制低中

HYBRI$D_{SHARD}$（推荐）：

  • 节点内（8 GPU）：FUL$L_{SHARD}$，利用 NVLink 高带宽
  • 节点间：DDP 复制，减少跨节点通信
  • 兼顾内存节省和通信效率

混合精度 + 并行

混合精度下的内存

# 混合精度训练 (bf16 前向 + fp32 主参数):

# 参数:
#   bf16 参数: 2P（用于前向/反向计算）
#   fp32 主参数: 4P（用于优化器更新）
# 梯度:
#   fp32 梯度: 4P（用于优化器）
# 优化器:
#   fp32 m: 4P
#   fp32 v: 4P

# 总计: 18P bytes（vs fp32 的 16P，稍多但激活值省一半）

混合精度 + FSDP

# FSDP + 混合精度:
# 每个 GPU 只存 1/N 的上述所有内容

# 8 GPU, 70B 模型:
# 每 GPU: 18P / 8 = 2.25P = ~157 GB → 还是超
# 16 GPU: 18P / 16 = ~79 GB → 勉强放得下

# 实际中还需要 activations 的内存
# 所以通常需要 gradient checkpointing

Gradient Checkpointing

用计算换内存——不保存中间激活，反向时重算：

from torch.utils.checkpoint import checkpoint

# 不 checkpoint: 保存所有激活 → 内存 $O(n^2)$
# Checkpoint: 只保存 checkpoint 点 → $O(n^2)$ 或 $O(n^2)$

# 在 FSDP 中:
model = FSDP(
    model,
    aut$o_{wrap}$_policy=siz$e_{based}$_aut$o_{wrap}$_policy,
    transforme$r_{layer}$_cls={TransformerBlock},  # 按层 checkpoint
)

通信原语实现

Ring All-Reduce

# Ring All-Reduce 的两个阶段:

# Phase 1: Reduce-Scatter
# 每个 GPU 把数据分成 N 份
# 在 ring 中传递并累加
# 经过 N-1 步，每个 GPU 有 1/N 的完整结果

# Phase 2: All-Gather
# 每个 GPU 把自己的 1/N 结果在 ring 中传递
# 经过 N-1 步，每个 GPU 有完整结果

# 总通信量: 2 $\times$ (N-1)/N $\times$ dat$a_{size}$ $≈$ 2 $\times$ dat$a_{size}$
# 与 N 无关！这是 ring algorithm 的美妙之处

NCCL：NVIDIA 的通信库

# NCCL 自动选择最优算法:
# - 小数据: Ring all-reduce
# - 大数据: Tree all-reduce（两步：reduce + broadcast）
# - 节点内: 利用 NVLink
# - 节点间: 利用 InfiniBand/RoCE

# PyTorch 接口:
import torch.distributed as dist

# All-Reduce
dist.al$l_{reduce}$(tensor, op=dist.ReduceOp.SUM)

# Reduce-Scatter
dist.reduc$e_{scatter}$_tensor(output, input, op=dist.ReduceOp.SUM)

# All-Gather
dist.al$l_{gather}$_int$o_{tensor}$(outpu$t_{tensor}$, inpu$t_{tensor}$)

带宽测量

# 实测 NCCL 带宽:

# All-Reduce benchmark

# InfiniBand (跨节点): ~30-40 GB/s

Scaling Efficiency

# 理想: N 个 GPU → N$\times$ 加速
# 实际: 通信开销导致亚线性加速

# 弱 scaling (固定每 GPU batch size):
# 效率通常 80-95%

# 强 scaling (固定总 batch size):
# 效率通常 60-80%（通信占比增大）

# 影响 scaling 的因素:
# 1. 模型大小（越大，计算占比越高，scaling 越好）
# 2. Batch size（越大，通信占比越低）
# 3. 网络带宽（NVLink vs InfiniBand）
# 4. 并行策略选择
