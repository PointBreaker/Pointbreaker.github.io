语言模型评估

评估看似机械——扔一些 prompt 进去，算个平均分——但实际上是一个深刻而丰富的话题。评估决定了语言模型的未来发展方向，选择错误的指标会引导整个领域走偏。

授课：Percy Liang & Sida Wang 预计用时：80 分钟 难度：中等 → 较高

为什么评估如此困难？

打开任何一个前沿模型的论文（DeepSeek-R1、Llama 4、OLMo 2），你会看到一张 benchmark 分数表。这些数字看起来精确而权威。但这一课要告诉你：每个数字背后都有很多主观选择。

评估框架四问：

  1. 输入是什么？（哪些用例？难度分布？）
  2. 如何调用模型？（prompt？chain-of-thought？工具？）
  3. 如何评估输出？（ground truth？自动指标？人类？）
  4. 如何解释结果？（91% 意味着什么？能部署吗？）

评估的目的决定方法

目的评估方式关注点
采购决策Chatbot Arena用户满意度
测量能力MMLU, GPQA知识/推理
改进模型开发集 loss训练信号
安全评估HarmBench, AIR-Bench风险/伤害
政策制定标准化测试可比较性

一个数字不够

单一数字（如"MMLU 86.4%"）隐藏了太多信息：

  • 不同科目的表现差异巨大（历史 95% vs 数学 60%）
  • few-shot vs zero-shot 差异显著
  • prompt 格式影响结果
  • 模型可能"记住"了测试集

Karpathy 的"评估危机"：很多 benchmark 已经饱和（最高分 > 90%），但模型在实际使用中仍然会犯明显错误。benchmark 分数和真实能力之间的鸿沟越来越大。

Perplexity

定义

语言模型是 token 序列上的概率分布 p(x)。Perplexity 衡量模型对测试数据的"惊讶程度"：

# 给定测试集 D = {$x_{1}$, $x_{2}$, ..., $x_{N}$}
# Perplexity = exp(-1/N $\times$ $Σ$ log p($x_{i}$))

# 等价形式:
# Perplexity = 1 / p(D)^(1/|D|)

# 直觉:
# Perplexity = 1 → 完美预测（每个 token 概率 = 1）
# Perplexity = V → 完全随机（V = 词表大小）
# Perplexity 越低越好

为什么用 Perplexity？

  • 平滑：是连续值，适合拟合 scaling law
  • 通用：任何语言模型都可以计算，不依赖下游任务
  • 理论基础：与信息论中的交叉熵直接相关
  • 可比：不同模型可以在相同测试集上比较

Perplexity 的局限

  • 不代表下游能力：低 perplexity $≠$ 好的助手
  • 对 tokenization 敏感：BPE vs byte-level 的 perplexity 不可比
  • 需要概率输出：闭源模型只给 text output，无法计算
  • 不区分错误类型：幻觉和事实错误的代价不同

数据集来源大小特点
Penn TreebankWSJ 新闻1M words小，经典

# GPT-2 的 perplexity 结果（zero-shot 迁移）
# 在 WebText 上训练，在其他数据集上评估

Perplexity on:
- Penn Treeband: 46.5 (LSTM SOTA was 51.3)
- WikiText-103: 17.3
- One Billion Word: 66.3 (在更大的数据集上迁移效果下降)

# 关键洞察: 在相似分布的数据上 perplexity 低
# 在 out-of-distribution 上 perplexity 更高

Perplexity Maximalist 观点

极端观点：如果我们能完美预测语言（perplexity = 英语的熵），就解决了所有 NLP 任务。推低 perplexity 是通往 AGI 的道路。

反驳：这可能不是最高效的路径——某些对 perplexity 影响小的能力（如推理）可能对下游任务至关重要。

Perplexity 的"精神亲戚"

有些任务本质上就是 perplexity 的变体：

  • LAMBADA：预测句子的最后一个词（需要长距离上下文）
  • HellaSwag：选择最合理的句子结尾（4 选 1）
  • Cloze tasks：完形填空

知识 Benchmark

MMLU (Massive Multitask Language Understanding)

MMLU 是最广泛使用的知识测试之一：

  • 57 个学科：数学、美国历史、法律、医学、道德等
  • 题型：4 选 1 多选题
  • 来源：研究生和本科生从网上收集
  • 评估方式：few-shot (5-shot) prompting
# MMLU 示例问题 (抽象代数):
# 以下哪个是域 F 上的向量空间 V 的子空间 W 的必要条件？
# A. W 非空
# B. W 对加法封闭
# C. W 对标量乘法封闭
# D. 以上都是
# 答案: D

# GPT-3 (175B) 5-shot: 43.9%
# Chinchilla (70B): 67.6%
# GPT-4: 86.4% (报告值)

MMLU 的问题

  • 已饱和：最高分超过 90%，区分度下降
  • 噪声/平凡问题：部分题目质量不高
  • 记忆 vs 理解：模型可能记住了答案而非理解
  • 对 prompt 敏感：system prompt、few-shot 示例影响结果

MMLU-Pro

MMLU 的改进版：

  • 移除噪声/平凡问题
  • 选项从 4 个扩展到 10 个（更难猜对）
  • 使用 chain-of-thought 评估
  • 模型分数下降 16-33%（不再饱和）

GPQA (Graduate-Level Google-Proof Q&A)

更难的知识测试：

  • 由 61 位 PhD 级别的合同工编写
  • PhD 专家能达到 65% 准确率
  • 非专家（即使有 Google）只能达到 34%
  • GPT-4 只能达到 39%（接近非专家水平）

Humanity's Last Exam (HLE)

最新的"终极测试"：

  • 2500 道多模态问题
  • 多个学科，多选 + 简答
  • 提供 USD 500K 奖金池
  • 经过前沿 LLM 筛选（过滤掉太简单的）

指令跟随评估

MMLU 等结构化任务之外，更现实的评估是"指令跟随"——像 ChatGPT 那样响应用户请求。问题是：如何自动评估开放式生成？

Chatbot Arena

目前最受信任的评估方式之一：

  • 用户提交 prompt，两个匿名模型同时回答
  • 用户投票选择哪个更好
  • 用 Elo 评分系统计算排名
  • 优势：动态的输入（不是静态 benchmark）
# Chatbot Arena 的特点:
# 1. 输入来自真实用户（多样、长尾）
# 2. 评估者是真实人类（主观但真实）
# 3. 可以不断加入新模型
# 4. 结果接近真实用户偏好

# 局限性:
# 1. 用户群体有偏（英文、技术向）
# 2. 投票可能受风格而非内容影响
# 3. 无法复现（每次运行结果不同）

IFEval (Instruction-Following Eval)

自动化的指令跟随评估：

  • 给指令添加可自动验证的约束
  • 例如："用 3 段话回答"、"包含关键词 X"、"用中文回答"
  • 约束可以程序化检查，但语义质量仍需要人类判断
# IFEval 约束示例:
# 1. 长度约束: "至少 5 句话"
# 2. 格式约束: "用 JSON 格式回答"
# 3. 关键词约束: "包含'综上所述'"
# 4. 语言约束: "用法语回答"
# 5. 编号约束: "用编号列表"

# 评估: 检查输出是否满足每个约束
# 优点: 自动化、可复现
# 缺点: 约束较简单，不能衡量真正质量

AlpacaEval

  • 805 个指令（多种来源）
  • 用 GPT-4 作为 judge，比较模型回答 vs GPT-4 reference
  • 指标：win rate（模型赢过 GPT-4 的比例）
  • 局限性：GPT-4 作为 judge 有偏好（偏好长回答、偏好自己）

WildBench

  • 从 100 万真实人机对话中采样 1024 个例子
  • 用 GPT-4 turbo 作为 judge，使用 checklist（类似 CoT）
  • 与 Chatbot Arena 的相关系数 0.95（高度相关）
  • 可以作为 Arena 的快速代理

LM-as-a-Judge

用语言模型评估语言模型的输出——这是目前最流行的自动评估方法。

基本框架

# 输入: prompt + mode$l_{output}$
# Judge prompt: "评估以下回答的质量，给出 1-10 分..."

judg$e_{prompt}$ = """
给定问题: {prompt}
模型回答: {response}

请评估回答的质量:
1. 准确性 (1-10):
2. 完整性 (1-10):
3. 清晰度 (1-10):
总分: """

Judge 的偏差

LM judge 有多种系统性偏差：

偏差表现缓解方法
位置偏差偏好先看到的回答交换位置取平均
长度偏差偏好更长的回答控制长度或使用 rubric
自我偏好偏好与自己风格一致的使用多个 judge
难度偏差对难题评分过松按难度分层

Pairwise vs Pointwise

  • Pointwise：给单个回答打分（绝对质量）
  • Pairwise：比较两个回答哪个更好（相对质量）
  • Pairwise 通常更可靠（人类也更擅长比较而非绝对评分）

纯推理：ARC-AGI

试图将推理与知识分离：

  • 输入：彩色网格图案
  • 任务：根据示例推断变换规则，应用到新输入
  • 不需要语言或世界知识
  • 人类可以轻松解决，但 LLM 表现不佳

Test-Time Compute Scaling

除了增加模型规模，另一种提升性能的方法是在推理时增加计算。

Chain-of-Thought (CoT)

# 直接回答:
# Q: 3 个苹果 + 2 个梨 = ?
# A: 5

# Chain-of-Thought:
# Q: 3 个苹果 + 2 个梨 = ?
# A: 让我想想。3 个苹果，加上 2 个梨，一共是 3 + 2 = 5 个水果。
#    答案是 5。

# CoT 的优势:
# - 让模型"说出"推理过程
# - 对数学、逻辑、多步推理特别有效
# - 不需要重新训练

Self-Consistency

# 思路: 多次采样，选出现最一致的答案

# 对同一问题采样 10 次，每次用不同的 temperature
answers = []
for i in range(10):
    response = model.generate(prompt, temperature=0.7, seed=i)
    answer = extrac$t_{answer}$(response)
    answers.append(answer)

# 选出现频率最高的答案
fina$l_{answer}$ = max(set(answers), key=answers.count)

# 例: 10 次采样得到 [5, 5, 5, 5, 5, 6, 5, 7, 5, 5]
# 最终答案: 5（出现 8 次）

计算与性能的关系

OpenAI o1/o3 和 DeepSeek-R1 展示了 test-time compute 的 scaling：

  • 让模型"思考更久"（生成更长的 CoT）可以提升性能
  • 性能与推理时 FLOPs 呈（近似）幂律关系
  • 小模型 + 更多推理计算 $≈$ 大模型 + 少推理计算（某些任务）

关键洞察：存在一个 trade-off——把算力投入训练（更大的模型）vs 投入推理（更长的思考）。对于不频繁的任务，推理时计算更划算；对于高频任务，训练时计算更划算。

评估的有效性

Train-Test Overlap

现代 LLM 在"整个互联网"上训练。测试集也来自互联网。所以测试集可能已经被模型"看过"：

# 检测训练-测试重叠的方法:

# 方法 1: 直接检测
# - 检查测试样本是否在训练数据中（精确匹配）
# - 问题: 你不知道训练数据是什么（闭源模型）

# 方法 2: 利用数据的 exchangeability
# - 如果模型记住了测试样本，它对相似样本的 loss 也会低
# - 通过比较 loss 的分布来检测

# 方法 3: 时间分割
# - 用"新"数据（训练截止日期之后）作为测试集
# - 例: 用 2024 年数据测试 2023 年训练的模型

Dataset Quality

Benchmark 本身可能有质量问题：

  • SWE-Bench：部分测试用例不准确 → SWE-Bench Verified（人工审核）
  • MMLU：部分题目有错误答案
  • Platinum benchmarks：经过专家审核的高质量版本

我们在评估什么？方法还是模型？

时代评估对象规则
前基础模型方法固定 train/test split
基础模型模型/系统anything goes
纳米 GPT speedrun训练效率固定数据，目标 loss

关键问题：现在我们评估的是"模型 + prompt + agent 脚手架"的整个系统，而不是模型本身。这导致不同论文的结果难以比较——每个团队使用不同的 prompt 和脚手架。

安全评估

什么是安全？

安全不是一个单一维度：

  • 拒绝能力：拒绝有害指令
  • 幻觉率：不产生虚假信息
  • 偏见：不歧视特定群体
  • 隐私: 不泄露训练数据中的 PII
  • 双重用途：网络安全能力既可用于防御也可用于攻击

HarmBench

  • 510 种有害行为（违反法律或规范）
  • 评估模型是否会生成有害内容

AIR-Bench

  • 基于监管框架和公司政策
  • 314 个风险类别，5694 个 prompt

Jailbreaking

自动化的安全绕过：

# GCG (Greedy Coordinate Gradient):
# - 自动优化对抗性 prompt
# - 目标: 让模型输出被拒绝的内容
# - 关键发现: 对抗性 prompt 可以从开源模型迁移到闭源模型

# 例: "生成恶意代码" → 被拒绝
#      "生成恶意代码 + [对抗性后缀]" → 可能被接受

# 这说明了安全评估的重要性:
# - 不仅要测试"正常" prompt
# - 还要测试对抗性 prompt

Capabilities vs Propensity

安全的两个维度：

能力 (Capabilities)倾向 (Propensity)
定义模型能做什么模型愿意做什么
API 模型重要更重要（可以绕过）
开放权重更重要（可以微调掉安全）重要
