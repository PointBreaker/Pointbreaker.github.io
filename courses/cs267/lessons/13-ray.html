Ray 分布式框架

从课程项目到全球分布式计算平台：Ion Stoica 讲述 Ray 如何通过极简 API 与统一计算模型，让 Python 开发者轻松编写分布式 AI 应用。

授课：Ion Stoica 视频：YouTube 预计用时：75 分钟

Ray 的诞生背景

Ray 起源于 2016 年加州大学伯克利分校的 ODI（Observatory on Distributed Intelligence）项目，由 Ion Stoica 和 Joseph E. Gonzalez 指导的学生团队（包括 Philipp Moritz、Robert Nishihara 等）最初作为课程研究项目的产物。其核心动机是：强化学习等新兴 AI 工作负载需要一种比 MapReduce / Spark 更灵活的分布式编程模型。

从 RLlib 到 Anyscale

  • RLlib：Ray 上构建的强化学习库，展示了 Ray 在复杂 RL 训练循环中的优势
  • Ray v1.0（2020）：核心 API 稳定，任务/ Actor 模型成熟
  • Ray v2.0（2022）：引入compiled graph，支持静态 DAG 低延迟执行
  • Anyscale：由同一团队创立的商业公司，提供托管 Ray 云服务

为什么需要 Ray？AI 工作负载的三大趋势

Ion Stoica 指出，推动 Ray 需求的三大趋势是：

趋势 含义 对框架的要求
AI 需求 > 硬件增长 AI 计算需求每年增长 10x，远超摩尔定律 必须能横向扩展到数千 GPU
异构集群 单机多卡 → 多机多卡 → CPU/GPU/TPU 混合 统一管理异构资源和调度
复杂 AI 工作负载 训练、推理、数据处理、超参搜索交织 统一框架支持多阶段 pipeline

传统框架的局限

Spark/MapReduce 适合批处理；MPI 适合 HPC 科学计算；但 AI 工作负载需要嵌套并行（任务中包含任务）、异构任务（CPU 预处理 + GPU 训练）和有状态计算（参数服务器、环境模拟器）。现有框架无法优雅地表达这些模式。

Ray 的核心设计理念：统一计算框架

Ray 的目标是成为一个统一的计算框架，用同一套 API 表达从单机 Python 程序到数千节点的分布式应用。其设计哲学是"minimalist API"——用最少的概念覆盖最多的场景。

极简 API：六行代码入门

Ray 的 API 核心仅由几个函数和装饰器组成：

import ray

# 1. 连接到 Ray 集群（或本地启动）
ray.init()

# 2. 将普通函数转为分布式任务（Task）
@ray.remote
def compute(x):
    return x * x

# 3. 异步提交任务，返回 Future
futures = [compute.remote(i) for i in range(10)]

# 4. 获取结果
results = ray.get(futures)

# 5. 将对象存入共享内存 Object Store
ref = ray.put(large_object)

# 6. 等待部分结果（不阻塞全部）
done, pending = ray.wait(futures, num_returns=3)
API 作用 特点
ray.init()初始化 Ray 运行时连接集群或本地启动
@ray.remote装饰器：函数→Task，类→Actor声明式并行
.remote()异步调用 remote 函数/方法返回 ObjectRef (Future)
ray.get()阻塞等待并获取结果可传入列表批量获取
ray.put()将对象存入 Object Store获得引用，零拷贝共享
ray.wait()非阻塞等待部分结果支持超时和 num_returns

FAST 计算模型

Ray 用四个核心抽象（FAST）统一所有分布式计算模式：

抽象 英文 语义 类比
Function Task 无状态、幂等的远程函数执行 类似函数调用，无副作用
Actor Actor 有状态的分布式对象，方法串行执行 带邮箱的 Actor 模型
Schedule 调度器 全局 + 两级调度，感知数据位置 混合调度架构
Transport Object Store 共享内存对象存储，零拷贝传输 分布式共享内存

Python 示例：从函数到 Task，从类到 Actor

import ray

ray.init()

# ===== Task：无状态函数 =====
@ray.remote
def add(a, b):
    return a + b

# 提交 1000 个任务，自动并行
refs = [add.remote(i, i) for i in range(1000)]
results = ray.get(refs)

# ===== Actor：有状态对象 =====
@ray.remote
class Counter:
    def __init__(self):
        self.value = 0

    def increment(self):
        self.value += 1
        return self.value

# 创建 10 个独立 Actor 实例
counters = [Counter.remote() for _ in range(10)]
# 每个 Actor 内部状态独立
refs = [c.increment.remote() for c in counters]
print(ray.get(refs))  # [1, 1, 1, ...]

Task vs Actor 选择指南

  • Task：无状态、 embarrassingly parallel、自动负载均衡
  • Actor：需要维护状态（模型权重、环境、参数服务器）、需要资源亲和性（绑定 GPU）

共享内存 Object Store：零拷贝的魔法

Ray 的核心创新之一是跨节点的共享内存 Object Store，基于 Apache Arrow Plasma 对象存储实现：

零拷贝传输

当 Task A 产生一个大数组（如 1GB 的 NumPy 数组），Task B 消费它时：

  • 数据写入本地 Object Store（基于共享内存）
  • Task B 通过引用（ObjectRef）访问
  • 同一节点：零拷贝（共享内存直接读取）
  • 跨节点：仅传输一次，后续 Task 从本地缓存读取

这避免了 Spark 的序列化/反序列化开销，对 AI 工作负载（大张量传输）至关重要。

Compiled Graph：静态 DAG 的低开销执行

Ray v2.0 引入 Compiled Graph（原名 Ray DAG），适用于延迟敏感的场景：

  • 用户用 @ray.remote 声明静态计算图（DAG）
  • Ray 在启动时预分配资源、预编译执行计划
  • 运行时直接执行，跳过调度开销
  • 适合在线推理（要求 P99 延迟极低）

GPU-GPU 传输：NCCL 集成

Compiled Graph 中，相邻 GPU 节点之间的数据传输通过 NCCL（NVIDIA Collective Communications Library）完成，支持 GPUDirect RDMA，绕过 CPU 拷贝，实现 100+ GB/s 的 GPU 间带宽。

Ray 架构深度解析

全局控制存储（GCS）

GCS（Global Control Store）是 Ray 集群的元数据中枢：

  • 存储所有 Actor 的位置、任务调度信息、对象位置映射
  • 基于 Redis 的改进版，支持 TTL 和故障检测
  • 集群中唯一的全局状态源（single source of truth）

分布式调度器

Ray 采用两级调度架构：p>

层级 职责 位置
全局调度器 跨节点调度，考虑数据位置和资源约束 GCS 内
本地调度器 节点内任务排队、CPU/GPU 资源分配 每个 Node 上

可扩展性：分片 GCS

随着集群规模增长，GCS 可能成为瓶颈。Ray 通过分片 GCS（Sharded GCS）将元数据分散到多个 GCS 分片，每个分片负责一部分 Actor/对象，从而支持 1000+ 节点的集群。

容错机制

Ray 提供两种互补的容错策略：

机制 原理 适用场景
Lineage-based 每个对象记录其计算 lineage（依赖图），丢失时重算 Task（无状态，可重放）
Ownership Actor 由 Owner 管理，Owner 失效则 Actor 不可恢复 Actor（有状态，需外部存储 checkpoint）

Actor 容错的限制

与 Task 不同，Actor 是有状态的，Ray 不会自动重建失效的 Actor。开发者需要自行实现 checkpoint 机制（如将状态保存到 S3），或使用 max_restarts 参数让 Ray 尝试重建空壳 Actor。

为什么需要 Actor？（深度分析）

Ion Stoica 强调，Actor 模型解决了 Task 无法表达的几种关键模式：

场景 为什么 Task 不够 Actor 如何解决
参数服务器 需维护全局模型状态 Actor 持有模型，方法串行更新
环境模拟 RL 环境需连续状态 Actor 封装环境，step() 保持状态
GPU 亲和性 Task 无绑定，GPU 切换开销大 Actor 绑定 GPU，避免 context switch
流水线阶段 需长期运行的计算阶段 Actor 常驻内存，低延迟响应

传递 Actor Handle：构建分布式应用

Ray 允许将一个 Actor 的 handle 作为参数传递给另一个 Task/Actor，实现复杂的分布式拓扑：

@ray.remote
class Worker:
    def __init__(self, param_server_handle):
        self.ps = param_server_handle  # 持有参数服务器的引用

    def train_step(self, batch):
        # 通过 handle 远程调用参数服务器
        weights = ray.get(self.ps.get_weights.remote())
        grads = compute_gradients(weights, batch)
        self.ps.apply_gradients.remote(grads)

# 创建参数服务器 Actor
param_server = ParameterServer.remote()

# 将 handle 传给所有 Worker
workers = [Worker.remote(param_server) for _ in range(8)]
ray.get([w.train_step.remote(batch) for w, batch in zip(workers, batches)])

调度演进：从 Direct Actor Call 到 ESCHER

Ray 的调度策略经历了三代演进：

代 策略 特点
第 1 代 Direct Actor Call Actor 方法调用直接发送到目标节点，简单但无法全局优化
第 2 代 集中式调度 所有调度决策经 GCS，全局最优但 GCS 成为瓶颈
第 3 代 ESCHER Ephemeral Resources：调度时动态创建临时资源，实现细粒度负载均衡

ESCHER：临时资源调度

ESCHER（Ephemeral Resources for Scheduling）的核心思想：为每个任务执行槽创建临时资源名（如 "slot_12345"），调度器将任务绑定到具体槽位，完成后销毁资源。这避免了"资源碎片"问题，实现近似最优的负载均衡，同时保持调度延迟极低。
