PS4 · Memory Scramble

Memory Scramble：共享可变数据类型的并发编程

本作业旨在探索并发使用共享可变数据类型的编程。你将构建网络多人版记忆翻牌游戏——Memory Scramble，玩家可同时翻牌而非轮流进行。

关键要求与截止时间

作业PS4

  • 设计并实现一个或多个 ADT 表示可变游戏棋盘
  • 将 ADT 连接到处理 HTTP 客户端的 Web 服务器
  • 修改系统以使用异步游戏棋盘处理多名并发玩家
  • 实现 map() 命令替换卡片，实现 watch() 命令监听棋盘变化
  • 坐标系统：(行, 列) 从左上角 (0, 0) 开始，垂直向下、水平向右递增
  • 评分比例：Alpha 自动 ~30% + Alpha 手动 ~20% + Beta 自动 ~25% + Beta 手动 ~25%

设计自由与限制

本作业你有大量的设计自由。必须满足 board.ts 和 commands.ts 中某些函数的提供规格。可重写或删除任何其他提供的代码，添加新的类和方法。测试仅针对你自己的实现运行。

获取代码

  1. 在 Didit 上创建远程 psets/ps4 仓库。
  2. 克隆仓库。
  3. cd ps4-«username»，运行 npm install，在 VS Code 中打开。

概述

构建网络多人版 Memory（又称 Concentration）：翻开成对面朝下的卡片，尝试找到匹配的对。我们的版本允许多名玩家同时翻牌。

Problem 1：游戏棋盘

设计并实现一个或多个 ADT。

Problem 2：连接 Web 服务器

将 ADT 连接到处理 HTTP 请求的游戏服务器。

Problem 3：修改为支持并发玩家

修改系统以使用异步游戏棋盘处理多个同时玩家。

Problem 4：更换卡片

设计并实现类似 map 的函数，替换棋盘上的卡片。

Problem 5：棋盘事件

设计并实现监听棋盘变化的功能。

迭代开发建议

  1. 首先实现 Problem 1 & 2，不考虑并发：使 Board 使用同步方法。
  2. 然后在 Problem 3 中修改为准备支持并发玩家。
  3. 最后进行 Problem 4 和 5。

游戏棋盘

Memory Scramble 游戏棋盘有网格空间。每个空间起始有一张卡片。卡片被匹配并移除后，空间变空。

卡片是非空字符串，由非空白非换行字符组成，允许 emoji。两张卡片匹配当字符相同。

棋盘文件语法

BOARD_FILE ::= ROW "x" COLUMN NEWLINE (CARD NEWLINE)+
CARD ::= [^\s\n\r]+
ROW ::= INT
COLUMN ::= INT
INT ::= [0-9]+
NEWLINE ::= "\r"? "\n"

游戏规则

多名玩家同时操作棋盘上的卡片，尝试翻开相同的对。

规则概要

  1. 玩家翻开第一张卡片时，控制该卡片；若他人已控制，则等待。
  2. 玩家翻开第二张卡片：若匹配则保持控制；否则放弃控制。卡片保持翻开。
  3. 玩家下次移动时：若之前匹配成功，移除卡片；否则若无人控制，翻回背面。
注意：与常规记忆游戏不同——可以"翻开"已翻开的卡片，等待其可用；翻开的卡片在玩家下次移动前保持翻开状态。

完整规则

第一张卡片：

  • 1-A — 无卡片（空位）→ 操作失败。
  • 1-B — 卡片朝下 → 翻为正面，玩家控制该卡片。
  • 1-C — 卡片正面朝上但无人控制 → 保持正面，玩家控制。
  • 1-D — 卡片正面朝上且被他人控制 → 操作等待。

第二张卡片：

  • 2-A — 无卡片 → 操作失败，放弃第一张卡片的控制（保持正面）。
  • 2-B — 卡片正面朝上且被控制 → 操作失败（不等待，避免死锁），放弃第一张卡片的控制。
  • 2-C — 卡片朝下则翻为正面。
  • 2-D — 两张卡片相同 → 成功匹配！玩家保持控制两张卡片。
  • 2-E — 不相同 → 放弃控制两张卡片（保持正面）。

下次移动（规则 3）：

  • 3-A — 若之前匹配成功：移除卡片，放弃控制。
  • 3-B — 否则：对每张卡片，若仍在棋盘上、正面朝上、无人控制，则翻为背面。

Web 协议

每个玩家通过 ID 标识。服务器响应棋盘状态，语法：

BOARD_STATE ::= ROW "x" COLUMN NEWLINE (SPOT NEWLINE)+
SPOT ::= "none" | "down" | "up " CARD | "my " CARD
  • none — 无卡片
  • down — 背面朝下
  • up — 正面朝上（被他人控制或无人控制）
  • my — 正面朝上且被请求玩家控制

Problem 1：游戏棋盘

规格化、测试并实现可变的 Board ADT。记住包含：每个类和方法的规格；抽象函数、表示不变量与防表示泄露论证；checkRep() 和 toString()。

解析棋盘文件

  • parseFromFile(filename)：从文件创建棋盘。
  • 使用 String.split() 与 String.match() 处理解析。
  • 使用 fs.promises.readFile() 异步读取文件。

跟踪玩家

  • 每个玩家可仅由命令函数中使用的 ID 标识，所有游戏状态存储在 Board 中。
  • 或使用 ADT（如 Player）表示玩家。
  • 需要跟踪谁控制哪张卡片以及每张卡片的状态。

实现等待

使用异步方法与 await，或回调函数实现等待。棋盘不得忙等待（busy-wait）。

你决定哪些操作是原子的。棋盘绝不能达到不一致状态——如两名玩家控制同一张卡片，或背面朝下的卡片仍被玩家控制。

模拟游戏

在 simulation.ts 中，使用 seedrandom 生成可重现的伪随机数序列，模拟单玩家与 npm run simulation 运行。

Problem 2：连接 Web 服务器

实现 commands.ts 中的函数以连接 Board 与 Web 服务器。首先实现：

  • look() — 查看棋盘状态
  • flip() — 翻牌操作

保持命令简单

  • 每个函数主体至多 3 行。
  • 无单独测试套件，现有 Board 测试应足够。
  • 若更复杂，需创建 test/commands.test.ts——先与职工讨论设计。

运行 Web 服务器

npm start 8080 boards/perfect.txt

在浏览器中打开服务器显示的 URL。可打开多个标签页模拟不同玩家。

Problem 3：修改为支持并发玩家

修改 Board 为异步，按需更新其他 ADT。

实现等待

使用 await 棋盘返回的承诺实现等待。参考：

  • Promise.withResolvers() 工厂函数——将回调转换为承诺
  • Deferred ADT——存储稍后解决的承诺

在 simulation.ts 中增加 players 值模拟多人游戏。

注意：若一名玩家在上次移动中匹配了卡片（留下两张正面卡片在其控制下），另一名玩家尝试翻开其中一张作为第一张卡片时，模拟不应终止。

修订测试策略以测试并发动作的不同交错。可使用 timeout() 函数强制短等待。不要在实现代码中放 timeout()——这是竞争条件的迹象。

Problem 4：更换卡片

实现 map() 命令，将变换函数 f 应用于棋盘上每张卡片，一致替换为 f(card)。

  • map() 独立于其他游戏状态——无论卡片正面/背面、是否被控制，都可替换。
  • 变换函数 f 是异步的，map() 可能需等待 f 调用完成。
  • map() 不得阻止其他命令交错运行。
  • 若两张卡片在 map() 开始时匹配，则在 map() 进行期间，不得使任何玩家观察到该对卡片不匹配的状态。
  • f 必须是数学函数，但不必是单射函数。

Problem 5：棋盘事件

实现 watch() 命令，等待直到棋盘下次变化，然后响应当前棋盘状态。

变化定义为：卡片翻为正面或背面、从棋盘移除、或从一个字符串变为不同字符串。

  • watch() 必须等待此类变化发生。无变化时（如玩家尝试翻开空位，或控制/放弃控制但卡片未翻面），待处理的 watch 请求必须继续等待。
  • 当 watch() 等待时，玩家可使用其他命令，将正常处理。
  • 你决定哪些变化是原子的。

使用棋盘的变化通知实现 watch()，首先尝试在 simulation.ts 中使用变化通知并发监听棋盘。

完成前检查

  • 为所有类型和操作记录规格（TypeDoc 格式）
  • 记录抽象函数与表示不变量，说明如何防止表示泄露
  • 使用等待行为时确保使用承诺，而非忙等待
  • 为所有不可变类型规格化、测试并实现 equalValue()
  • 实现 toString()（通过强化规格并测试来验证）
  • 使用 @inheritdoc 当类实现接口方法时
  • 为每个类型提供彻底、有原则的测试套件
