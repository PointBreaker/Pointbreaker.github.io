01 / PROBLEM

什么是并发

并发（concurrency）意味着多个计算在同时发生。注意"同时"并不一定指物理上的并行——单核 CPU 上通过快速切换也能实现逻辑上的并发。并发是现代软件的核心：用户界面需要同时响应鼠标和网络，服务器需要同时处理上千个请求。

但并发也带来了单线程程序不存在的问题：当多个计算模块访问共享资源时，结果可能依赖于它们执行的相对时序。这正是本讲要系统研究的主题。

02 / DEEP READING

两种并发模型：共享内存与消息传递

并发编程有两种根本不同的模型：

  • 共享内存（shared memory）：并发模块通过读写内存中的共享对象来交互。模块 A 写，模块 B 读，信息就传递了。
  • 消息传递（message passing）：并发模块通过通信信道互相发送消息来交互。没有共享状态，信息通过消息传递。

两种模型不是互斥的——一个系统的不同部分可以混合使用。但理解它们的区别是设计并发系统的第一步。6.102 后续会深入这两种模型：共享内存对应互斥（第 16 讲），消息传递对应 Worker 与网络（第 18 讲）。

FIELD TRACE

把两种模型想成两种"对话方式"：共享内存像两个人在同一块白板上写字，必须协调谁先写；消息传递像两个人发短信，每条消息独立到达。白板快但容易冲突，短信慢但天然隔离。

03 / DEEP READING

进程、线程与时间片

  • 进程（process）：一个运行中的程序实例，与其他进程隔离。进程有独立的内存空间。
  • 线程（thread）：程序内部的一个控制流线索。同一进程的线程共享内存空间。
  • 时间片（time slicing）：当线程数超过处理器数时，操作系统在多个线程之间快速切换，模拟并发。

共享内存模型通常依赖线程（因为线程共享内存），消息传递模型通常依赖进程或 Worker（因为隔离更好）。但线程也可以用消息传递，进程也可以通过操作系统机制共享内存。

04 / DEEP READING

TypeScript 中的 Worker

TypeScript/JavaScript 提供 Worker（Web Workers / worker_threads），行为类似轻量进程：每个 Worker 有独立的内存空间，通过消息传递与主线程通信。

// 主线程
const worker = new Worker("./worker.js");
worker.postMessage({ type: "compute", data: 42 });
worker.onmessage = (e) => {
  console.log("result:", e.data);
};

// worker.js
parentPort.on("message", (msg) => {
  if (msg.type === "compute") {
    parentPort.postMessage(msg.data * 2);
  }
});

Worker 是 6.102 实现消息传递并发的主要工具。

05 / DEEP READING

交错与竞态条件

并发指令可以交错（interleave）执行：两个线程的指令以某种顺序交替进行。交错的顺序通常不可预测——操作系统调度、硬件时序、输入数据都可能影响它。

以银行账户为例，用文件系统做共享内存：

// 线程 A：存款 100
const balance = readBalance();   // 读到 500
writeBalance(balance + 100);     // 写入 600

// 线程 B：取款 50
const balance = readBalance();   // 也可能读到 500！
writeBalance(balance - 50);      // 写入 450

如果两个线程都先读到 500，最终余额就是 450 或 600，而不是正确的 550。这就是竞态条件。

06 / DEEP READING

竞态条件的本质

竞态条件（race condition）意味着正确性依赖于事件发生的相对时序。如果时序不同，结果就不同——而时序恰恰是程序员无法完全控制的。

竞态条件的三个必要条件：

  1. 共享状态：多个模块访问同一可变数据
  2. 并发访问：多个模块同时（或交错）访问
  3. 至少一个写：至少一个模块修改共享状态

破坏任一条件就能消除竞斥条件：不可变性破坏条件 3，消息传递破坏条件 1，互斥破坏条件 2。

07 / DEEP READING

消息传递也不能消除竞态

初学者常误以为消息传递天然避免竞态。实际上，消息传递只是把"共享内存的读写"换成"消息的发送与接收"，如果消息到达的顺序不确定，仍然会产生竞态。

例如两个客户端同时向服务器请求预订同一航班座位，服务器收到消息的顺序决定了谁先谁后——这仍然是竞态。消息传递让问题更可控，但没有消除问题本身。

08 / DEEP READING

并发难以测试和调试

并发 bug 被称为 heisenbugs：非确定性、难以复现。当你试图观察它（加打印、用调试器）时，时序可能就变了，bug 消失。这与量子力学中的观察者效应类似。

应对策略：

  • 用确定性测试框架控制时序
  • 用静态分析工具检测数据竞争
  • 用消息传递或不可变性减少共享状态
  • 用互斥保护必须共享的状态
FIELD TRACE

把并发调试的难度记成"三不"：不确定（每次运行交错不同）、不可复现（加了探针就变样）、不可预测（测试通过不等于正确）。因此并发程序的正确性必须靠设计保证，而不是靠测试发现。

## Objectives

- the message-passing and shared-memory models of concurrency
- concurrent processes and threads, and time slicing
- the danger of race conditions

## Concurrency

*Concurrency* means multiple computations are happening at the same time.

## Two models for concurrent programming

### Shared memory

Concurrent modules interact by reading and writing shared objects in memory.

### Message passing

Concurrent modules interact by sending messages to each other
through a communication channel.

## Processes, threads, time-slicing

### Process

A process is an instance of a running program isolated from other processes.

### Thread

A thread is a locus of control inside a running program.

### Time slicing

When there are more threads than processors, concurrency is simulated
by **time slicing**.

## Workers in TypeScript

TypeScript has `Worker` (Web Workers), which behave like lightweight processes.

## Shared memory example

Bank account example using filesystem as shared memory.

## Interleaving

Concurrent instructions can *interleave* with each other.

## Race condition

A **race condition** means correctness depends on the relative timing of events.

## Message passing example

Message passing doesn't eliminate race conditions.

## Concurrency is hard to test and debug

Concurrency bugs are *heisenbugs*: nondeterministic and hard to reproduce.

## Summary

- **Concurrency**: multiple computations running simultaneously
- Shared-memory & message-passing paradigms
- Processes & threads
- Race conditions
