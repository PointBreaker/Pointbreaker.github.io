01 / PROBLEM

规格说明：团队协作的契约

在大型软件中，实现者（implementer）与客户端（client）往往不是同一个人，甚至不在同一个时区。他们之间需要一份精确的协议，规定“这个函数做什么、需要什么前提、保证什么结果”。这份协议就是规格说明（specification）。

规格说明是团队协作的枢纽（linchpin）。它像一份契约：客户端同意满足前置条件，实现者同意交付符合后置条件的结果。有了这份契约，双方可以独立工作、独立测试、独立替换——只要契约不变，整个系统就保持正确。

本讲的核心思想：规格说明是模块实现者与客户端之间的防火墙（firewall）。它把“做什么”与“怎么做”隔离开来，让修改实现不影响客户端，也让客户端的需求变化被契约精确捕获。

FIELD TRACE

写规格时，始终从两个角度审视：客户端能依赖什么？实现者被允许做什么？一份好的规格应当让客户端写得安心（行为有保证），也让实现者有自由（内部可优化）。如果规格太弱，客户端不敢用；如果太强，实现者无法优化。

02 / DEEP READING

行为等价性

如何判断两个函数做的是“同一件事”？我们引入行为等价（behavioral equivalence）的概念：如果能把一个实现替换为另一个，而不影响任何客户端的正确性，那么这两个实现就是行为等价的。

注意，行为等价不要求代码相同、算法相同、甚至性能相同——只要求从外部可观察的行为一致。规格说明正是定义“什么算行为等价”的工具：所有满足同一规格的实现，在客户端看来都是等价的。

03 / DEEP READING

为什么需要规格说明

代码中的精确规格说明让你能够分摊责任（apportion blame）。当程序出错时，规格说明是判断“谁违反了契约”的依据：

  • 如果客户端没有满足前置条件（例如传入了负数给要求正数的函数），责任在客户端。
  • 如果客户端满足了前置条件，但结果不符合后置条件，责任在实现者。

没有规格说明，错误就是一笔糊涂账。有了它，调试就变成了“对照契约检查哪一方违约”。

04 / DEEP READING

规格说明的结构

一份完整的规格说明包含三个部分：

  1. 函数签名（function signature）：函数名、参数类型与返回类型。
  2. 前置条件（precondition）：用 requires 子句描述函数被调用时必须满足的约束。
  3. 后置条件（postcondition）：用 effects 子句描述函数成功执行后必须满足的性质。

前置条件是客户端的义务，后置条件是保证给客户端的回报。只有当前置条件满足时，后置条件才生效。

/**
 * @param n 起始正整数 — requires: n > 0
 * @returns 冰雹序列到达 1 前的步数 — effects: 返回值 >= 0
 */
function hailstoneLength(n: number): number {
  // ...
}
05 / DEEP READING

TypeScript 中的规格说明

在 TypeScript 中，常见的约定是在函数前放置文档注释，使用 @param 描述参数约束，使用 @returns 描述返回值性质。虽然这些注释本身不会被编译器检查，但它们是与团队沟通契约的标准格式，也能被文档工具提取。

类型注解是规格的一部分（它约束了参数和返回值的“形状”），但规格说明通常还包含类型无法表达的约束——例如“正数”“非空数组”“排序后”等。这些需要文字描述。

06 / DEEP READING

规格能谈论什么

函数的规格说明可以谈论参数和返回值，但绝不能谈论局部变量。局部变量是实现细节，规格说明只描述外部可观察的行为。一旦规格提及了内部状态，实现者的自由就被不当地限制了，客户端也可能依赖本不应暴露的细节。

07 / DEEP READING

避免 null，包含空值

Null 值是麻烦且不安全的。Tony Hoare 曾称 null 引用为他的“十亿美元错误”：它能在编译期通过，却在运行期以 TypeError 的形式突然爆发。在 TypeScript 中，应当尽量避免返回或接受 null，除非规格明确允许。

与 null 相对，空值（empty values）——空字符串、空数组、空集合——是始终被允许的，除非规格明确禁止。空值是安全的、有意义的值，而 null 代表“不存在”，需要特殊处理。

08 / DEEP READING

测试与规格的关系

即便是白盒测试也必须遵循规格说明。测试是对规格的验证，而不是对实现的验证。如果测试断言了规格未保证的性质，那么当实现者合法地修改实现时，测试会错误地失败。

因此，设计测试时应当从规格出发：每个测试用例都应对应规格中的某个前置条件与后置条件的组合。

09 / DEEP READING

突变函数的规格

程序员默认假设突变是不被允许的，除非规格明确说明。如果一个函数会修改传入的参数或对象的状态，这必须在后置条件中明确写出。

例如 sort(arr) 的规格应当说明“效果：arr 被原地排序”。如果规格没有提到突变，客户端就有理由相信参数不会被修改。这是后续课程中不可变类型与别名问题的先声。

10 / DEEP READING

异常与特殊结果

异常有两类用途：

  • 信号 bug：当违反前置条件时抛出异常，表示客户端犯了错误。
  • 预期失败（anticipated failures）：用 @throws 文档化那些规格预期可能发生的失败场景（如文件不存在、网络超时）。

对于特殊-case 的结果，可以使用联合类型（union types）来信号。例如 find(index: number): string | NotFound，比返回 null 更安全、更明确。

在现代 TypeScript/JavaScript 中，每个文件是一个模块（module）。规格说明是模块对外暴露的接口契约，模块内部的所有实现细节都被隐藏起来。

FIELD TRACE

写规格时的检查清单：签名是否清晰？前置条件是否完整（包括边界和约束）？后置条件是否精确（包括突变和返回值）？是否避免了 null？异常是否文档化？逐项检查，就能写出可靠的契约。

# Reading 4: Specifications

[6.102 — Software Construction](http://web.mit.edu/6.102/www/sp26/)
Spring 2026

## Objectives

- Understand preconditions and postconditions in function specifications
- Be able to write tests against a specification
- Understand how to use exceptions

## Introduction

Specifications are the linchpin of teamwork. The specification acts as a contract.

## Behavioral equivalence

To determine *behavioral equivalence*, we ask whether we could substitute one implementation for the other without affecting correctness.

## Why specifications?

Precise specifications in the code let you apportion blame.

## Specification structure

- a function signature
- a *requires* clause (precondition)
- an *effects* clause (postcondition)

## Specifications in TypeScript

A common convention is to put a documentation comment before the function using `@param` and `@returns`.

## What a spec may talk about

The specification of a function can talk about the parameters and return value, but never about local variables.

## Avoid null

Null values are troublesome and unsafe.

## Include emptiness

Empty values are always allowed unless a spec explicitly disallows them.

## Testing and specifications

Even glass box tests must follow the specification.

## Specifications for mutating functions

Programmers assume that **mutation is disallowed unless stated otherwise**.

## Exceptions

- Exceptions for signaling bugs
- Exceptions for anticipated failures (documented with `@throws`)

## Special results

Use union types to signal special-case results.

## Modules

In modern TypeScript/JavaScript, each file is a module.

## Summary

A specification acts as a crucial firewall between the implementer of a module and its client.
