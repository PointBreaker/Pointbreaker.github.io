01 / PROBLEM

测试为什么难：穷举不可行

静态检查能捕获类型错误，但无法捕获逻辑错误。例如一个函数应当返回数组的最大值，却错误地返回了最小值——类型完全正确，结果却错了。测试正是为了弥补这一空白：用具体的输入运行程序，检查输出是否符合预期。

然而穷举测试（exhaustive testing）在绝大多数场景下不可行。一个接受两个 32 位整数参数的函数有 \(2^{64}\) 种输入组合，即便每秒跑十亿次，也需要数百年。对于字符串、数组、对象等无限或近似无限的输入空间，穷举更是天方夜谭。

因此测试用例必须谨慎而系统地选择。本讲的核心问题变成：如何用尽可能少的测试用例，捕获尽可能多的 bug？

FIELD TRACE

测试的本质是在“无限输入空间”与“有限测试预算”之间做权衡。不要问“这个测试套件够不够大”，而要问“这些测试用例是否系统地覆盖了输入空间的关键区域”。一个精心选择的小测试套件，远胜于随机堆砌的大测试套件。

02 / DEEP READING

验证与测试的关系

测试是一个更一般过程——验证（validation）——的一个实例。验证关心的是“我们是否在构建正确的产品”，而测试关心的是“这个实现是否满足规格”。本课更关注后者，但记住这个层次关系有助于理解测试的边界：测试能暴露 bug 的存在，却永远不能证明 bug 的不存在。

03 / DEEP READING

测试先行编程

测试先行编程（test-first programming）把写代码的顺序颠倒过来：

  1. 规格（Spec）：为函数写一份规格说明。
  2. 测试（Test）：写能验证这份规格的测试用例。
  3. 实现（Implement）：写实现代码。

这个顺序的价值在于：先写测试迫使你在动手实现之前想清楚函数“应当做什么”。测试成为规格的可执行版本——如果测试无法表达你对行为的期望，说明规格本身还不够清晰。

当实现写完并跑通测试时，你就同时拥有了代码和一份可重复运行的回归安全网。后续任何修改都可以立即验证是否破坏了已有行为。

04 / DEEP READING

系统测试：正确、彻底、精简

一个好的测试套件应当同时满足三个常常相互冲突的目标：

  • 正确（correct）：接受所有合法的实现——测试本身不应成为错误的来源。
  • 彻底（thorough）：尽可能多地发现实际存在的 bug。
  • 精简（small）：测试用例尽可能少，以降低编写与维护成本。

这三个目标构成一个工程三角：增加测试数量通常能提高彻底性，但会牺牲精简性；过度精简则可能遗漏关键场景。系统化的设计方法，正是在三者之间寻找平衡。

05 / DEEP READING

用划分选择测试用例

核心方法是划分（partitioning）：把函数的输入空间划分成若干子域（subdomains），每个子域是一组在某种意义上“相似”的输入。然后从每个子域中选取至少一个代表作为测试用例。

例如一个函数 abs(x: number): number，输入空间可以划分为两个子域：\(x \ge 0\) 和 \(x < 0\)。从每个子域各取一个代表（如 x=3 和 x=-5），就能覆盖两种本质不同的行为。

划分的关键在于完备性：所有子域的并集应当覆盖整个输入空间，否则未被覆盖的区域就是测试盲区。划分还应尽量让同一子域内的输入“行为相似”，这样选一个代表才有意义。

// 示例：对 abs 的划分测试
import { expect } from "chai";
import { abs } from "./abs";

describe("abs", () => {
  it("returns the same number for non-negative input", () => {
    expect(abs(3)).to.equal(3);
    expect(abs(0)).to.equal(0);
  });

  it("returns the negation for negative input", () => {
    expect(abs(-5)).to.equal(5);
  });
});
06 / DEEP READING

边界是 bug 的聚集地

经验与证据都表明，bug 往往出现在子域的边界（boundaries）上。对于 abs，边界是 x = 0；对于数组索引，边界是 0 和 length - 1；对于“正整数”约束，边界是 1。

因此在划分时，应当把边界单独作为子域或确保边界值被显式测试。遗漏边界是测试设计中最常见的失误之一。

FIELD TRACE

每次设计测试时，先问自己：输入空间的边界在哪里？对于数值，考虑零、负数、最大值、最小值；对于序列，考虑空序列、单元素序列、重复元素；对于自定义类型，考虑规格说明中 requires 子句的临界条件。

一个实用技巧：先列出所有边界，再为每个边界写至少一个测试。

07 / DEEP READING

自动化单元测试

手工运行测试既慢又不可重复。自动化测试让测试成为构建流程的一部分，每次修改后一键运行。对于 JavaScript 和 TypeScript，Mocha 是一个流行的测试框架。

自动化测试的关键特征是自检（self-checking）：测试自己断言结果是否正确，不需要人工查看输出。一个测试只有两种结果——通过或失败——没有模糊地带。

08 / DEEP READING

黑盒与白盒测试

黑盒测试（black box testing）仅根据规格说明选择测试用例，不关心函数内部如何实现。它的好处是测试与实现解耦：重构实现时，只要行为不变，测试就不需要修改。

白盒测试（glass box testing）则利用对实现的了解来选择测试用例——例如确保每个分支、每行代码都被执行到。白盒测试能发现实现中隐藏的分支，但也与实现耦合：重构时可能需要重写测试。

实践中两者结合：先用黑盒覆盖规格，再用白盒补充实现中遗漏的路径。

09 / DEEP READING

代码覆盖率

白盒测试的自然延伸是代码覆盖率（code coverage）度量：

  • 语句覆盖（statement coverage）：每条语句是否都被执行过？
  • 分支覆盖（branch coverage）：每个分支的两侧是否都被取过？
  • 路径覆盖（path coverage）：程序中的每条路径是否都被走过？

覆盖率从语句到路径越来越严格，但也越来越难以达到。路径覆盖在循环存在时甚至可能是无限的。覆盖率是测试充分性的一个有用信号，但高覆盖率不等于高质量测试——它只说明代码被执行过，不说明执行结果被正确验证过。

10 / DEEP READING

单元测试、集成测试与回归测试

测试一个独立模块的测试称为单元测试（unit test）；测试多个模块组合的称为集成测试（integration test）。单元测试小而快，定位问题精确；集成测试慢而全面，能发现模块间的交互问题。

每次修改后运行所有测试，称为回归测试（regression testing）。自动化的回归测试是持续集成的基石：它让你有信心修改代码，因为任何对已有行为的破坏都会立即暴露。

11 / DEEP READING

迭代测试与随机化测试

测试先行编程应当迭代（iterative）进行：先写少量测试覆盖主要场景，实现通过后再逐步补充边界和特殊情况。一次性写出完美测试套件既不现实也无必要。

此外，还有两类更高级的测试技术：

  • 模糊测试（fuzz testing）：自动生成大量随机输入，试图触发崩溃或异常。
  • 属性测试（property-based testing）：不检查具体输出，而是检查结果是否满足某个性质（例如“排序后数组长度不变”）。

随机化测试的价值在于能覆盖人类测试设计者想不到的输入，是对系统化测试的有力补充。

FIELD TRACE

把测试看作一个持续演进的资产，而不是一次性交付物。每次发现生产 bug，第一步应当是写一个能复现该 bug 的测试，修复后再运行整个套件。这样测试套件会随着项目成长，越来越强。

# Reading 2: Testing

[6.102 — Software Construction](http://web.mit.edu/6.102/www/sp26/)
Spring 2026

## Objectives

After today's class, you should:

- understand the value of testing, and know the process of test-first programming;
- be able to judge a test suite for correctness, thoroughness, and size;
- be able to design a test suite for a function by partitioning its input space and choosing good test cases;
- be able to judge a test suite by measuring its code coverage; and
- understand and know when to use black box vs. glass box testing, unit tests vs. integration tests, and automated regression testing.

## Validation

Testing is an example of a more general process called *validation*.

## Why software testing is hard

Exhaustive testing is infeasible. Test cases should be chosen carefully and systematically.

## Test-first programming

1. **Spec**: Write a specification for the function.
2. **Test**: Write tests that exercise the specification.
3. **Implement**: Write the implementation.

## Systematic testing

- **Correct**: accepts all legal implementations
- **Thorough**: finds actual bugs
- **Small**: few test cases

## Choosing test cases by partitioning

Divide the program's input space into *subdomains*, each consisting of a set of inputs.

## Include boundaries in the partition

Bugs often occur at *boundaries* between subdomains.

## Automated unit testing

A popular choice for JavaScript and TypeScript is Mocha.

## Black box and glass box testing

**Black box testing** means choosing test cases only from the specification. **Glass box testing** means choosing test cases with knowledge of how the function is actually implemented.

## Coverage

- **Statement coverage**: is every statement run?
- **Branch coverage**: is each side of each branch taken?
- **Path coverage**: is every path through the program taken?

## Unit and integration testing

A test that tests an individual module is called a **unit test**. An **integration test** tests a combination of modules.

## Automated regression testing

Running all your tests after every change is called **regression testing**.

## Iterative test-first programming

Practice **iterative** test-first programming.

## Randomized testing

*Fuzz testing* generates random inputs. *Property-based testing* checks that results satisfy some property.

## Summary

- Test-first programming
- Systematic testing with partitioning and boundary values
- Glass box testing and statement coverage
- Unit-testing each module
- Automated regression testing
- Iterative development
