01 / PROBLEM

代码审查：改善代码与改善程序员

在深入具体原则之前，先回到 6.102 对好软件的定义：

  • 安全免于缺陷（Safe from bugs）：现在正确，在未知的未来也正确。
  • 易于理解（Easy to understand）：与未来的程序员——包括未来的自己——清晰地沟通。
  • 随时可变（Ready for change）：设计时容纳变化，而不是每次变化都推倒重来。

代码审查（code review）是由代码原作者之外的人对源代码进行的认真、系统的研读。它实际上有两个目的：

  • 改善代码：发现 bug、预判可能的 bug、检查代码的清晰度。
  • 改善程序员：代码审查是程序员相互学习、相互教学的重要方式。

这两个目的同等重要。一次好的审查不仅产出更好的代码，还让参与双方都更深刻地理解语言、库和设计原则。下面的原则将通过三个“气味”（smelly）示例展开——所谓“气味”，是指代码中那些“看起来不太对劲”、暗示更深层次问题的模式。

FIELD TRACE

审查代码时，先问三个问题：这段代码正确吗（安全免于缺陷）？一个陌生人能快速读懂吗（易于理解）？如果需求明天变了，容易改吗（随时可变）？把答案和下面要学的原则对照，就能系统性地定位“气味”。

02 / DEEP READING

气味示例一：DRY、注释、快速失败、魔法数字、单一用途

不要重复自己（Don't Repeat Yourself，DRY）。重复的代码是安全的隐患：当逻辑需要修改时，你必须找到所有副本并一致地更新它们，任何一个遗漏都会引入 bug。与其复制粘贴，不如把公共逻辑提取成函数或常量。

在需要的地方写注释（Comment where needed）。优秀的开发者审慎地写注释：不是为了解释“代码做了什么”（好的代码自己会说话），而是为了解释“为什么这样做”——那些从代码本身无法看出的意图、约束和背景。

快速失败（Fail fast）。代码应当尽可能早地暴露它的 bug。如果一个函数收到了非法参数，立即抛出异常，而不是带着错误状态继续运行，直到某个无关的地方才以难以理解的方式崩溃。快速失败让 bug 的定位成本降到最低。

避免魔法数字（Avoid magic numbers）。魔法数字是指出现在代码中、没有解释的常量值。除了 0、1、-1 等少数被广泛理解的常量外，其他数字都应当被命名常量替代。if (status === 3) 中的 3 是什么意思？if (status === STATUS_COMPLETED) 则一目了然。

每个变量一个用途（One purpose for each variable）。不要复用参数，也不要复用变量。一个变量如果在不同阶段存放不同含义的值，读者就必须记住“现在这个时刻它代表什么”。为每个用途创建独立变量，名字本身就成为文档。

// 反面示例：魔法数字 + 变量复用
function price(n: number): number {
  let x = n * 1.1;   // 1.1 是什么？
  x = x - x * 0.05;  // x 先存含税价，又存折后价
  return x;
}

// 正面示例：命名常量 + 单一用途
const TAX_RATE = 1.1;
const DISCOUNT = 0.05;

function price(quantity: number): number {
  const withTax = quantity * TAX_RATE;
  const discounted = withTax - withTax * DISCOUNT;
  return discounted;
}
03 / DEEP READING

气味示例二：命名与排版

使用好的名字（Use good names）。好的函数名和变量名应当长且自描述。calc(a, b) 让人困惑；calculateTotalPrice(unitPrice, quantity) 则不需要任何注释。写代码时，读者（包括未来的你）的时间比你的时间更值钱，因此多打几个字母是值得的投资。

用空白与标点帮助读者（Use whitespace and punctuation to help the reader）。一致的缩进、适当的空行、运算符前后的空格，这些看似微小的细节，累积起来决定了代码的可读性。混乱的排版会让逻辑结构变得模糊，清晰的排版则让结构不言自明。

04 / DEEP READING

气味示例三：全局变量、返回结果、特殊用例、代码长度

不要使用全局变量（Don't use global variables）。全局变量在任何地方都可被读写，这使得程序的执行路径难以追踪，也让模块之间的依赖变得隐式。应当通过参数传递输入、通过返回值传递输出，让数据流清晰可见。

函数应当返回结果，而不是打印它们（Functions should return results, not print them）。直接打印的函数无法被其他代码复用——调用者拿不到返回值，只能看到控制台输出。返回结果的函数则可以被组合、测试和进一步处理。

避免特殊用例代码（Avoid special-case code）。充斥着 if (x === specialCase) 分支的函数往往意味着抽象不完整。更好的做法是把特殊情况纳入统一的处理逻辑，或者通过多态/重载来表达差异。

代码长度适当（Code at the right length）。函数应当足够短，以便在一个屏幕上完整阅读、在头脑中完整理解；但也不要为了短而短，把本应连贯的逻辑拆得支离破碎。长度是结果，不是目标——清晰才是目标。

05 / EVIDENCE

重构：改善代码而不改变行为

把代码改造成更好的结构，同时不改变它做什么，这个过程称为重构（refactoring）。上面讨论的每一条原则——提取重复代码为函数、重命名变量、消除魔法数字、拆分过长的函数——都是具体的重构手法。

重构的前提是有测试。没有测试的保护，任何“不改变行为”的重构都可能是自欺欺人。这正是上一讲测试与本讲代码审查的内在联系：测试提供安全网，重构改善结构，审查确保方向。

重构不应当是偶发的大改造，而应当是日常的微小改进。每次审查、每次修改时，让代码比你来时好一点。这种持续的小幅改善，累积起来就是巨大的质量差异。

FIELD TRACE

审查时的实用策略：先快速通读，把握整体结构；再逐段细读，对照原则清单标记“气味”；最后把发现按优先级排序——先改影响正确性的，再改影响可读性的，最后改影响可扩展性的。不要试图在一次审查中找出所有问题。

误区

注释越多越好。

注释应当解释“为什么”，而不是“做了什么”。冗余的注释不仅无用，还会在代码演变后与实现矛盾，成为误导。

误区

重构可以随时做，不需要测试。

没有测试保护的重构只是“改代码”。任何结构变更都可能在无意中改变行为，测试是重构的安全网。

# Reading 3: Code Review

## Software in 6.102

- **Safe from bugs**: Correct today and correct in the unknown future.
- **Easy to understand**: Communicating clearly with future programmers, including future you.
- **Ready for change**: Designed to accommodate change without rewriting.

## Objectives

In today's class, we will practice:

- code review: reading and discussing code written by somebody else
- general principles of good coding

## Code review

Code review is careful, systematic study of source code by people who are not the original author of the code.

Code review really has two purposes:

- **Improving the code.** Finding bugs, anticipating possible bugs, checking the clarity of the code.
- **Improving the programmers.** Code review is an important way that programmers learn and teach each other.

## Smelly example #1

### Don't repeat yourself (DRY)

Duplicated code is a risk to safety.

### Comment where needed

Good software developers write comments judiciously.

### Fail fast

*Failing fast* means that code should reveal its bugs as early as possible.

### Avoid magic numbers

All other constants are called magic.

### One purpose for each variable

Don't reuse parameters, and don't reuse variables.

## Smelly example #2

### Use good names

Good function and variable names are long and self-descriptive.

### Use whitespace and punctuation to help the reader

Use consistent indentation.

## Smelly example #3

### Don't use global variables

Avoid global variables.

### Functions should return results, not print them

### Avoid special-case code

### Code at the right length

## Refactoring

The process of changing code to improve it without changing what the code does is called **refactoring**.

## Summary

General practices for good code:

- Don't Repeat Yourself (DRY)
- Comment where needed
- Fail fast
- Avoid magic numbers
- One purpose for each variable
- Use good names
- Use whitespace and punctuation to help the reader
- Don't use global variables
- Functions should return results, not print them
- Avoid special-case code
- Code at the right length
