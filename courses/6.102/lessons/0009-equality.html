01 / PROBLEM

相等必须是等价关系

相等操作看似简单，但要作为可靠的程序基础，它必须是一个等价关系（equivalence relation），即同时满足三条性质：

  • 自反（reflexive）：对任意 a，有 a.equals(a) == true。
  • 对称（symmetric）：若 a.equals(b)，则 b.equals(a)。
  • 传递（transitive）：若 a.equals(b) 且 b.equals(c)，则 a.equals(c)。

这三条是相等操作的“安全门槛”。一旦被破坏，依赖相等的代码——排序、去重、哈希表查找——都会出现不可预测的错误。例如若相等不对称，把对象放进哈希表后再用“相等的”另一个键去查找，可能找不到原本存在的值。

FIELD TRACE

每次实现 equals 后，用“自反—对称—传递”三问自检。只要有一条不成立，相等就是不可靠的，所有依赖它的数据结构都会遭殃。

02 / DEEP READING

不可变类型的相等：抽象函数与观察

对不可变类型，相等有两种等价定义方式：

  • 使用抽象函数：两个实例相等当且仅当 AF(a) == AF(b)。由于不可变对象的表示与抽象值一一对应，这一定义简洁且自然。
  • 使用观察：两个对象相等，当它们无法通过任何观察（observer）区分。换句话说，对它们调用任何公开操作都得到相同结果。

对不可变类型，这两种定义通常等价：抽象值相同 ↔ 无法通过观察区分。这给了实现者自由——既可以从表示入手写相等，也可以从规格说明入手验证相等。

03 / DEEP READING

引用相等 vs. 值相等

相等有两个层次，必须严格区分：

  • 引用相等（reference equality）：测试两个引用是否指向同一块存储。TypeScript 的 === 对对象做的就是引用相等。
  • 值相等（value equality）：测试两个对象是否代表同一个抽象值。

问题在于：=== 不是值相等。两个内容完全相同的对象，用 === 比较会返回 false，因为它们位于不同内存位置。因此要实现值相等，必须提供专门的 equalValue() 方法，按抽象值或观察结果比较。

const a = new MyDate(2026, 2, 25);
const b = new MyDate(2026, 2, 25);
console.log(a === b);        // false —— 引用相等
console.log(a.equalValue(b)); // true  —— 值相等
04 / DEEP READING

破坏等价关系的常见方式

实现相等时，有几类常见错误会打破等价关系：

  • 把“类型标签”混进相等：子类与超类比较时返回 false，可能破坏对称性。
  • 依赖可变状态：若相等依赖一个可变字段，对象在不同时刻的“相等关系”会变，破坏传递性。
  • 把浮点近似当相等：用 == 比较浮点数会因舍入误差破坏对称与传递。

本课的结论很明确：相等的定义必须是一个干净的等价关系，任何让相等“偶尔成立”的捷径都会反过来伤害你。

05 / DEEP READING

可变类型的相等：观察相等与行为相等

可变类型让相等变得更微妙，因为它要回答“相等到底比的是什么”：

  • 观察相等（observational equality）：两个对象此刻无法通过观察区分。
  • 行为相等（behavioral equality）：两个对象此刻无法区分，且在任意未来操作序列下都保持不可区分。

观察相等较弱：两个可变对象此刻内容相同，但其中一个持有可变的内部状态，未来修改后就会暴露差异。行为相等更强：它要求对象在所有可能的未来演化中都保持一致。

对可变类型，===（引用相等）实际上是行为相等的一个近似：同一块存储的对象当然在未来也保持一致。这解释了为什么 TypeScript 不轻易给对象赋予值相等——可变对象的值相等本身就含糊。

FIELD TRACE

判断该用哪种相等，问自己：“我关心的是‘现在看起来一样’，还是‘以后也一直一样’？” 前者是观察相等，后者是行为相等。不可变类型因为不会变，两者重合。

06 / DEEP READING

集合上的“深度相等”

对内置集合（数组、对象），简单的 === 几乎总是引用相等。Node.js 的 assert.deepStrictEqual() 提供了一种观察相等：它递归比较集合的每个元素与嵌套结构，只要当前结构一致就认为相等。

测试 ADT 时，deepStrictEqual 非常有用，但它仍是观察相等——如果集合持有可变对象，未来修改后“已相等”的判断可能失效。理解这一边界，才能正确选择测试断言。

07 / DEEP READING

哈希函数必须与相等一致

只要实现相等，就必须同时实现哈希函数，并遵守一条铁律：若 a.equals(b)，则 hashCode(a) == hashCode(b)。这是哈希表、哈希集合等数据结构正确工作的前提。

违反这条规则的后果很直接：把对象放进哈希表，再用一个“相等的”对象去查找，可能落到不同的桶里，导致查找失败。因此哈希函数必须基于相等所依赖的同一组字段来计算。

对不可变类型，哈希值还可以缓存（因为对象不变，哈希值也不会变），这是不可变性的又一个性能优势。

# Reading 9: Equality

## Objectives

- Understand the properties of an equivalence relation.
- Understand equality for immutable types.
- Differentiate between reference equality and object equality.
- Differentiate between observational and behavioral equality for mutable types.

## Equivalence relation

An equality operation must be an **equivalence relation**: reflexive, symmetric, and transitive.

## Equality of immutable types

**Using the abstraction function**: two instances are equal iff AF(a) = AF(b).

**Using observation**: two objects are equal when they cannot be distinguished by observation.

## Reference equality vs. value equality

- *reference* equality tests whether two references point to the same storage.
- *value* equality tests whether two objects represent the same value.

In TypeScript, `===` is reference equality. Use `equalValue()` for value equality.

## Breaking the equivalence relation

The definition of equality must be an equivalence relation.

## Equality of mutable types

- *observational equality*: cannot be distinguished now
- *behavioral equality*: cannot be distinguished now or in the future

## "Deep equality" on collections

`assert.deepStrictEqual()` provides observational equality for built-in collections.

## Hash functions

Always implement hashing consistent with equality.

## Summary

- Equality should be an equivalence relation.
- The abstraction function is the basis for equality in immutable data types.
- Mutable data types have two notions: behavioral equality and observational equality.
