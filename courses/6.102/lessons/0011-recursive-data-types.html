01 / REVIEW

递归复习：基本情形与递归情形

递归函数由两部分组成：基本情形（base case）直接给出答案，不再递归；递归情形（recursive case）把问题归约为更小的自身调用。写递归函数时，先问自己两个问题：最小输入是什么（基本情形）？怎样把一般输入拆成更小的同类输入（递归情形）？

递归数据类型的设计遵循同样的思路：类型由一组变体（variant）组成，其中一部分变体是基本情形（不再引用自身），另一部分变体是递归情形（字段类型指向自身）。这种"类型定义中出现自身"正是"递归"一词的来源。

FIELD TRACE

把递归思维拆成三列：基本情形 / 递归情形 / 自身引用。每遇到一个递归数据类型，就把它的变体分别放进三列。例如 ImList 的 Empty 是基本情形，Cons 是递归情形，Cons.rest 字段是自身引用。如果一个变体没有自身引用，它就必须是基本情形，否则无法构造有限值。

02 / DEEP READING

不可变列表 ImList 的四个基本操作

ImList<Element> 是 6.102 的典范递归数据类型，它提供四个基本操作：

  • empty：构造一个空列表（基本情形）
  • cons(first, rest)：把一个元素拼到另一个列表前面，返回新列表（递归情形）
  • first：取出列表首元素
  • rest：取出除首元素外的剩余列表

因为 ImList 是不可变的（immutable），cons 不会修改原有列表，而是返回一个全新的列表。原有列表仍然可用，这正是后续回溯搜索能依赖列表共享的前提。

// 构造列表 [1, 2, 3]
const list: ImList<number> = ImList.empty<number>()
  .cons(3).cons(2).cons(1);
// first(list) === 1
// first(rest(list)) === 2
03 / DERIVATION

递归数据类型定义：变体的并集

数据类型定义（data type definition）把一个抽象类型表达为变体的并集（union）。ImList 的定义是：

\[ImList\langle Element\rangle = Empty + Cons(first: Element,\; rest: ImList\langle Element\rangle)\]

读作：一个 ImList<Element> 要么是 Empty，要么是一个 Cons，后者包含一个首元素 first 和一个剩余列表 rest，而 rest 本身又是一个 ImList<Element>。注意定义右侧出现了 ImList 自身——这就是递归。

这种记号是整门课描述 ADT 的核心语言。它只关心"类型由哪些变体、哪些字段组成"，完全不涉及具体实现。实现时，每个变体通常对应一个实现同一接口的类。

FIELD TRACE

把数据类型定义翻译成 TypeScript 接口 + 类：接口声明操作，每个变体一个实现类。对上面的定义，你会得到 interface ImList<E>、class Empty<E> implements ImList<E>、class Cons<E> implements ImList<E>。先画定义，再写代码，顺序不要反。

04 / DEEP READING

递归数据类型上的函数：解释器模式

递归数据类型上的函数通常声明在抽象接口中，并在每个变体类里递归实现——这就是解释器模式（interpreter pattern）。以 size() 为例：

// 接口中声明
interface ImList<E> {
  size(): number;
}

// Empty 的实现：基本情形
class Empty<E> implements ImList<E> {
  size(): number { return 0; }
}

// Cons 的实现：递归情形
class Cons<E> implements ImList<E> {
  constructor(
    private readonly first: E,
    private readonly rest: ImList<E>) {}
  size(): number { return 1 + this.rest.size(); }
}

解释器模式的核心是：每个变体只关心自己这一行代码，递归部分交给 rest 去处理。这与递归函数"基本情形 + 递归情形"的结构完全对应。

05 / DEEP READING

Rep 独立性与 Rep 暴露

规格说明（spec）绝不能谈论 rep。ImList 的规格只描述"一个不可变的元素序列"，而不会说"用 Empty 和 Cons 两个类实现"。Rep 独立性（rep independence）保证客户端不依赖实现细节，从而允许实现自由切换。

相反，rep 暴露（rep exposure）发生在实现细节泄漏到客户端时。对于不可变类型，暴露风险较低，但仍需注意：若返回内部可变对象的引用，客户端就可能修改它。不可变性 + 哨兵对象是防暴露的重要工具。

06 / DEEP READING

Null vs. Empty：哨兵对象

空列表应该用 null 还是用一个专门的 Empty 对象？6.102 选择后者。Empty 是一个哨兵对象（sentinel object）：它是 ImList 的一个合法值，所有操作在它上面都有定义。

若用 null 表示空，每次调用 first 或 rest 前都必须检查 null，否则抛 NullPointerException。哨兵对象把"空"纳入类型系统，让解释器模式能统一处理，而不是到处写 if (x === null)。

FIELD TRACE

把 null 视为"值不存在"，把 Empty 视为"一个具体的空值"。使用 Empty 后，first(Empty) 可以抛一个有意义的异常，而 rest(Empty) 同样如此——但至少这些调用在类型上是合法的，编译器不会漏掉检查。

07 / DEEP READING

静态类型 vs. 动态类型

变量有静态类型（static type），由声明时的类型注解决定；对象有动态类型（dynamic type），由实际构造它的类决定。例如：

const list: ImList<number> = new Cons<number>(1, new Empty<number>());
// 静态类型：ImList<number>
// 动态类型：Cons<number>

静态类型是编译期保证的边界：通过 list 只能调用 ImList 接口声明的方法。动态类型是运行期的真实身份。解释器模式依赖这种"静态接口 + 多态分派"机制：调用 list.size() 时，实际执行哪个变体的方法由动态类型决定。

08 / DEEP READING

动态类型检查：避免 instanceof

在递归数据类型上写逻辑时，初学者容易用 instanceof 判断变体，再分别处理。这种做法会破坏解释器模式，因为每加一个变体，所有 instanceof 代码都要修改。

正确做法是把变体特定的逻辑放进该变体自己的方法里，让多态分派替你"选择分支"。只有当操作确实无法用接口方法表达时，才考虑类型检查——这通常是设计需要重构的信号。

09 / DEEP READING

不可变类型的等价性 equalValue

对于不可变类型，6.102 定义 equalValue(other) 表示两个值在含义上相等。不可变列表的相等意味着长度相同且每个位置上的元素相等。注意区分：

  • ===：同一性（same object），引用相等
  • equalValue：值相等（value equality），含义相同

不可变类型特别适合值相等，因为值一旦创建就不会变，相等关系可以缓存和共享。

10 / DEEP READING

另一个例子：布尔公式

递归数据类型不限于列表。定义布尔公式：

\[Formula = Variable(name: String) + Not(formula: Formula) + And(left: Formula,\; right: Formula) + Or(left: Formula,\; right: Formula)\]

一个公式要么是变量，要么是 Not/And/Or 的组合，后三者的字段又指向公式自身。求值、变量收集、化简等操作都可以用解释器模式递归实现。

// 表示 (a AND b) OR (NOT c)
const f: Formula = new Or(
  new And(new Variable("a"), new Variable("b")),
  new Not(new Variable("c"))
);
11 / DEEP READING

不可变性与回溯搜索

不可变列表允许结构共享（structural sharing）：cons(x, list) 只新建一个 Cons 节点，rest 仍指向 list。在回溯搜索中，试探一步时 cons 一个新选择，回退时只需丢弃当前节点，原来的列表完好无损。

若列表是可变的，回溯就必须显式"撤销"修改，代码复杂且容易出错。不可变性把"状态变化"转化为"创建新值"，是函数式编程与搜索算法的基石。

13 / CALIBRATION

把直觉校准成不变量

误区

递归数据类型就是链表。

链表只是递归数据类型的一种。布尔公式、表达式树、JSON 值等都用递归定义，且往往有多个递归变体与多个自身引用字段。

误区

用 instanceof 判断变体是自然的做法。

instanceof 把变体逻辑散布到客户端，每加变体都要改所有检查点。解释器模式让每个变体自己处理自己的逻辑。

# Reading 11: Recursive Data Types

[6.102 — Software Construction](http://web.mit.edu/6.102/www/sp26/), Spring 2026

## Objectives

- Understand recursive data types
- Read and write data type definitions
- Understand and implement functions over recursive data types
- Understand immutable lists

## Recursion

Review recursive functions: base cases and recursive cases.

## Example: Immutable lists

Define `ImList<Element>` with four fundamental operations: `empty`, `cons`, `first`, `rest`.

## Recursive data type definitions

A **data type definition** expresses an abstract type as a union of variants.

```
ImList<Element> = Empty + Cons(first: Element, rest: ImList<Element>)
```

## Functions over recursive data types

Declared in the abstract interface and implemented recursively in each variant (interpreter pattern).

## Rep independence and rep exposure

Specs must not talk about the rep.

## Null vs. empty

Use sentinel objects (Empty class) rather than null.

## Static type vs. dynamic type

Variables have static types; objects have dynamic types.

## Dynamic type inspection

Avoid `instanceof` for variant-specific logic.

## Equality

Define `equalValue()` for immutable types.

## Another example: Boolean formulas

```
Formula = Variable(name: String) + Not(formula: Formula)
        + And(left: Formula, right: Formula)
        + Or(left: Formula, right: Formula)
```

## Backtracking search with immutability

Immutable lists permit sharing, good for backtracking.

## Summary

- **recursive data types** with data type definitions
- **functions over recursive data types** using the interpreter pattern
- **immutable lists** as a canonical example
