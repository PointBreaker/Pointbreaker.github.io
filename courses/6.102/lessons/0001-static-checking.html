01 / PROBLEM

先从一个具体问题开始：冰雹序列

本讲以一个贯穿始终的例子引入——冰雹序列（hailstone sequence）。规则如下：给定一个起始正整数 \(n\)，如果 \(n\) 是偶数则下一项是 \(n/2\)，如果 \(n\) 是奇数则下一项是 \(3n+1\)，序列在到达 1 时结束。

例如从 \(n=6\) 开始：\(6 \to 3 \to 10 \to 5 \to 16 \to 8 \to 4 \to 2 \to 1\)。这个序列的每一步都只依赖前一项，逻辑上非常简单，但当我们把它写成程序时，类型、边界和错误处理就会立刻浮现。

写这个序列时，你会自然产生一些假设：\(n\) 是整数、\(n>0\)、每一步的结果仍是整数。问题是，这些假设由谁来守护？是程序员自己记住、运行时崩溃时才发现，还是在写下来的那一刻就被检查？这正是静态检查要回答的问题。

FIELD TRACE

在动手编码之前，先把冰雹序列的假设列出来：输入是正整数、运算结果仍是整数、序列必然终止（这是著名的 Collatz 猜想，尚未被证明）。注意最后一条——程序无法保证数学上的终止，但类型系统可以保证“每一步产生整数”这类更基本的性质。

学习本讲时，反复问：哪些假设可以被类型系统静态捕获，哪些必须等到运行时？

02 / DEEP READING

类型是什么

类型（type）是一组值以及可对这些值执行的操作的集合。例如 TypeScript 中的 number 包含所有浮点数，并支持 +、-、*、/ 等操作；boolean 包含 true 与 false，并支持逻辑运算。

类型的作用是约束操作：它告诉你哪些表达式有意义。写 "hello" * 3 在数学上没有意义，类型系统应当阻止它。当我们说“某个变量的类型是 number”，实际上是在承诺：这个变量只持有数字，因此可以安全地参与算术运算。

03 / DEEP READING

静态类型与三种检查

TypeScript 是一门静态类型语言（statically-typed language）。变量可以在编译期（在程序运行之前）被赋予类型，编译器因此能推断出使用这些变量的表达式的类型。

错误检测的策略可以分为三类：

  • 静态检查（static checking）：bug 在程序运行之前就被自动发现。
  • 动态检查（dynamic checking）：bug 在程序执行期间被自动发现。
  • 无检查（no checking）：语言根本无助于你发现这个错误。

用一个典型例子说明：int n = "hello" 在 TypeScript 中会触发静态检查错误，因为类型不匹配在编译期就能确定；而数组越界访问只能在运行到那一行时才抛出异常，属于动态检查；至于“逻辑上应该用乘法却写成了加法”，语言通常完全无能为力。

FIELD TRACE

静态检查的核心收益是把错误发现的时间点尽量前移。一个在编译期被捕获的错误，成本远低于在测试期、生产期才暴露。但静态检查并非万能：它擅长捕获类型错误、签名不匹配等“形状”问题，却不擅长捕获业务逻辑错误。

判断一门语言在某个场景下属于哪种检查，不要看它的宣传，要看错误实际在哪个阶段暴露。

04 / DEEP READING

数组、函数与规格注释

数组（array）是另一种类型的可变长序列，类似 Python 的 list。在 TypeScript 中，number[] 表示由数字组成的数组，其长度在运行时可变，但元素类型固定。

当我们想把一段代码封装成可复用的模块时，可以写一个函数并附上规格注释（specification comment）。例如一个计算冰雹序列长度的函数：

/**
 * @param n 起始正整数，要求 n > 0
 * @returns 冰雹序列到达 1 之前的步数
 */
function hailstoneLength(n: number): number {
  let steps = 0;
  while (n !== 1) {
    if (n % 2 === 0) {
      n = n / 2;
    } else {
      n = 3 * n + 1;
    }
    steps++;
  }
  return steps;
}

注意这里 n: number 和 : number（返回值类型）都是静态类型注解。如果调用者传入 string，TypeScript 编译器会立即报错，而不必等到运行。

05 / DEEP READING

修改值 vs. 重新赋值

这两个概念在后续课程里至关重要，这里先做区分：

  • 修改（mutation）：改变某个值的内容。例如 arr.push(3) 修改了数组 arr 的内容。
  • 重新赋值（reassignment）：改变变量指向哪个值。例如 x = x + 1 让变量 x 指向一个新的数字。

在冰雹序列的例子中，n = n / 2 是重新赋值——变量 n 指向了新的数值，原来的数值本身并没有被改变（数字在 TypeScript 中是不可变的）。理解这一区别，对后续学习可变性（mutability）与别名（aliasing）至关重要。

06 / DEEP READING

把假设写下来

写下变量的类型，就是在记录关于它的一个假设。n: number 不仅告诉编译器“这里是数字”，也告诉未来的读者“这里应当是数字”。类型注解是一种最低成本、最高回报的文档。

但类型注解只能表达“形状”层面的假设。hailstoneLength 要求 n > 0，而 number 类型无法表达“正数”这一约束。这类更精细的假设需要借助规格说明（specification）来表达，这是后续几讲的核心主题。

FIELD TRACE

把类型注解看作“可执行的文档”。普通注释可能过时，但类型注解会被编译器持续验证。当你修改代码后编译器报类型错误，那不仅是编译失败，更是文档与实现之间出现了分歧——这往往意味着设计需要重新审视。

07 / EVIDENCE

黑客 vs. 工程师：6.102 的三大目标

软件构建不是黑客式的即兴编码。工程师是悲观主义者：他们假设自己会犯错、假设未来会修改代码、假设读者并不了解所有上下文。6.102 围绕好软件的三大目标展开：

  • 安全免于缺陷（Safe from bugs）：现在正确，在未知的未来也正确。
  • 易于理解（Easy to understand）：与未来的程序员——包括未来的自己——清晰地沟通。
  • 随时可变（Ready for change）：设计时容纳变化，而不是每次变化都推倒重来。

静态检查直接服务于“安全免于缺陷”：它在运行前自动捕获类型错误。类型注解同时服务于“易于理解”：读者无需阅读实现就能知道变量应当持有什么。而一个被类型系统良好约束的模块，往往也更“随时可变”，因为修改的影响范围被类型边界清晰地限制住了。

这三大目标贯穿整个课程：后续的规格说明、抽象数据类型、函数式编程、并发，都可以看作在不同维度上推进这同一个目标集合。

误区

静态检查能捕获所有错误。

静态检查只擅长“形状”错误——类型不匹配、签名错误。逻辑错误（如该乘却加）和许多业务约束（如“正数”）无法被类型系统表达。

误区

修改值和重新赋值是一回事。

修改变变值是改变某个值的内容（arr.push(3)）；重新赋值是让变量指向新值（x = x + 1）。两者在别名存在时行为截然不同。

## Objectives

Today's class has two topics:

* static typing
* the big three properties of good software

## Hailstone sequence

As a running example, we're going to explore the hailstone sequence, which is defined as follows: Starting with a number *n*, the next number in the sequence is *n/2* if *n* is even, or *3n+1* if *n* is odd. The sequence ends when it reaches 1.

## Types

A **type** is a set of values along with operations that can be performed on those values.

## Static typing

TypeScript is a **statically-typed language**. Variables can be assigned a type at **compile time** (before the program runs), and the compiler can therefore deduce the types of expressions using those variables.

## Static checking, dynamic checking, no checking

- **Static checking**: the bug is found automatically before the program even runs.
- **Dynamic checking**: the bug is found automatically during execution.
- **No checking**: the language doesn't help you find the error at all.

## Arrays

Arrays are variable-length sequences of another type, similar to Python lists.

## Functions

If we want to wrap this code into a reusable module, we can write a function with a specification comment.

## Mutating values vs. reassigning variables

**Mutation** refers to changing the content of a value. **Reassignment** means changing where a variable points.

## Documenting assumptions

Writing the type of a variable down documents an assumption about it.

## Hacking vs. engineering

Software engineering is not hacking. Engineers are pessimists.

## The goals of 6.102

- **Safe from bugs**
- **Easy to understand**
- **Ready for change**

## Summary

The main idea we introduced today is **static checking**.
