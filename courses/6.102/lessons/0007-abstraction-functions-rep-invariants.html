01 / PROBLEM

不变量：每个运行状态都成立的性质

不变量（invariant） 是一个程序性质，在程序每一个可能的运行状态下都为真。对本课而言，最关心的是与 ADT 对象绑定的不变量：只要对象存在，它的表示就必须落在合法范围内。

不变量并不是“通常成立”的启发式说法，而是一条必须在所有状态下都被保持的严格承诺。构造对象时要让它成立，每次改变对象的操作也必须维持它成立。一旦某个操作让不变量被打破，后续所有对该对象的推理都会失效。

本讲把 ADT 层面的不变量拆成两个精确概念：抽象函数（AF）回答“这个表示对应什么抽象值”，表示不变量（RI）回答“这个表示本身是否合法”。下一节先看一个更特殊但常见的情况：不可变性。

FIELD TRACE

用一句话区分：AF 是“表示 → 抽象值”的映射，RI 是“表示是否合法”的谓词。AF 关心语义，RI 关心结构。一个 ADT 可以没有显式 RI（所有表示都合法），但通常不能没有 AF（否则你不知道表示意味着什么）。

02 / DEEP READING

不可变性如何实现

不可变性本身就是最强的不变量：对象一旦创建，其状态永不改变。在 TypeScript 里要保证不可变性，需要两层机制：

  • private：阻止外部直接访问字段。
  • readonly：阻止方法内部重新赋值字段。
  • 防御性复制（defensive copying）：当方法返回或接受可变对象时，复制一份，避免外部通过别名改变内部状态。

仅有 private 不够——方法内部仍可能修改字段；仅有 readonly 也不够——如果字段引用的是可变对象，外部拿到引用后仍能修改对象内容。因此不可变性常常需要把“不暴露可变引用”也纳入 RI。

03 / DERIVATION

抽象函数 AF 与表示不变量 RI

设 R 为表示空间（rep values，即内部字段所有可能的取值组合），A 为抽象空间（abstract values，即类型对外呈现的抽象值）。两个核心定义：

  • 抽象函数 AF : R → A：把一个表示值映射到它代表的抽象值。例如用三个数字 (year, month, day) 表示日期，AF 把它映射到“2026 年 2 月 25 日”这个抽象日期。
  • 表示不变量 RI : R → boolean：判断一个表示值是否合法。例如月份必须在 1–12 之间、日期必须对应当前月份合法。

关键限定：AF 只对满足 RI 的表示值有定义。换句话说，AF 的定义域是 RI 为真的子集。一个表示值要么不合法（RI 为假），要么合法并对应某个抽象值（AF 有定义）。

把日期记号写清楚：若 r ∈ R 且 RI(r) == true，则 AF(r) 就是该对象对外呈现的抽象日期。客户端只应通过操作看到抽象值，实现者通过 AF 在两端之间翻译。

画一条水平线，上方写抽象空间 A（客户端看到的世界），下方写表示空间 R（实现者看到的世界），AF 是向下的箭头，RI 是 R 上方的一条“合法区域”分界线。每次写 ADT 都在纸上先画这张图。

04 / DEEP READING

用 checkRep() 检查表示不变量

RI 不能只停留在注释里。标准做法是实现一个 checkRep() 方法，用断言检查 RI 是否成立，并在每个操作（构造者、生产者、变者）的末尾调用它。一旦 RI 被打破，测试或运行时会立即失败，把 bug 暴露在离源头最近的地方。

private checkRep(): void {
  assert(this.month >= 1 && this.month <= 12);
  assert(this.day >= 1 && this.day <= daysInMonth(this.year, this.month));
}

checkRep() 是调试与测试的利器，生产环境可以关闭断言以避免性能开销，但开发阶段应始终开启。它把“不变量是否成立”从一个心智负担变成一个机械检查。

05 / DEEP READING

良性副作用

实现者可以自由改变对象的表示值，只要改变后它仍映射到同一个抽象值。这类对表示的内部修改称为良性副作用（benevolent side-effects）。

例如一个不可变集合在 insert 时内部可能维护一个缓存的哈希值；重新计算哈希值改变了表示，但抽象值（集合的内容）未变，客户端无法察觉。良性副作用让实现可以在不违反抽象契约的前提下做性能优化。

判断良性副作用是否安全，标准仍是 AF：修改前后，AF(r) 必须相等。只要这一条成立，客户端就不可能区分修改前后的对象。

06 / DEEP READING

记录 AF、RI 与表示暴露的安全性论证

好的 ADT 文档必须显式写出：

  • AF：用自然语言或公式说明每个表示字段如何参与抽象值。
  • RI：列出所有合法表示必须满足的条件。
  • 表示暴露的安全性论证（safety from rep exposure）：解释为什么 private 字段、readonly 和防御性复制足以阻止客户端获取并修改内部表示。

表示暴露（representation exposure）是 ADT 最脆弱的攻击面：一旦客户端拿到内部可变引用的别名，RI 和表示独立性都会被破坏。安全性论证不是形式化证明，而是一段清晰说明“每个可能泄漏表示的路径都被堵住”的文字。

07 / DEEP READING

ADT 不变量替代前置条件

一个设计良好的 ADT 会自行封装并强制保持它的不变量。这意味着方法的规格说明可以写得更干净：不必再在每种前置条件里重复“调用者必须保证月份合法”，因为构造者和变者本身就会拒绝让非法状态出现。

例如 setMonth(m) 的规格说明可以写“要求 1 ≤ m ≤ 12，否则抛出异常”，由 ADT 负责执行这一检查。前置条件的职责从“依赖调用者守规矩”变成“依赖 ADT 自身的不变量”。这让客户端代码更简洁、更不容易出错。

08 / DEEP READING

如何建立并维持不变量

建立不变量只有两步，但每一步都必须严格执行：

  1. 让不变量在初始状态为真：构造者必须只构造出满足 RI 的表示值。
  2. 确保所有改变状态的操作都保持不变量为真：每个变者和生产者在返回前必须仍让 RI 成立。

这两个步骤合起来构成一个归纳论证：初始成立，且每次操作都保持，因此不变量在所有可达状态下都成立。checkRep() 正是这一归纳论证的运行时验证。

09 / DEEP READING

编程方法：写方法、写 ADT、写程序

本课把前面各条凝成三份方法学（recipes）：

  • 写一个方法：先读规格说明，再确认前置条件、后置条件与异常；完成后用 checkRep() 验证。
  • 写一个 ADT：先定义操作与规格说明，再确定 R、A、AF、RI，最后实现并写安全性论证。
  • 写一个程序：先识别需要的 ADT，再按上一步逐个实现，最后用客户端代码把它们组装起来。

这些方法学的共同点是把“先规格、后实现、用不变量自检”变成默认动作，而不是事后补救。

11 / CALIBRATION

把直觉校准成不变量

误区

AF 和 RI 是同一件事。

AF 描述“表示对应什么抽象值”，RI 描述“表示是否合法”。AF 关心语义映射，RI 关心结构合法性。

误区

只要方法实现正确，就不需要 checkRep()。

checkRep() 把不变量变成机械检查，能在离 bug 最近的地方暴露问题。没有它，表示错误会悄悄传播到客户端。

  • checkRep() 把 RI 变成运行时断言，在离 bug 最近的地方暴露表示错误。

# Reading 7: Abstraction Functions & Rep Invariants

## Objectives

Today's reading introduces several ideas:

- invariants
- representation exposure
- abstraction functions
- representation invariants

## Invariants

An *invariant* is a property of a program that is always true, for every possible runtime state of the program.

## Immutability

Guaranteeing immutability requires `private readonly` fields and defensive copying.

## Rep invariant and abstraction function

- **Abstraction function**: AF : R → A maps rep values to abstract values
- **Rep invariant**: RI : R → boolean tells us whether a rep value is well-formed

## Checking the rep invariant

Implement a `checkRep()` method that asserts the rep invariant.

## Benevolent side-effects

The implementation is free to mutate a rep value as long as it continues to map to the same abstract value.

## Documenting the AF, RI, and safety from rep exposure

Write a rep exposure safety argument.

## ADT invariants replace preconditions

A well-designed ADT encapsulates and enforces properties.

## How to establish invariants

1. make the invariant true in the initial state
2. ensure all changes keep the invariant true

### Writing a method
### Writing an abstract data type
### Writing a program

## Summary

- An ***invariant*** is a property that is always true of an ADT object.
- A good ADT ***preserves its own invariants***.
- The ***rep invariant*** specifies legal values of the representation.
- The ***abstraction function*** maps a concrete representation to the abstract value.
- ***Representation exposure*** threatens both representation independence and invariant preservation.
