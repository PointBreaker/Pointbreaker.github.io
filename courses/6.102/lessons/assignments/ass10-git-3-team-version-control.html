Git 3：Team Version Control

理解 Git 合并（merge）与合并冲突（merge conflict），练习多人协作场景下的版本控制。

实验目标

  • 理解 Git 历史如何从序列变成树、再变成图（DAG）。
  • 掌握自动合并与手动解决合并冲突。
  • 练习多人同时 push / pull 时的协作流程。
  • 理解团队使用版本控制的最佳实践。

从序列到图

多人基于同一 commit 并行工作时，历史分叉成树；合并（merge）把分叉接回，形成图。合并会创建合并提交（merge commit），它有两个父提交。

合并

当 push 被拒绝（! [rejected] main -> main (non-fast-forward)），说明远程有你没有的提交。必须先 pull（拉取并合并）再 push。

  • 自动合并：两人改不同文件 / 不同部分，Git 自动合并。
  • 合并冲突：两人改同一部分，Git 标记冲突，需手动解决。

冲突标记

<<<<<<<<<<<
你的改动（当前分支）
||||||||||||||||||||
原始版本（共同祖先）—— 需开启 diff3
==================
传入的改动（刚拉取的）
>>>>>>>>>>>

推荐开启三方差异（three-way diff）：

git config --global merge.conflictstyle diff3

分步指引：处理合并冲突

  1. git pull 遇到冲突。
  2. 在 VS Code 中打开冲突文件，编辑到满意，删除 <<</===/>>> 标记。
  3. 编译并运行测试，确认合并真的正确。
  4. git add 所有受影响文件，git commit 写合并提交信息。
  5. git push。

团队最佳实践

  • 沟通：告诉队友你在做什么、做了什么。写有用的 commit 信息。
  • 先 pull 再工作：从最新版本开始，减少合并。
  • 写规格与测试：测试先行，确保大家对规格理解一致。
  • 自动化：用 Didit 每次 push 自动跑测试。
  • review 你的提交：用 git diff --staged 检查。不要用 commit -a。
  • 同步：工作结束时确保所有人 push / pull 到同一 commit。

常见陷阱

  • 不 pull 就开始编辑旧版本：必然导致合并。
  • 提交不编译的代码：会破坏队友的构建。
  • 用 commit -a：容易把调试输出、无用文件提交进仓库。
  • 让流程盖过清晰沟通与定期同步。
