01 / PROBLEM

缺陷画廊：几类常见 bug

在进入"怎么调"之前，先看"会出什么问题"。6.102 列举了五类典型 bug：

  • 别名 bug（aliasing bug）：两个引用指向同一可变对象，一处修改意外影响另一处
  • 差一 bug（off-by-one）：循环边界或索引偏差 1
  • 顺序 bug（ordering bug）：操作的实际顺序与预期不一致
  • 代码克隆 bug（code-clone bug）：复制粘贴的代码只改了一处，漏改另一处
  • 遍历时修改 bug（mutating-while-iterating）：在迭代集合的同时修改它

这些 bug 的共同点是：它们都逃过了程序员的直觉检查，只在特定输入或时序下才暴露。因此，光靠"更仔细地写代码"是不够的，需要系统性的防御。

FIELD TRACE

把每种 bug 和本课三大目标对应：别名 bug 和遍时常修改 bug 可用不可变性（SFB）消除；差一 bug 可用静态检查（更好的类型/范围）捕获；顺序 bug 和代码克隆 bug 可用模块化与封装（ETU/RFC）降低概率。先分类，再选武器。

02 / DEEP READING

第一道防线：让缺陷不可能

最强大的调试是不调试。三类机制让某些缺陷在编写阶段就被排除：

  • 静态检查（static checking）：编译器在运行前发现类型错误、未声明变量等。TypeScript 的类型系统就是静态检查。
  • 动态检查（dynamic checking）：运行时检查，如数组越界、除零、类型转换失败。
  • 不可变性（immutability）：用不可变类型与常量，从根本上消除别名 bug 和遍时常修改 bug。

三者的关系是互补的：静态检查捕获编译期可判定的错误，动态检查捕获运行期才暴露的错误，不可变性则让某些错误根本无法表达。

03 / DEEP READING

第二道防线：让缺陷容易发现

当缺陷无法完全避免时，下一步是让它们尽早、尽可能明显地暴露：

  • Fail fast：一旦发现异常状态立即失败，而不是带着错误状态继续运行
  • 断言（assertions）：文档化并强制执行为什么代码能继续的假设
  • 增量开发：每次只加一小部分，立即测试，缩小出错范围
  • 模块化与封装：把错误限制在模块内部，不让它传播
  • 最小化变量作用域：变量越局部，越容易被追踪

Fail fast 和断言的区别在于：fail fast 是"发现错误就停"，断言是"把假设写下来并检查"。两者配合，能让缺陷在离源头最近的地方暴露。

04 / DERIVATION

复现缺陷

调试的第一步不是改代码，而是复现（reproduce）缺陷：找到一个小的、可重复的测试用例，让失败稳定出现。

为什么复现这么关键？因为如果你不能让失败重复出现，你就无法判断修复是否成功。一个好的复现用例应该：

  • 小：输入最小化，排除无关因素
  • 可重复：每次运行都失败，而不是偶尔失败
  • 具体：明确输入、预期输出、实际输出

对于并发相关的 heisenbugs（非确定性 bug），复现尤其困难，这正是并发难以调试的原因之一。

05 / DEEP READING

用科学方法找缺陷

复现之后，用科学方法（scientific method）定位缺陷：

  1. 研究数据：观察失败现象、输入输出、错误信息
  2. 假设：提出一个可检验的解释
  3. 实验：设计实验验证或推翻假设
  4. 重复：直到找到根因

常用的探针（probe）包括：断言、打印语句、调试器。Delta debugging 则通过比较成功运行与失败运行的差异来缩小范围。

FIELD TRACE

把科学方法落到调试上：每次只做一个实验，记录假设与结果。不要同时改三处代码再运行——如果行为变了，你不知道是哪处起了作用。调试是搜索问题，不是碰运气。

06 / DEEP READING

修复缺陷

找到根因后，修复不是结束，而是开始：

  • 查找相关 bug：同一根因可能还有其它表现
  • 撤销调试探针：移除临时加入的打印和断言
  • 写回归测试：把复现用例固化为测试，防止复发
  • Add, Commit, Push, Reflect：提交代码并反思根因

回归测试是修复流程中最容易被跳过、却最关键的一步。没有回归测试，同样的 bug 很可能在下次改动时卷土重来。

07 / DEEP READING

其他调试建议

当科学方法卡住时，试试这些：

  • 换个视角（rubber-duck debugging）：向小黄鸭解释代码，往往说着说着就发现了问题
  • 写下来：用文字描述问题，强迫自己把模糊的直觉变成精确的描述
  • 寻求帮助：向同学、助教描述问题
  • 睡一觉：让潜意识处理，第二天常有新思路

这些看似"软"的技巧，背后都有共同原理：把你从当前的思维定势中拉出来。

09 / CALIBRATION

把直觉校准成不变量

误区

调试就是加打印语句看输出。

打印只是探针之一。系统调试 = 复现 + 假设 + 实验 + 重复。没有假设的打印是盲目搜索。

误区

修完 bug 就结束了。

没有回归测试的修复不完整。还要撤销探针、查找相关 bug、反思根因。

知识检查

调试的"第一道防线"是什么？

为什么调试的第一步是复现缺陷？

离开本讲前，你应能复述

  • 调试 = 先让缺陷不可能（静态/动态检查 + 不可变性），再让缺陷容易发现（fail fast + 断言）。
  • 系统调试：复现 → 研究数据 → 假设 → 实验 → 重复。
  • 修复后必须写回归测试，并撤销调试探针、查找相关 bug。

# Reading 13: (Avoiding) Debugging

[6.102 — Software Construction](http://web.mit.edu/6.102/www/sp26/)
Spring 2026

## Objectives

The topic of today's class is debugging: how to *avoid debugging*
and how to debug systematically.

## A rogue's gallery of bugs

- Aliasing bug
- Off-by-one bug
- Ordering bug
- Code-clone bug
- Mutating-while-iterating bug

## First defense: make bugs impossible

- Static checking
- Dynamic checking
- Immutability (immutable types and constants)

## Second defense: make bugs easy to find

- Fail fast
- Assertions (document and enforce assumptions)
- Incremental development
- Modularity & encapsulation
- Minimizing variable scope

## Reproduce the bug

Find a small, repeatable test case that reproduces the failure.

## Find the bug using the scientific method

1. **Study the data.**
2. **Hypothesize.**
3. **Experiment.**
4. **Repeat.**

### Probes: assertions, print statements, debuggers

### Delta debugging

Compare successful runs with failing runs.

## Fix the bug

- Look for related bugs
- Undo debugging probes
- Make a regression test
- Add, Commit, Push, and Reflect

## Other tips

- Get a fresh view (rubber-duck debugging)
- Describe it in writing
- Seek help
- Sleep on it

## Summary

- **Avoid debugging**: make bugs impossible
- **Keep bugs confined**: fail fast, incremental development, modularity
- **Debug systematically**: reproduce, hypothesize, experiment, fix
