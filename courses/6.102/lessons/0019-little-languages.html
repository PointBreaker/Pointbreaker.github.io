01 / PROBLEM

把代码表示为数据

一个 Formula 值（第 11 讲的布尔公式）是第一类值（first-class value）：它可以被存储在变量中、作为参数传递、作为返回值返回、被操纵和变换。这就是"把代码表示为数据"——程序本身可以当作数据来处理。

这个思想是小型语言（little language）的起点：如果我们能用数据结构表示一段"程序"，就能写函数来分析、变换、执行它。

02 / DEEP READING

构建语言解决问题：DSL

一个语言（language）比一个单纯的程序（program）更灵活。领域特定语言（Domain-Specific Language, DSL）分两类：

  • 外部 DSL（external DSL）：自定义语法，如正则表达式、ParserLib 文法。需要单独的解析器。
  • 内部 DSL（internal DSL）：嵌入在宿主语言中，利用第一类函数等特性。无需单独解析。

本讲的音乐语言是一个外部 DSL：它有自定义的 abc 记谱法语法，需要解析器把字符串转成 AST。

03 / DERIVATION

音乐语言的设计

设计一个用于生成和播放音乐的语言。底层用 MidiSequencePlayer 和 SequencePlayer 接口（提供 addNote 和 start）播放 MIDI 音乐。

核心是 Music 数据类型：

\[Music = Note(duration: number,\; pitch: Pitch,\; instrument: Instrument) + Rest(duration: number) + Concat(first: Music,\; second: Music)\]

一段音乐要么是一个音符，要么是一个休止符，要么是两段音乐的拼接。注意 Concat 的两个字段都指向 Music 自身——这是递归。

FIELD TRACE

把音乐类型和第 11 讲的 ImList 对比：ImList 是 Empty + Cons，Music 是 Note + Rest + Concat。两者都是递归数据类型，但 Music 的 Concat 有两个自身引用字段（first 和 second），形成一棵树而非一条链。树形递归是表达层次结构的关键。

04 / DEEP READING

音乐数据类型与组合模式

Music 类型体现了组合模式（composite pattern）：单个对象（Note、Rest 是原语）和组合对象（Concat）属于同一类型。客户端可以统一处理单个音符和整段乐曲，无需区分。

// 表示 "do re mi" 的简化示例
const do_ = new Note(1, Pitch.C, Instrument.PIANO);
const re_ = new Note(1, Pitch.D, Instrument.PIANO);
const mi_ = new Note(1, Pitch.E, Instrument.PIANO);
const melody: Music = new Concat(do_, new Concat(re_, mi_));

组合模式让递归数据类型的操作可以递归定义：处理 Concat 就是递归处理 first 和 second。

05 / DEEP READING

音乐记谱法：abc 表示

为了让人类书写音乐，定义简化的 abc 记谱法。例如 "C D E" 表示三个音符的序列。这种记谱法是外部 DSL 的语法，需要解析器转成 Music 值。

06 / DEEP READING

实现解析器

notes 函数把 abc 记谱法字符串解析为 Music 值。使用递归下降（recursive descent）实现——这与 ParserLib 的解析策略一致。

function notes(input: string): Music {
  // 递归下降：把字符串拆成 token，按文法构造 Music 树
  const tokens = tokenize(input);
  return parseSequence(tokens);
}

解析器的输出是 Music 递归数据类型，后续所有操作（播放、变换）都基于它。

07 / DEEP READING

实现播放器

play 函数把 Music 值播放出来，使用 SequencePlayer：

function play(music: Music, player: SequencePlayer): void {
  if (music instanceof Note) {
    player.addNote(music.duration, music.pitch, music.instrument);
  } else if (music instanceof Rest) {
    // 休止符：不添加音符，只推进时间
  } else if (music instanceof Concat) {
    play(music.first, player);
    play(music.second, player);
  }
}

这是解释器模式的典型实现：每个变体处理自己的逻辑，递归部分交给子结构。

08 / DEEP READING

递归类型上的函数：解释器模式

第 11 讲引入的解释器模式在这里再次出现：操作声明在 Music 接口中，每个变体（Note、Rest、Concat）各自实现。

但解释器模式有两个缺点：

  1. 代码分散：一个操作的逻辑分散在多个变体类中
  2. 添加操作困难：每加一个新操作，必须修改所有变体类

当操作很多、变体很少时，这种分散尚可接受；当变体很多、操作很少时，解释器模式反而是好选择。

09 / DEEP READING

模式匹配

函数式语言中，递归数据类型上的操作通常用模式匹配（pattern matching）定义。TypeScript 没有原生模式匹配，但判别联合 + switch 可以模拟：

function duration(m: Music): number {
  switch (m.type) {
    case "note":   return m.duration;
    case "rest":   return m.duration;
    case "concat": return duration(m.first) + duration(m.second);
  }
}

每个 case 对应一个变体，逻辑集中在一个函数里——这正是解释器模式所欠缺的。

10 / DEEP READING

访问者模式

访问者模式（visitor pattern）解决了解释器模式的第二个缺点：添加新操作更容易。它使用双重分派（double dispatch）：每个变体实现 accept(visitor)，调用访问者的 onVariant 方法。

// 访问者接口：每个变体一个方法
interface MusicVisitor<R> {
  onNote(n: Note): R;
  onRest(r: Rest): R;
  onConcat(c: Concat): R;
}

// 变体实现 accept
class Note {
  accept<R>(v: MusicVisitor<R>): R { return v.onNote(this); }
}

// 新操作 = 新访问者，无需修改变体类
class DurationVisitor implements MusicVisitor<number> {
  onNote(n: Note) { return n.duration; }
  onRest(r: Rest) { return r.duration; }
  onConcat(c: Concat) {
    return c.first.accept(this) + c.second.accept(this);
  }
}
FIELD TRACE

把访问者模式想成"插件系统"：变体类是固定的插座，访问者是可插拔的插件。加新操作 = 插新插件，不用改插座。代价是加新变体 = 改所有插座（所有访问者都要加一个 onX 方法）。

11 / DEEP READING

为什么用访问者

两种模式的取舍本质是代码组织方式的不同：

  • 解释器模式：代码按列（变体）分组。每个变体类包含所有操作的实现。
    • 访问者模式：代码按行（操作）分组。每个访问者类包含所有变体的处理。

选择依据：哪个维度更稳定？变体稳定 → 用访问者（加操作容易）；操作稳定 → 用解释器（加变体容易）。这是软件设计中"把变化封装起来"原则的又一体现。

# Reading 19: Little Languages

## Objectives

Explore the design of a **little language** for music.
Representing code as data.

## Representing code as data

A `Formula` value is a **first-class value** that can be stored,
passed, and manipulated.

## Building languages to solve problems

A _language_ has greater flexibility than a mere _program_.
Domain-specific languages (DSLs):

- **External DSL**: custom syntax (regular expressions, ParserLib grammars)
- **Internal DSL**: embedded in a host language (first-class functions)

## Music language

Design a language for generating and playing music.

### Playing MIDI music

`MidiSequencePlayer` and `SequencePlayer` interface
with `addNote` and `start`.

## Music data type

```
Music = Note(duration:number, pitch:Pitch, instrument:Instrument)
       + Rest(duration:number)
       + Concat(first:Music, second:Music)
```

### Composite pattern

Single objects (primitives) and groups (composites) belong to the same type.

## Music notation

Simplified abc notation for writing music.

## Implementing the parser

`notes` parses abc notation into `Music`. Uses recursive descent.

## Implementing the player

`play` plays the music using a sequence player.

## Functions on recursive types

### Interpreter pattern

Operations declared in the interface, implemented in each variant.

### Downsides of Interpreter pattern

1. Code distributed across variant classes
2. Adding operations requires modifying all classes

## Pattern matching

Functional definitions map to pattern matching.

## Visitor pattern

- A visitor implements `switch` over types
- Uses **double dispatch**: `accept` calls visitor's `onVariant` method
- Makes adding new operations easier

## Why visitor?

- Interpreter: code grouped by column (variant)
- Visitor: code grouped by row (operation)

## Summary

- ADTs can make domain-specific languages
- Composite pattern treats single objects and groups the same
- Visitor pattern makes adding new operations easier
