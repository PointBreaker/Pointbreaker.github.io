抽象数据类型

Abstract Data Types

抽象数据类型（Abstract Data Types）用“能对它做什么操作”来刻画一个类型。表示独立性（representation independence）把“是什么”和“怎么做”分开，让客户端只依赖行为规范，这是模块化与封装的基石。

01 / PROBLEM

客户端对表示做假设有多危险

假设你实现了一个 MyDate 类型，内部用三个数字字段 year、month、day 表示日期。起初一切都好，直到某个客户端写下 date.month = 13，因为它“知道”月份就是一个公开字段；或者另一个客户端在比较两个日期时直接访问内部数组下标。这些代码一旦写出来，就和你的内部表示绑定死了。

现在你想把表示改成从纪元日起的天数、或改成一个字符串。所有直接触碰内部字段的客户端都会崩溃。抽象数据类型要解决的正是这个问题：阻止客户端对类型的内部表示（representation）做假设。如果客户端只能经由你公开的操作与类型交互，那么你随时可以替换表示，而客户端无需改动。

本讲的两个核心思想是：第一，用操作定义类型；第二，让类型的使用与表示无关。这两个思想合起来，构成整门课程“抽象”线索的枢纽。

FIELD TRACE

判断一段代码是否违反 ADT 哲学，最快的问题是：“如果实现者明天把内部字段换掉，这段客户端代码还能编译、还能跑吗？” 如果答案是否，说明客户端依赖了表示，而不是依赖操作。

02 / DEEP READING

抽象、封装与信息隐藏

建立 ADT 之前，先统一五个常被混用的术语。它们相关但并不相同：

  • 抽象（abstraction）：省略或隐藏低层细节，只保留对当前目的重要的部分。
  • 模块化（modularity）：把系统拆成各自承担明确职责的组件。
  • 封装（encapsulation）：在模块周围筑起一道墙，外部只能通过墙上的窗口访问。
  • 信息隐藏（information hiding）：把模块实现的细节藏起来，只暴露最小接口。
  • 关注点分离（separation of concerns）：让每个功能只由单个模块负责。

ADT 把这几条凝聚成一个可操作的设计规则：类型的意义完全来自它的操作，所有关于“怎么实现”的信息都被隐藏在墙后。客户端看到的是操作签名和规格说明，看不到字段、算法和数据结构。

FIELD TRACE

把这五个术语画成同心圆：抽象是最外层的意图，模块化是结构划分，封装是边界机制，信息隐藏是边界内的策略，关注点分离是分配职责的原则。ADT 同时触及每一层。

03 / DEEP READING

类型由操作刻画

数据抽象的关键思想是：一个类型由你能对它执行的操作来刻画。问“这是什么类型”等价于问“我能对它做什么”。整数之所以是整数，是因为能对它做加、减、乘、比较；栈之所以是栈，是因为能 push、pop、peek。

这意味着设计 ADT 的第一步不是选数据结构，而是选操作。先决定客户端需要哪些能力，再回头决定用什么数据结构实现这些能力。这个次序一旦颠倒，你就会把特定的数据结构（比如“我用数组实现的”）泄漏成类型的身份，从而失去替换实现的自由。

老师把这种思想概括为：类型 = 操作 + 操作的规格说明。下一节我们把操作进一步分类。

04 / DEEP READING

四类操作：创建者、生产者、观察者、变者

抽象类型的操作可以分为四类，这是本讲最实用的分类工具：

  • 创建者（creators）：创建该类型的新对象。构造函数和静态工厂方法都属此类。
  • 生产者（producers）：从该类型的现有对象创建新对象。例如 concat 从两个字符串产生一个新字符串。
  • 观察者（observers）：接受该类型的对象，返回另一种类型的值。例如 size、toString、isEmpty。
  • 变者（mutators）：改变对象的状态，也叫修改者。

这个分类之所以重要，是因为它直接关系到可变性。变者越少，类型就越容易是不可变的（immutable），而不可变类型在并发和复用场景下显著更安全。阅读本课后面“函数式编程”时，你会看到 map/filter/reduce 几乎只依赖生产者和观察者，刻意避开变者。

FIELD TRACE

拿一个你熟悉的类型——比如集合 Set——列出它的全部操作，再逐一归入四类。重点检查：是否真的需要变者？能不能把变者替换为生产者（返回新集合而非修改原集合）？这一步能把“抽象类型设计”变成可执行的清单。

05 / DERIVATION

抽象类型由它的操作集定义

类型 T 的全部操作，连同它们的规格说明，就完整地刻画了“T 是什么”。这句话是 ADT 哲学的浓缩：只要两个类型暴露同样的操作、满足同样的规格说明，客户端就无法也无须区分它们。

举例：一个 ImmutableSet 可以内部用有序数组实现，也可以用哈希表实现，还可以用平衡二叉搜索树实现。只要 contains、insert、remove 的规格说明一致，客户端代码就完全不需要知道背后是哪一种。

这同时给出了一种阅读代码的方式：看到一个类型时，先读它的操作和规格说明，建立对“它是什么”的理解；至于字段和算法，是实现细节，应当被信息隐藏隔开。下一节我们把“可替换实现”精确化为表示独立性。

06 / DEEP READING

怎样设计一个好的抽象类型

设计 ADT 有几条经验规则：

  • 少而简单：操作数量尽量少，每个操作的语义尽量简单。复杂的操作应当拆解成简单操作的组合。
  • 目的明确：每个操作都应有清晰、单一的职责。
  • 充分（adequate）：操作集要足够表达客户端需要的能力，不能为了简洁而缺失关键操作。
  • 不混淆通用与领域特征：不要把通用工具逻辑和领域特定逻辑塞进同一个 ADT。

这些规则看起来朴素，但它们指向一个共同目标：让 ADT 的抽象既不过薄（暴露太多细节，客户端仍要自己拼复杂逻辑），也不过厚（堆砌操作、混入不相关职责）。好的抽象类型读起来像一份精简的词典，每个词都不可或缺。

07 / DEEP READING

表示独立性

表示独立性（representation independence） 指的是：抽象类型的使用与它的表示无关。换言之，你可以在不修改任何客户端代码的前提下，替换掉整个内部实现。

表示独立性带来的工程价值很直接：

  • 可替换实现：先用简单但慢的实现跑通，再换成复杂但快的实现。
  • 局部化修改：修复实现中的 bug 或优化性能时，改动被限制在 ADT 内部。
  • 可测试性：客户端代码可以在测试中注入另一种实现（比如用假对象）。

表示独立性依赖两个机制共同保障：把字段声明为 private 阻止直接访问，以及只通过规格说明精确的公开操作暴露行为。下一节看 TypeScript 如何落地这些机制。

FIELD TRACE

当你写完一个 ADT，做“表示独立性压测”：把实现从 A 换成 B，重新跑客户端测试。如果客户端测试全部通过，你才真正获得了表示独立性。任何因换实现而失败的测试，都暴露了一处客户端对表示的隐式依赖。

08 / DEEP READING

在 TypeScript 中实现 ADT

TypeScript 提供了几种实现 ADT 的方式，常见的有：

  • 类（class）：用 private 字段隐藏表示，用公开方法暴露操作。最直接，但一个类只能绑定一种实现。
  • 接口 + 类（interface + class）：用接口定义操作契约，让多个类实现同一接口。这是获得表示独立性的标准方式——客户端依赖接口，而非具体类。
  • 枚举（enum）：当 ADT 只包含有限个固定值时（比如星期、方向），枚举天然表达“小有限集”抽象。

这几种方式并不互斥。第 8 讲（接口与子类型）会系统展开接口与泛型；第 9 讲（枚举）会专门处理有限值域。本节只要建立直觉：接口定义契约，类实现契约，客户端只依赖契约。

// 接口定义操作契约 —— 客户端只看到这段
interface ImmutableSet<T> {
  contains(item: T): boolean;
  insert(item: T): ImmutableSet<T>;
  remove(item: T): ImmutableSet<T>;
  size(): number;
}

// 具体实现 A：用数组 —— 客户端完全不知道
class ArraySet<T> implements ImmutableSet<T> {
  private readonly items: T[];
  // ...
}
09 / DEEP READING

测试抽象数据类型

测试 ADT 的方式很直接：为它的每个操作写测试。由于 ADT 的意义完全来自操作，覆盖操作就覆盖了整个抽象。

测试时要用规格说明驱动：每个测试只通过公开操作构造对象、触发行为、断言结果，绝不直接检查内部字段。这样即便将来替换实现，测试仍然有效——这正是表示独立性在测试上的体现。

创建者、生产者、观察者、变者四类操作都要覆盖，尤其注意边界：空集合、单元素、重复操作、连续变者调用后的状态。不可变类型因为没有变者，测试会更简单，这也是不可变性的工程优势之一。

# Reading 6: Abstract Data Types

## Objectives

Today's class introduces two ideas:

- Abstract data types
- Representation independence

## Introduction

Abstract data types address a particularly dangerous problem: clients making assumptions about the type's internal representation.

## What abstraction means

- **Abstraction.** Omitting or hiding low-level details.
- **Modularity.** Dividing a system into components.
- **Encapsulation.** Building a wall around a module.
- **Information hiding.** Hiding details of a module's implementation.
- **Separation of concerns.** Making a feature the responsibility of a single module.

## User-defined types

The key idea of data abstraction is that a type is characterized by the operations you can perform on it.

## Classifying types and operations

Operations of an abstract type are classified as:

- **Creators** create new objects of the type.
- **Producers** create new objects from existing objects of the type.
- **Observers** take objects of the abstract type and return objects of a different type.
- **Mutators** change objects.

## An abstract type is defined by its operations

The set of operations for a type T, along with their specifications, fully characterize what we mean by T.

## Designing an abstract type

- A few, simple operations
- Each operation should have a well-defined purpose
- The set of operations should be adequate
- It should not mix general-purpose and domain-specific features

## Representation independence

The use of an abstract type is independent of its representation.

## Realizing ADT concepts in TypeScript

Various ways to implement ADTs: classes, interfaces + classes, enums, etc.

## Testing an abstract data type

Build a test suite by creating tests for each of its operations.

## Summary

- Abstract data types are characterized by their operations.
- Operations: creators, producers, observers, mutators.
- A good ADT is simple, coherent, adequate, and representation independent.
