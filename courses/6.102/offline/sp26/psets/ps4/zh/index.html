习题集 4：记忆翻牌

本习题集的截止日期见课程日历。

本习题集的目的是探索如何对共享的可变数据类型进行并发编程。

设计自由与限制

在本次习题集中，你拥有充分的设计自由。

请注意所提供代码中的 PS4 说明。 你必须满足 board.ts 和 commands.ts 中某些函数的既定规格。 你可以重写或删除任何其它已提供的代码，添加新的类和方法等。 在本次习题集中，与之前的习题集不同，我们不会针对任何其它实现来运行你的测试。

请注意，你的游戏棋盘的坐标系必须符合规格：(row, column) 坐标从左上角的 (0, 0) 开始，垂直向下、水平向右递增。

检查 Didit 反馈并确保你的代码能够编译和运行以接受评分，这是你自己的责任；但你必须自行测试以确保正确性。

获取代码

开始前，

  1. 让 Didit 在 github.mit.edu 上为你创建一个远程 psets/ps4 仓库。

  2. 克隆该仓库。 在你的 Didit 作业页面顶部找到 git clone 命令，完整复制，粘贴到终端中并运行。

  3. cd ps4-«username»，运行 npm install，然后在 Visual Studio Code 中打开。 如果你需要回顾如何创建、克隆或设置你的仓库，参见习题集 0。

概述

在本次习题集中，你将构建一个联网的多人版本Memory（又称 Concentration），即翻开背面的牌并试图找到配对的游戏。 我们的版本将让玩家同时翻牌，而不是轮流翻牌。 我们将它称为“记忆翻牌”。

问题 1：你将为此游戏设计并实现一个或多个抽象数据类型（ADT）。

问题 2：你将把你的抽象数据类型连接到一个使用 HTTP 处理客户端的游戏服务器。

当你完成问题 1-2 后，就可以在浏览器中玩“记忆翻牌”了。

问题 3：你将修改系统，使用异步游戏棋盘来处理多名同时在线的玩家。

问题 4：你将设计并实现一个类似 map 的函数（如 map/filter/reduce 中的 map），用于替换棋盘上的卡牌。

问题 5：你将设计并实现监视棋盘变化的功能，使“记忆翻牌”用户界面响应更迅速。

迭代开发建议

alpha 的自动和手动评分都会更侧重于没有并发情况下的棋盘和服务器。

首先，做问题 1 和 2 时无需考虑并发：让你的 Board 或其它抽象数据类型使用同步方法，不必担心服务器中多个并发玩家的问题。 通过编写测试、选择数据结构和编写代码来实现下面指定的游戏规则。 考虑所有数据类型的抽象函数和表示不变量。

然后，在问题 3 中修改你的工作，以让你的系统为并发玩家做好准备。 根据异步操作的需要，修改你对抽象数据类型操作的选择。

最后，继续完成问题 4 和 5。

游戏棋盘

“记忆翻牌”的游戏棋盘有一个由格子组成的网格。 每个格子最初都有一张卡牌。 当卡牌被配对并移除后，格子变为空。

我们游戏中的卡牌是一个由非空白、非换行字符组成的非空字符串。 这使得我们可以使用 emoji 字符来表示像 Hello 这样的“图画”以及像 🌈 这样的图画。 例如：

👁 💖 M √-1 ☕️

如果两张卡牌具有相同的字符字符串，则它们匹配。

所有卡牌初始为背面朝上。 玩家会将它们翻为正面朝上；这些卡牌随后要么再次翻为背面朝上（如果玩家翻开的卡牌不匹配），要么从棋盘上移除（如果它们匹配）。

游戏棋盘从文件加载。 以下是棋盘文件的形式化语法：

BOARD_FILE ::= ROW "x" COLUMN NEWLINE (CARD NEWLINE)+

CARD ::= [^\s\n\r]+
ROW ::= INT
COLUMN ::= INT
INT ::= [0-9]+
NEWLINE ::= "\r"? "\n"

在 BOARD_FILE 中，ROW 是行数，COLUMN 是列数，卡牌按行从左到右依次列出，从顶行开始。

在此示例中，使用 ↵ 表示换行。 该棋盘在习题集的 boards 文件夹中作为 perfect.txt 提供。

一个有效的棋盘文件必须恰好包含 ROW×COLUMN 个以换行符结尾的 CARD 行。

游戏规则

多名玩家同时操作棋盘上的卡牌。 他们通过尝试翻开成对的相同卡牌来进行游戏。

以下是规则的非正式总结：

1
当玩家翻开一对中的第一张牌时，该玩家即控制那张牌；但如果已有其他人控制它，则该玩家等待，直到能够取得控制权。
2
当玩家翻开第二张牌时，如果卡牌匹配，玩家保持对它们的控制权；否则，玩家放弃控制权。 目前这些卡牌保持正面朝上。
3
当玩家进行下一次操作时，如果之前翻的牌匹配，则那些牌从棋盘上移除；否则，如果没有人控制它们，则将它们翻为背面朝上。

请注意与通常的 Memory 游戏规则至少两处不同：你可以“翻开”一张已经正面朝上的牌，等待直到该牌可用；并且被翻开的牌在棋盘上保持正面朝上，直到翻开它的玩家进行下一次操作。

完整规则

第一张牌：玩家通过指定棋盘上的一个格子来尝试翻开第一张牌……

1-A
如果那里没有牌（玩家指定了一个空格，也许是因为那张牌刚刚被另一名玩家移除了），则该操作失败。
1-B
如果卡牌背面朝上，则将其翻为正面朝上（所有玩家现在都能看到它），并且该玩家控制那张牌。
1-C
如果卡牌已经正面朝上，但没有被其他玩家控制，则它保持正面朝上，并且该玩家控制那张牌。
1-D
如果卡牌正面朝上且被另一名玩家控制，则该操作等待。 该玩家将在下一次机会与其它玩家竞争以取得该牌的控制权。

第二张牌：一旦玩家控制了他们的第一张牌，就可以尝试翻开第二张牌……

2-A
如果那里没有牌，则该操作失败。 该玩家同时放弃其第一张牌的控制权（但目前它仍保持正面朝上）。
2-B
如果卡牌正面朝上且被一名玩家（另一名玩家或玩家自己）控制，则该操作失败。 为避免死锁，该操作不会等待。 该玩家同时放弃其第一张牌的控制权（但目前它仍保持正面朝上）。
—
如果卡牌背面朝上，或者卡牌正面朝上但没有被任何玩家控制，则：
2-C
如果它背面朝上，则将其翻为正面朝上。
2-D
如果两张卡牌相同，则匹配成功！ 该玩家保持对这两张牌的控制权（且目前它们在棋盘上保持正面朝上）。
2-E
如果它们不相同，该玩家放弃对这两张牌的控制权（同样，目前它们保持正面朝上）。

当一名玩家等待翻开第一张牌时，其他玩家继续正常游戏。 他们不会等待，除非他们也试图翻开一张由其他玩家控制的第一张牌。

1-A、2-A 和 2-B 中的失败意味着该玩家未能控制一张牌（在 2-A/B 中还放弃了控制权）。 该玩家仍然可以继续游戏。

在尝试翻开第二张牌（无论成功与否）之后，该玩家又可以再次尝试翻开第一张牌。 当他这样做时，在遵循上述规则之前，他先完成自己之前的操作：

3-A
如果他们翻开了一对匹配的牌，则他们控制这两张牌。 此时，那些牌从棋盘上移除，并且他们放弃对它们的控制权。 游戏的计分部分未在规格中规定。
3-B
否则，他们翻开了一张或两张不匹配的牌，放弃了控制权但将它们留在棋盘上正面朝上。 此时，对于每一张这样的牌，如果它仍在棋盘上、当前正面朝上、且当前没有被其他玩家控制，则将该牌翻为背面朝上。

如果该玩家从未尝试翻开一张新的第一张牌，则 3-A/B 中的步骤永远不会发生。

在网页上玩

为了支持通过网络进行的多人“记忆翻牌”游戏，我们定义了一个 HTTP 协议，以便可以在网页浏览器中玩该游戏。 Web 服务器的代码已经提供（在 server.ts 中），但它依赖本习题集代码中这些既有的函数规格，你需要实现这些函数：

  • parseFromFile() from board.ts
  • look(),flip(),map(), and watch() from commands.ts

在该协议中，每位玩家通过一个 ID 来标识自己，该 ID 是一个由字母、数字或下划线字符组成的非空字符串，可自主选择。 具有相同玩家 ID 的所有请求都属于单个玩家的操作。

对于所有请求，服务器以一个棋盘状态响应，从该玩家的视角展示棋盘的当前状态。棋盘状态由以下语法描述：

BOARD_STATE ::= ROW "x" COLUMN NEWLINE (SPOT NEWLINE)+

SPOT ::= "none" | "down" | "up " CARD | "my " CARD
CARD ::= [^\s\n\r]+
ROW ::= INT
COLUMN ::= INT
INT ::= [0-9]+
NEWLINE ::= "\r"? "\n"

在棋盘状态中，ROW 是行数，COLUMN 是列数，卡牌按行从左到右依次列出，从顶行开始。

none 表示该位置没有卡牌，down 表示背面朝上的卡牌，up 表示由另一名玩家（或无人）控制的正面朝上的卡牌，my 表示由发送请求的玩家控制的正面朝上的卡牌。

例如：

3x3↵
up␣A↵
down↵
down↵
none↵
my␣B↵
none↵
down↵
down↵
up␣C↵
AAA
B
CCC

在此示例中，使用 ␣ 表示空格，使用 ↵ 表示换行。

(1,0) 和 (1,2) 处没有卡牌。

(0,0)、(1,1) 和 (2,2) 处的卡牌正面朝上，收到此消息的玩家控制着 (1,1) 处的 B 卡牌。

问题 1：游戏棋盘

规格说明、测试并实现一个可变的 Board 抽象数据类型（ADT），用于表示“记忆翻牌”游戏棋盘。 定义其它抽象数据类型也可能有所帮助。

请记得包含：你所写的每个类和每个方法的规格说明；抽象函数、表示不变量以及防止表示暴露的论证；checkRep() 和 toString()。

Board 定义了一个用于创建新棋盘的静态工厂方法，你必须支持该方法：

  • parseFromFile(filename)：通过解析上述格式的文件来创建棋盘

用于解析棋盘文件时，解析器生成器（如 ParserLib）带来的复杂性超出了你的需要。

  • String.split() 和 String.match() 或许就能处理所有的解析和提取工作。

  • fs.promises.readFile() 异步读取文件。请务必使用基于 promise 的版本（在文档中称为 fsPromises.readFile，如果你导入 fs 则引用为 fs.promises.readFile），而不是较旧的基于回调函数的版本（也称为 readFile，但位于 fs 本身中）。

为了跟踪玩家及其状态：

  • 每个玩家或许可以简单地用他们在命令函数中使用的 ID 来标识。 所有游戏状态都将存储在 Board 中。

  • 每个玩家或许可以用一个抽象数据类型来表示，例如 Player。 玩家的部分状态可能存储在 Player 对象中，或者由 Board 存储所有状态。

根据游戏规则，你需要跟踪谁控制哪些卡牌以及每张卡牌的状态。

迭代开发建议：先实现一个同步的棋盘（即除 parseFromFile 外没有 async 方法），并在问题 2 中将其连接到服务器。 alpha 评分将更侧重于在没有并发的情况下玩游戏。 然后在问题 3 中修改，使其在并发玩家情况下表现正确。

为了根据游戏规则实现等待，请使用异步方法和 await，或者回调函数。 棋盘不应忙等待（busy-wait）。

由你决定哪些操作是原子的，因为规则并未作此规定。 例如，在规则 3-B 中，将两张牌翻回去可能是单个操作——其间没有其他玩家能看到或操作中间状态的棋盘——也可能是两个独立的操作。 但棋盘绝不能到达不一致的状态，例如两名玩家控制同一张牌，或者一张背面朝上的牌仍被某玩家控制。

请注意，翻牌操作可能在规则中的多处失败。 在 flip() 命令的规格中（你需要实现它以将你的 Board 连接到所提供的 Web 服务器），失败通过一个被拒绝的 promise 来表示，这可以通过从一个 async 函数抛出异常来实现。 在设计你自己的 Board 操作时，请牢记这一点。 要测试一个被拒绝的 promise，assert.rejects 很有用。

模拟游戏

在 simulation.ts 中，我们提供了一个程序的骨架代码，用于模拟一名玩家与棋盘交互，随机翻开若干卡牌。 你应该能够填写 simulationMain() 函数中的 TODO，并使用 npm run simulation 来运行模拟的单人“记忆翻牌”游戏。

simulation.ts 使用 seedrandom 包来生成可复现的伪随机数序列。 我们没有调用 Math.random()（其目标始终是完全不可预测），而是调用 seedrandom(seed) 返回的 random 函数：

  • 默认情况下，模拟会选取一个随机的 seed（使用 Node 的 randomBytes() 函数），使得每次运行都使用一个新的伪随机数序列，并探索新的事件序列。 该 seed 以及它的模拟其他参数会被打印到控制台。

  • 但是，使用相同的 seed（以及其它参数）多次运行模拟，应当产生相同的伪随机选择序列，使你能够添加插装代码或断言，从而帮助你将一次“随机”的失败转化为测试套件中的最小测试用例。

问题 2：连接 Web 服务器

为了将你的 Board 类型连接到所提供的 Web 服务器，以及连接到 Didit 自动评分器，你需要实现 commands.ts 中的函数，使其使用 Board 的操作。先从这两个函数开始，它们足以让你玩游戏：

  • look() from commands.ts
  • flip() from commands.ts

至此，你的 look() 和 flip() 可能尚未实现符合规则的正确等待行为，也可能无法处理并发玩家，但它们应当能够处理依次操作的多个客户端。

总体而言，让 commands.ts 中的所有函数保持极其简单。 它们应该仅仅是粘合代码（glue code），最多调用几个你的 Board 操作，而不含任何额外逻辑。 具体来说：

  • 每个函数的方法体最多 3 行，最多由几个简单的函数调用组成，可能使用局部变量，外加一条 return 语句。
  • 它们调用的所有函数都应当已经经过充分测试，无论是通过你的 Board 测试套件还是通过 TypeScript 本身。

如果是这种情况，你就不需要为 commands.ts 编写单独的测试套件。 你现有的针对 Board 的测试就足够了。

如果 commands.ts 中有任何函数比这更复杂——例如，包含 if 或 while 等控制语句，或字符串处理操作——那么你就需要创建 test/commands.test.ts 并为其设计测试套件。 在做这件事之前，停下来！ 先与课程工作人员讨论你的设计，因为这是一个迹象，表明你为 Board 类型选择的操作不够强大。

  • 规格（Spec）。 已给出 look() 和 flip() 的规格，但你可以按需加强它们。
  • 测试（Test）。 保持这些操作极其简单，这样你就不必单独测试它们。
  • 代码（Code）。 尽可能简单地实现 look() 和 flip()。

运行 Web 服务器

要启动服务器，请使用 npm start，它会运行 main.ts 中的 main()。 该代码解析命令行参数，根据这些参数调用 Board 解析函数，并从 server.ts 创建并启动一个 WebServer。 你不需要修改 main.ts 或 server.ts。

要运行 main()，先打开一个终端，可以在 Visual Studio Code 内部，也可以在单独的终端窗口中。 然后使用我们的 3×3 彩虹与独角兽棋盘在 8080 端口启动一个 Web 服务器：

npm start 8080 boards/perfect.txt

请记住，服务器会一直运行，直到你终止它的进程；如果你试图在同一个端口上运行第二个服务器，它会因“地址已被占用”而失败。 如果你在命令行运行服务器，请在该终端中使用 Ctrl-C 来停止它。

一旦你的服务器完成，你就可以在网页浏览器中玩游戏了！

在你的网页浏览器中，访问服务器启动时显示的 URL，它将返回一个与你的服务器使用游戏协议通信的网页。

你可以在多个标签页中打开该 URL，以模拟不同的玩家。每次你打开该页面时，它都会随机生成一个新的玩家 ID 供你的服务器使用。

你也可以通过 IP 地址连接到朋友的服务器，但你可能无法直接在浏览器中将其作为 URL 访问（因为你的浏览器可能要求通过 HTTPS 连接，而此服务器不支持 HTTPS）。作为替代，在你自己的 ps4 代码中找到该网页文件（其名称为 public/index.html），在你的网页浏览器中打开该 HTML 文件，然后通过 IP 地址指定另一台服务器。

问题 3：为并发玩家修改

修改 Board 使其成为异步的，并根据需要更新其它抽象数据类型。

考虑对棋盘返回的 promise 使用 await，以根据规则实现等待一张牌。 请参阅互斥（Mutual Exclusion）中“做出并信守一个 promise”，以了解以下内容的讨论：

  • Promise.withResolvers() 工厂函数，它对于将回调转换为 promise 最为有用
  • Deferred 的规格和实现，它对于存储稍后才解析的 promise 最为有用

在 simulation.ts 中，增大 players 的值以模拟多人“记忆翻牌”游戏。 通过插装你的代码（例如使用 console.log() 语句，或记录不同玩家翻开的牌），你应该能观察到对卡牌的正确控制、当玩家试图翻开第一张牌时的正确等待，以及当玩家进行下一次操作时对匹配卡牌的正确移除。

请注意，如果一名玩家在其最后一次操作中翻开了匹配的牌（在该玩家控制下留下两张正面朝上的牌），而另一名玩家试图将其中一张作为其第一张牌翻开，你的模拟不应终止。

考虑修改你的测试策略，以测试并发玩家操作的不同交错情况。 你可能会发现timeout() 函数有助于强制产生短暂的等待。 非常短的超时（1 毫秒甚至 0 毫秒）会交出足够的控制权，让并发操作运行完成。 避免等待数百毫秒，因为这可能导致你的测试在 Didit 上超时。 不要在你的实现代码中放置 timeout() 调用；这是你的设计存在竞态条件（race condition）的迹象。

检查你的 commands.ts 文件，确保它根据规则正确地使用异步的 Board。 你的命令不应忙等待或挂起。 当一个请求在等待时（例如等待一张牌翻开），其它请求必须被正常处理。

map() 命令与游戏的其它状态无关。 因此，无论卡牌是正面朝上还是背面朝上，或者是否由其他玩家控制，它仍然可以被替换，且其正面/背面状态和控制状态不受该替换的影响。

变换函数 f 是异步的（返回一个 promise），因此它可能以多种方式实现（例如进行数据库查询、访问语言翻译 Web API，甚至询问人类用户替换牌应该是什么）。 这意味着 map() 可能必须等待其对 f 的调用完成。 但是，在 map() 运行期间，它绝不能阻止棋盘上的其它命令与之交错执行（包括同一玩家发出的其它命令，以及其它 map() 命令）。 取决于你如何实现 map()，其它操作可能会看到部分变换后的棋盘（一些卡牌已被替换，而另一些尚未替换），但棋盘对玩家而言必须保持一致性，即：如果棋盘上某两张牌在一次 map() 开始时是匹配的，那么在该 map() 进行期间，它绝不能导致任何玩家观察到这对卡牌不匹配的棋盘状态。

函数 f 必须是 map() 规格中所述的数学函数，但它不必是单射函数（one-to-one function）。

规格说明、测试并实现棋盘抽象数据类型中的支持，使你能够在 commands.ts 中将 map() 函数实现为简单的无需自身测试的粘合代码。

问题 5：棋盘事件

本问题向协议中添加另一个命令 watch()。

该命令不会立即返回。 相反，它会等待，直到棋盘下一次发生变化。 此时，它以棋盘的当前状态作为响应。

变化被定义为：任何卡牌翻为正面朝上或背面朝上、从棋盘上移除，或从某一个字符串变为另一个不同的字符串。

watch() 调用必须等到此类变化发生。 当卡牌状态没有变化时——例如，如果玩家试图翻开一个空格，或者玩家取得或放弃了一张牌的控制权，但它没有翻为正面或背面朝上——挂起的 watch 请求必须继续等待。

当一个 watch(board, player) 请求在等待时，该玩家可以在同一个棋盘上使用其它命令，它们会被正常处理。 例如，一个并发的 look(board, player) 请求绝不能等待。

规格说明、测试并实现棋盘抽象数据类型中的支持，使你能够实现对棋盘变化的监视。 你的棋盘抽象数据类型可能实现仅单次变化的通知，或所有未来变化的通知：

  • 如果客户端仅接收单次变化，它可能是一个异步方法，其 promise 在棋盘变化时兑现。
  • 监听器可能向 Board 提供一个回调函数。 棋盘会在每次变化时回调它们。

首先尝试在 simulation.ts 中使用你棋盘的变化通知，在模拟游戏期间并发地监视棋盘。

然后使用你的变化通知，在 commands.ts 中将 watch() 函数规格说明、测试并实现为简单的无需自身测试的粘合代码。

请注意，由你决定哪些变化是原子的。 例如，watch() 规格并未说明：当一对匹配（或不匹配）的牌被移除（或翻为背面朝上）时，是报告为单次变化还是两次独立的变化。

一旦你将 watch() 添加到你的服务器，就可以将“记忆翻牌”网页用户界面中的开关从“通过轮询更新”切换到“通过监视更新”，你会发现此时 UI 能更快地显示由其它客户端做出的棋盘更新。

评分

你的 ps4 总评成绩将大致按以下方式计算：
约 30% alpha 自动评分（包括在线练习）+ 约 20% alpha 手动评分 + 约 25% beta 自动评分 + 约 25% beta 手动评分（包括代码审查）

从 alpha 到 beta，自动评分的测试用例不会改变，但它们的分值会改变。 为了鼓励增量式开发，alpha 自动评分将主要关注客户端依次操作（按时间分隔）的场景，而非并发场景。 在 beta 阶段，自动评分将考察全方位的并发场景。

alpha 的手动评分只会检查内部文档（AF、RI、测试策略等）以及与并发无关的实现。 beta 的手动评分可能会检查任何部分，包括重新检查那些文档或代码，以及你如何处理代码审查反馈。
