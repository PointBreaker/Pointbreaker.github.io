区间集合

在问题 1—3 中，我们将实现区间集合抽象类型，它是一个由唯一标签构成的可变集合，其中每个标签关联数轴上的一个互不重叠的区间。

例如，我们可以将区间集合 { A = [0,5), B = [10,30), C = [30,35) } 表示为：

在这个例子中，标签是唯一的字符串 "A"、"B" 和 "C"；每个标签关联一个区间，在我们的类型中，它将是 bigint 值的一个区间。 每个区间都是半开（也称为半闭）的，也就是说它包含起点但不包含终点，因此 [0,5) 表示 { x ∈ ℝ | 0 ≤ x < 5 }。

阅读由 src/intervalset.ts 生成的 IntervalSet 的 TypeDoc 文档。

我们的区间集合将支持任意类型的标签。 IntervalSet<Label> 是一个泛型类型，类似于 Array<E> 或 Map<K,V>。 在 Array 的规范中，E 是列表中元素类型的占位符。 在 Map 中，K 和 V 是键和值类型的占位符。 只有在之后，Array 或 Map 的客户端才会通过构造（例如）一个 Array<Clown> 或一个 Map<Car,number> 来为这些占位符选择特定的类型。

在本习题集中，我们将用两种不同的表示（rep）来实现两次 IntervalSet，以练习选择抽象函数和表示不变量以及防止表示暴露。 一个库为某种类型提供多种实现有很多充分的理由，例如具有不同的性能权衡，而我们正是遵循这一模式。

这些实现将放在 src/intervalset-impls.ts 中。

多重区间集合之间的相似度

有了我们的多重区间集合数据类型，你的新创“”创业公司的 MVP 需要一项关键的专有技术——一种衡量多重区间集合之间相似度的方法。 这就是问题 5。

例如，给定 { A = [[0,5),[20,25)], B = [[10,20),[25,30)] } 和 { A = [[20,35)], B = [[10,20)], C = [[0,5)] }：

我们的 similarity 函数将支持由客户端提供的标签相似度定义。 例如，让我们假设一种二值定义：当标签相等时它们完全相似（值为 1），否则完全不同（值为 0）。

由两个集合共同覆盖的区间的区间相似度就是它们标签的相似度。 仅由其中一个集合覆盖、或两个集合都未覆盖的区间，其区间相似度为 0。

多重区间集合之间的相似度将被定义为两个集合所覆盖范围的一个比值，因此采用二值的标签相似度定义时，这两个集合之间的相似度为：

( 5×0 + 5×0 + 10×1 + 5×1 + 5×0 + 5×0 ) ÷ ( 35 - 0 ) = 15 / 35 ≈ 0.42857

（将鼠标悬停或点击单独的项，即可高亮上方图形的对应部分。）

然而，假设客户端改为指定 "A" 和 "C" 的相似度为 0，但 "A" 和 "B" 更接近，相似度为 ½。 使用该定义：

( 5×0 + 5×0 + 10×1 + 5×1 + 5×0.5 + 5×0 ) ÷ ( 35 - 0 ) = 17.5 / 35 = 0.5

similarity 的客户端通过提供一组标签对以及它们介于 0 和 1 之间的数值相似度来定义标签相似度。 所有其他标签对之间的相似度为 1（如果它们相等）或 0（否则）。

阅读由 src/similarity.ts 生成的 similarity 的 TypeDoc 文档。

现在就规划该实现，但有以下要求：你必须再使用一个抽象数据类型，其设计完全由你决定，它要能提高你的 similarity 实现的防错安全性、易于理解和/或可更改性。

bigint 转 number

要将 bigint 转换为 number，请将 Number(..) 作为函数使用，不要带 new 关键字。

similarity 的规范包含一个关于精度的后置条件，因此请考虑在你的实现中是否能够以及何时可以将 bigint 值转换为 number，并在你的测试策略中包含相关的划分。

你来选择这个辅助 ADT 的规范（即操作），就像你会选择某个辅助函数的规范一样。

将你的新 ADT 作为一个类在 src/similarity.ts 底部规定其规范；然后在 test/similarity.test.ts 中测试它；并实现它。

5.3 实现 similarity

你的 similarity 代码应当仅依赖于 MultiIntervalSet 和其他 ADT 的规范，而不是任何特定实现的细节。

它应当充分利用你所设计的新辅助 ADT，同样仅依赖于它的规范而不是它的实现。

除此之外，similarity 的实现完全由你决定。

通过运行 npm test 来运行你所有的测试。

完成之前

  • 确保你已经为所有类型和操作编写了已记录的规范，格式为正确格式化的 TypeDoc 注释。

  • 确保你已经为所有实现编写了已记录的抽象函数和表示不变量，格式为靠近字段声明处的一条注释。

    此外，还要编写该类型如何防止 rep 暴露的文档。 请参阅编写 AF、RI 与 SRE 的文档。

    确保所有类型都使用 checkRep 来检查 rep 不变量，并实现 toString，给出抽象值的一个有用的人类可读表示。

  • 确保你为每种类型都有一套彻底的、有原则的测试套件。

提交

确保你将作业 commit 并 push 到你在 github.mit.edu 上的仓库。 我们将使用截止日期当天晚上 9:00 时你在 github.mit.edu 上仓库的状态。 当你 git push 时，持续构建系统会尝试编译你的代码并运行公开测试（这些测试只是自动评分测试的一个子集）。 你可以随时在 didit.mit.edu/6.102/sp26 查看你的构建结果。

评分

你的 ps2 总评成绩将大致按以下方式计算：
~30% alpha 自动评分（含在线练习）+ ~20% alpha 人工评分 + ~25% beta 自动评分 + ~25% beta 人工评分（含代码审查）

从 alpha 到 beta，自动评分测试用例不会改变，但它们的分值会改变。 测试用例在 alpha 上可能值零分，而在 beta 上值非零分，或反之亦然。

对 alpha 的人工评分可能会检查你解答的任何部分，包括规范、测试套件、实现以及你的 Git 提交历史。 对 beta 的人工评分可能会检查任何部分，以及你如何处理来自 alpha 的人工评分和代码审查反馈。
