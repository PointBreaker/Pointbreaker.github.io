What you can and can’t change

  • 不要更改任何提供的文件或文件夹名称。
  • 不要更改函数签名：lerp.ts 中的函数必须使用我们提供的函数签名。
  • 不要更改函数签名和规格说明：colors.ts 中导出的函数必须使用我们提供的函数签名和规格说明。
  • 不要削弱规格说明：curves.ts 中导出的函数必须具有比我们提供的更强的规格说明。
  • 不要导出任何新内容：在 lerp.ts、colors.ts 和 curves.ts 中，只能导出所提供的函数。
  • 不要包含非法的测试用例：你编写的测试必须尊重你所测试的规格说明。 针对我们提供的规格说明的测试将针对这些规格说明的其他实现运行。

然而，除了这些要求之外，你可以自由地添加新函数和新类。

规格说明

在开始之前，仔细阅读规格说明，并记录你观察到的内容。 你可以直接在 VS Code 中阅读 TypeScript 源文件，也可以阅读从源文件生成的 所有函数的 TypeDoc 文档。

请记住关于规格说明的以下事实：

  • 某些规格说明具有前置条件。 回顾规格说明阅读材料， 当前置条件被客户端违反时，函数的行为是完全未指定的。

  • 某些规格说明具有欠定的后置条件。 回顾欠定的后置条件允许一定范围的行为。 当你实现这样的函数时，你的函数在该范围内的确切行为由你决定。 当你为该函数编写测试用例时，测试必须允许实现行为在该范围内的全部变化，因为否则你的测试用例就不是如上所要求的规格说明的合法客户端。

  • 导出的函数可以在任何地方使用。 这些函数是独立的模块，可能会被图形系统的各个部分调用，而不一定是你编写的代码。 函数实现必须能够处理所有满足前置条件的输入，即使它们不会在你使用这些函数时出现。 函数可以返回任何满足其后置条件的输出，即使在你想要调用它的上下文中这似乎没有用。

在本习题集中，我们使用浮点数进行工作，但指定计算的数值精度以及编写实现指定精度的算法都不在 6.102 的范围内。 因此，在所有规格说明中：

  • 整数 number 值被认为是安全的，介于 MIN_SAFE_INTEGER 和 MAX_SAFE_INTEGER 之间（当然它们可能受到进一步约束）。

  • 当非整数 number 的计算受到约束时，允许最多 tolerance = 0.001 的误差。 对于我们要求你指定或实现的任何函数，你不得使用任何其他浮点数等价性的定义。 如果你被要求加强或削弱某个规格说明，你不得通过更改浮点误差的容差来实现。 你可以使用 utils.ts 中提供的 assertApproxEqual 函数来编写与此规格说明兼容的测试。

  • 我们做出这些假设的目的是简化而非复杂化本习题集。 如果你认为由于数值精度的原因，正确测试或实现某个所需的规格说明很困难，或者这些假设使其变得更加困难，请提出问题。

加强 bezierInterpolate 和 bezierPath 的规格说明

要加强 bezierInterpolate 的规格说明……

  • 考虑削弱其对 renameMe 的静态检查前置条件（并重命名该参数）
  • 避免削弱其提供的特殊情况后置条件

要加强 bezierPath 的规格说明……

  • 考虑通过使用联合类型来削弱其对 renameMe 的静态检查前置条件（并重命名该参数）
  • 然后考虑当该参数提供 undefined 时你的后置条件，因为你不能添加特殊情况

测试

你应该对每个函数的输入和输出进行划分，在测试策略注释中写下你的划分，并选择测试用例来覆盖这些划分。

函数的规格说明和实现位于 src/ 下的文件中，而相应的 Mocha 测试位于 test/ 下的文件中。 将实现代码与测试代码分离是开发项目中的常见实践。 它使实现代码更容易理解、不被测试干扰，并且更容易打包发布。

函数的测试套件中可能已经包含作为示例提供的测试。 建议你阅读这些示例测试，然后丢弃它们，编写你自己的测试。

关于测试的一些建议：

  • 你的测试用例应使用划分方法来选择。 这种方法在关于测试的阅读材料中有解释。

  • 在每个测试套件顶部添加一个描述你测试策略的注释。 示例展示在关于测试的阅读材料中。

  • 你的测试用例应该小而有针对性。 不要对每个测试使用大量数据集。 相反，要仔细选择输入，以测试你想要测试的划分。

  • 你的测试应该发现错误。 我们将部分通过针对有错误的实现运行你的测试用例，并查看你的测试是否捕获了这些错误，来为你的测试用例评分。 因此，请考虑实现可能无意中不符合规格说明的方式，并选择能够暴露这些错误的测试。

  • 你的测试必须是规格说明的合法客户端。 我们还将针对仍然严格满足规格说明的合法变体实现运行你的测试用例，你的测试用例不应该对这些良好的实现提出异议。 这意味着你的测试用例不能做出仅对你自己的实现成立的额外假设。

  • 将每个测试用例放在它自己的 it() 函数中。 这将比单个大测试函数有用得多，因为它能精确定位实现中的问题。

  • 运行测试覆盖率。 当需要进行白盒测试时，使用 npm run coverage 运行你的测试套件。

  • 从测试代码中调用辅助函数时要小心。 你在（例如）test/colors.test.ts 中的测试用例不得调用你在 src/colors.ts 中定义的新辅助函数。 记住，你的测试将针对 colors.ts 函数的助教实现运行，而你版本的该文件中的代码将不可用。 将仅由测试代码需要的辅助函数放入 test/；将同时由实现和测试代码需要的辅助函数放入 src/utils.ts（在下方部分中讨论）。

  • 再次强调，保持你的测试小而精。 不要使用不合理的资源量（例如长度为 MAX_SAFE_INTEGER 的数组或字符串）。 我们不期望你的测试套件捕获与资源耗尽相关的错误；当资源耗尽时，每个程序都会失败。

  • 使用 strictEqual 和 deepStrictEqual。 例如， assert.equal(1, '1') 通过，因为它使用了危险的 == 比较。 不要使用它，对于不可变的内置类型，始终使用 strictEqual。

    然而，assert.strictEqual([1], [1]) 失败，因为它检查两个参数是否引用同一个数组实例。 要比较数据结构，请使用 deepStrictEqual，如所提供的示例测试中所示。

  • 使用 assertApproxEqual。 如上方部分中所讨论的，当允许误差时，使用 assertApproxEqual 来比较浮点数。

  • 频繁地 Add/commit/push。 每当你完成一项有意义的工作时——例如，在编写测试策略注释之后；在选择一些测试输入之后；在编写 Mocha 测试并看到它们通过之后——你应该用 git add/commit/push 你的工作。

Implementation

实现每个函数，并修改你的实现和测试，直到你所有的测试都通过。

关于实现的一些建议：

  • 小型辅助函数。 如果你想为单个模块的实现编写小型辅助函数，那么你可以将它们与其他函数一起放在相关的实现文件中。 不要导出 lerp.ts、colors.ts 或 curves.ts 中的辅助函数，因为那样会以你不被允许的方式更改这些模块的规格说明。 这意味着你不能为这些辅助函数编写测试，这就是为什么它们必须很小。 你依赖那些模块公共函数的测试套件来实现覆盖并发现这些小型辅助函数中的错误。

  • 较大的辅助函数。 如果你想编写任何复杂程度的辅助函数，那么你应该将它们放在 utils.ts 文件中，并在 utils.test.ts 中为它们编写 Mocha 测试。 这也是放置同时由实现代码和测试代码需要的辅助函数的地方。 在 utils.ts 中，如果你导出了一个名为 myHelper 的函数，那么在 colors.ts 和 utils.test.ts 中你可以将该函数作为 utils.myHelper(..) 调用。

    不要要求我们告诉你某个辅助函数是小还是大。 如果你不确定，那么这个函数就足够大，应该拥有 TypeDoc 文档和自己的测试。 将辅助函数放在 utils.ts 中，给它一个清晰的规格说明，并在 utils.test.ts 中测试它。

  • 不要调用测试代码。 如果你需要从 src/ 中的实现代码调用它，不要把辅助函数放在 test/ 文件夹中。 测试代码应该与实现完全可分离，以便实现可以单独打包部署。 当我们针对你的实现运行助教测试时，我们也会分离你的测试代码。 将实现代码需要的辅助函数，或同时由测试和实现代码需要的辅助函数，放入 src/utils.ts 中。

  • 消除警告。 修改你的代码以解决 VS Code 中显示的所有黄色下划线警告。 这些警告应包括 TypeScript 编译器警告和 ESLint 警告，因为本习题集启用了 ESLint。

  • 检查测试覆盖率。 进行白盒测试并修改你的测试，直到你获得令人满意的代码覆盖率。

  • 审查你自己的代码。 批判性地阅读你的代码，着眼于使其尽可能做到 SFB、ETU 和 RFC。

  • 频繁测试。 每当你对代码进行更改时，重新运行你的测试。

  • 使用 Mocha 的 -f 参数调试单个测试。 要运行整个测试套件中的一个测试用例子集，请使用 npm test -- -f 'pattern'。 只有其 it() 描述包含字符串 pattern 的测试才会被运行。 例如，在所提供的起始代码中，命令 npm test -- -f 'lerpColor covers...' 仅运行 lerpColor 的示例测试。 这对调试很有用，因为它允许你一次只关注一个失败的测试。

  • 使用 console.log 或 util.inspect 进行打印调试。 许多类型，包括 Map 和 Set，都有非常无益的 toString() 方法。 这意味着如果你尝试使用（例如）console.log("gradient is " + gradientMap) 进行调试，你可能会看到类似“gradient is [object Map]”的无益内容。 有两种方法可以改善这一点：

    • 使用多个参数调用 console.log()，而不是依赖 + 和 toString()：

      console.log("gradient is", gradientMap);

      这意味着 console.log() 负责显示 gradientMap 对象，它在展示其内部内容方面做得更好。

    • 使用 util.inspect() 将对象转换为字符串：

      import util from 'node:util';
console.log("gradient is " + util.inspect(gradientMap));

  • 频繁地 Add/commit/push。 每当你完成一项有意义的工作时——例如，在编写函数体并看到测试通过之后，或在发现一个错误、为其添加回归测试并修复它之后——你应该用 git add/commit/push 你的工作。

Learning about colors and curves, and a Python notebook

RGB 颜色将颜色表示为红、绿、蓝光的混合。 RGB 对应于你屏幕的物理红、绿、蓝子像素，你应该从 6.101 的图像处理中对 RGB 颜色有一些经验。

HSL 颜色将颜色表示为色相（想想红色 vs. 橙色 vs. 等等）、饱和度（想想从灰色到灰暗到鲜艳）和明度（想想从黑色到彩色到白色）。 它最好被可视化为一个颜色圆柱，底部为黑色，顶部为黑色，核心为灰色，纯颜色位于中途的边缘周围。 请参阅 Wikipedia 页面上的图表。 （我们不使用 HSV，它也在同一页面上解释。）

如果你使用过允许通过定义控制点来绘制平滑路径的图形编辑器，那么贝塞尔曲线可能很熟悉。 这些路径通常是复合贝塞尔曲线，其中多条曲线在特定约束下连接在一起。 在本习题集中我们不考虑复合曲线，所以我们的曲线行为不完全相同。 相反，关键的直观理解在 Wikipedia 页面上的构造贝塞尔曲线部分，配有有用的动画。

  • 曲线的阶对应于控制点的数量：二次曲线有 3 个控制点，三次有 4 个，而n 阶曲线有 n+1 个控制点 P0 到 Pn。
  • 注意曲线如何总是以第一个和最后一个控制点作为起点和终点，但它不一定要经过任何其他控制点。

Designing your toolbox of animation functions

如果你识别出两个示例都必须执行的计算，那就是将其抽象为工具箱函数的自然候选。

然而，这两个示例动画相当不同。 所以你可能会改为识别一个你预期在创建类似动画时会频繁涉及的计算，并为其构建一个工具箱函数——即使你只用该函数来实现两个必需示例中的一个。

你可能会发现 colors.ts（你不能更改）和 curves.ts（你只能加强）中所需的规格说明对于构建这些动画并不总是完全合适。 如何继续由你决定。 保持你的代码 DRY 且你的规格说明清晰。

保持你的工具箱精简，最多三个新函数。 你希望 handoutExample­One 和 -Two 简短，但它们可能仍然有工作要做，而且它们可能直接使用的你已实现的其他函数。

如果你在 utils.ts 中有一个对工具箱有用的现有函数，将其导入 toolbox.ts 然后从中重新导出，使其成为该模块规格说明的一部分。 不要复制测试套件，将其保留在 utils.test.ts 中。

你的规格说明应该没有错误、易于理解，并且为变化做好准备。 尽可能使用静态类型。

当你的规格说明具有无法静态检查的前置条件时，你的实现应该检查前置条件，如果前置条件不满足则快速失败。

评分

你的 ps1 总评成绩将大致按以下方式计算：
~30% alpha 自动评分（包括在线练习）+ ~20% alpha 手动评分 + ~25% beta 自动评分 + ~25% beta 手动评分（包括代码审查）

从 alpha 到 beta，自动评分测试用例不会改变，但它们的值分会变化。 为了鼓励测试优先编程，alpha 自动评分会将更多权重放在你的测试上，较少权重放在你的实现上。 在 beta 上，自动评分将同时寻找良好的测试和良好的实现。 测试用例在 alpha 上可能值零分，而在 beta 上值非零分，或者反之。

alpha 的手动评分可能会检查你解答的任何部分，包括规格说明、我们要求的解释、测试套件、实现以及你的 Git 提交历史。 beta 的手动评分可能会检查任何部分，以及你如何处理来自 alpha 的手动评分和代码审查反馈。
