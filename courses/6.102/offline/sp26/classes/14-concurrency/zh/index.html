并发

并发 意味着多个计算同时发生。并发在现代编程中无处不在，无论我们是否喜欢：

  • 网络中的多台计算机
  • 一台计算机上运行多个应用程序
  • 一台计算机中的多个处理器（如今，通常是单芯片上的多个处理器核心）

事实上，并发在现代编程中不可或缺：

  • 网站必须处理多个同时访问的用户。
  • 移动应用需要在服务器上进行部分处理（"云端"）。
  • 图形用户界面几乎总是需要不打断用户的后台工作。例如，Visual Studio Code 在你编辑 TypeScript 代码的同时编译它。

能够进行并发编程在未来仍将非常重要。处理器时钟频率不再增长。相反，每一代新芯片都提供更多的核心。因此，在未来，为了让计算运行得更快，我们必须将计算拆分为并发片段。

并发编程的两种模型

并发编程有两种常见模型：共享内存 和 消息传递。

共享内存。在并发共享内存模型中，并发模块通过读写内存中的共享对象进行交互。右图中，A 和 B 是并发模块，可以访问相同的共享内存空间。蓝色对象是 A 或 B 的私有对象（只有一个模块可以访问），而橙色对象由 A 和 B 共享（两个模块都持有对它的引用）。

共享内存模型的示例：

  • A 和 B 可以是同一台计算机中的两个处理器（或处理器核心），共享相同的物理内存。

  • A 和 B 可以是同一台计算机上运行的两个程序，共享一个可以读写文件的公共文件系统。

  • A 和 B 可以是同一程序中的两个线程（下面我们会解释什么是线程），共享相同的对象。

消息传递。在消息传递模型中，并发模块通过通信通道相互发送消息。模块发出消息，每个模块的传入消息排队等待处理。示例包括：

  • A 和 B 可以是网络中的两台计算机，通过网络连接进行通信。

  • A 和 B 可以是一个 Web 浏览器和一个 Web 服务器 — A 打开与 B 的连接并请求网页，B 将网页数据发送回 A。

  • A 和 B 可以是一个即时通讯客户端和服务器。

  • A 和 B 可以是同一台计算机上运行的程序，其输入和输出通过 管道 连接，比如在命令提示符中输入 ls | grep。

进程、线程、时间片

消息传递和共享内存模型是关于并发模块如何通信的。并发模块本身有两种不同的类型：进程和线程。

进程。进程是一个正在运行的程序的实例，它与同一机器上的其他进程是 隔离的。特别是，它拥有自己的私有内存空间。

抽象地说，你可以把进程看作一台 虚拟计算机。它让程序感觉好像自己拥有整台机器 — 就像一台全新的计算机，拥有自己的内存，只用来运行那个程序。

就像网络上连接的计算机一样，进程之间通常不共享内存。一个进程根本无法访问另一个进程的内存或对象。在大多数操作系统上，进程间共享内存是 可能的，但这需要特殊的努力。相比之下，新进程自动准备好进行消息传递，因为它创建时带有标准输入和输出流。

每当你在计算机上启动一个程序时，也会创建一个新进程来容纳正在运行的程序。

线程。线程是正在运行的程序中的一个控制点。可以把它想象成程序中正在被执行的位置，加上导致该位置的函数调用栈（这样线程在遇到 return 语句时可以沿着栈返回）。

正如进程代表一台虚拟计算机，线程代表一个 虚拟处理器。创建一个新线程模拟在进程所代表的虚拟计算机内部创建一个全新的处理器。这个新的虚拟处理器运行相同的程序，并与进程中的其他线程共享相同的内存。因此，我们可以说进程包含线程。

线程自动准备好进行共享内存访问，因为线程共享进程中的所有内存。要获得私属于单个线程的"线程本地"内存，则需要特殊的努力。

每当你运行一个 TypeScript/JavaScript 程序时，程序以一个线程开始，该线程以执行你正在运行的文件作为其第一步。

时间片。当计算机中只有一两个处理器时，如何拥有许多并发线程？当线程数量超过处理器数量时，并发通过 时间片 来模拟，即处理器在线程之间切换。右图展示了三个线程 T1、T2 和 T3 如何在一台只有两个实际处理器的机器上进行时间片轮转。在图中，时间向下推进，因此起初，处理器 P1 运行线程 T1，处理器 P2 运行线程 T2，然后处理器 P2 切换到运行线程 T3。线程 T2 只是暂停，直到它在同一处理器或另一个处理器上获得下一个时间片。图的最右部分展示了从每个线程的视角看是什么样子。有时线程在处理器上主动运行，有时它暂停等待下一次在某个处理器上运行的机会。注意，线程最多只会在一个处理器上运行；让线程同时在多个处理器上运行是没有意义的。

当线程在两个不同的处理器上同时运行时，称它们 并行 运行，从而在软件中产生 并行性。如果线程改为共享同一处理器，与彼此进行时间片轮转，则它们是并行的，但不是并行的。

不过，即使没有并行性，并发也可能很棘手。在大多数系统上，时间片以不可预测和非确定性的方式发生，这意味着线程可能在任何时候被暂停或恢复。

Python 中的线程

让我们先看看线程在 Python 中是如何工作的。Python 的线程 API 类似于其他面向对象语言（包括 Java）提供的 API。

在 Python 中，你通过创建 Thread 的实例并告诉它 start() 来启动一个新线程。你通过向 Thread 构造函数传递一个函数来为新线程提供要运行的代码。新线程要做的第一件事就是调用这个函数。例如：

from threading import Thread

def hello():
  print("Hello from a thread!")

t = Thread(target=hello)  # 创建一个准备调用 hello() 的线程
t.start()                 # 在新线程中实际调用 hello()

TypeScript 中的 Worker

TypeScript 没有用户可访问的线程，但它有一个称为 Worker 的抽象。有时被称为 Web Workers，因为该 API 最初出现在 Web 浏览器中，该 API 也被 Node 支持。

通过指定 Worker 应执行的 JavaScript 文件作为其起始点来创建它。例如，假设我们已经有了通过编译以下 TypeScript 代码生成的 hello-world.js 文件：

// hello-world.ts（编译为 hello-world.js）
console.log('Hello from a worker!')

然后我们可以这样为它启动一个 worker：

let worker: Worker = new Worker('./hello-world.js');
// ...

这段代码将立即开始为 Worker 创建新环境，开始执行 hello-world.js，并打印问候消息。它还会继续并发执行启动 worker 的代码。

注意，new Worker 需要一个 JavaScript 文件（.js）。如果 worker 代码是用 TypeScript 编写的，则必须先将其编译为 JavaScript，然后才能用它启动 worker。

Mozilla 和 Node 的 worker 文档都将它们称为 线程，但它们的行为更像独立的 进程：

  • 像线程一样，worker 可以使用 SharedArrayBuffer 来共享 二进制数据，从而访问共享内存。

  • 但像进程一样，每个新的 Worker 在一个全新的全局环境中执行其 JavaScript 文件。当它导入一个模块时，会加载该模块的私有副本；它不与其他 worker 共享模块。Worker 不能共享变量或普通对象的实例。

  • 相反，由于其共享内存能力非常有限，worker 通常通过消息传递进行通信。在创建 Worker 的代码和在该 Worker 内部运行的代码之间会自动建立一个双向消息传递通信通道。

总体而言，我们可以将 Worker 视为一个轻量级进程。

共享内存示例

让我们看一个共享内存系统的示例。这个示例的目的是说明并发编程很难，因为它可能有微妙的 bug。

在这个示例中，我们将文件系统用作共享内存。

想象一家银行有使用共享内存模型的取款机：一个公共文件系统。银行账户的信息存储在一个文件中，所有取款机都可以读写该文件来更新账户。

为了说明可能出错的地方，让我们将银行简化为单个账户，其美元余额以文本形式存储在名为 account 的文件中：

import fs from 'node:fs';

// 假设所有取款机共享一个银行账户，存储在名为 `account` 的文件中
export function readBalance(): number {
  const fileData = fs.readFileSync('account.txt').toString();
  return parseInt(fileData);
}

export function writeBalance(balance: number): void {
  fs.writeFileSync('account.txt', balance.toString());
}

两个操作 deposit 和 withdraw 更新该文件，简单地增加或减少一美元：

def deposit(): void {
  let balance = readBalance();
  balance = balance + 1;
  writeBalance(balance);
}

def withdraw(): void {
  let balance = readBalance();
  balance = balance - 1;
  writeBalance(balance);
}

客户使用取款机进行如下交易：

deposit(); // 存入一美元
withdraw(); // 取出来

每笔交易只是一美元的存款后跟一美元的取款，因此应该保持账户余额不变。在一天中，我们网络中的每台取款机都在处理一系列存款/取款交易：

// 在 cash-machine.ts 中

// 每台 ATM 执行大量交易，
// 修改余额，但之后保持余额不变
for (let txn = 0; txn < TRANSACTIONS_PER_MACHINE; ++txn) {
    deposit(); // 存入一美元
    withdraw(); // 取出来
}

如果我们在一天开始时账户中有 200 美元，那么在一天结束时，无论有多少台取款机在运行，或者我们处理了多少笔交易，我们都应该期望账户余额保持 200 美元不变：

// 以 200 的余额开始
writeBalance(200);

for (let machine = 0; machine < NUMBER_OF_CASH_MACHINES; ++machine) {
    new Worker('./cash-machine.js'); // 运行上面的 cash-machine 代码
}

但如果我们运行这段代码，我们会经常发现一天结束时的余额 不是 200 美元。如果多个 worker 同时运行 — 比如在同一台计算机的不同处理器上 — 那么 balance 在一天结束时可能不是 200 美元。为什么？

交错执行

以下是一种可能发生的情况。假设两个取款机 worker A 和 B 同时在进行存款操作。以下是 deposit() 步骤如何分解为低级指令：

readBalance() 返回 200
加 1
writeBalance(201)

当 A 和 B 并发运行时，这些指令可以相互 交错执行，这意味着实际的执行序列可以任意穿插 A 的操作和 B 的操作。（如果 A 和 B 在不同的处理器上运行，某些操作很可能是同时或重叠的，但现在我们只关注交错执行。）以下是一种可能的交错执行：

A B
A readBalance() 返回 200
A 加 1
A writeBalance(201)
B readBalance() 返回 201
B 加 1
B writeBalance(202)

这种交错执行没问题 — 我们最终得到余额 202，所以 A 和 B 都成功存入了一美元。但如果交错执行看起来像这样会怎样：

A B
A readBalance() 返回 200
B readBalance() 返回 200
A 加 1
B 加 1
A writeBalance(201)
B writeBalance(201)

余额现在是 201 — A 的一美元丢失了！A 和 B 同时读取了余额，计算了各自的最终余额，然后竞相存储新的余额 — 没有考虑到对方的存款。

竞态条件

这是竞态条件的一个示例。竞态条件 意味着程序的正确性（其规范的满足和不变量的保持）取决于并发计算 A 和 B 中事件的相对时间。当这种情况发生时，我们说"A 在与 B 竞争"。

某些事件的交错执行可能是可以的，因为它们与单个非并发进程产生的一致，但其他交错执行会产生错误的答案 — 违反规范或不变量。

消息传递示例

现在让我们看看银行账户示例的消息传递方法。

现在不仅每台取款机是一个模块，每个账户也是一个模块。模块通过相互发送消息进行交互。传入的请求被放入队列中逐一处理（例如，图中显示了为账户 1 排队的三个待处理请求）。发送方在等待请求答案时不会停止工作。它处理自己队列中的更多请求。对其请求的回复最终以另一条消息的形式返回。

不幸的是，消息传递并不能消除竞态条件的可能性。假设每个账户支持 get-balance 和 withdraw 操作，并有对应的消息。两个用户在取款机 A 和 B 上，都试图从同一账户取出一美元。他们先检查余额，以确保永远不会提取超过账户持有的金额，因为透支会触发大额银行罚款：

send get-balance message, and store the reply in local variable bal
if bal >= 1 then send withdraw-1-dollar message

问题仍然是交错执行，但这次是发送给银行账户的 消息 的交错执行，而不是 A 和 B 执行的 指令 的交错执行。如果账户中起始只有一美元，那么什么样的消息交错执行会欺骗 A 和 B，让他们认为都可以取出一美元，从而透支账户？

并发难以测试和调试

如果我们还没有说服你并发是棘手的，那么这是最糟糕的部分。使用测试发现竞态条件非常困难。即使测试发现了 bug，也可能很难将其定位到导致它的程序部分。

并发 bug 表现出非常差的可重复性。很难让它们以相同的方式发生两次。指令或消息的交错执行取决于受环境强烈影响的事件的相对时间。延迟可能由其他正在运行的程序、其他网络流量、操作系统调度决策、处理器时钟速度的变化等引起 — 这些都是程序员几乎无法控制的事情。每次你运行包含竞态条件的程序时，你可能会得到不同的行为。

这类 bug 是 heisenbug，它们是非确定性的且难以重现，相比之下，bohrbug 每次你查看时都会重复出现。顺序编程中的几乎所有 bug 都是 bohrbug。

当你试图用 console.log 或调试器查看 heisenbug 时，它甚至可能消失！原因是打印和调试比其他操作慢得多（通常慢 100-1000 倍），这极大地改变了操作的时间安排和交错执行。因此，你可能很容易自欺欺人地认为仅仅通过插入打印语句就修复了并发 bug。但它只是被掩盖了，并没有真正修复。程序其他地方的时间变化可能突然使 bug 再次出现。

在 TypeScript 银行账户示例中，使用 worker 读写共享文件，用打印语句隐藏并发 bug 更难，因为文件访问与打印相比相对较慢。但 heisenbug 现象仍然存在，如果你在断点处停止其中一台取款机并尝试用调试器单步执行它，另一台取款机将能够不受干扰地完成运行，问题似乎就消失了。

并发很难做对。本阅读的部分目的是让你稍微感到害怕。在接下来的几篇阅读中，我们将看到设计并发程序的原则性方法，使它们对这类 bug 更安全。

总结

  • 并发：多个计算同时运行
  • 共享内存和消息传递范式
  • 进程和线程
    • 进程就像一台虚拟计算机；线程就像该虚拟计算机中的虚拟处理器
    • TypeScript 的 Worker 就像一个轻量级进程。
    • 时间片允许处理器在多个线程之间切换
  • 竞态条件
    • 当结果的正确性（后置条件和不变量）取决于事件的相对时间时

这些概念与我们优秀软件的三个关键属性之间的联系主要是负面的。并发是必要的，但它会导致严重的正确性问题。我们将在接下来的几篇阅读中致力于解决这些问题。

  • 免受 bug 侵害。 并发 bug 是最难发现和修复的 bug 之一，需要仔细的设计来避免。

  • 易于理解。 预测并发代码可能如何与其他并发代码交错执行，对程序员来说非常困难。最好设计你的代码，使程序员根本不需要考虑交错执行。

  • 适应变化。 选择正确的并发设计 — 例如哪些数据在共享内存中，或者消息传递协议中的消息是什么 — 不仅会现在防止 bug，还会影响未来适应不同变化的难易程度。
