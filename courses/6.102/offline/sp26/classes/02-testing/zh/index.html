验证

测试是一个更通用的过程的例子，该过程称为验证。 验证的目的是发现程序中的问题，从而增强你对程序正确性的信心。 验证包括：

  • 对程序进行形式化推理，通常称为校验。 校验构建一个形式化证明来证明程序是正确的。 手动进行校验很繁琐，而自动化工具支持仍然是一个活跃的研究领域。 尽管如此，程序中一些小的、关键的部分可能被形式化校验，例如操作系统中的调度器，或虚拟机中的字节码解释器，或操作系统中的文件系统。
  • 代码审查。 让别人仔细阅读你的代码并对其进行非正式推理，可以是发现 bug 的好方法。 这很像让别人校对你写的文章。 我们将在另一篇阅读中讨论代码审查。
  • 测试。在精心选择的输入上运行程序并检查结果。

为什么软件测试很难

以下是一些在软件领域不幸效果不佳的方法。

穷举测试是不可行的。可能的测试用例空间通常太大，无法穷尽覆盖。想象一下穷举测试一个 32 位浮点乘法运算 a*b。有 264 个测试用例！

随意测试（"试试看能不能行"）不太可能发现 bug，除非程序 bug 太多以至于随机选择的输入更可能失败而不是成功。 它也不能增强我们对程序正确性的信心。

随机或统计测试在发现其他类型工程缺陷方面比发现软件 bug 更有效。其他工程学科可以测试小的随机样本（例如，生产的 1% 的硬盘），并推断整个生产批次的缺陷率。物理系统可以使用许多技巧来加速时间，比如在 24 小时内开关冰箱 1000 次而不是 10 年。这些技巧给出了已知的故障率（例如，硬盘的平均寿命），但它们假设在缺陷空间中具有连续性或均匀性。这对物理制品来说是真的。

但对软件来说这不是真的。软件行为在可能输入空间上是离散且不连续变化的。系统可能在很宽的输入范围内看起来工作正常，然后在某个边界点突然失败。著名的 Pentium 除法 bug影响了大约 90 亿次除法中的 1 次。栈溢出、内存不足错误和数值溢出 bug 往往突然发生，且总是以同样的方式发生，没有概率变化。这与物理系统不同，在物理系统中，通常有可见的证据表明系统正在接近故障点（例如，桥梁中的裂缝），或者故障在故障点附近概率分布（因此即使在到达该点之前，统计测试也会观察到一些故障）。

因此，测试用例应该谨慎且系统地选择。 系统化测试技术是本阅读的主要关注点。 请注意，随机测试确实被用作软件工程的工具（特别是为了增强对常见情况下行为将可靠或足够高效的信心，而不仅仅是为了发现 bug），但最好将其与系统化测试结合使用。

测试优先编程

在我们深入之前，我们需要定义一些术语：

  • 模块是软件系统的一部分，可以独立于系统的其余部分进行设计、实现、测试和推理。 在本阅读中，我们将重点关注作为函数的模块。 在未来的阅读中，我们将扩大视野，考虑更大的模块，比如具有多个交互方法的类。

  • 规约（或 spec）描述模块的行为。 对于函数，规约给出参数类型及其任何额外约束（例如，sqrt 的参数必须是非负的）。 它还给出返回值的类型以及返回值与输入之间的关系。 在 TypeScript 代码中，规约由函数签名和描述其功能的注释组成。

  • 模块有一个实现来提供其行为，以及客户端来使用该模块。 对于函数，实现是函数体，客户端是调用该函数的其他代码。 模块的规约同时约束客户端和实现。 我们将在接下来的几节课中更多地讨论规约、实现和客户端。

  • 测试用例是一个特定的输入选择，以及规约所要求的预期输出行为。

  • 测试套件是一组针对模块的测试用例。

你已经在问题集 0 中开始使用这些概念了。 你得到了一些 TypeScript 函数的规约，并被要求为每个函数编写实现。 你还得到了每个函数的测试套件，可以运行它们来查看你的实现是否遵守规约。

事实证明，这是从头设计程序时应该遵循的好模式。 在测试优先编程中，你在编写任何代码之前就编写规约和测试。 单个函数的开发按以下顺序进行：

  1. 规约：为函数编写规约。
  2. 测试：编写测试来验证规约。
  3. 实现：编写实现。

一旦你的实现通过了你编写的测试，你就完成了。

测试优先编程最大的好处是免受 bug 侵害。 不要把测试留到开发结束时，那时你有一大堆未经验证的代码。 把测试留到最后只会让调试时间更长、更痛苦，因为 bug 可能在你代码的任何地方。 在开发过程中测试你的代码要愉快得多。

系统化测试

我们想要系统化地测试，而不是穷举地、随意地或随机地测试。 系统化测试意味着我们以有原则的方式选择测试用例，目标是设计一个具有三个理想属性的测试套件：

  • 正确。 正确的测试套件是规约的合法客户端，它接受规约的所有合法实现而不抱怨。 这给了我们自由，可以在不一定要更改测试套件的情况下更改模块的内部实现方式。 我们将在即将发布的阅读中更详细地讨论合法在规约方面的含义。

  • 全面。 全面的测试套件能够发现实现中程序员可能犯的错误导致的实际 bug。

  • 小巧。 小巧的测试套件，测试用例少，一开始编写更快，如果规约演变也更容易更新。 小巧的测试套件运行也更快。 如果你的测试套件小巧且快速，你就能更频繁地运行测试。

按照这些标准，穷举测试是全面的但大得不可行。 随意测试往往小巧但不全面。 随机化测试只能以大规模为代价来实现全面性。

设计一个既全面又小巧的测试套件需要正确的态度。 通常当你编码时，你的目标是让程序工作。 但作为测试套件设计者，你想要让它失败。 这是一个微妙但重要的区别。 一个好的测试人员会故意在程序可能脆弱的所有地方戳一戳，以便消除这些漏洞。

需要采用测试态度是测试优先编程的另一个论据。 人们太容易把你已经写好的代码当作珍贵的东西，一个脆弱的蛋壳，只是轻轻地测试一下看看它是否工作。 但对于全面的测试，你必须毫不留情。 测试优先编程允许你在编写任何代码之前就戴上测试帽，采用那种残酷的视角。

通过划分选择测试用例

创建一个好的测试套件是一个具有挑战性且有趣的设计问题。 我们想要选择一组测试用例，小到易于编写和维护、运行快速，又全面到足以发现程序中的 bug。

为此，我们将程序的输入空间划分为子域，每个子域由一组输入组成。 （子域这个名称来源于它是域（数学函数的输入空间）的子集这一事实。） 合在一起，子域构成一个划分。划分是一组非空的不相交集合，完全覆盖输入空间，使得每个输入恰好属于一个子域（子域之间没有重叠）。 然后，我们从每个子域中选择一个测试用例，这就是我们的测试套件。

子域背后的思想是将输入空间分成相似输入的集合，在这些输入上程序有相似的行为，这样我们只需要测试每个集合的一个代表。 这种方法通过选择不相似的测试用例（为了小巧）并迫使测试探索随意或随机测试可能无法到达的输入空间区域（为了全面），最有效地利用有限的测试资源。

请注意，为了划分的目的，程序的输入空间只包括合法输入，即指定了正确行为（因此可测试）的输入。 程序没有定义行为的输入不是合法输入空间的一部分，不应包含在划分中。 这种区别很微妙，在未来的阅读中通过一些示例和对规约的进一步讨论会更有意义。

示例：abs()

让我们从 JavaScript 库中的一个简单例子开始，Math.abs() 函数：

/**
 * ...
 * @param a  要确定绝对值的参数
 * @returns  参数的绝对值。
 */
function abs(a: number): number

从数学上讲，这是一个以下类型的函数：

abs : number → number

该函数有一个一维输入空间，由 a 的所有可能值组成。 考虑到绝对值函数的行为，我们可能首先将输入空间划分为这两个子域：{ a | a ≥ 0 } 和 { a | a < 0 }。 在第一个子域上，abs 应该返回不变的 a。 在第二个子域上，abs 应该取反。

为了紧凑地书写划分，我们省略每个集合描述的 { a | … } 框架，简单地写一个谓词列表，如下所示：

// 划分: a >= 0; a < 0

为了为我们的测试套件选择测试用例，我们从划分的每个子域中选择一个任意的 a 值，例如：

  • a = 17 覆盖子域 a ≥ 0
  • a = -3 覆盖子域 a < 0

示例：max()

现在让我们看另一个来自 JavaScript 库的例子，Math.max()。 虽然 max() 可以接受任意数量的参数，但我们现在只关注双参数形式：

/**
 * ...
 * @param a  一个参数
 * @param b  另一个参数
 * @returns a 和 b 中较大的一个。
 */
function max(a: number, b: number): number

从数学上讲，这是一个双参数函数：

max : number × number → number

所以我们有一个二维输入空间，由所有数对 (a,b) 组成。 现在让我们来划分它。 从规约来看，选择子域 { (a,b) | a < b } 和 { (a,b) | a > b } 是合理的，因为规约要求每个子域有不同的行为：前一个子域的输入应该返回 b，后一个子域的输入应该返回 a。 但我们不能就此停止，因为这些子域还不是输入空间的划分。 划分必须完全覆盖可能的输入集合。 所以我们需要添加 { (a,b) | a = b }，其中函数可以返回 a 或 b。 紧凑地表达，划分如下所示：

// 划分: a < b; a > b; a = b

我们的测试套件可能是：

  • (a,b) = (1, 2) 覆盖 a < b
  • (a,b) = (10, -8) 覆盖 a > b
  • (a,b) = (9, 9) 覆盖 a = b

总结一下，为了形成划分，子域应该具有三个理想属性：

  • 子域应该是不相交的，它们之间没有交集；
  • 子域应该是完备的，使得它们的并集覆盖合法输入空间；
  • 子域应该是非空的，使得可以从每个子域中选择一个合法的测试用例。

在划分中包含边界

Bug 经常发生在子域之间的边界上。 一些例子：

  • 0 是正数和负数之间的边界
  • 数值类型的最大值和最小值，如 Number.MAX_SAFE_INTEGER 或 Number.MAX_VALUE
  • 集合类型的空值，如空字符串、空数组或空集合
  • 序列的第一个和最后一个元素，如字符串或数组

为什么 bug 经常发生在边界？ 一个原因是程序员经常犯差一错误，比如把 <= 写成 <，或者把计数器初始化为 0 而不是 1。 另一个原因是某些边界可能需要在代码中作为特殊情况处理。 还有一个原因是边界可能是代码行为不连续的地方。 例如，当用作整数的 number 变量增长超过 Number.MAX_SAFE_INTEGER 时，它会突然开始失去精度。

我们将边界作为划分中的单元素子域纳入，这样测试套件必然会将边界值作为测试用例包含进来。 对于 abs，我们会为相关边界添加一个子域：

  • a = 0，因为 abs 在正数和负数上的行为不同

我们原来的两个子域将缩小以排除边界值：{ a | a > 0 } 和 { a | a < 0 }。

这仍然是 abs 输入空间的一个划分：三个子域不相交且完全覆盖输入空间。 紧凑地书写的一种方式如下所示：

// 划分:
//   a < 0
//   a = 0
//   a > 0

我们的测试套件可能是：

  • a = 0
  • a = 17 覆盖子域 a > 0
  • a = -3 覆盖子域 a < 0

示例：BigInt 乘法

让我们看一个稍微复杂一点的例子。 BigInt 是 TypeScript 内置的一种类型，可以表示任意大小的整数，不像 number 类型只有有限的范围。 BigInt 支持通常的整数运算，如 +、-、*、/ 和 **。 例如，它可能这样使用：

let a = BigInt(Number.MAX_SAFE_INTEGER); // 2^53 - 1
let b = BigInt(4);
let ab = a * b; // 应该是 2^55 - 4

我们可以把 * 看作一个（重载的）函数，接受两个输入，每个都是 BigInt 类型，产生一个 BigInt 类型的输出：

multiply : BigInt × BigInt → BigInt

我们再次有一个二维输入空间，由所有整数对 (a,b) 组成。 考虑到符号规则如何与乘法配合，我们可能首先从这些子域开始：

  • a 和 b 都是正数
  • a 和 b 都是负数
  • a 是正数，b 是负数
  • a 是负数，b 是正数

乘法还有一些我们应该检查的边界值：

  • a 或 b 是 0，因为结果总是 0
  • a 或 b 是 1，乘法的单位元

最后，因为 BigInt 的目的是表示任意大的整数，我们应该确保尝试非常大的整数——至少比 Number.MAX_SAFE_INTEGER（即 253 - 1，一个 16 位十进制整数）大。

  • a 或 b 在量级上小或大（即，小到可以在 number 值中精确表示，或太大而无法用 number 表示）

让我们把这些观察整合成一个对整个 (a,b) 空间的单一划分。我们将独立地从以下选项中选择 a 和 b：

  • 0
  • 1
  • 小的正整数（≤ Number.MAX_SAFE_INTEGER 且 > 1）
  • 小的负整数（≥ Number.MIN_SAFE_INTEGER 且 < 0）
  • 大的正整数（> Number.MAX_SAFE_INTEGER）
  • 大的负整数（< Number.MIN_SAFE_INTEGER）

所以这将产生 6 × 6 = 36 个子域，划分整数对的空间。

为了从这个划分生成测试套件，我们会从网格的每个方格中选择一个任意的数对 (a,b)，例如：

  • (a,b) = (0, 0) 覆盖 (0, 0)
  • (a,b) = (0, 1) 覆盖 (0, 1)
  • (a,b) = (0, 8392) 覆盖 (0, 小的正整数)
  • (a,b) = (0, -7) 覆盖 (0, 小的负整数)
  • …
  • (a,b) = (-1060, -10810) 覆盖 (大的负数, 大的负数)

右边的图显示了二维 (a,b) 空间如何被这个划分分割，这些点是我们可能选择来完全覆盖划分的测试用例。

使用多个划分

到目前为止的例子在整个输入空间上只使用了一个划分——一个不相交子域的集合。 对于具有多个参数的函数，这可能会变得昂贵。 每个参数可能都有有趣的行为变化和几个边界值，因此从每个参数的行为的笛卡尔积形成输入空间的单一划分会导致结果测试套件规模的组合爆炸。 我们已经在 BigInt 乘法中看到了这一点，其中笛卡尔积划分已经有 6 × 6 = 36 个子域，需要 36 个测试用例来覆盖。 对于具有 n 个参数的函数，笛卡尔积方法产生的测试套件大小是 n 的指数，这对于手动测试编写来说很快变得不可行。

另一种方法是将每个输入 a 和 b 的特征视为输入空间的两个独立划分。 一个划分只考虑 a 的值：

  • (a,b) 使得 a = 0, 1, 小的正数, 小的负数, 大的正数, 大的负数

另一个划分只考虑 b 的值：

  • (a,b) 使得 b = 0, 1, 小的正数, 小的负数, 大的正数, 大的负数

这两个划分在右边说明。 每个输入对 (a,b) 属于每个划分中恰好一个子域。

我们可能紧凑地书写这两个划分如下：

// 在 a 上的划分:
//   a = 0
//   a = 1
//   a 是小的正整数 > 1
//   a 是小的负整数
//   a 是大的正整数
//   a 是大的负整数
//      （"小"适合 TypeScript number，"大"不适合）
// 在 b 上的划分:
//   b = 0
//   b = 1
//   b 是小的正整数 > 1
//   b 是小的负整数
//   b 是大的正整数
//   b 是大的负整数

我们仍然想用测试用例覆盖每个子域，但现在单个测试用例可以覆盖来自不同划分的多个子域，使测试套件更高效。 我们只需用 6 个测试用例就可以完全覆盖两个划分，如右图所示。

独立划分 a 和 b 增加了你不再测试它们之间交互的风险。 例如，乘法中的符号处理是一个可能的 bug 来源，结果的符号取决于 a 和 b 的符号。 但我们可以添加一个额外的划分来捕捉这种交互：

// 在 a 和 b 的符号上的划分:
//   a 和 b 都是正数
//   a 和 b 都是负数
//   a 为正，b 为负
//   a 为负，b 为正
//   一个或两个都是 0

现在我们有三个划分，分别有 6、6 和 5 个子域，但我们不需要 6 × 6 × 5 个测试用例的笛卡尔积来覆盖它们。 一个包含 6 个精心选择的测试用例的测试套件可以覆盖所有三个划分的子域。

我们可以继续以这种方式添加划分，因为我们更多地思考规约并观察可能导致 bug 的其他行为变化。 通过仔细选择测试用例，额外的划分应该需要很少（如果有的话）额外的测试用例。

有时我们可能想在多个划分上使用笛卡尔积方法，以生成更全面的测试套件。 但即使在这些情况下，笛卡尔积也可能比我们预期的要小。 当来自不同划分的子域被发现是互斥的时，笛卡尔积不会包含该特定子域组合的子域。 我们将在下面的一个练习中看到一个例子。

然而，作为测试优先编程的起点，一个覆盖几个精心选择的划分的每个子域的小型测试套件在大小和全面性之间取得了良好的平衡。 然后，测试套件可以通过玻璃盒测试、覆盖率测量和回归测试进一步增长，我们将在本阅读的后面看到。

自动化单元测试

一个经过充分测试的程序会对其包含的每个单独模块进行测试。 测试一个单独模块的测试，尽可能隔离的，称为单元测试。

没有什么比完全自动化更能使单元测试更容易运行且更可能被运行了。 自动化测试意味着自动运行测试并检查结果。 在模块上运行测试的代码是测试驱动程序（也称为测试工具或测试运行器）。 测试驱动程序不应该是一个提示你输入并打印结果供你手动检查的交互式程序。 相反，测试驱动程序应该在固定的测试用例上调用模块本身，并自动检查结果是否正确。 测试驱动程序的结果应该是"所有测试通过"或"以下测试失败：…"。

大多数编程语言至少有一个流行的库用于编写自动化单元测试，包括 Java 的 JUnit 和 Python 的 unittest。 对于 JavaScript 和 TypeScript，一个流行的选择是 Mocha。

Mocha 单元测试被写为对 it() 函数的调用，第一个参数是测试名称，第二个参数是测试体（写为函数表达式）。 测试体通常包含一个或多个对被测模块的调用，然后使用断言函数如 assert、assert.strictEqual 或 assert.throws 来检查结果。 例如，max 的单个单元测试可能如下所示：

it("covers a < b", function() {
  assert.strictEqual(Math.max(1, 2), 2);
});

请注意，assert.strictEqual 的参数顺序很重要。 第一个参数应该是实际结果——代码实际做的。 第二个参数应该是预期结果——通常是一个常量——测试想要看到的。 如果你把它们弄反了，那么当测试失败时，Mocha 可能会产生令人困惑的错误消息。 断言也可以选择性地将一个消息字符串作为最后一个参数，你应该用它来使测试失败更清晰。

为了将一组单元测试收集到一个测试套件中，将它们放在对 describe() 的调用中。 例如，我们上面为 max 选择的测试在实现为 Mocha 时可能如下所示：

describe("Math.max", function() {
  it("covers a < b", function() {
    assert.strictEqual(Math.max(1, 2), 2);
  });

  it("covers a = b", function() {
    assert.strictEqual(Math.max(9, 9), 9);
  });

  it("covers a > b", function() {
    assert.strictEqual(Math.max(10, -9), 10);
  });
});

测试套件可以包含任意数量的 it() 函数，当你用 Mocha 运行测试套件时，这些函数是独立运行的。 如果测试用例中的断言失败，则该测试用例立即返回，Mocha 记录该测试的失败。 即使一个测试失败，套件中的其他测试仍会运行。

请注意，像 Mocha 这样的自动化测试框架使运行测试变得容易，但你仍然必须自己想出好的测试用例。 自动生成测试是一个难题，仍然是计算机科学研究的活跃课题。

记录你的测试策略

在 describe() 函数顶部的注释中记录划分和子域。 例如，为了记录我们测试 max 的策略，我们会写这个：

describe("max", function() {
  /*
   * 测试策略
   *
   * 划分:
   *   a < b
   *   a > b
   *   a = b
   */

   it(...); // 测试用例写这里
   it(...);
   it(...);
   ...
});

每个测试用例应该以它覆盖的子域命名，例如：

it("covers a < b", function() {
  assert.strictEqual(Math.max(1, 2), 2);

黑盒与玻璃盒测试

回顾上面，规约是函数行为的描述——参数的类型、返回值的类型，以及它们之间的约束和关系。

黑盒测试意味着只从规约中选择测试用例，而不是从函数的实现。 这就是我们到目前为止在例子中所做的。 我们在 abs、max 和 BigInt 乘法中划分和寻找边界时，没有查看这些函数的实际代码。 事实上，如果我们遵循测试优先编程方法，我们甚至还没有编写这些函数的代码。

玻璃盒测试意味着在了解函数实际实现方式的情况下选择测试用例。 例如，如果实现根据输入选择不同的算法，那么你应该围绕选择不同算法的点进行划分。 如果实现保留一个内部缓存来记住之前输入的答案，那么你应该测试重复的输入，看看缓存是否正常工作。

对于 BigInt 乘法的情况，当我们最终实现它时，我们可能决定将整数表示为十进制数字数组。 这个决定在函数的行为中引入了新的边界。 两个个位数相乘是微不足道的，但两个或更多位数的数组需要更复杂的多位数乘法。 所以这个实现的玻璃盒测试可能会引入一个基于内部数组长度的新划分。 （BigInt 的一个更有效的表示可能是 32 位无符号整数数组，如 Uint32Array，但原理是相同的——基为 232 的数字序列，而不是基为 10。）

进行玻璃盒测试时，你必须小心，你的测试用例不要要求规约没有明确要求的特定实现行为。例如，如果规约说"如果输入格式错误则抛出异常"，那么你的测试不应该特别检查 TypeError 异常，只是因为当前实现是这样做的。在这种情况下，规约允许抛出任何异常，所以你的测试用例同样应该是通用的，以保持正确性，并保留实现者的自由。我们将在关于规约的课程中更多地讨论这个问题。

覆盖率

评估测试套件的一种方法是问它对程序的测试有多彻底。这个概念称为覆盖率。以下是三种常见的覆盖率：

  • 语句覆盖率：每条语句是否至少被一个测试用例运行？
  • 分支覆盖率：对于程序中的每个控制分支（如 if 或 while 或 ?: 三元表达式），分支的每一边是否至少被一个测试用例执行？
  • 路径覆盖率：每种可能的分支组合——程序中的每条路径——是否至少被一个测试用例执行？

分支覆盖率比语句覆盖率更强（即需要更多测试来实现），路径覆盖率比分支覆盖率更强。在工业界，100% 语句覆盖率是一个常见的目标，但由于不可达的防御性代码（比如"不应该到达这里"的断言），即使这个目标也很少实现。100% 分支覆盖率是非常理想的，安全关键的工业代码甚至有更严格的标准（例如，MC/DC，修正条件/判定覆盖率）。不幸的是，100% 路径覆盖率是不可行的，需要指数级大小的测试套件才能实现。

测试的标准方法是添加测试直到测试套件达到足够的语句覆盖率：即，使得程序中每个可到达的语句至少被一个测试用例执行。 在实践中，语句覆盖率通常由代码覆盖率工具测量，该工具计算你的测试套件运行每条语句的次数。 有了这样的工具，玻璃盒测试很容易；你只需测量黑盒测试的覆盖率，然后添加更多测试用例，直到所有重要的语句都被记录为已执行。

JavaScript 和 TypeScript 的一个好的代码覆盖率工具是 c8，如右图所示。 在该工具的 HTML 输出中，被测试套件执行的行在左边缘有一个绿色标记（还显示该行被执行的次数）。 尚未被覆盖的行被涂成红色。 包含只在一个方向执行的分支的行——总是真但从不假，反之亦然——有一个 I 或 E 图标，指示哪个路径从未被采用（I 代表"if"，E 代表"else"）。 如果你从覆盖率工具中看到右边的结果，你的下一步是想出一个测试用例，使得 if 测试至少一次为真，并将其添加到你的测试套件中，使红色行变成绿色。

单元测试与集成测试

我们到目前为止一直在讨论隔离测试单个模块的单元测试。 隔离测试模块使得调试更加容易。 当模块的单元测试失败时，你可以更有信心地认为 bug 就在那个模块中，而不是在程序的任何地方。

与单元测试相比，集成测试测试的是模块的组合，甚至整个程序。 如果你只有集成测试，那么当测试失败时，你必须到处寻找 bug。 它可能在程序的任何地方。 集成测试仍然很重要，因为程序可能在模块之间的连接处失败。 例如，一个模块可能期望从另一个模块获得与其实际接收到的不同的输入。 但是如果你有一套全面的单元测试，让你对单个模块的正确性有信心，那么你在寻找 bug时就会少做很多搜索。

假设你正在构建一个文档搜索引擎。 你的两个模块可能是 load()（加载文件）和 extract()（将文档拆分为其组成词）：

/**
 * @returns 文件的内容
 */
function load(filename: string): string { ... }

/**
 * @returns 字符串 s 中的词，按它们出现的顺序，
 *          其中词是连续的
 *          非空白和非标点字符序列
 */
function extract(s: string): Array<string> { ... }

这些函数可能被另一个模块 index() 用来制作搜索引擎的索引：

/**
 * @returns 一个将词映射到包含该词的
 *         文件名集合的索引，针对输入集中的所有文件
 */
function index(filenames: Set<string>): Map<string, Set<string>> {
    ...
    for (const file of files) {
        const doc = load(file);
        const words = extract(doc);
        ...
    }
    ...
}

在我们的测试套件中，我们想要：

  • 只针对 load 的单元测试，在各种文件上测试它
  • 只针对 extract 的单元测试，在各种字符串上测试它
  • 针对 index 的单元测试，在各种文件集合上测试它

程序员有时会犯的一个错误是以这样一种方式为 extract 编写测试用例，即测试用例依赖于 load 的正确性。 例如，测试用例可能使用 load 来加载文件，然后将其结果作为输入传递给 extract。 但这不是 extract 的单元测试。 如果测试用例失败，我们不知道失败是由于 load 还是 extract 中的 bug。

最好单独思考和测试 extract。 使用涉及真实文件内容的测试划分可能是合理的，因为那是 extract 在程序中的实际使用方式。 但不要实际从测试用例中调用 load，因为 load 可能有 bug！ 相反，将文件内容存储为字面量字符串，直接传递给 extract。 这样你就是在编写一个隔离的单元测试，如果它失败，你可以更有信心地认为 bug 在实际测试的模块中。

请注意，index 的单元测试不能轻易地以这种方式隔离。 当测试用例调用 index 时，它不仅测试 index 内部代码的正确性，还测试 index 调用的所有函数。 如果测试失败，bug 可能在任何这些函数中。 这就是为什么我们要分别测试 load 和 extract，以增加我们对这些模块各自的信心，并将问题定位到连接它们的 index 代码。

如果我们为它所调用的模块编写桩版本，隔离像 index 这样更高级别的模块是可能的。 例如，load 的桩根本不会访问文件系统，而是无论传入什么 File 都返回模拟的文件内容。 类的桩通常称为模拟对象。 桩在构建大型系统时是一项重要技术（一些单元测试框架包括对模拟的支持，如 TypeScript 中的 jest 和 Python 中的 unittest），但我们通常在 6.102 中不会使用它们。

自动化回归测试

一旦你有了测试自动化，当你修改代码时重新运行测试是非常重要的。 软件工程师从痛苦的经验中知道，对大型或复杂程序的任何更改都是危险的。 无论你是修复另一个 bug、添加新功能，还是优化代码使其更快，一个保留正确行为基线的自动化测试套件——即使只有几个测试——也能救你一命。 在更改代码时频繁运行测试可以防止你的程序回归——在修复新 bug 或添加新功能时引入其他 bug。 在每次更改后运行所有测试称为回归测试。

每当你发现并修复一个 bug，把引发该 bug 的输入拿出来，作为测试用例添加到你的自动化测试套件中。 这种测试用例称为回归测试。这有助于用好的测试用例填充你的测试套件。记住，如果一个测试能引发 bug，那它就是一个好测试——而每个回归测试在你代码的某个版本中确实做到了！保存回归测试还可以防止重新引入 bug 的倒退。这个 bug 可能是一个容易犯的错误，因为它已经发生过一次了。

这个思想还引出了测试优先调试。当 bug 出现时，立即为它编写一个能引发它的测试用例，并立即将其添加到你的测试套件中，用一个表明它来自 bug 报告而不是划分的名称，如 it("covers bug #1079")。一旦你找到并修复了这个 bug，你所有的测试用例都会通过，你也就完成了调试，并拥有了一个针对该 bug 的回归测试。

在实践中，自动化测试和回归测试这两个思想几乎总是结合使用。 只有当测试能够频繁、自动地运行时，回归测试才实用。 反之，如果你已经在项目中建立了自动化测试，那么你不妨用它来防止回归。 所以自动化回归测试是现代软件工程的最佳实践。

迭代式测试优先编程

让我们重新审视我们在本阅读开头介绍的测试优先编程思想，并对其进行完善。 有效的软件工程不遵循线性过程。 实践迭代式测试优先编程，其中你准备好回头修改之前步骤的工作：

  1. 为函数编写规约。
  2. 编写验证规约的测试。 当你发现问题时，迭代规约和测试。
  3. 编写实现。 当你发现问题时，迭代规约、测试和实现。

每一步都有助于验证前面的步骤。 编写测试是理解规约的好方法。 规约可能不正确、不完整、有歧义或缺少边界情况。 尝试编写测试可以及早发现这些问题，在你浪费时间为有 bug 的规约编写实现之前。 同样，编写实现可能帮助你发现缺失或不正确的测试，或者促使你重新审视和修改规约。

由于可能需要迭代之前的步骤，所以在进入下一步之前花费大量时间使一步变得完美是没有意义的。 计划迭代：

  • 对于大型规约，首先只编写规约的一部分，继续测试和实现该部分，然后用更完整的规约进行迭代。

  • 对于复杂的测试套件，首先选择几个重要的划分，为它们创建一个小型测试套件。 继续编写一个通过那些测试的简单实现，然后用更多划分迭代测试套件。

  • 对于棘手的实现，首先编写一个简单的暴力实现来测试你的规约和验证你的测试套件。 然后带着信心继续更难的实现，因为你的规约是好的，你的测试是正确的。

迭代是每个现代软件工程过程（如 Agile 和 Scrum）的一个特性，有很好的实证支持其有效性。 迭代需要与你作为学生解决作业和考试问题时可能习惯的不同的心态。 迭代不是试图从头到尾完美地解决一个问题，而是尽快达到一个粗略的解决方案，然后稳步完善和改进它，以便你有时间在必要时丢弃和重做。 当问题困难且解决方案空间未知时，迭代最有效地利用你的时间。

随机化测试

我们在上面解释了为什么随机统计测试（以其他工程学科实践的方式）对软件是无效的。

但随机生成的测试用例确实在测试中发挥作用，通常在项目的后期迭代中，在代码被更系统地测试验证之后。

模糊测试为函数或整个程序生成随机输入，以发现 bug 或安全漏洞。 因为它不知道任何给定输入的正确答案，模糊测试器只是寻找没有不良行为：程序应该干净地运行，检测和报告错误，但不应该任意崩溃。

基于属性的测试比模糊测试更有原则。 基于属性的测试器也生成随机输入（通常由自定义代码引导以使其逼真地伪造，并由前置条件过滤），然后检查结果是否满足某个特定属性（比实际的后置条件弱）。 例如，字符串切片函数的基于属性的测试器可能检查返回的切片作为子串出现在原始字符串中。 模糊测试是基于属性的测试的一个特例，其中期望的属性是"没有崩溃"。

总结

在本阅读中，我们看到了以下思想：

  • 测试优先编程。在编写代码之前编写测试。
  • 使用划分和边界值的系统化测试，以设计一个正确、全面且小巧的测试套件。
  • 玻璃盒测试和语句覆盖率，用于填充测试套件。
  • 对每个模块进行单元测试，尽可能隔离。
  • 自动化回归测试，防止 bug 再次出现。
  • 迭代开发。计划重做一些工作。

今天阅读的主题与我们优秀软件的三个关键属性关联如下：

  • 免受 bug 侵害。 测试是关于在你的代码中发现 bug，而测试优先编程是关于尽早发现它们，就在你引入它们之后。

  • 易于理解。 使用记录在案的测试策略进行系统化测试，使得更容易理解测试用例是如何选择的以及测试套件有多全面。

  • 为变更做好准备。 正确的测试套件只依赖于规约中的行为，这允许实现在规约的范围内进行变更。 我们还讨论了自动化回归测试，这有助于在代码更改时防止 bug 再次出现。
