引言

在本次阅读中，我们将研究类似行为的不同规范，并讨论它们之间的权衡。 我们将从三个维度来比较规范：

  • 确定性程度。 规范是否只为给定输入定义了单一可能的输出，还是允许一组合法输出？

  • 声明式程度。 规范是仅描述输出应该是什么，还是明确说明如何计算输出？

  • 强度。 规范是否有少量的合法实现，还是大量的合法实现？

我们为模块选择的所有规范并非同样有用，我们将探讨是什么让某些规范比其他规范更好。

确定性规范与欠确定规范

考虑以下两个 find 的实现：

由于我们还将讨论 find 的多个规范，我们将用上标来标识每个规范，如 ExactlyOne:

function findExactlyOne(arr: Array<number>、 val: number): number
前置条件：
val occurs exactly once in arr
效果：
返回满足 arr[i] = val 的索引 i

The findExactlyOne 规范是 确定性：当给定满足前置条件的状态时，结果是完全确定的。 只可能有一个返回值和一个最终状态。 不存在具有多个有效输出的有效输入。

Both findFirst 和 findLast implementations 满足 规范，因此如果这是客户端依赖的规范，那么这两个实现可以相互替换。

以下是一个略有不同的规范：

function findOneOrMore、Any在dex(arr: Array<number>、 val: number): number
前置条件：
val 在 arr 中出现
效果：
返回满足 arr[i] = val 的索引 i

This 规范是 not 确定性字段。 它没有说明当 val 出现多次时返回哪个索引。 它只是说，如果你查找返回值给定索引处的条目，你会找到 val。 对于某些输入，此规范允许多个有效输出。

但即使此规范不是确定性的，我们也不会称其为 non确定性 在通常意义上。 非确定性代码有时表现一种方式，有时表现另一种方式，即使在同一程序中使用相同输入调用。 例如，当代码的行为依赖于随机数，或者当它依赖于并发进程的时间时，可能会发生这种情况。 但非确定性的规范不一定需要非确定性的实现。 它可以被完全确定性的实现所满足。

为了避免混淆，我们将非确定性的规范称为 欠确定字段。

This 欠确定 findOneOrMore、Any在dex 规范再次被 findFirst 和 findLast字段。 这些实现中的每一个都以自己的（完全确定性）方式满足欠确定规范。 此规范的客户端不能依赖当 val 出现多次时将返回哪个索引。 非确定性实现也可以满足此规范 — 例如，抛硬币决定是从数组的开头还是结尾开始搜索。 但在我们遇到的几乎所有情况下，规范中的欠确定性提供了一个由实现者在实现时做出的选择。 欠确定规范通常由完全确定性的实现来实现。

更强规范与更弱规范

我们在上次阅读（规范）中讨论了规范的存在如何允许你安全地用一个实现替换另一个实现，只要两个实现都满足规范。 但假设你不仅需要更改实现，还需要更改规范本身？ 假设已经有客户端依赖该函数的当前规范。 你如何比较两个规范的行为，以决定用新规范替换旧规范是否安全（对于这些客户端而言）？
