可以修改和不能修改的内容

  • 不要更改任何提供的文件或文件夹名称。
  • 不要更改函数签名：lerp.ts 中的函数必须使用我们提供的函数签名。
  • 不要更改函数签名和规格说明：colors.ts 中导出的函数必须使用我们提供的函数签名和规格说明。
  • 不要削弱规格说明：curves.ts 中导出的函数必须具有比我们提供的更强的规格说明。
  • 不要导出任何新内容：从 lerp.ts、colors.ts 和 curves.ts 中，只能导出提供的函数。
  • 不要包含非法的测试用例：你编写的测试必须遵守你正在测试的规格说明。 针对我们提供的规格的测试将针对这些规格的其他实现运行。

然而，除了这些要求之外，你可以自由地添加新函数和新类。

规格说明

在开始之前，仔细阅读规格说明，并记录你观察到的内容。 你可以直接在 VS Code 中阅读 TypeScript 源文件，或阅读从源文件生成的所有函数的 TypeDoc 文档。

请记住关于规格说明的以下事实：

  • 某些规格说明有前置条件。 回顾关于规格说明的阅读材料，当前置条件被客户端违反时，函数的行为是完全未指定的。

  • 某些规格说明有未完全确定的后置条件。 回顾未完全确定的后置条件允许一定范围的行为。 当你实现这样的函数时，你的函数在该范围内的确切行为由你决定。 当你为该函数编写测试用例时，测试必须允许实现行为在全部范围内的变化，否则你的测试用例就不是规格说明的合法客户端，如上文所要求的。

  • 导出的函数可以在任何地方使用。 这些函数是独立的模块，可能由图形系统的各个部分调用，不一定是你的代码。 函数实现必须能够处理所有满足前置条件的输入，即使它们不出现在你对这些函数的使用中。 函数可以返回任何满足其后置条件的输出，即使在你调用它的上下文中这似乎没有用。

在本问题集中，我们使用浮点数，但指定计算的数值精度以及编写实现指定精度的算法都不在 6.102 的范围内。 因此，在所有规格说明中：

  • 整数 number 值被认为是安全的，介于 MIN_SAFE_INTEGER 和 MAX_SAFE_INTEGER 之间（当然它们可能受到进一步限制）。

  • 当非整数 number 的计算受到约束时，允许最多 tolerance = 0.001 的误差。 你不得对我们要求你指定或实现的任何函数使用任何其他浮点数等价定义。 如果你被要求强化或削弱规格说明，你不得通过更改浮点数误差的容限来做到这一点。 你可以使用 utils.ts 中提供的 assertApproxEqual 函数来编写与此规格说明兼容的测试。

  • 我们做出这些假设的目的是简化而不是复杂化问题集。 如果你认为由于数值精度的原因，正确测试或实现某个要求的规格说明很困难，或者因为这些假设而变得更加困难，请提出问题。

强化 bezierInterpolate 和 bezierPath 的规格说明

要强化 bezierInterpolate 的规格说明……

  • 考虑削弱其对 renameMe 的静态检查前置条件（并重命名该参数）
  • 避免削弱其提供的例外情况后置条件

要强化 bezierPath 的规格说明……

  • 考虑通过使用联合类型来削弱其对 renameMe 的静态检查前置条件（并重命名该参数）
  • 然后考虑当该参数提供 undefined 时你的后置条件，因为你不能添加例外情况

测试

你应该对每个函数的输入和输出进行分区，在测试策略注释中写下你的分区，并选择测试用例来覆盖这些分区。

函数规格说明和实现位于 src/ 下的文件中，对应的 Mocha 测试位于 test/ 下的文件中。 将实现代码与测试代码分离是开发项目中的常见实践。 它使实现代码更容易理解，不受测试的干扰，并且更容易打包发布。

函数的测试套件中可能已经包含作为模型提供的示例测试。 建议你阅读这些示例测试，然后丢弃它们并编写自己的测试。

关于测试的一些建议：

  • 你的测试用例应通过分区来选择。 这种方法在关于测试的阅读材料中有解释。

  • 在每个测试套件顶部包含一个描述你测试策略的注释。 示例展示在关于测试的阅读材料中。

  • 你的测试用例应该小且精选。 不要对每个测试使用大量数据。 相反，精心选择的输入来测试你想要测试的分区。

  • 你的测试应该找到 bug。 我们将部分通过将你的测试运行于有缺陷的实现来评分你的测试用例，看看你的测试是否能捕获这些 bug。 因此，考虑实现可能无意中不满足规格说明的方式，选择能暴露这些 bug 的测试。

  • 你的测试必须是规格说明的合法客户端。 我们还将把你的测试用例运行于严格满足规格说明的合法变体实现上，你的测试用例不应该对这些好的实现提出异议。 这意味着你的测试用例不能对你的实现特有的属性做出额外假设。

  • 将每个测试用例放在其自己的 it() 函数中。 这比一个大型测试函数有用得多，因为它能精确定位实现中的问题。

  • 运行测试覆盖率。 当需要进行白盒测试时，使用 npm run coverage 运行你的测试套件。

  • 从测试代码中调用辅助函数时要小心。 你在 test/colors.test.ts 中的测试用例不得调用你在 src/colors.ts 中定义的新辅助函数。 记住，你的测试将运行于 colors.ts 函数的教员实现，而你版本的该文件中的代码将不可用。 将仅由测试代码需要的辅助函数放入 test/；将同时由实现代码和测试代码需要的辅助函数放入 src/utils.ts（在下面的部分中讨论）。

  • 同样，保持你的测试小而精。 不要使用不合理的资源量（如长度为 MAX_SAFE_INTEGER 的数组或字符串）。 我们不会期望你的测试套件能捕获与资源耗尽相关的 bug；每个程序在资源耗尽时都会失败。

  • 使用 strictEqual 和 deepStrictEqual。 例如， assert.equal(1, '1') 通过，因为它使用了危险的 == 比较。 不要使用它，始终对不可变的内置类型使用 strictEqual。

    然而，assert.strictEqual([1], [1]) 失败，因为它检查两个参数是否引用同一个数组实例。 要比较数据结构，请使用 deepStrictEqual，如提供的示例测试中所示。

  • 使用 assertApproxEqual。 如上面部分中讨论的，当允许误差时，使用 assertApproxEqual 来比较浮点数。

  • 频繁地 Add/commit/push。 每当你做了大量工作——例如，在编写测试策略注释之后；在选择了一些测试输入之后；在编写 Mocha 测试并看到它们通过之后——你都应该用 git 添加/提交/推送你的工作。

实现

实现每个函数，并修改你的实现和测试，直到所有测试通过。

关于实现的一些建议：

  • 小型辅助函数。 如果你想为单个模块的实现编写小型辅助函数，那么你可以将它们与其他函数一起放在相关的实现文件中。 不要导出 lerp.ts、colors.ts 或 curves.ts 中的辅助函数，因为那样会以不允许的方式更改这些模块的规格说明。 这意味着你不能为这些辅助函数编写测试，这就是为什么它们必须很小。 你依赖于那些模块公共函数的测试套件来实现覆盖并找到这些小型辅助函数中的 bug。

  • 较大型的辅助函数。 如果你想编写任何复杂程度的辅助函数，那么你应该将它们放在 utils.ts 文件中，并在 utils.test.ts 中为它们编写 Mocha 测试。 这也是放置同时由实现代码和测试代码需要的辅助函数的地方。 在 utils.ts 中，如果你导出了一个名为 myHelper 的函数，那么在 colors.ts 和 utils.test.ts 中你可以将该函数作为 utils.myHelper(..) 调用。

    不要要求我们告诉你一个辅助函数是小还是大。 如果你不确定，那么这个函数就足够大，应该有 TypeDoc 文档和自己的测试。 将辅助函数放在 utils.ts 中，给它一个清晰的规格说明，并在 utils.test.ts 中测试它。

  • 不要调用测试代码。 如果你需要从 src/ 中的实现代码调用辅助函数，不要将其放在 test/ 文件夹中。 测试代码应该与实现完全分离，以便实现可以单独打包部署。 当我们将教员测试运行于你的实现时，我们也会分离你的测试代码。 将实现代码需要的辅助函数，或同时由测试和实现代码需要的辅助函数，放入 src/utils.ts。

  • 消除警告。 修改你的代码以解决 VS Code 中显示的所有黄色下划线警告。 这些警告应该包括 TypeScript 编译器警告和 ESLint 警告，因为本问题集启用了 ESLint。

  • 检查测试覆盖率。 进行白盒测试并修改你的测试，直到你有满意的代码覆盖率。

  • 审查你自己的代码。 批判性地阅读你的代码，着眼于使其尽可能做到 SFB、ETU 和 RFC。

  • 频繁测试。 每当你对代码进行更改时，重新运行你的测试。

  • 使用 Mocha 的 -f 参数来调试单个测试。 要从整个测试套件中运行一部分测试用例，使用 npm test -- -f 'pattern'。 只有 it() 描述中包含字符串 pattern 的测试才会运行。 例如，在提供的起始代码中，命令 npm test -- -f 'lerpColor covers...' 仅运行 lerpColor 的示例测试。 这对调试很有用，因为它允许你一次只关注一个失败的测试。

  • 使用 console.log 或 util.inspect 进行打印调试。 许多类型，包括 Map 和 Set，有非常无帮助的 toString() 方法。 这意味着如果你尝试使用，比如说，console.log("gradient is " + gradientMap) 来调试，你可能会看到像 "gradient is [object Map]" 这样无帮助的内容。 有两种方法可以改善这一点：

    • 使用多个参数调用 console.log()，而不是依赖 + 和 toString()：

      console.log("gradient is", gradientMap);

      这意味着 console.log() 负责显示 gradientMap 对象，它在显示内容方面做得更好。

    • 使用 util.inspect() 将对象转换为字符串：

      import util from 'node:util';
console.log("gradient is " + util.inspect(gradientMap));

  • 频繁地 Add/commit/push。 每当你做了大量工作——例如，在编写函数体并看到测试通过之后，或者在找到一个 bug、为其添加回归测试并修复它之后——你都应该用 git 添加/提交/推送你的工作。

了解颜色和曲线，以及 Python 笔记本

RGB 颜色 将颜色表示为红、绿、蓝光的混合。 RGB 对应于你屏幕的物理红、绿、蓝子像素，你应该在 6.101 的图像处理中对 RGB 颜色有一些经验。

HSL 颜色 将颜色表示为色调（想象红色与橙色与其他）、饱和度（想象灰色到灰褐色到鲜艳），以及亮度（想象黑色到彩色到白色）。 最好将其可视化为一个颜色圆柱体：底部为黑色，顶部为白色，核心为灰色，边缘中间为纯色。 参见 Wikipedia 页面上的图示。 （我们没有使用 HSV，该页面也对此有解释。）

贝塞尔曲线 可能是你熟悉的，如果你使用过允许通过定义控制点来绘制平滑路径的图形编辑器。 这些路径通常是复合贝塞尔曲线，其中多条曲线在特定约束下连接在一起。 我们在本问题集中不考虑复合曲线，因此我们的曲线行为方式不完全相同。 相反，关键的直观理解在 Wikipedia 页面的构建贝塞尔曲线部分，有有用的动画。

  • 曲线的阶数对应于控制点的数量：二次曲线有 3 个控制点，三次有 4 个，n 阶曲线有 n+1 个控制点 P0 到 Pn。
  • 注意曲线如何总是从第一个控制点开始并在最后一个控制点结束，但它不一定经过任何其他控制点。

你可以找到许多关于这些主题的其他资源，但请记住，我们期望你为问题集中的所有函数编写自己的测试和实现代码。

你可以通过在 Google Colab 上打开 问题 集 1 工作手册 Jupyter 笔记本，用 Python 调查 RGB 和 HSL 颜色以及贝塞尔曲线。 要在 Colab 上修改和运行笔记本，你必须登录。

  • 你也可以在 GitHub 上查看和下载笔记本。 如果你下载该文件，你可以在 VS Code 中本地打开和运行它，VS Code 内置了 Jupyter 笔记本支持，但可能需要在你的机器上进行设置。

该笔记本可以帮助你使用 Python 经过充分测试的库来可视化颜色和曲线，检查你的工作，并为测试用例创建数据。

设计你的动画函数工具箱

如果你识别出两个示例都必须执行的计算，那就是将其抽象为工具箱函数的自然候选。

然而，这两个示例动画非常不同。 所以你可能会识别出一个你预期在创建类似动画时经常使用的计算，并为其构建一个工具箱函数——即使你只在实现两个必需示例之一时使用该函数。

你可能会发现 colors.ts 中要求的规格说明（你不能更改）和 curves.ts 中的（你只能强化）并不总是完美适合构建这些动画。 如何进行由你决定。 保持你的代码 DRY，保持你的规格说明清晰。

保持你的工具箱小而精，最多三个新函数。 你希望 handoutExampleOne 和 -Two 简短，但它们可能仍然有工作要做，它们也可以直接使用的你实现的其他函数。

如果你在 utils.ts 中有一个在工具箱中有用的现有函数，将其导入 toolbox.ts 并从中重新导出，使其成为该模块规格说明的一部分。 不要复制测试套件，保持在 utils.test.ts 中。

你的规格说明应该无 bug、易于理解，并且易于更改。 尽可能使用静态类型。

当你的规格说明有无法静态检查的前置条件时，你的实现应该检查前置条件，如果前置条件不满足则快速失败。

评分

你的 ps1 总成绩将按以下方式计算：
约 30% alpha 自动评分（包括在线练习）+ 约 20% alpha 手动评分 + 约 25% beta 自动评分 + 约 25% beta 手动评分（包括代码审查）

自动评分测试用例从 alpha 到 beta 不会改变，但它们的分值会改变。 为了鼓励测试优先编程，alpha 自动评分将更侧重于你的测试，而较少侧重于你的实现。 在 beta 上，自动评分将同时寻找好的测试和好的实现。 测试用例在 alpha 上可能值零分，在 beta 上值非零分，或者反之亦然。

alpha 的手动评分可能检查你解决方案的任何部分，包括规格说明、我们要求的解释、测试套件、实现以及你的 Git 提交历史。 beta 的手动评分可能检查任何部分，以及你如何解决 alpha 的手动评分和代码审查反馈。
