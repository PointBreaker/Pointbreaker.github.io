Problem Set 4: 记忆乱序

本问题集的截止日期见课程日历。

本问题集的目的是探索共享可变数据类型的并发编程。

设计自由度与限制

在本问题集中，你拥有充分的设计自由度。

请注意所提供代码中的 PS4 说明。 你必须满足 board.ts 和 commands.ts 中某些函数的既定规范。 你可以重写或删除所提供的其他任何代码，也可以添加新的类和方法等。 在本问题集上，与之前的问题集不同，我们不会针对任何其他实现运行你的测试。

请确保你的游戏棋盘坐标系符合规范：（行，列） 坐标从左上角的 (0, 0) 开始，垂直向下递增，水平向右递增。

你有责任检查 Didit 反馈并确保你的代码能够编译和运行以供评分，但你必须自行测试以确保正确性。

获取代码

要开始，

  1. 让 Didit 在 github.mit.edu 上为你创建一个远程 psets/ps4 仓库。

  2. 克隆仓库。 在你的 Didit 作业页面顶部找到 git clone 命令，完整复制，粘贴到终端中并运行。

  3. cd ps4-«username»，运行 npm install，然后在 Visual Studio Code 中打开。 如需回顾如何创建、克隆或设置仓库，请参阅Problem Set 0。

概述

在本问题集中，你将构建一个联网多人版的记忆翻牌（Memory，又称 Concentration）游戏，即翻开背面向下的卡牌并尝试找到匹配的一对。 在我们的版本中，玩家将同时翻牌，而不是轮流翻牌。 我们称之为「记忆乱序」。

问题 1：你将为此游戏设计并实现一个或多个抽象数据类型（ADT）。

问题 2：你将把 ADT 连接到一个使用 HTTP 处理客户端的游戏服务器。

完成问题 1-2 后，你就可以在浏览器中玩「记忆乱序」了。

问题 3：你将修改系统，使用异步棋盘来处理多个同时在线的玩家。

问题 4：你将设计并实现一个类似 map 的函数（如 map/filter/reduce），用于替换棋盘上的卡牌。

问题 5：你将设计并实现监视棋盘变化的功能，使「记忆乱序」用户界面更具响应性。

迭代开发建议

alpha 的自动和手动评分将更多地关注你在非并发情况下的棋盘和服务器。

首先，在不考虑并发的情况下完成问题 1 和 2：让你的 Board 或其他 ADT 使用同步方法，不用担心服务器中的多个并发玩家。 通过编写测试、选择数据结构和编写代码来实现下文规定的游戏规则。 考虑所有数据类型的抽象函数和表示不变量。

然后，在问题 3 中修改你的工作，使系统为并发玩家做好准备。 根据异步操作的需要，修改你对 ADT 操作的选择。

最后，继续完成问题 4 和 5。

游戏棋盘

「记忆乱序」的游戏棋盘有一个格子网格。 每个格子起始时都有一张卡牌。 当卡牌被匹配并移除后，格子变为空。

我们游戏中的卡牌是一个由非空白、非换行字符组成的非空字符串。 这允许使用 emoji 字符来显示「图案」，如 Hello 和 🌈。 例如：

👁 💖 M √-1 ☕️

如果两张卡牌具有相同的字符字符串，则它们匹配。

所有卡牌起始时均为背面向下。 玩家会将它们翻为正面朝上，然后这些卡牌要么重新翻回背面（如果玩家翻开的卡牌不匹配），要么从棋盘上移除（如果匹配）。

游戏棋盘是从文件加载的。 以下是棋盘文件的形式语法：

BOARD_FILE ::= ROW "x" COLUMN NEWLINE (CARD NEWLINE)+

CARD ::= [^\s\n\r]+
ROW ::= INT
COLUMN ::= INT
INT ::= [0-9]+
NEWLINE ::= "\r"? "\n"

在 BOARD_FILE 中，ROW 是行数，COLUMN 是列数，卡牌按行从左到右列出，从顶行开始。

例如，这个由彩虹和独角兽组成的棋盘：

在此示例中，↵ 用于表示换行。 该棋盘在问题集的 boards 文件夹中作为 perfect.txt 提供。

有效的棋盘文件必须恰好包含 ROW×COLUMN 个以换行符结尾的 CARD 行。

游戏规则

多个玩家同时操作棋盘上的卡牌。 他们通过尝试翻开一对相同的卡牌来进行游戏。

以下是规则的简要说明：

1
当玩家翻开一对中的第一张卡牌时，他们控制该卡牌；但如果其他玩家已经控制了它，则该玩家等待，直到能够取得控制权。
2
当玩家翻开第二张卡牌时，如果卡牌匹配，玩家保持控制；否则，玩家放弃控制。 这些卡牌暂时保持正面朝上。
3
如果并且当玩家进行下一步操作时，如果之前的卡牌匹配，这些卡牌将从棋盘上移除；否则，如果没有人控制它们，它们将翻回背面。

请注意与通常的记忆翻牌游戏规则至少有两点不同：你可以「翻开」一张已经正面朝上的卡牌，等待直到该卡牌可用；并且翻开的卡牌在棋盘上保持正面朝上，直到翻牌的玩家进行下一步操作。

完整规则

第一张卡牌：玩家通过指定棋盘上的一个格子来尝试翻开第一张卡牌……

1-A
如果那里没有卡牌（玩家指定了一个空格，也许是因为卡牌刚刚被另一个玩家移除了），则操作失败。
1-B
如果卡牌背面朝下，则翻为正面朝上（所有玩家现在都能看到它），且玩家控制该卡牌。
1-C
如果卡牌已经正面朝上，但没有被其他玩家控制，则保持正面朝上，且玩家控制该卡牌。
1-D
如果卡牌正面朝上且被其他玩家控制，则操作等待。 该玩家将在下一次机会中与其他玩家争夺该卡牌的控制权。

第二张卡牌：一旦玩家控制了第一张卡牌，他们就可以尝试翻开第二张卡牌……

2-A
如果那里没有卡牌，则操作失败。 玩家同时放弃对第一张卡牌的控制（但它暂时保持正面朝上）。
2-B
如果卡牌正面朝上且被某位玩家控制（无论是其他玩家还是自己），则操作失败。 为避免死锁，操作不等待。 玩家同时放弃对第一张卡牌的控制（但它暂时保持正面朝上）。
—
如果卡牌背面朝下，或者卡牌正面朝上但没有被玩家控制，则：
2-C
如果背面朝下，则翻为正面朝上。
2-D
如果两张卡牌相同，则匹配成功！ 玩家保持控制两张卡牌（它们在棋盘上暂时保持正面朝上）。
2-E
如果不相同，则玩家放弃对两张卡牌的控制（同样，它们暂时保持正面朝上）。

当一名玩家等待翻开第一张卡牌时，其他玩家继续正常游戏。 他们不会等待，除非他们也尝试翻开一张被其他玩家控制的第一张卡牌。

在 1-A、2-A 和 2-B 中的失败意味着玩家未能控制一张卡牌（在 2-A/B 中，还放弃了控制）。 玩家仍然可以继续游戏。

在尝试翻开第二张卡牌（无论成功与否）之后，玩家可以再次尝试翻开第一张卡牌。 当他们这样做时，在遵循上述规则之前，先完成上一步操作：

3-A
如果他们翻开了一对匹配的卡牌，则控制两张卡牌。 现在，这些卡牌从棋盘上移除，且他们放弃对它们的控制。 游戏不规定计分方式。
3-B
否则，他们翻开了一张或两张不匹配的卡牌，放弃了控制但将它们留在棋盘上正面朝上。 现在，对于每张这样的卡牌，如果卡牌仍在棋盘上，当前正面朝上，且当前没有被其他玩家控制，则将该卡牌翻回背面。

如果玩家从未尝试翻开新的第一张卡牌，则 3-A/B 的步骤永远不会发生。

在 Web 上玩

为了支持多人的联网「记忆乱序」游戏，我们定义了一个 HTTP 协议，使游戏可以在 Web 浏览器中进行。 Web 服务器的代码已经提供（在 server.ts 中），但它依赖于本问题集代码中提供的以下函数规范，你需要实现这些函数：

  • board.ts 中的 parseFromFile()
  • commands.ts 中的 look()、flip()、map() 和 watch()

在该协议中，每位玩家通过 ID 来标识自己，ID 是由字母数字或下划线字符组成的非空字符串，可自选。 具有相同玩家 ID 的所有请求均视为同一玩家的操作。

对于所有请求，服务器会响应一个棋盘状态，显示从该玩家视角看到的当前棋盘状态。棋盘状态由以下语法描述：

BOARD_STATE ::= ROW "x" COLUMN NEWLINE (SPOT NEWLINE)+

SPOT ::= "none" | "down" | "up " CARD | "my " CARD
CARD ::= [^\s\n\r]+
ROW ::= INT
COLUMN ::= INT
INT ::= [0-9]+
NEWLINE ::= "\r"? "\n"

在棋盘状态中，ROW 是行数，COLUMN 是列数，卡牌按行从左到右列出，从顶行开始。

none 表示该位置没有卡牌，down 表示背面朝下的卡牌，up 表示正面朝上且由其他玩家控制（或无人控制）的卡牌，my 表示正面朝上且由发送请求的玩家控制的卡牌。

例如：

3x3↵
up␣A↵
down↵
down↵
none↵
my␣B↵
none↵
down↵
down↵
up␣C↵
AAA
B
CCC

在此示例中，␣ 用于表示空格，↵ 用于表示换行。

(1,0) 和 (1,2) 处没有卡牌。

(0,0)、(1,1) 和 (2,2) 处的卡牌正面朝上，且收到此消息的玩家控制着 (1,1) 处的 B 卡牌。

问题 1：游戏棋盘

规范、测试和实现一个可变的 Board 抽象数据类型（ADT）来表示「记忆乱序」游戏棋盘。 你可能还需要定义其他 ADT。

记得包含：为你编写的每个类和每个方法提供规范；抽象函数、表示不变量和防止表示暴露的论证；checkRep() 和 toString()。

Board 定义了一个用于创建新棋盘的静态工厂方法，你必须支持：

  • parseFromFile(filename)：通过解析上述格式的文件来创建棋盘

对于解析棋盘文件，使用解析器生成器（如 ParserLib）会带来不必要的复杂度。

  • String.split() 和 String.match() 可能就能处理所有的解析和提取工作。

  • fs.promises.readFile() 异步读取文件。请确保使用此函数的基于 Promise 的版本（在文档中称为 fsPromises.readFile，如果导入 fs 则引用为 fs.promises.readFile），而不是较旧的基于回调的版本（也称为 readFile，但在 fs 本身中）。

为了跟踪玩家及其状态：

  • 每位玩家可以简单地用其在命令函数中使用的 ID 来标识。 所有游戏状态都将存储在 Board 中。

  • 每位玩家可以用一个 ADT 来表示，例如 Player。 玩家的部分状态可以存储在 Player 对象中，或者 Board 可以存储所有状态。

你需要根据游戏规则跟踪谁控制哪些卡牌以及每张卡牌的状态。

迭代开发建议：先实现一个同步棋盘（即除 parseFromFile 外没有 async 方法），并在问题 2 中将其连接到服务器。 alpha 评分将更多地关注在没有并发的情况下进行游戏。 然后在问题 3 中修订以支持并发玩家的正确行为。

要根据游戏规则实现等待，使用异步方法和 await，或者回调函数。 棋盘不应忙等待（busy-wait）。

你来决定哪些操作是原子的，因为规则并未规定。 例如，在规则 3-B 中，将两张卡牌翻回背面可能是单个操作——其他玩家无法看到或操作中间棋盘状态——也可能是两个独立的操作。 但棋盘绝不能达到不一致的状态，例如两个玩家控制同一张卡牌，或者一张背面朝下的卡牌仍被某位玩家控制。

请注意，翻牌操作可能在规则中的多个位置失败。 在 flip() 命令的规范中（你需要实现它来将 Board 连接到所提供的 Web 服务器），失败通过 rejected promise 来表示，这可以通过从 async 函数中抛出异常来实现。 在设计你自己的 Board 操作时请记住这一点。 对于测试 rejected promise，assert.rejects 很有用。

模拟游戏

在 simulation.ts 中，我们提供了一个模拟程序骨架代码，用于模拟单个玩家与棋盘的交互，随机翻开若干张卡牌。 你应该能够填写 simulationMain() 函数中的 TODO，并使用 npm run simulation 来运行单人「记忆乱序」游戏的模拟。

simulation.ts 使用 seedrandom 包来生成可复现的伪随机数序列。 我们调用的是 seedrandom(seed) 返回的 random 函数，而不是目标始终是完全不可预测的 Math.random()：

  • 默认情况下，模拟会随机选择一个 seed（使用 Node 的 randomBytes() 函数），以便每次运行使用新的伪随机数序列并探索新的事件序列。 该 seed 以及模拟的其他参数会被打印到控制台。

  • 但是，使用相同的 seed（和其他参数）多次运行模拟应产生相同的伪随机选择序列，使你能够添加日志或断言，帮助将「随机」失败转化为测试套件中的最小测试用例。

问题 2：连接 Web 服务器

为了将你的 Board 类型连接到所提供的 Web 服务器，以及连接到 Didit 自动评分系统，你需要实现 commands.ts 中的函数，使其使用 Board 的操作。先从以下两个函数开始，它们足以让你进行游戏：

  • look()（来自 commands.ts）
  • flip()（来自 commands.ts）

此时，你的 look() 和 flip() 可能还不能按规则实现正确的等待行为，也不能处理并发玩家，但它们应该能够处理按顺序行动的多个客户端。

一般来说，保持 commands.ts 中的所有函数极其简单。 它们应该不过是胶水代码，最多调用几个你的 Board 操作，不包含任何额外逻辑。 具体来说：

  • 每个函数的主体最多 3 行，由最多几个简单的函数调用组成，可能使用局部变量，加上一个 return 语句。
  • 它们调用的所有函数应当已经经过充分测试，无论是通过你的 Board 测试套件还是通过 TypeScript 本身。

如果是这种情况，你就不需要为 commands.ts 编写单独的测试套件。 你对 Board 的现有测试应该足够了。

如果 commands.ts 中的任何函数比那更复杂——例如，包含 if 或 while 等控制语句，或字符串处理操作——那么你需要创建 test/commands.test.ts 并为其设计测试套件。 在你这样做之前，停下来！ 先与课程工作人员讨论你的设计，因为这表明你为 Board 类型选择的操作功能不够强大。

  • 规范。 已提供 look() 和 flip() 的规范，但你可以根据需要进行加强。
  • 测试。 保持这些操作极其简单，这样就不必单独测试它们。
  • 代码。 尽可能简单地实现 look() 和 flip()。

运行 Web 服务器

要启动服务器，使用 npm start，它会运行 main.ts 中的 main()。 此代码解析命令行参数，根据这些参数调用 Board 的解析函数，然后创建并启动来自 server.ts 的 WebServer。 你不应该需要修改 main.ts 或 server.ts。

要运行 main()，首先在 Visual Studio Code 内部或单独的终端窗口中打开一个终端。 然后在端口 8080 上使用我们的 3×3 彩虹和独角兽棋盘启动 Web 服务器：

npm start 8080 boards/perfect.txt

请记住，服务器会一直运行直到你终止其进程，如果你尝试在同一端口上运行第二个服务器，会因「地址已被占用」而失败。 如果你从命令行运行服务器，请使用 Ctrl-C 在该终端中停止它。

一旦你的服务器完成，你就可以在 Web 浏览器中玩游戏了！

在你的 Web 浏览器中，转到服务器启动时显示的 URL，它会返回一个与你的服务器进行游戏协议通信的网页。

你可以在多个标签页中打开该 URL 来模拟不同的玩家。每次打开页面时，它会随机生成一个新的玩家 ID 供你的服务器使用。

你也可以通过 IP 地址连接到朋友的服务器，但你可能无法直接在浏览器中将其作为 URL 访问（因为你的浏览器可能要求通过 HTTPS 连接，而此服务器不支持 HTTPS）。相反，在你自己的 ps4 代码中找到该网页文件（文件名为 public/index.html），在 Web 浏览器中打开该 HTML 文件，然后通过 IP 地址指定另一台服务器。

问题 3：修订以支持并发玩家

修改 Board 使其变为异步，根据需要更新其他 ADT。

考虑使用 await 等待棋盘返回的 promise，以实现规则中要求的等待卡牌。 关于以下内容的讨论，请参阅互斥中「建立和保持一个 promise」：

  • Promise.withResolvers() 工厂函数，对于将回调转换为 promise 最为有用
  • Deferred 的规范和实现，对于存储待稍后解析的 promise 最为有用

在 simulation.ts 中，增加 players 的值来模拟多人「记忆乱序」游戏。 通过添加日志（例如使用 console.log() 语句）或跟踪不同玩家翻开的卡牌，你应该能观察到正确的卡牌控制、玩家尝试翻开第一张卡牌时的正确等待，以及玩家进行下一步操作时匹配卡牌的正确移除。

请注意，如果你的模拟中一名玩家在最后一步翻开了匹配的卡牌（留下两张正面朝上的卡牌在该玩家控制下），而另一名玩家尝试将其中一张作为第一张卡牌翻开，则模拟不应终止。

考虑修改你的测试策略，测试并发玩家操作的不同交错情况。 你可能会发现 timeout() 函数对于强制短等待很有用。 非常短的超时（1 甚至 0 毫秒）会放弃足够长的控制权，使并发操作能够完成。 避免等待数百毫秒，因为这可能导致你的测试在 Didit 上超时。 不要在实现代码中放置 timeout() 调用；这是你的设计存在竞态条件的信号。

检查你的 commands.ts 文件，确保它按照规则正确地使用异步的 Board。 你的命令不应忙等待或挂起。 当一个请求在等待时（例如等待卡牌翻转），其他请求必须正常处理。

map() 命令独立于游戏的其他状态。 因此，无论卡牌是正面朝上还是背面朝上，还是被其他玩家控制，仍然可以被替换，且其正面/背面状态和控制状态不受替换影响。

变换函数 f 是异步的（返回一个 promise），因此可能有多种实现方式（例如进行数据库查询、访问语言翻译 Web API，甚至询问人类用户替换卡牌应该是什么）。 这意味着 map() 可能需要等待其对 f 的调用完成。 但是，在运行过程中，map() 不得阻止棋盘上的其他命令与之交错执行（包括同一玩家发出的其他命令，以及其他 map() 命令）。 根据你实现 map() 的方式，其他操作可能会看到部分转换的棋盘（某些卡牌已替换，而其他尚未替换），但棋盘必须在玩家看来保持一致性，即如果棋盘上的两张卡牌在 map() 开始时相互匹配，那么在该 map() 进行期间，不得导致任何玩家观察到该对卡牌不匹配的棋盘状态。

函数 f 必须是 map() 规范中所述的数学函数，但它不必是单射函数。

规范、测试和实现棋盘 ADT 中的支持功能，使你能够在 commands.ts 中将 map() 函数实现为简单的胶水代码，无需单独测试。

问题 5：棋盘事件

本问题向协议中添加了一个新命令：watch()。

此命令不会立即返回。 相反，它会等待，直到棋盘下次发生变化。 此时，它以棋盘的当前状态作为响应。

变化定义为任何卡牌翻为正面或背面、从棋盘上移除，或从一个字符串变为不同的字符串。

watch() 调用必须等待直到发生此类变化。 当卡牌状态没有变化时——例如，玩家尝试翻开一个空格，或者玩家取得或放弃卡牌的控制权但卡牌没有翻转——待处理的 watch 请求必须继续等待。

当 watch(board, playeri>) 请求在等待时，玩家可以在同一棋盘上使用其他命令，这些命令将正常处理。 例如，并发的 look(board, playerId 请求不得等待。

规范、测试和实现棋盘 ADT 中的支持功能，使你能够实现监视棋盘变化的功能。 你的棋盘 ADT 可以实现仅通知单次变化，或通知所有未来变化：

  • 如果客户端仅接收单次变化，可以是一个异步方法，其 promise 在棋盘变化时兑现。
  • 监听器可以向 Board 提供回调函数。 棋盘将在每次变化时回调它们。

首先尝试在 simulation.ts 中使用你的棋盘变化通知，在模拟游戏期间并发地监视棋盘。

然后使用你的变化通知，在 commands.ts 中将 watch() 函数规范、测试和实现为简单的胶水代码，无需单独测试。

请注意，你来决定哪些变化是原子的。 例如，watch() 规范并未说明，当一对匹配（或不匹配）的卡牌被移除（或翻回背面）时，是报告为单次变化还是两次独立的变化。

一旦你将 watch() 添加到服务器，你就可以将「记忆乱序」Web 用户界面从「轮询更新」切换为「监视更新」，你会发现界面能更快地显示其他客户端所做的棋盘更新。
