Git 工作流

你已经在习题集和课堂练习中使用 Git 一段时间了。 大多数时候，你不需要与其他人协调同时推送到和拉取同一个仓库。 对于小组项目，这种情况将发生改变。

现在你对 Git 基础知识更加熟悉了，是时候回顾一下学期初的一些资源了。

提交图

回顾一下，Git 仓库中记录的历史是一个有向无环图（DAG）。

当你独立工作时，在单台机器上，你的版本历史的 DAG 通常看起来像一个序列：提交1是提交2的父提交，提交2是提交3的父提交……

示例仓库的历史涉及三位程序员。 其中两位——Alyssa 和 Ben——"同时"进行了修改。 在这种情况下，"同时"并不意味着精确的同一时刻。 相反，它意味着他们基于同一个前一个版本创建了两个不同的新版本，就像Alice 在她的笔记本电脑和台式机上创建了版本"5L"和"5D"一样。

当多个提交共享同一个父提交时，我们的历史 DAG 从序列变成了树形：它分叉开来。 请注意，项目历史中的分支不需要任何人创建新的 Git 分支，只需从同一个提交开始并在仓库的不同副本上并行工作即可：

合并

有时候，当你尝试推送时，会出现问题。 你可能会得到这样的输出：

! [rejected]      main -> main (non-fast-forward)

这里发生的情况是，Git 不允许你推送提交到仓库，除非你的所有提交都排在远程仓库中已有提交之后。 如果你收到这样的错误消息，意味着远程仓库中有你本地仓库中没有的提交（在项目中，可能是因为队友在你之前推送了）。 如果你遇到了这种情况，你必须先拉取再推送。

让我们看看当并行更改发生时会发生什么：

并行创建并提交 hello.scm 和 hello.rb

将鼠标悬停或点击每个步骤以更新图示：

  1. Alyssa 和 Ben 都克隆了包含两个提交（41c4b8f 和 1255f4e）的仓库。
  2. Alyssa 创建 hello.scm 并将她的修改提交为 6400936。
  3. 与此同时，Ben 创建 hello.rb 并将他的修改提交为 82e049e。
    此时，他们两人的修改都只存在于各自的本地仓库中。 在每个仓库中，main 现在指向不同的提交。
  4. 假设 Alyssa 是第一个推送她的修改到远程的人。
  5. 如果 Ben 现在尝试推送会发生什么？ 推送将被拒绝：如果服务器将 main 更新为指向 Ben 的提交，Alyssa 的提交将从项目历史中消失！
  6. Ben 必须将他的修改与 Alyssa 的合并。
    为了执行合并，他从远程拉取她的提交，这做了两件事：
    (a) 将新提交下载到 Ben 仓库的对象图中
  7. (b) 将 Ben 的历史与 Alyssa 的历史合并，创建一个新提交（3e62e60），将两个历史连接在一起。 这个提交就像其他提交一样是一个快照：应用了两人修改后的仓库快照。
  8. 现在 Ben 可以 git push 了，因为这样做不会丢失任何历史。
  9. Alyssa 可以 git pull 来获取 Ben 的工作。

在这个例子中，Git 能够自动合并 Alyssa 和 Ben 的修改，因为他们各自修改了不同的文件。 如果他们两人编辑了相同文件的相同部分，Git 将报告一个合并冲突。 Ben 将不得不手动将他们的修改交织在一起，然后再提交合并。

自动合并

如果你对你的仓库做了一些修改，并且你正在尝试合并来自另一个仓库的修改，你需要以某种方式将它们合并在一起。 从提交的角度来看，实际发生的是你需要创建一个特殊的合并提交来组合双方的修改。 这个过程实际如何发生取决于具体的修改内容。

如果你幸运的话（像上面例子中的 Alyssa 和 Ben），你做的修改和你从远程仓库下载的修改不会冲突。 例如，也许你修改了一个文件，而你的项目伙伴修改了另一个文件。 在这种情况下，包含双方的修改是安全的。 同样，也许你修改了同一个文件的不同部分。 在这些情况下，Git 可以自动合并。 当你运行 git pull 时，它会弹出一个编辑器，就像你在创建提交一样：这是 Git 自动生成的合并提交的提交消息。 一旦你保存并关闭这个编辑器，合并提交就会被创建，你将已经合并了双方的修改。 此时，你应该编译代码并运行测试（以确保合并确实有效），然后再尝试 git push。

假设你的 Git 现在已配置为使用你熟悉的编辑器，尝试通过运行以下命令让 Git 打开编辑器：

git config --global --edit

这将在编辑器中打开你的 Git 配置文件。如果编辑器是 VS Code 或其他图形文本编辑器，Git 会显示"hint: Waiting for your editor to close the file…"这是一个信号，提示你去 VS Code 找到 Git 刚刚在那里打开的标签页。

如果这是一个合并提交，那么你应该继续编辑文件以添加你的提交消息。 但对于这个测试，不要更改你的配置文件。 如果你不小心输入了内容，请确保撤销并不保存。

相反，只需关闭标签页。 然后回到你运行 git 命令的提示符处，你应该会看到命令现在已经回到了提示符。

当 Git 在 VS Code 中弹出标签页时，你总是需要关闭标签页才能让 Git 继续执行。

合并冲突

有时候，你没有那么幸运。 如果你做的修改和你拉取的修改编辑了同一个文件的同一部分，Git 将不知道如何解决。 这被称为合并冲突。 在这种情况下，你会得到一个大写字母显示 CONFLICT 的输出。 如果你运行 git status，它会用 Both modified 标签显示冲突的文件。 你现在需要编辑这些文件并手动解决冲突。

首先，在 Visual Studio Code 中打开文件。 冲突的部分会用醒目的 <<<<<<<<<<<<<<<<<<、================== 和 >>>>>>>>>>>>>>>>>> 行标记。 <<<< 和 ==== 行之间的所有内容是你做的修改。 ==== 和 >>>> 行之间的所有内容是你拉取的修改。 你的任务是弄清楚如何组合这些修改。 答案当然取决于具体情况。 也许一个修改在逻辑上取代另一个，或者它们可以以某种方式合并。 你应该将文件编辑到满意的状态，并在完成后删除 <<<</====/>>>> 标记。

如刚才所述，Git 的默认行为是在你遇到合并冲突时显示双向差异——你做的修改和你拉取的修改。

为了更容易理解合并冲突，让 Git 改为显示三向差异会有所帮助，其中还包括代码的原始版本，即在你或你的队友修改之前的版本。 三向差异在代码文件中看起来像这样：

<<<<<<<<<<<<<<<<<
.
. 你的代码版本，包含你的修改
.
|||||||||||||||||||
.
. 代码的原始版本
.       （你的修改和传入修改的共同祖先）
.
==================
.
. 传入的代码版本
.       （包含你刚拉取的修改）
.
>>>>>>>>>>>>>>>>>>

立即启用三向差异，因为它对即将到来的 GitStream 练习以及你将遇到的任何合并冲突都有帮助：

git config --global merge.conflictstyle diff3

一旦你解决了所有冲突（注意可能有多个冲突文件，每个文件中也可能有多个冲突），你应该编译代码并运行测试。 然后 git add 所有受影响的文件，再执行 git commit。 你将有机会编写合并提交消息（你应该在其中描述你是如何执行合并的）。 现在你应该可以推送了。

避免合并和合并冲突：

开始工作前先拉取

在你开始工作之前，务必先 git pull。 这样，你将基于最新版本的代码进行工作，并且不太需要在之后执行合并。

在团队中使用版本控制

每个团队都会制定自己的版本控制标准，团队规模和项目大小是主要因素。 以下是一些针对你在6.102中将进行的小规模团队项目的指导方针：

  • 沟通。 告诉你的队友你打算做什么。 告诉他们你正在做。 并告诉他们你做完了。 编写有用的、描述性的提交消息。 沟通是避免浪费时间和精力清理错误代码的最佳方式。

  • 编写规格说明。 对于我们在6.102中关注的内容来说必不可少，也是良好沟通的一部分。

  • 编写测试。 不要等到积累了大量代码后才尝试测试。 避免让一个人写测试而另一个人写实现（除非实现是你打算丢弃的原型）。 先写测试以确保你们对规格说明达成一致。 每个人都应该对自己代码的正确性负责。

  • 运行测试。 如果你不运行测试，测试就无法帮助你。 在开始工作前运行测试，在提交前再次运行。

  • 自动化。 你已经使用 Mocha 等工具自动化了测试，但你现在想在项目每次变更时自动运行这些测试。 对于6.102的小组项目，我们提供 Didit 作为每次团队成员推送到 github.mit.edu 时自动运行测试的方式。 这也消除了"在我的机器上能运行"的借口：要么在自动化构建中运行正常，要么需要修复。

  • 审查你的提交。 使用 git diff --staged 或 GUI 程序查看你即将提交的内容。 运行测试。 不要使用 commit -a，这是用调试打印语句和其他你无意提交的内容填满仓库的好方法。 不要通过提交无法编译的代码、输出调试信息、实际未使用的代码等来烦扰你的队友。

  • 开始工作前先拉取。 否则，你可能没有以最新版本作为起点——你正在编辑旧版本的代码！ 你肯定需要在之后合并修改，并且面临浪费时间解决合并冲突的风险。

  • 同步。 在一天结束时或工作会话结束时，确保每个人都已推送和拉取所有修改，你们都在同一个提交上，并且每个人都对项目状态感到满意。

我们不一定要为6.102规模的项目推荐使用分支或变基等功能。 当项目规模、时间长度或人数远大于本课程中1-2周的3人期末项目时，在单独的分支上工作才显得极为重要。 对于6.102，专注于清晰的沟通和整个团队的频繁同步。
