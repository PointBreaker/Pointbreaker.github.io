引言

Specifications are the linchpin of teamwork. It’s impossible to delegate responsibility for implementing a function without a specification. The specification acts as a contract: the implementer is responsible for meeting the contract, and a client that uses the function can rely on the contract. In fact, we’ll see that like real legal contracts, specifications place demands on both parties: when the specification has a precondition, the client has responsibilities too.

In this reading we’ll look at the role played by specifications of functions. We’ll discuss what preconditions and postconditions are, and what they mean for the implementer and the client of a function. We’ll also talk about how to use exceptions, an important language feature found not only in TypeScript, but also Python, Java, and many other modern languages, which allows us to make a function’s interface safer from bugs and easier to understand.

行为等价

假设你正在处理一个包含以下函数的程序，该函数查找整数在数组中的索引：

function find(arr: Array<number>, val: number): number {
    for (let i = 0; i < arr.length; i++) {
        if (arr[i] === val) return i;
    }
    return -1;
}

这个 find 函数有很多 客户端 in the program (places where the function is called). You’ve just realized that frequently in this program, when find is called with a large array, the value it finds is likely to be either close to the start of the array (which is very fast to find), or close to the end (which is very slow, because it requires checking almost the entire array). So you have the clever idea to speed things up by searching from both ends of the array at the same time:

function find(arr: Array<number>, val: number): number {
    for (let i = 0, j = arr.length-1; i <= j; i++, j--) {
        if (arr[i] === val) return i;
        if (arr[j] === val) return j;
    }
    return -1;
}

替换 find with this new implementation? Can we make this change without introducing bugs? To determine 行为等价，我们问是否可以用一个实现替换另一个而不影响正确性。

Not only do these implementations have different performance characteristics, they actually have different output behavior for certain inputs. If val 碰巧出现 不止一次 在数组中，原始 find always returns the lowest index at which it occurs. But the new find 可能返回最低索引或最高索引，取决于它先找到哪个。

当 val occurs at exactly one index of the array, however, the two implementations behave the same: they both return that index. It may be that the clients never rely on the behavior outside of that case. Whenever they call the function, they will be passing in an array with exactly one element matching val. For such clients, these two versions of find 是相同的，我们可以从一个实现切换到另一个实现而不会有问题。

The notion of behavioral equivalence is in the eye of the beholder — that is, the client. In order to make it possible to substitute one implementation for another, and to know when this is acceptable, we need a specification that states exactly what the client depends on.

在这种情况下，一个允许这两个实现行为等价的规格说明可能是：

find(arr: Array<number>, val: number): number
requires:
val 恰好出现在 arr
effects:
returns index i 的集合，使得 arr[i] = val

正如我们将更详细地看到的， 要求 子句指定了对 find的合法调用必须为真的条件，而 效果 子句指定当客户端进行合法调用时实现将如何表现。

为什么需要规格说明？

我们的 find example showed how a specification can help make a program both ready for change and safe from bugs. Many of the nastiest bugs in programs arise because of misunderstandings about behavior at the interface between two pieces of code. Although every programmer has specifications in mind, not all programmers write them down. As a result, different programmers on a team may have 不同的 specifications in mind. When the program fails, it’s hard to determine where the error is. Precise specifications in the code let you apportion blame (to code fragments, not people!), and can spare you the agony of puzzling over where a bug fix should go.

Specifications are good for the client of a module because they help make the module easier to understand, like a label on the outside of a black box. Having a specification lets you understand what the module does without having to read the module’s code. If you’re not convinced that reading a spec is easier than reading code, compare our spec for find 的规格说明（左侧）与其棘手的实现（右侧）进行比较：

find(arr: Array<number>, val: number): number
requires:
val 恰好出现在 arr
effects:
returns index i 的集合，使得 arr[i] = val
 
function find(arr: Array<number>, val: number): number {
    for (let i = 0, j = arr.length-1; i <= j; i++, j--) {
        if (arr[i] === val) return i;
        if (arr[j] === val) return j;
    }
    return -1;
}

Specifications are good for the implementer of a function because they give the implementer freedom to change the implementation without telling clients. Specifications can make code faster, too. We’ll see that a specification can rule out certain states in which a function might be called. Restricting the inputs might allow the implementer to skip an expensive check that is no longer necessary and use a more efficient implementation. We will see an example of this later in this reading.

合同充当 防火墙 between client and implementer. It shields the client from the details of the 工作 of the module: as a client, you don’t need to read the source code of the module if you have its specification. And it shields the implementer from the details of the 使用 of the module: as an implementer, you don’t have to ask every client how they plan to use the module. This firewall results in 解耦，允许模块和客户端的代码独立更改，只要更改遵守规格说明——每一方遵守其在合同下的义务。

规格说明的结构

抽象地说，一个 规格说明 有几个部分：

  • 函数签名，给出名称、参数类型和返回类型
  • 一个 要求 子句，描述对参数的额外限制
  • 一个 效果 子句，描述返回值、异常和函数的其他效果

合在一起，这些部分构成 前置条件 和 后置条件 的函数。

The precondition is an obligation on the client (the caller of the function). It is a condition on the state in which the function is invoked. One aspect of the precondition is the number and types of the parameters in the function signature, which TypeScript can 静态检查. Additional conditions are written down in the 要求 子句中，例如：

  • 缩小参数类型（例如 x is an integer >= 0 来说明 number 参数 x 必须实际上是一个非负整数）
  • interactions between parameters (e.g., val 恰好出现在 arr)

The postcondition is an obligation on the implementer of the function. TypeScript can statically check some parts of the postcondition, notably the return type. Additional conditions are written down in the 效果 clause, including:

  • 返回值与输入的关系
  • 抛出哪些异常，何时抛出
  • 对象是否以及如何被修改

一般来说，后置条件是程序状态的条件 之后 函数被调用的状态，假设前置条件在 之前。

整体结构是一个逻辑蕴含： 如果 前置条件在函数调用时成立， 那么 后置条件必须在函数完成时成立。

如果前置条件 不 在函数调用时成立，实现 不 bound by the postcondition. It is free to do anything, including never returning, throwing an exception not mentioned in the spec, returning arbitrary results, making arbitrary mutations, etc.

TypeScript 中的规格说明

某些语言（特别是 Eiffel）将前置条件和后置条件作为语言的基本组成部分，作为运行时系统（甚至编译器）可以自动检查的表达式，以执行客户端和实现者之间的合同。

TypeScript 没有那么深入，但它的静态类型声明 是 effectively part of the precondition and postcondition of a function, a part that is automatically checked and enforced by the compiler. The rest of the contract — the parts that we can’t write as types — must be described in a comment preceding the function, and generally depends on human beings to check it and guarantee it.

一个常见的约定，最初为 Java 设计，但现在也被 TypeScript 和 JavaScript 使用，就是在函数前面放一个 文档注释 ，其中：

  • 参数通过 @param 子句描述
  • 结果通过 @returns 子句

前置条件通常放在 @param 中（如果可能），后置条件放在 @returns. So a specification like this:

find(arr: Array<number>, val: number): number
requires:
val 恰好出现在 arr
effects:
returns index i 的集合，使得 arr[i] = val

… might be rendered in TypeDoc like this:

/**
 * Find a value in an array.
 * @param arr array to search, requires that val occurs exactly once
 *            in arr
 * @param val value to search for
 * @returns index i such that arr[i] = val
 */
function find(arr: Array<number>, val: number): number

使用此 TypeDoc 格式记录你的规格说明可以让 Visual Studio Code 向你（以及代码的客户端）显示有用的信息，并允许你 生成 HTML 文档 自动地。

规格说明可以谈论的内容

The specification of a function can talk about the parameters and return value of the function, but it should never talk about local variables of the function, or helper functions defined inside the function body. You should consider the implementation invisible to the reader of the spec. It’s behind the firewall as far as clients are concerned.

The source code of the function may even be unavailable to the reader of your spec, because the TypeDoc tool extracts just the spec comments from your code and renders them as HTML. This separation is a good thing: a spec frees the client from worrying about (or inappropriately depending on!) the details of the function’s implementation. The client is only obliged to pay attention to the spec.

避免 null

许多语言允许变量采用像 None 或 null, which means that the variable doesn’t point to an object. By default, TypeScript behaves this way, so that any variable can be null regardless of the variable’s type:

let word: string = null;  // legal by default!

这是静态类型系统中一个不幸的漏洞，因为 null 不是真正的合法 string value. You can’t call any methods or use any properties with this reference:

word.toLowerCase() // throws TypeError
word.length        // throws TypeError

特别注意 null 不等于空字符串 "" 或空数组 [ ]. On an empty string or empty array, you 可以 call methods and access instance variables. The length of an empty array or an empty string is 0. The length of a string variable that points to null isn’t anything: accessing length 抛出 TypeError。

还要注意，数组可能是非 null 但包含 null 作为值：

let words: Array<string> = [ null ];

这些 nulls are likely to cause errors as soon as someone tries to use the contents of the array.

Null values are troublesome and unsafe, so much so that good programming tries to avoid them. As a general convention, null 值在参数和返回值中是不允许的 unless the spec explicitly says otherwise. So every function has a precondition on the object and array types in its parameters that they be non-null – including elements of collections like arrays, sets, and maps. Every function that can return object or array types implicitly has a postcondition that their values are non-null, again including elements of collection types.

当 TypeScript 启用了 严格 null 检查 (which is the 6.102 configuration), the static type checker guarantees this:

let word: string = null;  // compile error when strict null checking is on
let words: Array<string> = [ null ]; // compile error when strict null checking is on

如果函数允许 null 在参数或返回值中，它需要显式声明 null 在类型中（例如 string|null). But this should be done sparingly. 避免 null。

Google 有自己的 关于 null in Guava, the company’s core Java libraries. The project explains:

粗心使用 null can cause a staggering variety of bugs. Studying the Google code base, we found that something like 95% of collections weren’t supposed to have any null values in them, and having those 快速失败* rather than silently accept null 对开发者会很有帮助。

此外， null is unpleasantly ambiguous. It’s rarely obvious what a null 返回值应该意味着什么——例如， Map.get(key) [在 Java 中] 可以返回 null 要么因为映射中的值是 null, or the value is not in the map. Null can mean failure, can mean success, can mean almost anything. Using something other than null 以外的东西使你的含义清晰.*

*（粗体为强调而添加。）

包含空值

确保理解 null 和空值之间的区别。

回想一下，在 Python 中， None 不等于空字符串 ""、空数组 [ ]或空字典 { }. These empty objects like these are 有效对象 that simply happen to contain no elements. But you can use them with all the usual operations allowed by the type. For example, len("") 返回 0，而 "" + "a" 返回 "a". That’s not true of None不成立： len(None) 和 None + "a" 都会产生错误。

The same idea translates to TypeScript. The null reference is not a valid string, or array, or map, or any other object. But the empty string "" 是有效的 string 值，空数组 [ ] 是有效的数组值。

这意味着 空值始终允许作为参数或返回值 除非规格说明明确禁止它们。

测试与规格说明

在 测试中，我们谈论 黑盒测试 ，它们仅根据规格说明选择，和 玻璃盒测试 that are chosen with knowledge of the actual implementation. But it’s important to note that 即使玻璃盒测试也必须遵循规格说明. Your implementation may provide stronger guarantees than the specification calls for, or it may have specific behavior where the specification is undefined. But your test cases should not count on that behavior. Test cases must be 正确的，像其他客户端一样遵守合同。

例如，假设你正在测试 find, slightly different from the one we’ve used so far:

find(arr: Array<number>, val: number): number
requires:
val occurs in arr
effects:
returns index i 的集合，使得 arr[i] = val

这个规格说明有一个强前置条件，在某种意义上 val 需要被找到；并且它有一个相当弱的后置条件，在某种意义上，如果 val 在数组中出现不止一次，这个规格说明对 val is returned. Even if you implemented find so that it always returns the lowest index, your test case can’t assume that specific behavior:

let array: Array = [7, 7, 7];
let i = find(array, 7);
assert.strictEqual(i, 0);  // bad test case: assumes too much, more than the postcondition promises
assert.strictEqual(array[i], 7);  // correct

同样，即使你实现了 find 使其（合理地）在 val isn’t found, instead of returning some arbitrary misleading index, your test case can’t assume that behavior, because it can’t call find() 。

So what does glass box testing mean, if it can’t go beyond the spec? It means you are trying to find new test cases that exercise different parts of this particular implementation, but assert the behavior in an implementation-independent way, following the spec.

}

然后我们讨论了 单元测试, the idea that we should write tests of each module of our program in isolation. A good unit test is focused on just a single specification. Our tests will nearly always rely on the specs of JavaScript library functions, but a unit test for one function we’ve written shouldn’t fail if a 不同的 function fails to satisfy its spec. As we saw in the example, a test for extract() shouldn’t fail if load() doesn’t satisfy its postcondition.

好的 集成测试, tests that use a combination of modules, will make sure that our different functions have compatible specifications: callers and implementers of different functions are passing and returning values as the other expects. Integration tests cannot replace systematically-designed unit tests. From the example, if we only ever test extract 通过调用 index，我们只会在其输入空间的潜在小部分上测试它： load. In doing so, we’ve left a place for bugs to hide, ready to jump out when we use extract 在程序的其他地方用于不同目的时，或者当 load 开始返回以新格式编写的文档等时候跳出来。

    }
    return a;
}

We cannot test for behavior when a precondition is violated: for example, we cannot check that a function fails fast as opposed to returning a garbage value on some illegal input, because 所有测试必须遵循规格说明. If the precondition is one that the implementer can reasonably check, then it often makes sense to change the spec: remove the precondition, and instead specify the behavior in the postcondition. We’ll discuss two ways to do that below (异常 和 特殊结果），并在下一次阅读中深入讨论这样的规格说明编写决策。

可变函数的规格说明

我们在早期的阅读中讨论了可变与不可变对象（静态检查). But our specification examples thus far haven’t illustrated how to describe side-effects ——对可变对象或输入/输出状态的更改——在后置条件中。

So here’s a specification that describes a function that mutates an object:

addAll(array1: Array<string>, array2: Array<string>): boolean
requires:
array1 和 array2 不是同一个对象
effects:
修改 array1 通过将 array2 的元素添加到其末尾，并且当且仅当 array1 因调用而更改时返回 true

First, look at the postcondition. It gives two constraints: the first telling us how array1 如何被修改，第二个告诉我们返回值如何确定。

Second, look at the precondition. It tells us that array1 不能与 array2. The behavior of the function if you attempt to add the elements of an array to itself is undefined. You can easily imagine why the implementer of the function would want to impose this constraint: it’s not likely to rule out any useful applications of the function, and it makes it easier to implement. The specification allows a simple implementation in which you take an element from array2 中取一个元素并将其添加到 array1，然后继续处理 array2 的下一个元素，直到到达末尾。

如果 array1 和 array2 are the same array, this simple algorithm will not terminate, as shown in the sequence of snapshot diagrams on the right — or practically speaking it will throw a memory error when the array object has grown so large that it consumes all available memory. Either outcome, infinite loop or crash, is permitted by the specification because of its precondition.

这是另一个可变函数的例子：

sort(array: Array<string>): void
requires:
无
effects:
将 array 按排序顺序排列， 即 array[i] ≤ array[j] for all 0 ≤ i < j < array.length

以及一个不修改其参数的函数的例子：

toLowerCase(array: Array<string>): Array<string>
requires:
无
effects:
返回一个新数组 t，长度与 array相同，其中 t[i] = array[i].toLowerCase()

正如 null 除非另有说明否则被隐含禁止，程序员也假设 除非另有说明否则修改被禁止. The spec of to­Lower­Case 可以明确地将 effect that “array is not modified”, but in the absence of a postcondition describing mutation, we demand no mutation of the inputs.

在 TypeDoc 中编写规格说明时，影响参数的修改可以在相应的 @param 子句中描述：

/**
 * Sorts an array.
 * @param array - mutated into sorted order, so that
 *     array[i] ≤ array[j] for all 0 ≤ i < j < array.length.
 */
function sort(array: Array<string>): void { ... }

异常

Now that we’re writing specifications and thinking about how clients will use our functions, let’s discuss how to handle 例外的 情况，以安全且易于理解的方式。

由于 异常 is a possible output from a function, it may have to be described in the postcondition for the function. An exception can be documented with a @throws 子句 in the documentation comment. This section discusses when to include an exception in a specification, and when not to.

用于信号传递 bug 的异常

You’ve probably already seen some 异常 in your Python or TypeScript programming so far. For example, in Python:

  • IndexError 在数组索引 array[i] 超出数组 array
  • KeyError 在字典查找 dict[key] 找不到匹配的键时抛出
  • TypeError 在各种动态类型错误时抛出，例如在 None

TypeScript 也有 TypeError 用于动态类型错误，但大多数动态错误用通用的 Error 类来信号传递。

这些类型的异常通常表示 bug ——在客户端或实现中——抛出异常时显示的信息可以帮助你找到并修复 bug。

信号传递 bug 的异常不是函数后置条件的一部分，所以它们不应该出现在 @throws. For example, TypeError normally should never be mentioned in a spec. The types of the arguments are part of the precondition, which means that a valid implementation is free to throw TypeError without any warning if those types are violated (for example, if a client manages to pass a null value). So this spec, for example, never mentions TypeError不成立：

/**
 * @param array array of strings to convert to lower case
 * @returns new array t, same length as array, 
 *         where t[i] is array[i] converted to lowercase for all valid indices i
 */
function toLowerCase(array: Array<string>): Array<string>

用于预期失败的异常

Exceptions are not just for signaling bugs. They can be used to signal anticipated sources of failure, in such a way that the caller can catch them and respond to them. Exceptions that signal anticipated failures should be documented with a @throws clause, specifying the conditions under which that failure occurs. For example:

/**
 * Compute the integer square root.
 * @param x integer value to take square root of
 * @returns square root of x
 * @throws NotPerfectSquareError if x is not a perfect square
 */
function integerSquareRoot(x: number): number

And here’s a new version of the addAll 规格说明的新版本：

/**
 * If array1 !== array2, adds the elements of array2 to the end of array1.
 * @returns true if array1 changed as a result
 * @throws AliasingError if array1 === array2
 */
function addAll(array1: Array<string>, array2: Array<string>): boolean

在 原来的 addAll 上面，规格说明包含 array1 !== array2 as a precondition: the behavior of the function was undefined if that requirement was violated. In this version of the spec, the precondition is removed, and instead we have a postcondition that defines the behavior both when the arrays are different objects (“adds the elements…” and the @returns 子句）以及当它们是同一个对象时（ @throws 子句）的行为。

特殊结果

异常是传达调用者不太可能处理的问题的最佳方式，例如因为他们提供了非法输入：调用者或调用他们的人有 bug。

对于调用者 应该 be prepared to handle, different programming languages take different approaches. In the Java language, for example, the implementer can declare exceptions that the caller is statically required to handle: if they don’t either catch the exception or add it to their own specification as a thrown exception, the compiler gives a static error.

TypeScript does not provide static checking for exception handling, so using exceptions for special-case results can be a source of bugs. For example, suppose we use integerSquareRoot 使用从文件获取或用户输入的输入，而我们忽略了 try ... catch 的 NotPerfect­Square­Error. An invalid number will crash the program, when it would be better to produce a clear error message or prompt the user to try again. But TypeScript lacks the static checking of exceptions that would help us see and account for the problem ahead of time.

一个好的替代方案是将函数的返回类型设为 联合类型，其值集合是由两个（或更多）其他类型定义的值集合的并集：

/**
 * Compute the integer square root.
 * @param x integer value to take square root of
 * @returns square root of x if x is a perfect square, undefined otherwise
 */
function integerSquareRoot(x: number): number|undefined

undefined 与 null非常相似：在 JavaScript 中，已声明但未初始化的变量的值为 undefined 而不是 null. Without 严格 null 检查，任何变量都可以是 undefined 或 null. With strict checking on, both are excluded.

按照惯例， null is used to mean “a value that is no value,” and it should be avoided at all times. In contrast, undefined is used to mean “no value here at all,” and as long as strict null checking is on, we can use it in a union type to signal a special case result. In our example, trying to use the updated integerSquareRoot 而不考虑它可能返回 undefined 在许多情况下是静态错误：

let twice = integerSquareRoot(input) * 2; // static error
if (integerSquareRoot(input) > 4) { ... } // static error

……尽管我们仍然必须小心：

console.log('Your lucky number is:', integerSquareRoot(5)); // no error

As a client, how can we use integerSquareRoot() correctly? We need to check for the possibility of the special result. For example:

let root = integerSquareRoot(input); // type of `root` is `number|undefined`
if (root === undefined) {
    // in this branch, TypeScript knows that `root` has type `undefined`
    ... 
} else {
    // in this branch, TypeScript knows that `root` has type `number`
    let twice = root * 2; // now legal
    ...
}

如果特殊结果将指示 bug，那么一个常见的简化方法是直接断言它：

let root = integerSquareRoot(input); // type of `root` is `number|undefined`
assert(root !== undefined);
// if we got past the assertion, TypeScript knows that `root` has type `number`
let twice = root * 2; // now legal

这通常与 空值合并运算符不成立：

let root = integerSquareRoot(input) ?? assert.fail('root is undefined');
// `root` now simply has type `number`
let twice = root * 2; // now legal

缺失 Map 键

如果你有一个 Python 字典，当你尝试查找字典中不存在的键时会发生什么？

zoo = { 'Tim': 'beaver' }
zoo['Tim']     # => 'beaver'
zoo['Bao Bao'] # => raises KeyError: 'Bao Bao'

Python considers this an exception. TypeScript makes a different choice:

const zoo = new Map([['Tim', 'beaver']]);
zoo.get('Tim');     // => 'beaver'
zoo.get('Bao Bao'); // => undefined

在 Python 中，后置条件指定 KeyError. In TypeScript, for a Map 具有类型 V的 Map，后置条件指定返回类型为 V|undefined。

模块

This reading has focused on specifications for functions. But TypeScript/JavaScript and Python (and many other languages) also support modules，它们是函数级别之上的抽象，允许将一组相关函数收集在一起。

（术语 模块作为语言特性的这种特定用法，不幸地与更通用的计算机科学术语 模块冲突，我们 之前讨论过。Python 和 TS/JS 模块确实是通用 CS 意义上的模块，但函数、类、库等其他代码单元也是模块。）

In modern TypeScript/JavaScript, each file is a module. A module can 导出 通过 export. A client of a module must 导入 从模块中导入，要么指定要导入的特定函数，要么简单地导入它希望使用的所有导出函数。

The specification of a module is the combination of its exported function specifications (or constants, or user-defined types). Functions and variables that are not exported are private to the module’s implementation of the module, much like local variables and internal helper functions are private to a function body. They are not part of the specification, because clients cannot access them or depend on them.

Python 模块的工作方式类似，只是 Python 没有显式的 export 声明，而是使用命名约定（以下划线开头的函数和变量被视为实现内部）和 _ 来控制模块名义上导出什么 __all__。

A specification acts as a crucial firewall between the implementer of a module and its client. It makes separate development possible: the client is free to write code that uses the module without seeing its source code, and the implementer is free to write the code that implements the module without knowing how it will be used.

Let’s review how specifications help with the main goals of this course:

  • 远离 bug. A good specification clearly documents the mutual assumptions that a client and implementer rely on. Bugs often come from disagreements at the interfaces, and the presence of a specification helps avoid those disagreements. Using machine-checked language features in your spec, like static typing and exceptions rather than just a human-readable comment, can reduce bugs still more.

  • 易于理解. A short, simple spec is easier to understand than the implementation itself, and saves other people from having to read the code.

  • 适应变化. Specs establish contracts between different parts of your code, allowing those parts to change independently as long as they continue to satisfy the requirements of the contract.
