引言

In the previous readings we’ve developed a rigorous notion of 数据抽象 by creating types that are characterized by their operations, not by their representation. For an abstract data type, the 抽象函数 explains how to interpret a concrete representation value as a value of the abstract type, and we saw how the choice of 抽象函数 determines how to write the code implementing each of the ADT’s operations.

在本次阅读中，我们转向如何定义 相等性 of values in a data type: the 抽象函数 will give us a way to cleanly define the 相等性 operation on an ADT.

Convertibles are overrated

Now suppose we decide that == should automatically convert different types before comparing them. If the righthand side of == has a different type than the lefthand side, then the righthand side converts itself to the type of the lefthand side before testing for 相等性.

So if s is a string and n is an integer, then s == n would be the same as s == str(n), and n == s would be the same as n == int(s). If the conversion fails, the 相等性 test returns false. Thus, for example:

不可变类型的相等性

Now that we have a mathematical foundation 对于所有 相等性 operations, let’s look at 相等性 in the context of abstract data types, starting with immutable types.

Formally, we can define 相等性 on immutable types in two ways.

Using the 抽象函数. Recall that an 抽象函数 AF: R → A maps concrete instances of a data type to their corresponding abstract values. To use AF as a definition for 相等性, we would say that two concrete instances a and b are equal 当且仅当 AF(a) = AF(b).

使用观察. We can say that two objects are equal when they cannot be distinguished by observation – every operation we can apply produces the same result for both objects. Consider the set expressions {1,2} and {2,1}. Using the observer operations available for sets, cardinality |…| and membership ∈, these expressions are indistinguishable:

  • |{1,2}| = 2 and |{2,1}| = 2
  • 1 ∈ {1,2} is true, and 1 ∈ {2,1} is true
  • 2 ∈ {1,2} is true, and 2 ∈ {2,1} is true
  • 3 ∈ {1,2} is false, and 3 ∈ {2,1} is false
  • … and so on

In terms of abstract data types, “observation” means calling operations on the objects. So two objects are equal 当且仅当 they cannot be distinguished by calling any operations of the abstract data type (which for immutable types means any observer or producer operations).

的 two definitions of 相等性 – by 抽象函数, and by observation – should be consistent with each other, or something is wrong.

示例：Duration

Here’s a simple example of an immutable ADT.

class Duration {
    private readonly mins: number;
    private readonly secs: number;
    // 表示不变量：
    //    mins >= 0, secs >= 0
    // 抽象函数：
    //    AF(mins, secs) = the span of time equal to `mins` minutes plus `secs` seconds

    /** Make a duration lasting for m minutes and s seconds. */
    public constructor(m: number, s: number) {
        this.mins = m;
        this.secs = s;
    }
    /** @returns length of this duration in seconds */
    public get length(): number {
        return this.mins*60 + this.secs;
    }
}

引用相等与值相等

Many languages have two different operations for testing 相等性 between objects, with different semantics.

  • reference 相等性 tests whether two references point to the same storage in memory. In terms of the snapshot diagrams we’ve been drawing, two references are equal by reference 相等性 if their arrows point to the same object bubble.
  • value 相等性 tests whether two objects represent the same value – in other words, the sense we’ve been talking about in this reading.

的 == operator unfortunately flips its meaning between Python and most other languages.

TypeScript and JavaScript use triple-equals ===, the strict 相等性 operator. 的 double-equals == operator also exists in these languages, but it does a variety of automatic type conversions that make it difficult to use safely as an 相等性 operator. 的 automatic type conversions mean that the == is sometimes a reference-相等性 operation, and sometimes a value-相等性 operation on converted values. It isn’t even an 等价关系! (We saw why in the exercise above.) 的 == is not safe from bugs or easy to understand, so modern TS/JS programmers strenuously avoid it.

Note also that this table is only about 相等性 for object types, like we use to define a new ADT. Built-in primitive types, like number or string in TypeScript, follow different rules. For primitives like string in TypeScript, the === operator does value 相等性, and there is no notion of reference 相等性 at all.

For immutable object types, the reference-相等性 === operation is generally not the right 相等性 operation. And TypeScript and JavaScript unfortunately have no built-in 操作，用于 value 相等性 on object types, unlike the other languages. But when we define a new data type, value 相等性 is a useful operation, so it makes sense to introduce it as a method. Our convention will be to name the method equalValue():

/** Some immutable type T. */
class T {
    ...

    /**
     * @param that  value to compare `this` with
     * @returns true iff this and that represent the same abstract value.
     *    Must be an 等价关系 (自反性, 对称性, and 传递性).
     */
    public equalValue(that: T): boolean;
}

It’s our responsibility to decide what value 相等性 means for values of the data type, and implement equalValue() appropriately. Here’s the equalValue() 操作，用于 Duration:

class Duration {
    ...   
    public equalValue(that: Duration): boolean {
        return this.length === that.length;
    }
}

Breaking the 等价关系

We have to make sure that the definition of 相等性 implemented by equalValue() is actually an 等价关系 as defined earlier: 自反性, 对称性, and 传递性. If it isn’t, then other operations that depend on equalValue() (like searching through an array) will behave erratically and unpredictably. You don’t want to program with a data type in which sometimes a equals b, but b doesn’t equal a. Subtle and painful bugs will result.

Here’s an example of how an innocent attempt to make 相等性 more flexible can go wrong. Suppose we wanted to allow for a tolerance in comparing Duration objects, because different computers may have slightly unsynchronized clocks:

private static readonly CLOCK_SKEW: number = 5; // seconds

// returns true iff this and that represent the same abstract value within a clock-skew tolerance
public equalValue(that: Duration): boolean {
    return Math.abs(this.length - that.length) <= Duration.CLOCK_SKEW;
}

可变类型的相等性

We’ve been focusing on 相等性 of immutable objects so far in this reading. What about mutable objects?

Equality must still be an 等价关系.

We also want 相等性 to respect the 抽象函数 and respect observer operations. But with mutable objects, there is a new possibility: by calling a 修改器 on one of the objects before doing the observation, we may change its state and thus create an observable difference between the two objects.

So let’s refine our definition and allow for two notions of 相等性 based on observation:

  • observational 相等性 means that two references cannot be distinguished now, in the current state of the program. A client can try to distinguish them only by calling operations that don’t change the state of either object (i.e. only observers and producers, not 修改器s) and comparing the results of those operations. This tests whether the two references “look” the same for the current state of the objects.
  • behavioral 相等性 means that two references cannot be distinguished now or in the future, even if a 修改器 is called on one reference but not the other. This tests whether the two references will “behave” the same, in this and all future states.

For immutable types, observational and behavioral 相等性 are identical, because there aren’t any 修改器 methods that can change the state of the objects. So we only need one kind of 相等性 – which for immutable object types is the equalValue() operation that we have already defined, and for immutable primitive types (like string and number) is ===.

For mutable types, it is useful to have both kinds of 相等性 available as operations. 的 === operator provides behavioral 相等性, and we can use the equalValue() 操作，用于 observational 相等性:

/**
 * Some mutable type T.
 * Use === to compare elements of type T for behavioral 相等性.
 */
class T {
    ...

    /**
     * @param that  value to compare `this` with
     * @returns true iff this and that are observationally equivalent.
     *    Must be an 等价关系 (自反性, 对称性, and 传递性).
     */
    public equalValue(that: T): boolean;

}

“Deep 相等性” on collections

One thing unfortunately missing from TypeScript/JavaScript is a standard 操作，用于 observational 相等性 on the built-in collection types, Array, Set, and Map（映射）. 例如：

const arr1: Array<number> = [1, 2, 3];
const arr2: Array<number> = [1, 2, 3];

const set1: Set<string> = new Set(["a", "b"]);
const set2: Set<string> = new Set(["b", "a"]);

Since Array and Set are mutable, === implements behavioral 相等性 as expected. In this case, arr1 !== arr2 and set1 !== set2, because each points to a different mutable object in memory.

But there is no standard operator for observational 相等性, comparable to the equalValue() operation we introduced in the previous section. 的re is no built-in way to tell that arr1 and arr2 currently represent the same sequence of elements, and likewise that set1 and set2 represent the same set of elements.

Some libraries have tried to rectify this omission by providing a “deep 相等性” operation, defined not only on collections like Array and Set but on a wide variety of object types:

  • assert.deepStrictEqual() in the Node library
  • isEqual() in Underscore.js and its successor Lodash

的se operations are “deep” in the sense that they can unravel multiple levels of collections. For example, two values of type Array<Map（映射）<T,Set<U>>> can be compared for observational 相等性.

But these deep 相等性 operations must be used with great care. 的 spec for assert.deepStrictEqual() has special treatment for built-in collections like Map（映射） and Set – for example, ignoring the order of elements – so that it can correctly compare the abstract values of these collections. But for other object types, these deep 相等性 operations blindly compare the rep, field by field, without any knowledge at all of the 抽象函数 that governs how the rep should be interpreted.

Deep 相等性 can be safe to use when the leaf types of the collections are primitive types like number, string, and boolean – e.g. Array<Map（映射）<string,Set<number>>>. But when the leaf types are user-defined object types, like the types Duration and Bag we have used in this reading, then the behavior of deep 相等性 may be unexpected and undesirable.

哈希函数

In most languages (including TypeScript and Python), the Set and Map（映射） types are implemented using a hash table, which supports fast lookup of set elements or map keys. A hash table requires the set element type or map key type to offer a hash function operation, which converts the object value into an integer.

This section discusses the interactions between hash functions and 相等性. Because TypeScript does not allow implementing the hash function yourself, we will use Python in this section.

In Python, the 相等性 操作，用于 object types is __eq__(..), much as we have defined equalValue() for TypeScript. And the hash function operation is __hash__():

def __hash__(self):
    '''
    Called by built-in function hash() and for operations on members of hashed
    collections including set, frozenset, and dict. __hash__() should return an
    integer. 的 only required property is that objects which compare equal
    have the same hash value.
    '''

To understand why __hash__ needs to be compatible with __eq__, you’ll need to have some idea of how hash tables work. Python sets and dictionaries use a hash table data structure, and depend on the __hash__ method to be implemented correctly for the objects stored in the set and used as keys in the dictionary.

A hash table is a representation for a mapping: an abstract data type that maps keys to values. Hash tables offer constant time lookup, so they tend to perform better than trees or lists. Keys don’t have to be ordered, or have any particular property, except for offering 相等性 and hashing operations.

Here’s how a hash table works. It contains an array that is initialized to a size corresponding to the number of elements that we expect to be inserted. When a key and a value are presented for insertion, we compute the hash code of the key, and convert it into an index in the array’s range (e.g., by a modulo division). 的 value is then inserted at that index.

的 rep invariant of a hash table includes the fundamental constraint that a key can be found by starting from the array slot determined by its hash code.

Hash codes are designed so that the keys will be spread evenly over the indices. But occasionally a conflict occurs, and two keys are placed at the same index. So rather than holding a single value at an index, a hash table typically holds a list of key/value pairs, called a hash bucket. On insertion, you add a key/value pair to the list in the array slot determined by the hash code. For lookup, you hash the key, find the right array slot, and then examine each of the pairs until one is found whose key equals the query key.

Now it should be clear why the __hash__ spec requires equal objects to have the same hash code. If two equal objects had distinct hash codes, they might be placed in different array slots. So if you attempt to lookup a value using a key equal to the one with which it was inserted, the lookup may fail.

A simple and drastic way to ensure that the contract is met is for __hash__ to always return some constant value, so every object’s hash code is the same. This satisfies the specification, but it would have a disastrous performance effect, since every key will be stored in the same slot, and every lookup will degenerate to a linear search along a long list.

的 standard way to construct a more reasonable hash code that still satisfies the contract is to compute a hash code for each component of the object that is used in the determination of 相等性 (in Python by using hash()), and then combining these, throwing in a few arithmetic operations.

(In the context of Java, where this operation is named hashCode, Josh Bloch’s book Effective Java explains this issue in more detail, and gives some strategies for writing decent hash code functions. 的 advice is summarized in a good StackOverflow post.)

Note, however, that as long as you satisfy the requirement that equal objects have the same hash code value, then the particular hashing technique you use doesn’t make a difference to the correctness of your code. It may affect its performance, by creating unnecessary collisions between different objects, but even a poorly-performing hash function is better than one that breaks the contract.

In a language like Python or Java where you can implement your own hashing and 相等性 operations:

Always implement hashing consistent with 相等性.

Breaking a hash table’s rep invariant

Now let’s look at another kind of bug that arises with hash functions for mutable types.

Python’s __eq__() implements observational 相等性, and the hash function must be consistent with that. So two different list objects with the same elements, like [0,1] and [0,1], are equal to each other, and have the same hash value.

But the possibility of mutation means that 相等性 isn’t consistent over time. Two objects that are observationally equal (or unequal) at one moment in the program may stop being equal (or unequal) after a 可变性。 Because the hash function must be consistent with the 相等性 operation, this means that the hash function also changes over time. This fact allows us to inadvertently break the rep invariants of collection data structures that depend on hashing.

Let’s imagine that Python did provide a hash function for lists, so that we could put a list into a set. Here is what could happen:

>>> l1 = ['a','b']
>>> l2 = ['a']
>>> s = { l1, l2 }    # not actually legal, but suppose Python did allow it...
>>> s
{ ['a','b'], ['a'] }

Now we mutate one of the lists, and look at the set again:

>>> l2.append('b')
>>> s
{ ['a','b'], ['a','b'] }

We’ve clearly broken something, because a set is not supposed to have any duplicate elements, but this set now has two identical lists in it. But it gets worse. Let’s try to remove one of them:

>>> s.remove(l1)
>>> s
{ ['a','b'] }

OK, good. Can we remove the other?

>>> s.remove(l2)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
KeyError: ['a','b']

KeyError? 的 set can’t find l2 anymore! What’s going on?

Lists are mutable. In Python, the 相等性 operation __eq__ implements observational 相等性, and our hypothetical list hash function __hash__() needs to be consistent with that. When l2 is first put into the set, it is stored in the hash bucket corresponding to its __hash__() result for the value it has at that time (['a']). When the list is subsequently mutated to ['a','b'], its __hash__() value likely changes (because it must be consistent with __eq__(), which also changes), but the set doesn’t realize it should be moved to a different bucket. So the list is now hiding in the wrong hash bucket. It can be seen when iterating through all the elements in the set (which is what happens when you print the set), but it can’t be specifically located to remove it, because the set will look for it in the wrong hash bucket.

When 相等性 and hashing can be affected by mutation, we can break the rep invariant of a hash table that uses that object as a key. 的 rep invariant requires that every key be found in the hash bucket associated with its __hash__() value. If the value of __hash__() for an object can be changed by mutating the object, then we can break this invariant.

This example has been a hallucination to illustrate why, for mutable types like lists, Python forbids implementing __hash__:

If a class defines mutable objects and implements an __eq__() method, it should not implement __hash__(), since the implementation of hashable collections requires that a key’s hash value is immutable (if the object’s hash value changes, it will be in the wrong hash bucket).

Python needs this requirement because __eq__() implements observational 相等性, which may change over time for mutable types; but __hash__() cannot change over time, or the hash table breaks.

Always use behavioral 相等性 for hashing, so that hash values do not change over time.

Since observational and behavioral 相等性 are identical for immutable types, Python can only hash immutable types.

Hashing in TypeScript/JavaScript

In TypeScript and JavaScript, the hash function is built-in and cannot (currently) be overridden for user-defined types. 的 predefined hash functions are designed to be consistent with ===, so any type that uses === for behavioral 相等性 is safe for use as a Set element or Map（映射） key. So Set elements and Map（映射） keys can be immutable built-in types (like number or string) or mutable object types (using reference 相等性). 的se types have a built-in hash function that is consistent with ===.

But unfortunately we cannot easily use immutable object types as Set elements or Map（映射） keys in TypeScript because Set and Map（映射） don’t give us any way to define our own 相等性 operation or hash function for an immutable type (and remember that === does the wrong thing for immutable types).

One approach to this problem is interning, a 设计模式 that creates exactly one object instance of the immutable type for each abstract value that the program uses, and reuses that instance any time the same value is used again. When exactly one object for each abstract value exists, then observational 相等性 becomes the same as reference 相等性; the object hash function (which uses reference 相等性) can be used to correctly hash and identify the object in a Set or Map（映射）. Using the interning pattern requires keeping a cache of all the objects of the type that have been created, and a factory function that first consults the cache before creating a new instance of the object.

Another approach is to define a canonical primitive-type representation for every value of the type. For example, a Date object can be effectively used as a map key by converting it to a timestamp number or a standardized string format.

Another approach is to use a third-party library that implements maps and sets with user-defined 相等性 and hashing, such as collections.js or Immutable.

总结

  • Equality should be an 等价关系 (自反性, 对称性, 传递性).
  • 的 抽象函数 is the basis for 相等性 in immutable data types.
  • Mutable data types have two useful notions of 相等性: behavioral 相等性 (which provides consistent 相等性 over time) and observational 相等性 (which uses the 抽象函数). For immutable types, observational and behavioral 相等性 are identical.

In TypeScript, for immutable built-in types (e.g. number, string, bigint):

  • Use === for behavioral and observational 相等性, which are identical because there are no 修改器s.
  • Avoid == because of its automatic conversions.
  • Safe for use as Set elements and Map（映射） keys.

For immutable object types (e.g. Duration):

  • Use equalValue() for both behavioral and observational 相等性, which are identical because there are no 修改器s.
  • Avoid === because it is too strong, and avoid == because of its automatic conversions.
  • Not safe for use as Set elements or Map（映射） keys because those data structures compare objects using ===.

For mutable object types:

  • Use === for behavioral 相等性.
  • Use equalValue() for observational 相等性.
  • Avoid == because of its automatic conversions.
  • Safe for use as Set elements and Map（映射） keys.

Equality is one part of implementing an abstract data type, and we’ve already seen how important ADTs are to achieving our three primary objectives. Let’s look at 相等性 in particular:

  • 免受 bug 侵害. Correct implementation of 相等性 is essential for clients of a data type, and also highly desirable for writing tests.

  • 易于理解. Clients and other programmers who read our specs will expect our types to implement an appropriate 相等性 operation, and will be surprised and confused if we do not.

  • 适应变化. Correctly-implemented 相等性 for immutable types separates 相等性 of reference from 相等性 of abstract value, hiding from clients our decisions about whether values are shared.
