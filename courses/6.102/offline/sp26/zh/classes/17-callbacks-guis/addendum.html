Promise 与事件循环

我们从本阅读中对事件循环的当前理解是牢固的。 就本课程的目的而言，这就是你需要了解的关于 JavaScript 运行时系统如何实际运行代码和异步回调的知识。 对于那些好奇的人来说，事实证明，这一切是如何工作的还有一些额外的细节，可能会产生与我们当前理解不一致的结果。

例如，考虑这段代码：

/** Wait for `milliseconds` to pass before returning. */
function busyWait(milliseconds: number): void {
    const now = new Date().getTime(); // new Date().getTime() is always the current clock time in milliseconds
    const deadline = now + milliseconds;
    while (new Date().getTime() < deadline) {
        // do nothing, just wait until the clock reaches the deadline time
    }
}

let { promise, resolve, reject } = Promise.withResolvers();

setTimeout(() => {
  console.log("timer expired");
}, 0);

promise.then((result) => {
  console.log(result);
});

busyWait(5000);

resolve("promise resolved");

console.log("End of the code");

你期望控制台打印什么？先猜一试，然后自己试试看！你可以在自己的机器上运行代码，也可以在这里运行。

有趣！如果只有一个事件队列，我们期望传递给 setTimeout 的回调会在传递给 promise 的回调之前被添加到事件队列中，特别是因为我们在 resolve promise 之前忙等待了 5 秒。 那么为什么我们没有看到 timer expired 在 promise resolved 之前打印呢？ 原来 promise 回调实际上不会被添加到主 JavaScript 事件队列中。它们被添加到另一个队列中，称为微任务队列（microtask queue）。

微任务队列就像主事件队列（也称为任务队列或宏任务队列）一样是另一个包含要运行的回调的队列。 然而，这些微任务比任务队列具有更高的优先级：

任务队列和微任务队列之间的区别很简单但非常重要：

  • 当事件循环的新迭代开始时，运行时执行任务队列中的下一个任务。在迭代开始后添加的进一步任务和队列中的任务将不会运行，直到下一次迭代。
  • 每当一个任务退出且执行上下文栈为空时，微任务队列中的所有微任务都会依次执行。不同之处在于，微任务的执行会持续到队列为空——即使在中间调度了新的微任务。换句话说，微任务可以入队新的微任务，这些新的微任务将在下一个任务开始运行之前执行，以及在当前事件循环迭代结束之前执行。

这澄清了上面的不一致之处。 setTimeout 回调在定时器完成时（0 秒后，即立即）被添加到任务队列中。 与此同时，promise.then() 回调在调用 resolve() 时被添加到微任务队列中。 当当前执行上下文栈为空时——即当你到达代码末尾并在控制台打印 End of the code 时——微任务队列上的 promise 回调先运行并打印 promise resolved，然后微任务队列被耗尽。 最后，我们从任务队列中取出 setTimeout 回调并运行它。

就像我们可以使用 setTimeout 手动调度任务到任务队列一样，我们可以使用 queueMicrotask() 在微任务队列上调度微任务。 然而，通常你不需要使用 queueMicrotask。此外，由于微任务队列在事件循环的下一次迭代之前会被完全排空，我们必须小心，如果我们的微任务曾经入了其他微任务，因为这种递归模式可能会使事件循环饥饿。

动画

作为另一个例子，我们来看看在动画中使用微任务与宏任务会发生什么。 下面的动画使用 requestAnimationFrame 来移动容器中的球并改变其颜色。 传递给 requestAnimationFrame 的回调函数在浏览器执行下一次重绘之前被调用一次。 这段动画的代码可以在本网页 <head> 中的 <script> 标签中找到，所以你可以自由地使用开发者工具来参考它。 我们传递给 requestAnimationFrame 的回调函数改变球的位置：

function animateMacrotask() {
    [currentLeftMacrotask, deltaLeftMacrotask] = updatePosition(currentLeftMacrotask, deltaLeftMacrotask);
    [currentTopMacrotask, deltaTopMacrotask] = updatePosition(currentTopMacrotask, deltaTopMacrotask);
    ballMacrotask.style.left = `${currentLeftMacrotask}%`;
    ballMacrotask.style.top = `${currentTopMacrotask}%`;
    requestIdMacrotask = requestAnimationFrame(animateMacrotask);
}

典型的动画会在点击控制按钮后立即开始移动球。 为了引入更长的延迟，这个示例模拟了必须发出异步请求才能完成按钮操作的效果（例如，在处理用户输入时必须接收网络响应或必须读取文件）。 为了模拟这一点，我们将要执行的操作（例如朝上、朝左等）存储为要执行的微任务和宏任务。当你按下"开始"时，它将把所有这些微任务和宏任务入队，由事件循环执行。 我们预填充了在点击开始按钮时要运行的微任务和宏任务列表：

for (let i = 0; i < 10000; i++) {
    microtasks.push(faceLeftMicrotask, faceRightMicrotask, faceUpMicrotask, faceDownMicrotask);
    macrotasks.push(faceLeftMacrotask, faceRightMacrotask, faceUpMacrotask, faceDownMacrotask);
}

累积的微任务和宏任务在处理方式上的唯一区别是在点击开始按钮时：

startButton.addEventListener('click', () => {
    resetAnimation();
    // delay to let repaint occur and update ball position
    setTimeout(() => {
        microtasks.forEach((task) => queueMicrotask(task));
        macrotasks.forEach((task) => setTimeout(task, 0));
    }, 200);
});

代码分别使用 queueMicrotask 和 setTimeout，但有多种方式可以实现这一点。 左边的框显示了将任务作为微任务入队所产生的动画，右边的框显示了将任务作为宏任务入队所产生的动画。

Macrotasks

为什么两个球没有回到相同的位置？微任务在下一次重绘之前被全部批量处理，但宏任务不一定在下一次重绘之前被批量处理。 渲染回调不是任务队列上的宏任务，它们的处理方式不同。 HTML 规范包含一个关于处理模型的章节，描述了动画帧回调如何与宏任务和微任务交互。

在从任务队列中处理完每个宏任务后，渲染可以被更新，这会导致重绘并调用所有动画帧回调。 浏览器运行时可能决定不更新渲染，程序员对此没有直接控制权。由于微任务具有更高的优先级，它们会在下一次重绘发生之前全部被处理。 宏任务可以与动画帧回调交错执行，这导致了动画中的差异。 由于浏览器有决定何时更新渲染的自由度，宏任务动画是不确定的。

然而，微任务通常不需要被程序员显式地使用或考虑。当需要对事件顺序进行细粒度控制时，它们可能非常有用，但否则它们可以留在程序员的脑海深处。

Node 中的事件循环

Node 中的事件循环稍微复杂一些。Node 将事件循环分成不同的阶段，比如一个处理来自 I/O 操作的回调的阶段。 每个阶段都有自己的队列，每个队列在移动到下一个队列之前会被耗尽（或达到回调限制）。

微任务在哪里介入？微任务队列仍然存在，并在每个阶段中的每个操作完成后被排空。 所以现在，我们可以将 Node 视为具有多个任务（也称为宏任务）队列，每个阶段一个，在移动到下一个任务队列之前被排空。 微任务队列的工作方式与之前相同，具有比所有其他任务队列更高的优先级，这样在任务队列中的每个任务之后，微任务队列都会被完全排空。

nextTick 队列

Node 中另一个不同的队列是nextTick 队列，可以认为它具有与微任务队列相同的优先级；在从事件循环的某个阶段的任务队列中取出任何任务之前，两个队列都会被完全排空，并且 nextTick 队列会先被处理。 与 queueMicrotask 一样，我们可以使用 process.nextTick() 向 nextTick 队列添加事件。

有趣的事实：Node 在内部使用开源的 V8 JavaScript 引擎，该引擎也被 Chrome 和其他浏览器使用。 Node 中的微任务队列由 V8 管理，但 nextTick 队列独立于 V8，完全由 Node 管理。

微任务队列和 nextTick 队列具有非常相似的语义，以至于Node 通常推荐使用 queueMicrotask 而不是 process.nextTick。

总结

总结一下：

  • JavaScript 事件循环有一个宏任务队列和一个微任务队列
  • 微任务队列在每个宏任务从其队列中被取出之前以及下一次浏览器重绘之前被完全排空
    • 宏任务可以与浏览器重绘和 requestAnimationFrame 回调交错执行
  • Promise 回调被添加到微任务队列
  • Node 对事件循环的不同阶段有不同的宏任务队列，以及一个与微任务队列具有相同优先级的 nextTick 队列
  • queueMicrotask 可以用于在微任务队列上调度回调，同样，process.nextTick 用于 nextTick 队列。
    • 这些通常不需要被使用，除非需要对事件顺序进行细粒度控制。
