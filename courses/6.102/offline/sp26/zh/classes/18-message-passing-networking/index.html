学习目标

阅读完本讲笔记并检查代码后，你应该能够使用消息传递（而非共享内存）在 TypeScript worker 之间进行通信，并理解客户端/服务器通信如何通过网络进行消息传递。

网络通信本质上是并发的，因此构建客户端和服务器需要我们推理它们的并发行为，并以线程安全的方式来实现它们。 我们还必须设计客户端和服务器用来通信的协议，就像我们设计 ADT 客户端用来操作它的操作一样。

两种并发模型

在并发简介中，我们看到了两种并发编程模型：共享内存和消息传递。

  • 在共享内存模型中，并发模块通过读写共享可变对象进行交互。 在单个进程内创建多个线程是我们共享内存并发的主要示例。 由于 TypeScript 没有创建线程的 API，我们的许多代码示例使用文件系统作为共享可变状态。

  • 在消息传递模型中，并发模块通过在通信通道上互相发送不可变消息来进行交互。 该通信通道可以连接网络上的不同计算机，如我们的一些初始示例：网页浏览、即时通讯等。

消息传递模型相比共享内存模型有几个优势，归结为更高的 Bug 安全性。 在消息传递中，并发模块显式地交互——通过通信通道传递消息，而不是隐式地通过共享数据的变更。 共享内存的隐式交互太容易导致无意的交互——在不知道自己是并发程序且未正确配合并发安全策略的程序部分中共享和操作数据。 消息传递还只在模块之间共享不可变对象（消息），而共享内存要求共享可变对象，即使在非并发编程中，可变对象也可能是Bug 的来源。

我们将在本阅读中讨论如何在两种上下文中实现消息传递：

  • 在同一进程中运行的 TypeScript worker 之间
  • 在不同机器上运行的进程之间，通过网络通信

对于 TypeScript worker 之间的消息传递，我们将使用通道抽象来发送和接收消息，并使用回调函数来接收消息。

对于网络上的消息传递，我们将使用通过 HTTP 通信的客户端和服务器。

Worker 之间的消息传递

让我们首先看看 TypeScript worker 之间的消息传递。 我们将关注 Node 的 Worker 接口（可在 worker_threads 包中找到）。 Worker 的浏览器版本（称为 Web Workers）在细节上略有不同，但消息传递的基本操作在该上下文中也存在。

创建 worker 时，它会带有一个双向通信通道，通道的两端称为消息端口。 通道的一端可由创建 worker 的代码访问，使用 Worker 对象上的 postMessage 操作：

import { Worker } from 'worker_threads';

const worker = new Worker('./hello.js');
worker.postMessage('hello!'); // 向 worker 发送消息

通道的另一端可由 worker 访问，作为 worker_threads 模块中的全局对象 parentPort：

// hello.ts
import { parentPort } from 'worker_threads';

parentPort.postMessage('bonjour!'); // 向父级发送消息

这些示例发送简单字符串作为消息，双方实际上还没有接收消息。 让我们逐一解决这些问题。

消息类型

消息端口通常可以承载多种类型，包括数组、映射、集合和记录类型。 然而，一个重要的限制是它们不能是用户自定义类的实例，因为方法代码不会通过通道传递。

一个常见的模式是使用记录类型来表示消息，例如本阅读主要代码示例中的这条消息，表示从冰箱中取放饮料的结果：

type FridgeResult = {
  drinksTakenOrAdded: number,
  drinksLeftInFridge: number
};

当可能需要通过通道发送不同种类的消息时，我们可以使用可辨识联合将它们组合在一起。 可辨识联合是共享用于区分的字符串或数字字面量的对象类型的联合。例如：

type DepositRequest =  { name: 'deposit', amount: number };
type WithdrawRequest = { name: 'withdrawal', amount: number };
type BalanceRequest =  { name: 'balance' };
type BankRequest = DepositRequest | WithdrawRequest | BalanceRequest;

这里，name 字段是一个字面量类型，用于区分我们可以向银行发出的三种不同类型的请求，每个对象类型的其他字段可能根据每种请求类型所需的信息而有所不同。

接收消息

要从消息端口接收传入消息，我们提供一个事件监听器：一个在消息到达时将被调用的函数。 例如，以下是 worker 侦听来自其父级消息的方式：

import { parentPort } from 'worker_threads';

parentPort.on('message', (greeting: string) => {
  console.log('received a message', greeting);
});

当父级调用 worker.postMessage('hello!') 时，worker 会将此消息作为对匿名函数的调用接收，其中 greeting 设置为 "hello!"。

TypeScript 消息传递示例

这是一个表示冰箱的消息传递模块：

 * 一个表示装有饮料的冰箱的可变类型。

class DrinksFridge {

    //   AF(drinksInFridge, port) = 一个装有 `drinksInFridge` 瓶饮料的冰箱
    //                              从 `port` 接收请求并向 `port` 发送回复
    // 表示不变量：
    //   drinksInFridge >= 0

    /**
     * 创建一个 DrinksFridge，它将监听请求并生成回复。
     *
     * @param port 用于接收请求和发送回复的端口
     */
    public constructor(
        private readonly port: MessagePort

        this.checkRep();

    ...

冰箱有一个 start 方法，开始监听传入消息，并将其转发给处理方法：

drinksfridge.ts 
/** 开始处理饮料请求。 */
public start(): void {
    this.port.on('message', (n: number) => {
        const reply: FridgeResult = this.handleDrinkRequest(n);
        this.port.postMessage(reply);
    });
}

传入消息是整数，表示要从冰箱中取出的饮料数量（如果整数为正）或放入冰箱的饮料数量（如果为负）：

drinksfridge.ts 
/** @param n 从冰箱请求的饮料数量（>0），或要放入冰箱的数量（<0） */
private handleDrinkRequest(n: number): FridgeResult {
    const change = Math.min(n, this.drinksInFridge);
    this.drinksInFridge -= change;
    this.checkRep();
    return { drinksTakenOrAdded: change, drinksLeftInFridge: this.drinksInFridge };
}

传出消息是 FridgeResult 的实例，一个简单的记录类型：

drinksfridge.ts 
/** DrinksFridge 回复消息的记录类型。 */
type FridgeResult = {
    drinksTakenOrAdded: number, // 从冰箱取出的饮料数量（>0）或放入冰箱的数量（<0）
    drinksLeftInFridge: number
};

停止

如果我们想关闭 DrinksFridge，使其不再等待新输入，该怎么办？ 一种策略是毒丸消息：一种特殊消息，通知该消息的消费者结束其工作。

要关闭冰箱，由于其输入消息仅为整数，我们必须选择一个魔法毒丸整数（也许永远不会有人要 0 瓶饮料……？坏主意，不要使用魔法数字）或使用 null（坏主意，不要使用 null）。 相反，我们可以将输入消息的类型更改为可辨识联合：

type FridgeRequest = DrinkRequest | StopRequest;
type DrinkRequest = { name: 'drink', drinksRequested: number };
type StopRequest =  { name: 'stop' };

当我们想停止冰箱时，发送一个 StopRequest，即 fridge.postMessage({ name:'stop' })。

当 DrinksFridge 收到此停止消息时，它需要停止监听传入消息。 这要求我们跟踪监听器回调，以便稍后可以移除它。

竞态条件

在之前的阅读中，我们在银行账户示例中看到，消息传递并不能消除竞态条件的可能性。 并发的消息传递进程仍然可能以不好的方式交错它们的工作。

当客户端必须向模块发送多条消息才能完成其所需操作时，这种情况尤其会发生，因为这些消息（以及客户端对它们响应的处理）可能与其他客户端发送的消息交错。 DrinksFridge 的消息协议经过精心设计来管理部分这种交错，但仍然存在竞态条件可能出现的情况。 下一个练习探讨了这个问题。

客户端/服务器设计模式

现在让我们关注另一种重要的消息传递：用于网络通信的客户端/服务器设计模式。

在这种模式中，有两种类型的进程：客户端和服务器。 客户端通过连接服务器来发起通信。 客户端向服务器发送请求，服务器发回回复。 最后，客户端断开连接。 服务器可能同时处理来自许多客户端的连接，客户端也可能连接到多个服务器。

许多互联网应用程序都是这样工作的：网页浏览器是网页服务器的客户端，像 Outlook 这样的电子邮件程序是邮件服务器的客户端，等等。

在互联网上，客户端和服务器进程通常运行在不同的机器上，仅通过网络连接，但不一定非得如此——服务器可以是与客户端运行在同一台机器上的进程。

网络基础

我们从一些与网络通信相关的重要概念开始。

IP 地址

网络接口由 IP 地址 标识。 IPv4 地址是 32 位数字，写成四个 8 位部分。 例如（截至本文撰写时）：

  • 18.9.22.69 是 MIT 网页服务器的 IP 地址。

  • 173.194.193.99 是 Google 网页服务器的地址。

  • 104.47.42.36 是 Microsoft Outlook 邮件处理器的地址。

  • 127.0.0.1 是 回环或 本地主机地址：它总是指向本地机器。 从技术上讲，任何第一个八位字节为 127 的地址都是回环地址，但 127.0.0.1 是标准。

你可以向 Google 查询你当前的 IP 地址。 通常，当你携带笔记本电脑四处走动时，每次将机器连接到网络都可能被分配一个新的 IP 地址。

主机名

主机名是可以翻译为 IP 地址的名称。 一个主机名可以在不同时间映射到不同的 IP 地址；多个主机名可以映射到相同的 IP 地址。 例如：

  • web.mit.edu 是 MIT 网页服务器的名称。 你可以使用命令行上的 dig、host 或 nslookup 自行将此名称翻译为 IP 地址，例如：

    $ dig +short web.mit.edu
18.9.22.69

  • google.com 是 Google 的名称。 尝试使用上述命令之一查找 google.com 的 IP 地址。 你看到了什么？

  • mit-edu.mail.protection.outlook.com 是 MIT 入站邮件处理器的名称，一个由 Microsoft 托管的垃圾邮件过滤系统。

  • localhost 是 127.0.0.1 的名称。 当你想与运行在自己机器上的服务器通信时，与 localhost 通信。

将主机名翻译为 IP 地址是 域名系统 (DNS) 的工作。 这非常酷，但不是我们今天讨论的一部分。

端口号

一台机器可能运行着多个客户端希望连接的服务器应用程序，所以我们需要一种方式将同一网络接口上的流量引导到不同的进程。

网络接口有多个由 16 位数字标识的 端口。 端口 0 被保留，因此端口号实际上从 1 到 65535（即 216 - 1，最大的 16 位数）。

当服务器进程绑定到特定端口时，它就开始监听该端口。 一个端口同一时间只能有一个监听器，因此如果其他服务器进程尝试监听同一端口，它将会失败。

客户端必须知道服务器正在监听哪个端口号。 有一些为系统级进程保留的知名端口，它们为某些服务提供标准端口。 例如：

  • 端口 22 是标准 SSH 端口。 当你使用 SSH 连接到 athena.dialup.mit.edu 时，软件会自动使用端口 22。
  • 端口 25 是标准邮件服务器端口。
  • 端口 80 是标准网页服务器端口。 当你在网页浏览器中连接到 URL http://web.mit.edu 时，它会连接到 18.9.22.69 的端口 80。
  • 端口 443 是标准安全网页服务器端口，当你使用 https 而非 http 时。 当你连接到 https://web.mit.edu 时，它改为连接端口 443。

当端口不是标准端口时，它作为地址的一部分指定。 例如，URL http://128.2.39.10:9000 指的是 128.2.39.10 机器上的端口 9000。

Web API

当网页客户端和网页服务器建立网络连接时，它们通过该连接来回传递什么？ 与通过消息端口在 worker 之间发送的内存对象不同，网络连接以低级字节序列发送和接收请求和回复。 我们不会选择或设计消息的抽象数据类型，而是选择或设计一个Web API（应用程序编程接口）。

超文本传输协议 (HTTP) 是万维网的语言。 我们已经知道端口 80 是向网页服务器说 HTTP 的知名端口，所以让我们使用 curl 程序在命令行上与一些服务器通信。（curl 很可能已经在你的机器上了；Windows、MacOS 和大多数 Linux 发行版默认包含它。）

路由

网页服务器通常将其提供的网站分成多个部分，称为路由。 例如，web.mit.edu 的服务器可能有以下路由：

  • /education（可通过 URL http://web.mit.edu/education 访问）
  • /research
  • /campus-life

等等。

在 Web API 中，路由通常定义请求的函数名。 例如，美国国家气象局 API 定义了以下路由：

  • https://api.weather.gov/points/... 获取与经纬度点相关的信息
  • https://api.weather.gov/gridpoints/... 获取特定区域的天气预报
  • https://api.weather.gov/alerts/active... 获取特定区域的天气预警消息

参数

要将调用 Web API 想象为调用函数，我们需要理解如何向其传递参数，以及如何获取结果。

有三种提供参数的方式。

路径组件。URL 的路径由 / 分隔的组件组成。除了指定函数名之外，其余组件可能是额外的参数，例如：

  • https://api.weather.gov/points/42.3541,-71.1104 将经纬度对作为路径组件提供
  • https://api.weather.gov/gridpoints/BOX/69,75/forecast 有三个路径组件参数：预报办公室标识符 BOX、该办公室的网格位置 69,75 和所需的信息类型 forecast。

查询参数。URL 路径之后是一个可选的查询，以 ? 开头，由 & 分隔的 name=value 对组成。你可能已经在网页浏览中见过这一点，因为它通常被网页表单使用。例如：

  • https://www.google.com/search?q=MIT 有一个查询参数 q，值为 MIT。
  • https://api.weather.gov/alerts/active?area=MA&severity=Minor 有两个查询参数：area 值为 MA，severity 值为 Minor。

请求体参数。这些参数不会出现在 URL 中。某些 HTTP 请求可以有一个请求体，即任意序列的额外字节。请求体的格式可以不同：

  • 纯文本
  • 二进制数据块，可能从文件加载
  • 表单数据，类似于查询参数的名称-值对集合
  • JSON

请求体参数不如路径或查询参数常见。HTTP 请求有两种常见类型，只有一种允许有请求体：

  • GET 请求是 curl 发出的正常请求，也是你在地址栏输入 URL 或点击普通超链接时浏览器发出的请求。GET 请求有 URL 但没有请求体，因此只能有路径和查询参数。GET 专为观察者操作设计，不会更改服务器上的任何状态。网页客户端可以确信重复发出 GET 请求不会改变或创建任何新内容，因此如果浏览器需要重新发出 GET 请求来重新加载页面，它可以安全地做到。 换句话说，GET 应该是幂等的。

  • POST 请求同时有 URL 和请求体。你不能从浏览器的地址栏发出 POST 请求，但curl 可以做到，网页表单也经常使用 POST。POST 旨在用于更改或创建服务器上数据的操作：修改器、生产者、创建者。网页客户端对重新发出 POST 请求更加谨慎。在你的网页浏览过程中，你可能曾经看到一个确认对话框询问你是否真的要重新发送表单——这是因为浏览器不确定进行两次 POST 是否安全，可能会购买第二套昂贵的机票。

HTTP 还有几种其他类型的请求，包括 PUT 和 DELETE，但这些在 Web API 中很少使用。HTTP 请求的类型称为其 方法，令人困惑的是，它与对象的方法概念关系不大。HTTP 请求方法更像我们对 ADT 操作的分类，因为 GET 最初是为观察者设计的，POST 是为创建者和修改器设计的。

结果

客户端的 HTTP 请求之后通常会有服务器的 HTTP 响应，其中包含两种提供结果的方式：

状态码。每个 HTTP 响应都有一个三位数的状态码，指示是否成功。以下是一些常见的状态码：

  • 200 OK 表示请求成功完成
  • 404 Not Found 表示 Web API 或网页不存在
  • 400 Bad Request 通常在请求参数有误时使用
  • 500 Internal Server Error 当请求因其他原因失败时使用

还有一些不太常见的：

  • 412 Precondition Failed 当条件请求中的条件未满足时（6.102 的现实例子！）
  • 418 I'm a teapot 当服务器因为自己是茶壶而拒绝煮咖啡时

你还可以看猫表演 HTTP 状态码。

响应体。与请求一样，响应也可以附任意类型的数据体。典型的体类型有：

  • HTML（通常用于为人类浏览设计的网页服务器，而非 Web API）
  • 纯文本
  • JSON

文本适合简单的、易于解析的结果（如逗号分隔的数字对）。 然而，对于复杂的结果，JSON 已成为首选的结果类型。 我们在上面查询国家气象局获取剑桥天气时看到了 JSON 结果的样子。

指定一个 Web API

指定参数如何传递和结果如何返回还不够：它的作用类似于定义 ADT 时的方法签名。 我们仍然需要规范的其余部分：

  • 请求的前置条件是什么？ 例如，如果请求的特定参数是一个数字字符串，任何数字都有效吗？ 还是必须是服务器已知的记录的 ID 号？

  • 后置条件是什么？ 服务器将基于请求执行什么操作？ 服务器端哪些数据会被修改？ 服务器将向客户端发回什么回复？

TypeScript 中的 Web 服务器

让我们看看用 TypeScript 编写简单 Web 服务器的细节。 作为入门介绍，我们来看一个简单的服务器，它只是回显客户端发送给它的内容。

你可以查看此 Web 服务器的完整代码。 本阅读中的一些代码片段为了展示目的进行了简化。

路由处理

Web 服务器的控制流是一个等待来自网页浏览器的传入连接的输入循环。 当新连接到达时，服务器读取并解析请求。 然后将请求路由到为匹配请求的路由注册的处理器。 通常只有请求的前缀需要匹配路由，因此请求 http://web.mit.edu/community/topic/arts.html 将被路由到 /community 的处理器，除非注册了更具体的（更长前缀）路由。

然后处理器负责构建对请求的响应。

Node 最流行的路由器是 Express。 你可以像这样创建一个新的 Express Application 对象：

import express, { Request, Response } from 'express';

const app = express();

注意 express 是一个工厂函数，返回 Application 对象。 有时复杂的服务器有多个 Application，但大多数只需要一个。

你可以让应用开始监听 HTTP 连接：

const PORT = 8000;  // 服务器将监听传入连接的端口
app.listen(PORT);

然后使用 get() 向应用添加路由：

app.get('/echo', (request: Request, response: Response) => {
    ...
});

这里，get 指的是 HTTP 协议的 GET 方法，如上文所述。 当你在网页浏览器的地址栏中输入 URL 时，你是在告诉浏览器发出 GET 请求。

第一个参数是路由前缀，第二个参数是回调函数。 app 对象会在传入请求以 /echo 前缀开头时调用回调函数。 回调的参数是一个 Request 对象，提供观察者方法来获取请求信息，以及一个 Response 对象，带有修改器方法来生成返回给网页浏览器的响应。

回调函数的函数体（上面显示为 ...）应该检查请求并生成响应。 作为如何检查请求的示例，如果传入的请求是 http://localhost:8000/echo?greeting=hello，那么：

const greeting = request.query['greeting'];

返回 "hello"，它来自 URL 的查询部分（以问号开头的部分，?greeting=hello）。

作为生成响应的示例，处理器应该首先提供一个状态码（当请求成功时通常为 200 OK），以及它返回的响应类型（HTML、纯文本、JSON 或其他）：

response.status(StatusCodes.OK); // 使用 http-status-codes 库
response.type('text');

然后使用 send 方法写入响应：

response.send(`${greeting} to you too!`);

响应现在已完成，网页浏览器应该显示传递给 send 的文本。

这些修改器操作（status、type 和 send）被声明为返回 Response 对象本身而非 void，所以常见的是将它们链式调用，如下所示：

response.status(StatusCodes.OK).type('text').send(`${greeting} to you too!`);

或者，更具可读性地：

response
  .status(StatusCodes.OK)
  .type('text')
  .send(`${greeting} to you too!`);

这种函数调用语法——方法的返回值立即用于调用另一个方法——称为方法调用链。 你也可以对 map、filter、reduce 这样的函数做同样的事情！

以下是 /echo 路由的完整代码：

app.get('/echo', (request: Request, response: Response) => {
  const greeting = request.query['greeting'];
  response
    .status(StatusCodes.OK)
    .type('text')
    .send(`${greeting} to you too!`);
});

再次说明，这个 lambda 函数是监听器回调的一个示例：我们作为客户端交给 Application 对象的一段代码，每当事件发生时（在本例中是匹配路由的请求到达时）供其调用。

查询参数与路由参数

正如我们上面所见，有几种方式向 Web API 传递参数。在我们目前的示例中，greeting 是一个查询参数：

app.get('/echo', (request: Request, response: Response) => {
  const greeting = request.query['greeting'];
  ...
      .send(`${greeting} to you too!`);
})

当此服务器收到对 http://localhost:8000/echo/Ben?greeting=Gday 的客户端请求时，它产生的响应是：

Gday to you too!

让我们扩展示例以包含路径参数（也称为路由参数），方法是在路由的适当位置放置参数名，前面加上 :。

app.get('/echo/:person', (request: Request, response: Response) => {
  const person   = request.params['person'];   // <-- 注意！路由参数在 request.params 中，
  const greeting = request.query['greeting'];  // <--      而查询参数在 request.query 中
  ...
      .send(`${greeting} to you too, ${person}!`);
})

当此服务器收到对 http://localhost:8000/echo/Ben?greeting=hi 的客户端请求时，"Ben" 绑定到路由参数 person，"hi" 绑定到查询参数 greeting，产生的响应是：

hi to you too, Ben!

Web API 可以有任意数量的查询参数或路由参数。 路由参数必须按特定顺序出现在路径中（很像 Python 和 TypeScript 中的函数参数），而查询参数可以按任意顺序提供，但必须包含参数名（很像 Python 中的关键字参数）。

客户端

自从规范阅读以来，我们使用术语 客户端 来指代使用类的代码。 在本阅读中，我们开始使用客户端来表示网络客户端/服务器通信中的一方。 使用 Express，我们需要跟踪客户端的两种具体含义：

  • Web 服务器的客户端是一个网页浏览器，通过网络向其发送请求。 例如，我们的 Echo Web 服务器的客户端向 GET /echo?greeting=hello 发送 HTTP 请求

  • Express Application 对象的客户端是我们针对其提供的 API 编写的代码。 例如，Application 的客户端调用 get() 并传入一个准备处理 /echo 路由请求的回调函数。

错误处理

虽然Express 中的错误处理的完整主题超出了本课程的范围，但幸运的是，最简单的错误处理很容易：在回调函数中抛出异常会向浏览器发回显示堆栈跟踪的错误。 例如：

app.get('/bad', (request: Request, response: Response) => {
  throw new Error('always fails');
});

当网页浏览器访问 http://localhost:8000/bad 时显示类似以下内容：

在回调中使用 await

Web 服务器通常需要响应 Web 请求做一些工作：从文件系统读取文件、查询数据库、在某处写入数据。 如果该工作涉及调用异步函数，那么我们可能需要在回调函数中使用 await，这意味着回调函数本身必须用 async 关键字定义：

app.get('/lookup', async (request: Request, response: Response) => {
  ...
  const data = await database.lookup(query);
  ...
});

总结

消息传递系统通过共享通信通道（如流或队列）来避免与同步共享可变数据操作相关的 Bug。 并发模块（线程、进程、独立机器）只来回传递（不可变）消息，变更被限制在每个模块内部，而不是开发一个可并发使用的可变 ADT，就像我们在互斥阅读中所做的那样。

在客户端/服务器设计模式中，并发是不可避免的：多个客户端和多个服务器在网络上连接，同时发送和接收消息，期望及时回复。 一个在等待一个慢速客户端时阻塞的服务器，当有其他客户端等待连接或接收回复时，不会让那些客户端满意。

使并发代码免受 Bug 侵害、易于理解和适应变化的所有挑战，在我们设计网络客户端和服务器时同样适用。 这些进程彼此并发运行（通常在不同机器上），任何想要同时与多个客户端通信的服务器（或想要同时与多个服务器通信的客户端）必须管理这种并发。
