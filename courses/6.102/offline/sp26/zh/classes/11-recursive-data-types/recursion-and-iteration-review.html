6.101: 递归与迭代

引言

这篇阅读材料通过将递归与迭代进行比较和对比，更深入地研究了递归。 两种方法都创建了重复的计算模式。递归通过在更简单的或更小的子问题上递归地调用相同的函数来产生重复计算。迭代使用 for 循环或 while 循环来产生重复计算。

如果我们能想出一个迭代版本，我们还需要递归吗？ 从某种意义上说，不，我们不需要递归——任何可以用递归写的函数也可以用迭代来写。 但是，有些问题天然 naturally 适合递归解决方案。 当我们尝试用迭代方式解决这类问题时，我们会发现自己在 simulating 模拟递归，使用一个显式的议程来跟踪我们接下来需要做什么。 对于这类问题，直接表达递归算法更为简单，让Python使用其调用栈来处理议程的记录。

反过来也是成立的：任何可以用循环迭代编写的函数，也可以递归地编写。 因此，能够以 both 两种方式思考，并选择对我们试图解决的问题最自然、最合适的那种，这一点很重要。

这篇阅读材料探讨了这些方法之间的本质等价性，以及它们在简洁性和性能方面的一些权衡。 我们将回到之前阅读材料中编写的一些函数，包括递归和迭代的，并展示如何用另一种技术来编写每一个。

def factorial(n):

    out = 1

你会选择这些实现中的哪一种？每种方法各有什么优缺点？

以下是一些比较点：

  • 迭代版本可能更高效，因为它不需要为递归调用创建新的栈帧。
  • 递归版本可能感觉更简单，与阶乘的数学定义更匹配。
  • 两个版本在处理 illegal inputs, like

    n

    <

    0

对于任何一个版本，如果函数在接收到非法输入时立即产生错误，那就更好了：

def factorial(n):
    assert n >= 0, "need a nonnegative integer"
    if n == 0:
        return 1
    else:
        return n * factorial(n-1)

factorial(-1) 的结果指出了递归与迭代在许多编程语言（包括Python）中的一个重要区别：递归受最大调用栈深度限制。在Python中，这个默认限制是1000次调用。当函数试图进行比这更深的调用时，Python会产生 RecursionError. 这个限制可以通过 sys.setrecursionlimit(), ，但它不能无限制地增大，因为操作系统本身对Python的调用栈设置了限制。

类列表模式

这篇阅读材料的其余部分通过研究几种常见的重复计算类型来组织，具体取决于它所处理的数据的形状：类列表（即一系列值）、类树和类图。我们将回顾之前阅读材料中针对每种形式所研究过的递归或迭代算法，讨论如何用另一种方式来编写该算法。

让我们从列表开始。回顾 sum_list from the 递归阅读材料中的 sum_list，我们既用迭代方式也递归方式编写了它：

def sum_list(x):
    sum_so_far = 0
    for num in x:
        sum_so_far += num
    return sum_so_far
def sum_list(x):
    if not x:
        return 0
    else:
        return x[0] + sum_list(x[1:])

迭代版本自然地使用了 for 循环。

递归版本将列表分解为其第一个元素 x[0] 和列表的其余部分 x[1:]。其余部分是更小的递归子问题。这种首元素/其余部分分解是递归处理类列表数据的一种非常常见的方法。 x[0] x[1:]。其余部分是更小的递归子问题。这种首元素/其余部分分解是递归处理类列表数据的一种非常常见的方法。

对于类列表数据，还有哪些其他的递归分解方式可能是自然的或合理的？

回顾一下你在6.100A/L中学到的内容：

  • what decomposition does 二分搜索 （也称为二分搜索）使用了什么分解方式？
  • 归并排序 使用了什么分解方式？

我们还可以想象一种分解方式，取出最后一个元素 x[-1] and 然后递归地处理它前面的列表前缀 x[:-1]. 例如，这可能是从列表末尾开始进行线性搜索的正确分解方式。

二分搜索检查排序列表中间的元素，比如 m = len(x)//2, ，然后递归地处理左边部分 x[:m] 或右边部分 x[m+1:], ，取决于目标元素小于还是大于 x[m]. 这种分解可能被称为中/左/右。

归并排序通过将列表分成左半部分和右半部分，递归地对每一半进行排序，然后通过合并将已排序的子列表重新组合，从而对列表进行排序。

请注意，在每一种分解中，算法都必须小心地使递归子问题变得更小。首元素/其余部分和中/左/右分解通过从列表中剥离一个元素（第一个或中间的那个）并将其从递归子问题中排除来实现这一点，从而使它们肯定比原始问题更小。这就是这些分解如何保证子问题比原始问题更小，因此我们最终会在基准情况处终止（基准情况通常是——但不总是——空列表）。

使用辅助函数累积结果

sum_list 的递归版本和迭代版本之间的一个区别是它们进行求和的顺序。虽然两个版本都按从头到尾的顺序考虑列表元素，但递归版本会延迟任何加法操作，直到到达列表末尾，然后反向进行求和。所以计算最终看起来是这样的：

  • 迭代版本：从 0 开始，然后加上 x[0]，然后 x[1]，然后 x[2]，……，最后加上 x[n-1]
  • 递归版本：从 0 开始，然后加上 x[n-1]，然后 x[n-2]，然后 x[n-3]，……，最后加上 x[0]
    • x[0], then x[1], then x[2], …, finally add x[n-1]
  • x[n-1], then x[n-2], then x[n-3], …, finally add x[0]

递归版本将加法操作推迟到其组合步骤，在该步骤中将递归子问题的结果组合起来。

但是，我们不必以这种方式编写。我们可以编写一个在行进过程中进行加法的递归版本，通过定义一个 recursive helper function 的递归辅助函数，并将迄今为止计算出的部分和传递给它：

def sum_list(x):
    def sum_helper(sum_so_far, lst):
        if not lst:
            return sum_so_far
        else:
            num = lst[0]
            rest = lst[1:]
            return sum_helper(sum_so_far + num, rest)
    return sum_helper(0, x)

The sum_helper 函数是一个递归辅助函数。它需要是一个不同于原始 sum_list 的新函数，因为它有一个新的参数 sum_so_far，用于跟踪迄今为止计算出的部分和。递归调用稳步地累加到 sum_so_far，直到最终到达列表末尾（基准情况），此时已完成的总和作为唯一的结果被返回。 sum_list 函数体通过调用 sum_helper 来启动，初始值为 0 作为 sum_so_far （这是之前的递归版本中基准情况返回的值）。

将递归辅助函数像这样隐藏为一个内部函数是一个好主意，因为它只在 sum_list. （它也有助于共享在递归过程中不需要改变的参数或局部变量，因为所有对递归辅助函数的调用都会自动拥有对外层函数栈帧中变量的访问权，但在本例中我们不需要这样做。）

这个例子演示了一个通用原则：迭代循环可以转化为递归辅助函数，方法是使用参数来携带迭代循环在每次迭代中更新的局部变量。

在 sum_list, 的循环中，相关的局部变量是 sum_so_far, ，以下就是如何将该循环转换为上面所示的递归版本：

def sum_list(x):
    sum_so_far = 0           # becomes initial call to sum_helper(0, x)
    for num in x:            # becomes num = lst[0], rest = lst[1:]
        sum_so_far += num    # becomes recursion step sum_helper(sum_so_far + num, rest)
    return sum_so_far        # becomes the base case

一个使这种模式更加简短的技巧：我们可以消除辅助函数 sum_helper ，而改为在 sum_list 自身上进行递归，通过为额外的参数提供默认初始值。这样，原始调用初始化递归，后续的递归调用更新参数：

def sum_list(x, sum_so_far=0):
    if not x:
        return sum_so_far
    else:
        return sum_list(x[1:], sum_so_far + x[0])

优化

Python中的类列表递归存在一些性能缺陷：

  1. 每次递归调用都会创建一个新的栈帧，而且递归深度是有限的（默认限制为1000次调用）。对于首元素/其余部分分解，这意味着可以处理的列表长度同样受到限制。（但对于其他分解方式，比如左半部分/右半部分，这完全不是限制。为什么不是呢？如果你被限制为1000次递归调用，通过连续对半分割，能处理的列表最大长度是多少？）

  2. 在首元素/其余部分分解中，每次递归调用都需要复制列表的其余部分，使用类似 lst[1:]. 在整个计算过程中，所有这些复制操作累积起来的时间与列表长度的平方成正比。 （为什么？如果原始列表的长度为

这两个问题都可以通过巧妙的优化来解决：

  1. 递归深度限制可以通过 tail-call optimization. 如果递归的写法使得递归调用是函数体中最后执行的事情——比如上面的递归版本中的 return sum_helper(...) 这一行——那么这次递归调用被称为 sum_list ，它位于函数必须完成的工作的末端。 tail call, Tail-call optimization 意味着，当运行时系统遇到一个尾调用时，它推断不再需要当前调用的栈帧，可以简单地 reuse 复用它来用于新的递归调用，而不是创建一个新的栈帧。通过尾调用优化，每次对 sum_helper 的递归调用都简单地复用同一个栈帧，递归深度永远不会超过1，递归版本的性能本质上就像循环一样。

    尾调用优化不能应用于不在函数最末尾的递归调用。如果 sum_list 被写成我们最初的方式，即 return x[0] + sum_list(x[1:]), ，那么这就不是尾调用，因为在递归调用返回后，函数还需要做更多的工作（加上 x[0]) ）。如果在调用期间创建了一个函数对象需要保留其栈帧，尾调用优化也会被阻止。

    遗憾的是，Python没有实现尾调用优化，但 其他语言实现了。

  2. 列表复制问题可以通过使用 链表（我们将在后面的几周中详细研究）而不是数组来实现列表，这样列表的"其余部分"可以在常数时间内获得。Python没有这样做，所以在Python中避免列表复制的另一种方法是使用索引来表示列表的其余部分，这里称为 i:

    def sum_list(x):
    def sum_helper(i, sum_so_far)
        if i >= len(x):
            return sum_so_far
        else:
            return sum_helper(i+1, sum_so_far + x[i])
    return sum_helper(0, 0)

类树模式

在研究了顺序的、类列表的数据之后，现在让我们转向"树形"数据。

A tree 是一种递归定义的数据结构，它从一个 root 节点开始，该节点有零个或多个本身是树的 children （递归地应用该定义）。当一个节点没有子节点时，树达到了其基准情况，该节点被称为 leaf 节点。计算机科学家通常将树画成从根节点向下生长的，像这样：

作为"类树"数据在Python中可以出现的一种方式的例子，回顾 sum_nested from the 递归阅读材料：

def sum_nested(x):
    """
    >>> sum_nested([[1, 2], [3, [4, 5]], [[[[[6]]]]]])
    21
    """
    if not x:
        return 0
    elif isinstance(x[0], list):
        return sum_nested(x[0]) + sum_nested(x[1:])
    else:
        return x[0] + sum_nested(x[1:])

为什么我们将 sum_nested 的输入视为树形的？因为 x 中的每个子节点就像一个节点，其子节点可能是更深的子列表，直到我们到达简单的数字，这些数字就是叶子节点。假设 x = [[1, 2], [3, [4, 5]], [[[[[6]]]]]] — ——以下是将其视为树时的样子：

树形数据有一种直接的递归分解，它反映了树的结构：我们对所有子节点进行递归调用，直到到达叶子节点。

但是，请注意，这里编写的 sum_nested 不仅递归地分解了树结构，而且还递归地分解了子节点列表。

为了将这个递归函数转换为迭代循环，我们将回到早期阅读材料中使用的一个思想： agenda. 在这里，我们的议程将跟踪我们尚未进行的递归调用。具体来说，议程中的每一项将包含一次递归调用的参数。议程用原始列表初始化（我们将把它重命名为 original_x ，这样我们就可以继续使用 x 来表示代码的其余部分而不会混淆），然后，每次遇到对 sum_nested(), 的递归调用时，我们将其放入议程中，以便在循环的后续迭代中处理它。这就是代码：

def sum_nested(original_x):
    sum_so_far = 0
    agenda = [original_x] # agenda consists of parameters for pending recursive calls
    while agenda:
      x = agenda.pop(0)
      if not x:
          sum_so_far += 0
      elif isinstance(x[0], list):
          agenda.insert(0, x[0])
          agenda.insert(0, x[1:])
      else:
          sum_so_far += x[0]
          agenda.insert(0, x[1:])
    return sum_so_far

在这个迭代实现中，我们选择在议程的末尾添加和删除项目，以便按照递归算法相同的顺序探索树——即深度优先。但是，我们不一定非得做出那个选择——我们该如何改变代码，使得迭代版本改为按广度优先遍历树呢？无论哪种方式，对于 sum_nested 来说并不重要（加法满足交换律，所以数字可以以任何顺序求和），但对于其他问题，顺序可能很重要。

从另一个角度观察我们刚刚做的转换，递归版本的内部隐藏着一个议程数据结构——议程就是调用栈，由Python管理，它跟踪递归过程中需要完成的剩余工作。因此，递归为我们提供了一种方便而简单的方式来表达深度优先遍历，而不必自己管理议程数据结构。

Graph-Like Patterns

Now that we have explored the equivalence between recursive traversal and iterative (depth-first) traversal using an explicit agenda, let’s go back to graph-traversal problems we explored in earlier readings. A graph consists of a set of vertices and the edges between them. Here is an example of a graph:

So “graph-like” data is data that can be regarded as vertices connected by edges. A tree is actually a special case of a graph (since it also has vertices and edges). But in general, a graph may have multiple paths reaching the same vertex, or it may have cycles (paths that return to the same vertex again), neither of which is allowed for a tree.

In previous readings, we solved graph-traversal problems using iteration, like this flood-fill function:

def flood_fill(image, starting_location, new_color):
    # recall that "*location" is equivalent to "location[0],location[1]"
    original_color = get_pixel(image, *starting_location)

    agenda = [starting_location]  # agenda: all of the cells we need to color in
    visited = {starting_location}  # visited set: all pixels ever added to the agenda
    while agenda:
        location = agenda.pop(0)
        set_pixel(image, *location, new_color)
        for neighbor in get_neighbors(location):
            if (neighbor not in visited
                    and get_pixel(image, *neighbor) == original_color):
                visited.add(neighbor)
                agenda.append(neighbor)

Now that we know that we can use the recursive call stack as an agenda, how can we write this recursively? Everywhere we would put a work item on the agenda, let’s make a call to a recursive helper function instead, using the work item as its parameter. This recursive helper function replaces the while loop:

def flood_fill(image, starting_location, new_color):
    original_color = get_pixel(image, *starting_location)
    visited = {starting_location}  # visited set: all pixels ever added to the agenda
    def fill_from(location):
        set_pixel(image, *location, new_color)
        for neighbor in get_neighbors(location):
            if (neighbor not in visited
                    and get_pixel(image, *neighbor) == original_color):
                visited.add(neighbor)
                fill_from(neighbor)
    fill_from(starting_location)

Let’s reflect on how we’re using recursion here and think carefully about whether the recursion would actually stop.

What makes the recursive call fill_from(neighbor) a smaller or simpler subproblem?

And what is the base case of the recursion?


Before we make the recursive call to fill_from(neighbor), we first add neighbor to the visited set, so that we won’t visit that pixel again. The graph of pixels we’re trying to fill has effectively become one pixel smaller.

The base case happens when we have no recursive calls to make – when we reach a pixel which is a dead end, because all its neighbor pixels are either not original_color or already visited.

The observation we just made leads to a further observation. For flood fill, we have another guarantee that the recursive subproblem is smaller. What is it?


The fact that every recursive call changes a pixel’s color from original_color to new_color also makes the problem smaller. So, we actually don’t need a visited set when we solve flood fill recursively!

def flood_fill(image, starting_location, new_color):
    original_color = get_pixel(image, *starting_location)
    if original_color == new_color:
      return # nothing to do
    def fill_from(location):
        set_pixel(image, *location, new_color)
        for neighbor in get_neighbors(location):
            if get_pixel(image, *neighbor) == original_color:
                fill_from(neighbor)
    fill_from(starting_location)

When To Use Recursion and When To Use Iteration

How might you decide to use recursion?

  • When the problem is easy to express recursively (as factorial)
  • When the data itself is defined recursively (like a tree often is)
  • When depth-first traversal is fine
  • When the recursion won’t get too deep (this constraint may be relaxed for programming languages other than Python)

Recursive solutions are often shorter and simpler, by moving agenda bookkeeping into the programming language rather than representing it explicitly.

As you gain comfort with recursion, you may find that a recursive solution is easier to express at first, because of natural decompositions (like first/rest, or left-half/right-half, or recursing into children or graph neighbors). So, it may be good to start with a recursive approach and then convert it to an iterative algorithm (using one of the strategies here) if you run into problems like recursion depth limits or excessive copying.

Common Mistakes in Recursion

Here are three common ways that a recursion can go wrong:

  • The base case may be missing entirely, or the problem needs more than one base case, but not all the base cases are covered.
  • The recursive step doesn’t reduce to a smaller subproblem, so the recursion doesn’t converge.
  • Aliases to a mutable data structure are inadvertently shared, and mutated, among the recursive calls.

We saw the first two issues in an exercise above, when we tried to convert sum_list to use a left/right decomposition. When the subdivided list reached length 1, the decomposition was no longer able to make two smaller subproblems, so we needed to make that into a new base case.

Aliases to mutable data are sometimes necessary in recursion, as we saw above when we shared the visited set across all calls in a recursive traversal of a graph. For flood fill, of course, sharing the mutable image is necessary because the whole point of the recursion is to fill in more pixels. But, when you are doing a recursive depth-first search without a visited set (which, as we saw with flood fill, is often possible when a move in the search automatically makes the problem smaller or simpler), it can be tempting to keep the search state mutable. This becomes tricky, because then multiple pending recursive calls have aliases to the same mutable state. We will see an example of this in the next reading, when we use recursive search to solve Sudoku puzzles.

Look for these mistakes when you’re debugging. A RecursionError is a sign of the first two. The third bug can be harder to spot, because it’s fundamentally an aliasing bug.

Summary

We have explored several kinds of problems, based on the shape of the data or repeated computation that needs to be done (list-like, tree-like, graph-like), and have seen how to do the repeated computation both recursively and iteratively.

Along the way, we’ve seen more strategies for thinking recursively, including:

  • recursive decompositions that are commonly used for list-like data (first/rest, left-half/right-half), tree-like data (recursing into children), and graph-like data (recursing to neighbors);
  • using a recursive helper function with parameters that accumulate partial results;
  • using recursion for a depth-first traversal of a tree or graph.
