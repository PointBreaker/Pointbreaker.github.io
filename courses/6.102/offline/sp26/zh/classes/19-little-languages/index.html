学习目标

In this reading we will begin to explore the design of a 小语言 for constructing and manipulating music. Here’s the bottom line: when you need to solve a problem, instead of writing a 程序 来解决那一个问题，构建一个 语言 可以解决一系列相关问题。

The goal for this reading is to introduce the idea of 将代码表示为数据 并让你熟悉 音乐语言.

在这个过程中，我们将介绍 访问器模式, which is another example of treating functions as first-class values, and an alternative implementation strategy for operations on recursive data types. Visitors are a common feature of little languages implemented as recursive data types.

将代码表示为数据

回顾 Formula 数据类型，来自 递归数据类型:

Formula = Variable(name:String)
          + Not(formula:Formula)
          + And(left:Formula, right:Formula)
          + Or(left:Formula, right:Formula)

我们使用了 Formula 的实例来表示命题逻辑公式，例如 (p ∧ q)，并将它们表示为数据结构，例如：

And(Variable("p"), Variable("q"))

用语法和解析器的术语来说，公式是一种 语言、 Formula 是一个 抽象语法树.

但我们为什么要定义一个 Formula type? TypeScript already has a way to represent expressions of Boolean variables with 逻辑与, 或、 不. For example, given boolean variables p 和 q，我们可以直接写：

p && q

完成！

答案是，代码表达式 p && q 一旦在我们的运行程序中遇到就会被求值。 Formula 值 And(...) 是一个 一等值 ，可以存储、在函数间传递和返回、操作，以及根据需要随时或稍后求值（或多次求值）。

这个 Formula 类型是 将代码表示为数据, and we’ve seen others. Here is a 一等函数:

const andFunction = (p: boolean, q: boolean) => p && q;

构建语言来解决问题

当我们定义一个 抽象数据类型, we’re extending the universe of built-in types provided by TypeScript to include a new type, with new operations, appropriate to our problem domain. This new type is like a new language: a new set of nouns (values) and verbs (operations) we can manipulate. Of course, those nouns and verbs are abstractions built on top of the existing nouns and verbs which were themselves already abstractions.

一个 语言 比单纯的 程序, because we can use a language to solve a large class of related problems, instead of just a single problem.

  • That’s the difference between writing p && q 与设计一个 Formula 类型来表示语义等价的布尔公式之间的区别。

  • And it’s the difference between writing an integer addition function and devising a IntegerExpression 类型 来表示整数算术表达式——并存储、操作、重排、求值等之间的区别。

这种语言称为 领域特定语言 （DSL）, because it solves problems in a narrower domain than a general-purpose programming language like TypeScript or Python. DSLs can be further classified into 外部和内部:

  • An external DSL has custom syntax and semantics, independent of any general-purpose programming language. Examples that we’ve already seen in this class include regular expressions, ParserLib grammars, and the language of 问题集 3.

  • An internal DSL, by contrast, is embedded in a general-purpose programming language, using the syntax and abstraction mechanisms of the host language rather than inventing its own. First-class functions enable us to create particularly powerful internal DSLs because we can capture patterns of computation as reusable abstractions. The music language that we’ll develop in this class is an example of an internal DSL.

音乐数据类型

这个 Pitch data type is useful, but if we want to represent a whole piece of music using Pitch 对象来表示整首音乐，我们应该创建一个抽象数据类型来封装该表示。

To start, we’ll define the Music 类型，包含以下操作：

notes : String × Instrument → Music (MusicLanguage.ts) makes a new Music from a string of simplified abc notation, described below.

duration : Music → number (Music.ts) returns the duration, in beats, of the piece of music.

play : Music × SequencePlayer × number → void (Music.ts) plays the piece of music using the given sequence player.

We’ll implement duration 和 play 作为 Music, so we declare them in the Music 接口。

notes 将是一个工厂函数；我们不会把它放在 Music (which we could do, as with Pitch), we’ll put it in a separate file: MusicLanguage 将是我们编写的所有用于操作 Music.

Now that we’ve chosen some operations in the spec of Music, let’s choose a representation.

  • 查看 ScaleSequence, the first concrete variant that might jump out at us is one to capture the information in each call to addNote: a particular pitch on a particular instrument played for some amount of time. We’ll call this a Note.

  • 音乐的另一个基本元素是音符之间的静音： Rest.

  • Finally, we need a way to glue these basic elements together into larger pieces of music. We’ll choose a tree-like structure: Concat(first:Music,second:Music) 表示 first 后跟 second，其中 first 和 second 可以是任何音乐。

    当我们进一步开发我们的 Music 类型时，这个树状结构被证明是一个优雅的决定。 在真实的设计过程中，我们可能不得不对 Music 的递归结构进行迭代，然后才找到最佳实现。

Here’s the data type definition:

Music = Note(duration:number, pitch:Pitch, instrument:Instrument)
        + Rest(duration:number)
        + Concat(first:Music, second:Music)

组合

Music 是 组合模式的一个示例，其中单个对象（原语，例如 Note 和 Rest）和对象组（组合，例如 Concat) all belong to the same type, so they can be treated the same way.

  • The recursive data types we’ve been using, like Formula，都是组合模式的示例。

  • HTML’s Document Object Model (DOM) relies heavily on the composite pattern: there are 原始元素 如 <img> 和 <input> that don’t have children, and 组合元素 如 <div> 和 <span> 包含其他元素作为子元素。 它们都实现了共同的 Element 接口。

  • 的语言 问题集 3 包含了原语和组合；你能识别它们吗？

组合模式产生一种树数据结构，原语在叶节点，组合在内部节点。

空

One last design consideration: how do we represent the empty music? It’s always good to have a representation for 空, and we’re certainly not going to use null 或 undefined.

我们可以引入一个 Empty variant, but instead we’ll use a Rest 持续时间为 0 来表示空。

动态分派 of method calls is what powers the Interpreter pattern.

理解动态分派需要回顾 静态类型和动态类型. The 静态类型 变量或方法调用返回的静态类型是其声明中找到的类型。 因为它在代码中声明，所以编译器在编译时就知道它。

但在运行时，对象变量或方法调用返回引用内存中的实际对象值。 该对象有一个类型，称为其 动态类型，即它构造自的类。

动态分派意味着使用对象值的动态类型来决定执行哪个方法体。 如果变量声明为 Formula f，但其值的动态类型是实现 Formula的具体类型，那么当我们调用 f.variables() is that concrete type’s implementation of the variables method. If f 指向一个 Not 对象，那么 f.variables() 运行 Not.variables().

对象值的动态类型不必与指向它的变量的静态类型相同。 事实上，当静态类型是接口时，动态类型 总是 different, because a dynamic type must be a class. (Recall that interfaces don’t have constructors, so only a class can produce an object value at runtime.)

但动态类型必须在重要方面与静态类型一致：动态类型始终是静态类型的一个 子类型 。 这保证了我们可以为静态类型调用的任何方法也存在于动态类型中，具有相同或更强的规范。 Not 是实现 Formula interface, so it is a subtype of Formula. TypeScript enforces this requirement by static checking; you can’t, for example, just write f = "not"，因为 string 的子类型 Formula.

Downsides of Interpreter pattern

Let’s consider two disadvantages of the Interpreter pattern:

  1. For a complicated operation on a data type with many variants, the code to implement the operation will be distributed across all the different variant classes. If we want to inspect all the code, refactor it, or fix a bug, we must find it in all those different places: the code is harder to understand. Bugs in our recursive implementations are easier to introduce and harder to find.

  2. If we wish to add a new operation to our type, we must modify the interface and every implementing class. If there are many concrete variants that already have substantial code, perhaps written and maintained by other programmers, this change will be more difficult to make than if we could keep the code for the new operation in its own separate location.

我们用 FormulaFunction 类型和 callFunction 操作创建了一种特殊的迭代器，它遍历 Formula 的树结构并逐个处理树中的节点。 这种模式的名字是 访问器:

  • 访问器实现了 switch 按类型进行 Variables­In­Formula 的代码与我们 的原始目标 switch 语句非常接近，但每个情况都有其自己的 onVariant method. The dynamic dispatch in the visitor implicitly acts like a switch 语句一样执行 callFunction ，执行对应于动态类型的适当具体变体。

  • 访问器表示递归类型上的函数：我们可以创建特定 Formula­Function, pass it around, apply it as needed, etc. If the function we’re representing takes additional parameters, we can make them arguments to the visitor constructor and store those values in fields to be referenced as we go. The exercise at the end of this section explores this idea.

We’ll make a few changes to nomenclature to arrive at a final version of our Formula 的访问器：

  • We’ll call it FormulaVisitor 而不是 FormulaFunction.
  • 在实例上遍历访问器称为 接受 it, so we’ll rename callFunction 重命名为 accept.

以下是代码：

interface FormulaVisitor<R> {  // renamed from FormulaFunction<R>
    onVariable(variable: Variable): R;
    onNot(not: Not): R;
    onAnd(and: And): R;
    onOr(or: Or): R;
}

interface Formula {

    accept<R>(visitor: FormulaVisitor<R>): R; // renamed from callFunction()

    // ... other operations ...
}

class Variable implements Formula {
    // ...
    public accept<R>(visitor: FormulaVisitor<R>):R {
        return visitor.onVariable(this);
    }

}
class Not implements Formula {
    // ...
    public accept<R>(visitor: FormulaVisitor<R>):R {
        return visitor.onNot(this);
    }
}
class And implements Formula {
    // ...
    public accept<R>(visitor: FormulaVisitor<R>):R {
        return visitor.onAnd(this);
    }
}
class Or implements Formula {
    // ...
    public accept<R>(visitor: FormulaVisitor<R>):R {
        return visitor.onOr(this);
    }
}

class VariablesInFormula implements FormulaVisitor<Set<string>> {
    public onVariable(variable: Variable): Set<string> {
        return new Set([variable.name]);
    }
    public onNot(not: Not): Set<string> {
        return not.formula.accept(this);
    }
    public onAnd(and: And): Set<string> {
        return setUnion(and.left.accept(this), and.right.accept(this));
    }
    public onOr(or: Or): Set<string> {
        return setUnion(or.left.accept(this), or.right.accept(this));
    }
}

为什么使用访问器？

为了理解访问器模式和解释器模式之间的对比，想象一下 Formula 的所有操作的所有代码，就好像写在一个表格里，变体类在顶部，操作在侧面。 表格中的一个条目是实现该变体的该操作的代码。 以下是表格的一部分（用数学符号而不是 TypeScript 紧凑地编写）：

Variable(name) And(f1,f2) Or(f1,f2) Not(f)
variables :
 Formula → Set<string>		 { name } variables(f1) ∪ variables(f2) variables(f1) ∪ variables(f2) variables(f)
evaluate :
 Formula × Map<string,boolean>
    → boolean		 map.get(name) evaluate(f1, map)
 ∧ evaluate(f2, map)		 evaluate(f1, map)
 ∨ evaluate(f2, map)		 ¬ evaluate(f, map)
conjunctiveNormalForm :
 Formula → Formula		 ... ... ... ...
... etc. ...

现在我们可以比较解释器模式和访问器模式在实现递归数据类型上的函数：

解释器
代码按列分组。 每个变体都有该变体的所有代码，实现所有操作。
访问器
代码按行分组。 一个操作的所有代码将位于一个访问器类中，包含处理所有变体的代码。

解释器模式使得添加新的 变体, because we don’t have to change any of our existing code: we just need to implement all the various operations as methods in the new variant class. All the code for the new variant class can be neatly added in one place.

访问器模式使得添加新的 操作. Instead of having to modify both the interface and every variant class, we just need to create a new visitor implementation with all the code for our new operation. There is no change to existing classes or interfaces. All the code for the new operation can be neatly added in one place.

因此，如果添加新操作是我们最希望准备好的变化，我们可能会选择定义一个访问器接口并将我们的函数写成访问器。

  • How could we use that inferred type to get static checking that we’ve covered all the cases?

There’s that default case throwing an exception again: we don’t have static checking to make sure we’ve covered all the variants (although this problem can be fixed with a little work, see the sidebar).

ParserLib 具有简单的优势，但在更复杂的解析包中，我们可能会发现 makeAST 使用访问器实现。 不同的具体语法树节点可能具有不同的类型，例如，根据其语法规则要求的形状，其子节点的数量和类型可以包含在静态类型中。

对具体语法树有效的方法通常对抽象语法树也很有帮助，实现者为 AST 的客户端提供访问器接口，以便他们可以通过递归遍历树来定义自己的操作。 例如，回想 IntegerExpression ADT 语法与解析阅读中的 。如果我们希望接口的客户端能够设计自己的操作，超越 IntegerExpression 提供的功能，我们可以定义一个访问器接口并 accept method in IntegerExpression. The interpreter and visitor patterns aren’t mutually exclusive; an interface can be defined with a set of methods like the interpreter pattern, but also provide an accept 方法以及配套的访问器接口。 许多递归 ADT 确实同时使用这两种模式。

总结

  • ADT 可以用来创建 领域特定语言 (DSL), which solves a class of related problems instead of a single one
    • DSL 可以是外部的，如正则表达式，也可以是内部的，如本课程中开发的音乐语言
  • 组合模式以相同的方式对待单个对象和对象组，它们属于同一类型
    • Music 是一个组合模式，其中 Note, Rest、 Concat 都实现了 Music
  • 解释器模式将代码 按列分组:
    • 将每个操作声明为定义数据类型的接口中的实例方法
    • 在每个具体变体中实现该操作
    • 这使得添加新变体更容易
  • The visitor pattern groups code by row，与解释器模式相反
    • 使用双重分派，访问器就像一个 switch 在 ADT 的具体变体上
    • 每个具体变体中的接受器方法将使用适当的访问器操作调用访问器，而访问器又将调用子具体变体的接受器方法，遍历 ADT 的递归结构
    • 这使得添加新操作更容易

思考我们代码质量的三个主要衡量标准：

  • Safe from bugs. 访问器模式克服了许多面向对象语言中缺失的功能，为我们提供了一种类型安全的方式来表示和实现递归数据类型上的函数，作为自包含的模块。

  • Easy to understand. 如果我们希望在未来向递归 ADT 添加新操作，使用访问器使我们的代码更容易理解，因为新操作的所有代码都在同一个地方，同时不牺牲静态检查提供的免受 bug 影响的安全性。

  • Ready for change. 如果我们正在构建一个 小语言 ，其中 ADT 的设计目的是允许客户端从我们的实现类外部在我们类型上定义自己的操作，访问器模式使这成为可能且可行。
