学习目标

今天课程的主题是调试。

首先，我们将探讨如何避免调试——即如何编写代码来完全避免调试，或者至少让调试变得更容易。

但有时你别无选择，只能进行调试——尤其是当 bug 只有在整个系统集成在一起时才会被发现，或者是在系统部署后由用户报告的情况下，这时可能很难将其定位到特定的模块。 对于这些情况，我们可以提出一个系统化的策略来进行更有效的调试。

一本关于系统化调试的好书是 Andreas Zeller 所著的 Why Programs Fail。 本次阅读的很多内容都受到那本书的启发。

另一篇相关的文章是 John Regehr 的 "How to Debug"，这是一门嵌入式系统课程的讲座，内容比 6.102 更底层，但系统化调试的一般原则是相同的。

最后，David Agans 所著的 Debugging: The Nine Indispensable Rules for Finding Even the Most Elusive Software and Hardware Problems 是一本通俗易懂、极具实用性的调试指南，涵盖了从软件到硬件再到汽车和管道等各种技术场景。 我们在本次阅读中引用了其中几条 九条规则。

常见 bug 集锦

在我们开始之前，让我们先回顾一下我们要解决的问题，列出一些常见的 bug 类别。你们应该已经在本次课程的前几篇阅读中或在自己的编程经验中遇到过其中的大部分。

别名 bug。当同一个可变对象有两个或多个别名，而其他别名需要它保持不变时，其中一个别名对其进行了修改，就会产生这种 bug。我们在设计规格说明以及抽象函数和表示不变量中看到过例子，因为不可变类型的表示暴露所导致的别名可能是一种特别出人意料且隐蔽的 bug。

差一 bug。此类 bug 的例子包括：

  • 0 基索引与 1 基索引之间的混淆。在你使用的日期处理函数中，月份是从 0 到 11 编号，还是从 1 到 12 编号？
  • 循环的终止条件。当逆向遍历数组时，终止条件应该是 i > 0 还是 i >= 0？或者当你处理数组中相邻的元素对 a[i] 和 a[i+1] 时，终止条件应该是 i < a.length 还是 i < a.length-1？
  • 栅栏柱 bug：如果你有 n 根横杆的栅栏，需要多少根栅栏柱？

顺序 bug。与别名 bug 和差一 bug 不同，这种 bug 没有常规的名称。但当不同的群体或上下文对顺序做出了任意的不同选择，或者取决于你对情境的心智模型时，就会出现这种 bug。例如，你是靠右行驶还是靠左行驶？即使你不开车，你走人行道的哪一侧？双开门的哪一侧？搞错了就会导致碰撞。编程中常见的顺序混淆包括：

  • 原点和 y 轴方向。在二维坐标系中，有时原点在左下角，y 轴向上增加（如大多数数学课堂中）；有时原点在左上角，y 轴向下增加（如几乎所有计算机图形学中）。
  • 坐标顺序。一个相关的二维混淆是：坐标是按 x,y 顺序指定（如几何学中，水平坐标在前），还是按行、列顺序指定（如矩阵索引中，水平坐标在后面！）
  • 复制。在复制或数据转移的修改器中，哪个应该是第一个参数，源还是目标？你应该写 copy(from,to) 还是 copy(to,from)？（在你觉得 copy(to,from) 毫无意义之前，赋值语句传统上使用什么顺序？to = from！所以确实存在这样的心智模型让它讲得通，两种顺序都出现在真实的 API 中。）

代码克隆 bug。正如我们在不要重复你自己中讨论过的那样，被克隆（复制粘贴）并改编到新位置的代码块是另一个 bug 的来源，因为改编可能不完整，对一个克隆的修改或修复可能无法传播到其他克隆。一项工具研究在 Linux 内核中发现了 28 个代码克隆 bug。

迭代时修改 bug。当你想要在遍历列表、映射或集合等数据结构的同时添加或删除元素时，就会出现这类 bug。我们在函数式编程阅读中见过这种 bug。

真正的昆虫。罕见，但有一个著名的故事。

第一道防线：让 bug 不可能发生

"犯错难以避免，但不重视预防错误是不可接受的。"

Zeller，《Why Programs Fail》，第 3 章

抵御 bug 最好的方法是从设计上让它们不可能发生。

我们已经讨论过的一种方式是静态检查。 静态检查通过在编译时捕获 bug 来消除许多 bug。

我们在前面的阅读中也看到了一些动态检查的例子。 例如，Python 通过动态捕获数组越界错误，使其不可能发生。 如果你试图使用列表边界之外的索引，Python 会自动产生错误。 JavaScript 就没那么好了，因为它对错误的读取会静默返回 undefined。 在 C 和 C++ 等更古老的语言中，情况更糟，它们会静默允许超出固定大小数组边界的错误写入，从而导致 bug 和安全漏洞。 事实上，在 2024 年 2 月，国家网络总监办公室发布了一份报告，详细说明了改善网络安全实践的多种方法，包括远离 C 和 C++ 等不内存安全的语言。

不可变性是另一种防止 bug 的设计原则，它有两种形式：不可变类型和不可重新赋值的引用（常量）。

String 是一种不可变类型。 没有任何方法可以在字符串上调用以改变它所代表的字符序列。 字符串可以安全地传递和共享，不用担心被其他代码修改。

TypeScript 还为我们提供了不可重新赋值的引用：使用 const 关键字声明的变量，它们只能被赋值一次，之后不能再被重新赋值。 在声明局部变量时，尽可能使用 const 是一个好习惯。 像变量的类型一样，这些声明是重要的文档，对代码读者很有用，并由编译器进行静态检查。

考虑这个例子：

const letters: Array<string> = ['a', 'e', 'i', 'o', 'u'];

letters 变量被声明为 const，但它真的不可变吗？以下哪些语句是非法的（会被编译器静态捕获），哪些是允许的？

letters = ['x', 'y', 'z'];
letters[0] = 'z';

你会在下面的练习中找到答案。注意 const 的含义！它只是让引用不可重新赋值，但引用指向的对象可能是可变的。

第二道防线：让 bug 易于发现

"我想说我是某种超级程序员——我从不犯错——但我只是普通人，和其他人一样。"

Zeller，《Why Programs Fail》，前言

静态检查、动态检查和不可变性在防止 bug 方面只能起到有限的作用，所以我们的下一个设计策略是在 bug 不可避免地出现时让它们更容易被发现。 我们可以将 bug 定位到程序的一小部分，这样就不需要大范围地搜索就能找到它们的原因。 当 bug 被定位到单个方法或小模块时，可能只需研究程序文本就能发现。

我们已经讨论过快速失败：问题被观察到的时间越早（越接近其原因），就越容易修复。

让我们从一个简单的例子开始：

/**
 * @param x  requires x >= 0
 * @returns approximation to square root of x
 */
function sqrt(x: number): number { ... }

现在假设有人用负数参数调用 sqrt。 sqrt 的最佳行为是什么？ 由于调用者未能满足 x 应为非负数的要求，sqrt 不再受其合同条款的约束，所以从技术上讲它可以为所欲为：返回任意值、进入无限循环、或者让 CPU 过热。 然而，由于错误的调用表明调用者存在 bug，最有用的行为应该是尽早指出这个 bug。 我们通过对前置条件进行运行时检查来实现这一点。 以下是我们可能编写该检查的一种方式：

/**
 * @param x  requires x >= 0
 * @returns approximation to square root of x
 */
function sqrt(x: number): number {
    if ( ! (x >= 0)) throw new Error("required x >= 0, but was: " + x);
    ...
}

当前置条件不满足时，这段代码通过抛出一个包含调用者传入值的信息性错误来终止程序。 调用者的 bug 的影响被阻止传播，调用者收到了关于其前置条件违反的有用信息。

检查前置条件是防御性编程的一个例子。 真正的程序很少是没有 bug 的。 防御性编程提供了一种即使你不知道 bug 在哪里，也能减轻 bug 影响的方法。

断言

为这类防御性检查定义一个函数是常见的做法，通常称为 assert。 这种方式将断言失败时具体发生什么进行了抽象。 失败的断言可能会退出程序；可能会在日志文件中记录一个事件；可能会向维护者发送电子邮件报告。

JavaScript/TypeScript 没有内置的 assert，但我们将在 6.102 中使用 Node 的 assert 包。 断言最简单的形式接受一个布尔表达式，如果布尔表达式计算为 false，则抛出 AssertionError：

assert(x >= 0);

断言还有一个额外的好处，就是记录了程序在该点关于状态的假设。 对于阅读你代码的人来说，assert(x >= 0) 表示"在这一点上，x >= 0 应该始终成立。" 然而，与注释不同，断言是可执行的代码，在运行时强制执行该假设。

断言还可以包含一个字符串消息，在断言失败时打印。这可以用来向程序员提供关于失败原因的额外细节。例如：

assert(x >= 0, "x is " + x);

如果 x === -1，那么这个断言会以错误消息失败：

x is -1

以及一个堆栈跟踪，它告诉你断言在代码中的哪个位置被发现，以及将程序带到该点的调用序列。 这些信息通常足以让你开始定位 bug。

关于断言需要注意的一点是，在许多语言（如 Java）中，它们默认是关闭的。 这意味着如果你像平常一样运行程序，你的所有断言都不会被检查！ 语言设计者可能选择这样做的一个原因是，检查断言有时对性能影响较大。 例如，一个使用二分搜索搜索数组的函数要求数组是有序的。 断言这个要求需要扫描整个数组，然而这将一个应该在对数时间内运行的操作变成了需要线性时间的操作。 在测试期间，你应该愿意（渴望！）付出这个代价，因为它使调试变得容易得多，但在程序发布给用户之后则不然。 然而，对于大多数应用程序来说，与代码的其余部分相比，断言并不昂贵，它们在 bug 检查方面提供的好处值得付出那一点点性能代价。

在断言默认关闭的语言中，确保显式启用它们。 我们在 6.102 中使用的 Node assert 库始终运行其断言语句，因此无需担心显式开启断言。

应该断言什么

以下是一些你应该断言的内容：

参数前置条件，就像我们上面 之前对 sqrt 看到的。

返回值后置条件。这种断言有时被称为自检。例如，sqrt 方法可能会将其结果平方，以检查它是否合理地接近 x：

function sqrt(x: number): number {
    assert(x >= 0);
    let r: number;
    ... // compute result r
    assert(Math.abs(r*r - x) < .0001);
    return r;
}

表示不变量。当然，我们已经一直在断言表示不变量了，即为每个抽象数据类型编写 checkRep 方法，并在操作中的适当位置调用它。

什么时候应该编写运行时断言？ 在你编写代码的时候，而不是事后。 当你编写代码时，你的脑海中已经有了不变量。 如果你推迟编写断言，你就不太可能去做，而且你可能会遗漏一些重要的不变量。

不应该断言什么

运行时断言并非没有代价。 它们可能会使代码变得杂乱，因此必须谨慎使用。 避免平凡的断言，就像避免无信息量的注释一样。 例如：

// don't do this:
x = y + 1;
assert(x === y+1);

这个断言不会在你的代码中发现 bug。 它发现的是编译器或 JavaScript 解释器中的 bug，这些是你应该信任的组件，除非你有充分的理由怀疑它们。 如果一个断言从其局部上下文来看是显而易见的，就不要写它。

永远不要使用断言来测试程序外部的条件，例如文件的存在性、网络的可用性或人类用户输入的正确性。 断言测试的是程序的内部状态，以确保它在其规格说明的范围内。 当断言失败时，它表明程序在某种意义上已经偏离了轨道，进入了一个它未被设计来正常运作的状态。 因此，断言失败表明存在 bug。 外部失败并不是你的系统中的 bug（它们甚至可能根本不是 bug！），而且你无法提前对程序做任何更改来防止它们的发生。 外部失败应该使用异常来处理。

如前所述，许多断言机制被设计为仅在测试和调试期间执行断言，当程序发布给用户时则关闭。 （重申一下，Node 断言不是这种情况，它们不能被禁用；但例如 Java 断言实际上默认是禁用的。） 由于断言有时被禁用，确保程序的正确性不依赖于断言表达式是否被执行是一个好习惯。 特别是，断言表达式不应该有副作用。 例如，如果你想从列表中弹出一个元素，并在弹出之前断言列表非空，不要这样写：

// don't do this:
assert(list.pop());

如果断言被禁用，整个表达式会被跳过，列表不会被弹出任何元素。应该这样写：

const found = list.pop();
assert(found);

类似地，如果一个条件语句没有覆盖所有可能的情况，使用检查来阻止非法情况是一个好习惯。

if (level == UNDERGRAD) {
  return 'U';
} else if (level == GRAD) {
  return 'G';
} else {
  assert.fail('should never get here');
}

这相当于断言 level 必须是 UNDERGRAD 或 GRAD。

增量开发

将 bug 定位到程序的一小部分的一个好方法是增量开发。 每次只构建程序的一小部分，并在继续之前彻底测试该部分。 这样，当你发现 bug 时，它更可能在你刚刚编写的部分中，而不是在一大堆代码的任何地方。

我们关于测试的课程讨论了两种有助于此的技术：

  • 单元测试：当你隔离地测试一个模块时，你可以确信你发现的任何 bug 都在该单元中——或者可能在测试用例本身中。
  • 回归测试：当你向一个大型系统添加新功能时，尽可能频繁地运行回归测试套件。如果测试失败，bug 可能在你刚刚更改的代码中。

我们还讨论过版本控制。 频繁地添加、提交和推送不仅是保存你的工作以免因断电而丢失的好方法， 也是保存可运行的、无 bug 的代码的好方法。 如果你经常添加、提交和推送可运行的代码，那么在 bug 出现的瞬间， 你可以将你的更改与上次保存的可运行版本进行比较，并从差异中调试。

模块化与封装

"好的设计不仅使程序更易于理解、维护、重构和复用，也更易于调试。"

Zeller，《Why Programs Fail》，第 4 章

你也可以通过更好的软件设计来定位 bug。

模块化意味着将系统划分为组件或模块，每个模块都可以独立于系统的其余部分进行设计、实现、测试、推理和复用。 模块化系统的反面是单体系统——庞大且所有部分相互纠缠、相互依赖。

由单个非常长的函数组成的程序是单体的——更难理解，也更难隔离 bug。 相比之下，分解为小函数和类的程序更加模块化。

封装意味着在模块周围建立墙壁，使模块对其自身内部行为负责，系统其他部分的 bug 无法破坏其完整性。

一种封装是访问控制，使用 public 和 private 来控制变量和方法的可见性和可访问性。 公共变量或方法可以被任何代码访问（假设包含该变量或方法的类也是公共的）。 私有变量或方法只能被同一类中的代码访问。 （通常有办法绕过访问控制，但只有通过编写底层或特殊代码才能实现，不太可能意外完成。） 尽可能将内容保持为私有，特别是对于变量，可以提供封装，因为它限制了可能无意中导致 bug 的代码。

另一种封装来自变量作用域。 变量的作用域是定义该变量的程序部分，即表达式和语句可以引用并可能更改变量的范围：

  • 函数参数的作用域是函数体。
  • 局部变量的作用域从其声明处延伸到下一个闭合花括号。
  • 未导出的全局变量的作用域从其声明处延伸到文件末尾。
  • 导出的全局变量在其被导入的每个其他模块中都处于作用域内。

尽可能缩小变量作用域使得推理 bug 在程序中的位置变得更加容易。 例如，假设你有这样一个循环：

for (i = 0; i < 100; ++i) {
    ...
    doSomeThings();
    ...
}

……你发现这个循环永远在运行——i 永远达不到 100。有人在某个地方修改了 i。 但在哪里？ 如果 i 被声明为全局变量，像这样：

let i: number;
...
for (i = 0; i < 100; ++i) {
    ...
    doSomeThings();
    ...
}

……那么它的作用域是整个模块。 它可能在文件中的任何地方被修改：被 doSomeThings()，被 doSomeThings() 调用的某个其他函数，被运行完全不同代码的并发线程。 但如果 i 被声明为作用域狭窄的局部变量，像这样：

for (let i = 0; i < 100; ++i) {
    ...
    doSomeThings();
    ...
}

……那么 i 可以被修改的唯一位置是在 for 语句内部——实际上，只在我们省略的 ... 部分中。 你甚至不需要考虑 doSomeThings()，因为 doSomeThings() 无法访问这个局部变量。

最小化变量作用域是定位 bug 的强大实践。 以下是一些对 TypeScript 有益的规则：

  • 始终在 for 循环初始化器中声明循环变量。所以不要在循环之前声明它：

    let i: number;
for (i = 0; i < 100; ++i) {

    这使得变量的作用域是包含这段代码的整个外层花括号块的其余部分，你应该这样做：

    for (let i = 0; i < 100; ++i) {

    这使得 i 的作用域仅限于 for 循环。

  • 始终使用 const 或 let，永远不要使用 var。 const 或 let 变量的作用域是包围它的最小花括号块，而 var 声明的作用域是包围它的整个函数（顺便说一下，这与 Python 局部变量使用的规则相同）。你会在网上看到很多使用 var 的旧 JavaScript 代码；避免使用它。现代 JavaScript/TypeScript 编程始终使用 const 或 let。

  • 只在首次需要时才声明变量，并在尽可能内的花括号块（最小作用域）中声明。 将变量声明放在包含所有需要使用该变量的表达式的最内层块中。 不要在函数开头声明所有变量——这会使它们的作用域不必要地变大。

  • 避免使用全局变量。 使用全局变量是一个非常糟糕的主意，特别是当程序变得庞大时。 使用全局变量作为捷径来在程序的多个部分之间共享一些数据可能很诱人；不要上当。 最好将参数传递给需要它的代码，而不是将其放在全局空间中，在那里它可能被无意中重新赋值。 或者更好的是，对全局变量的感知需求可能恰好是一个好机会，可以创建一个 ADT 来包含该状态，以便方法可以共享它。

使用科学方法定位 bug

要定位 bug 及其原因，你可以使用科学方法：

  1. 研究数据。 查看导致 bug 的测试输入，并检查由此产生的不正确结果、失败的断言和堆栈跟踪。

  2. 提出假设。 提出一个与所有数据一致的假设，关于 bug 可能在哪里，或者它不可能在哪里。 最好一开始让这个假设具有普遍性。

  3. 实验。 设计并运行一个测试你假设的实验。 最好一开始让实验成为一种观察——一个尽可能少干扰系统的探测。

  4. 重复。 将实验中收集的数据添加到之前已知的信息中，并做出新的假设。 希望你已经排除了一些可能性，缩小了 bug 可能的位置和原因的范围。

这种深思熟虑的过程对于每个 bug 都是不必要的。 有了良好的快速失败设计，你有望在非常接近 bug 源头的地方得到一个异常，堆栈跟踪会直接引导你找到它，错误通过检查代码就会显而易见。 那么什么时候需要应用科学方法呢？ 一个好的经验法则是10 分钟规则。 如果你已经花了 10 分钟使用临时的、非系统化的检查来搜索 bug，那么是时候退后一步，开始应用科学方法了。

作为这个过渡的一部分，你还应该将你的调试过程从你的脑海中移出来——你的脑海对你尝试过什么以及从中学到了什么的有限工作记忆——并开始记笔记，无论是在纸上还是在笔记本电脑上。 在过程的每次迭代中，你都会写下：

  • 假设。基于你目前学到的，你对 bug 的位置或原因的下一个假设是什么？
  • 实验。你即将尝试什么来验证或证伪这个假设？
  • 预测。根据你的假设，你预期实验的结果会是什么？
  • 观察。当你做实验时，实际发生了什么？

这些问题应该对你来说非常熟悉，来自你过去在科学课堂上的经验。 在接下来的几节中，我们将看到它们在调试代码时采取什么形式。 在调试中，一些假设和一些实验比其他的好。

2. 提出假设

程序实际失败的点——通过抛出异常或产生错误答案——不一定是 bug 所在的位置。 有 bug 的代码可能在最终失败之前已经通过程序的良好部分传播了一些错误值。所以你的假设应该是关于 bug 实际在哪里（或不在哪里），以及可能是什么原因导致的。

将你的程序视为数据流或算法中的步骤，并尝试一次排除整个程序的部分，可能会有所帮助。 让我们在 mostCommonWord() 例子的上下文中思考这个问题，用三个辅助函数进一步展开：

/**
 * Find the most common word in a string.
 * ...
 */
function mostCommonWord(text: string): string {
    let words: Array<string> = splitIntoWords(text);
    let frequencies: Map<string,number> = countOccurrences(words);
    let winner: string = findMostFrequent(frequencies);
    return winner;
}

mostCommonWord() 中的数据流如右图所示。

假设我们在 countOccurrences() 中得到了一个意外的异常。 这就是我们正在调查的失败。 然后我们可以排除该点下游的所有内容（即数据流中更晚的部分）作为 bug 的可能位置。 例如，我们不会通过查看 findMostFrequent() 来找到 bug，因为当失败发生时它甚至还没有被执行。

所以这里有一些与我们目前掌握的信息一致的假设。 它们按与失败的时间倒序排列：

  • bug 在 countOccurrences 中：其输入有效，但它抛出了异常
  • bug 在 splitIntoWords 和 countOccurrences 之间的连接处：两个函数都满足它们各自的契约，但前者保证的后置条件不满足后者期望的前置条件
  • bug 在 splitIntoWords 中：其输入有效，但它产生了错误的输出
  • bug 在 mostCommonWord 的原始输入中：text 不满足整个函数的前置条件

先尝试哪个假设？ 调试是一个搜索过程，你可以使用二分搜索来加速这个过程。 要进行二分搜索，你可以将这个数据流分成两半，也许猜测 bug 在第一个辅助函数和第二个之间的连接处，并使用下面的一个实验（如打印语句、断点或断言）来检查那里的值。 从那个实验的答案中，你会知道是应该在数据流的前半部分还是后半部分追踪 bug。

Delta 调试

隔离小测试用例的过程也可能为你提供有助于形成假设的数据，特别是如果它发现了两个紧密相关的测试用例，它们夹住了 bug，即一个成功，一个失败。 例如，也许 mostCommonWord("c c, b") 有 bug，但 mostCommonWord("c c b") 没问题。 现在你可以检查这两个测试用例执行之间的差异来帮助形成你的假设。 哪些代码在通过的测试用例中执行了，但在失败的测试用例中被跳过了，反之亦然？ 一个假设是 bug 就在那些代码行中，即通过运行和失败运行之间的增量。

这是 bug 查找中一个通用思想的具体例子，称为delta 调试，即通过比较成功运行和失败运行来尝试定位 bug。 另一种 delta 调试在回归测试开始失败时很有用。 使用你的版本控制系统，你检索仍然通过测试的最新版本，然后系统地探索旧的可运行版本和新的失败版本之间的代码更改，直到找到引入 bug 的更改。 Delta 调试工具可以自动化这种搜索过程，尽管像切片工具一样，它们尚未被广泛使用。

优先排序假设

在做出假设时，你可能需要记住，系统的不同部分有不同的失败可能性。 例如，旧的、经过充分测试的代码可能比最近添加的代码更值得信赖。 TypeScript 库代码可能比你的代码更值得信赖。 TypeScript 编译器和运行时、操作系统平台和硬件越来越值得信赖，因为它们经过了更多的测试和验证。 你应该信任这些较低层级，直到你有充分的理由不再信任它们。

断言，再探

我们已经详细讨论了一种探测：断言，用于测试变量值或其他内部状态。 在上面 x 永远不允许超过 100 的例子中，我们可以在任何点插入 assert(x <= 100); 作为探测。 断言的优势在于它们不需要你手动检查输出，甚至可以在调试后保留在代码中，如果测试是普遍成立的（一些调试断言只对你正在调试的特定测试用例成立，那些需要被移除）。 断言的缺点是，在许多语言（如 Java）中，它们默认不开启，所以你可能会被看似通过但实际上根本没有运行的断言所欺骗。

打印语句与日志

另一种熟悉的探测是打印语句。 打印调试 （出于历史原因也称为 printf 调试 ）， 其优势在于它几乎适用于每一种编程语言。 其缺点在于它对程序进行了更改，你必须记得撤销。 经过长时间的调试后，程序中到处都是打印语句太容易了。 在编写调试打印语句时，稍微深思熟虑一下也是明智的。 与其在十五个不同的地方打印相同的 hi! 来追踪程序的执行方式，并失去对哪个是哪个的跟踪，不如打印一些清晰且具有描述性的内容，如 start of calculateTotalBonus。

一种更复杂的打印调试方式是日志，它将信息性的打印语句永久保留在代码中，并通过全局设置来开启或关闭它们，比如布尔值 DEBUG 常量或日志级别变量。 日志级别思想的一个简单版本可以在标准 JavaScript console API中找到，它不仅提供 console.log()，还提供 console.info()、console.warn() 和 console.error()，代表所显示消息越来越高的重 要性级别。 console 框架允许用户过滤日志输出以隐藏不太重要的消息，而发送到最关键日志级别（如 console.error()）的消息通常以红色显示，以便无论过滤器如何都能突出显示。 像 winston 这样更复杂的日志框架还可以将日志定向到文件或网络上的服务器，可以记录结构化数据以及人类可读的字符串，并且可以在部署环境中使用，而不仅仅是开发中。 如果没有日志，大型复杂的系统将非常难以运营。

像断言一样，你必须注意不要在打印或日志探测中引入副作用。 例如，考虑以下函数：

function recursiveHelper(arr: Array<number>): number {
  // base case 
  ...
  return recursiveHelper(arr);
}

不要像下面这样进行打印调试：

function recursiveHelper(arr: Array<number>): number {
  // base case 
  ...
  console.log("recursiveHelper returning:", recursiveHelper(arr)); // BAD BAD BAD
  return recursiveHelper(arr);
}

将返回值提取到一个常量中，然后打印并返回它，安全得多：

function recursiveHelper(arr: Array<number>): number {
  // base case 
  ...
  const output = recursiveHelper(arr);
  console.log("recursiveHelper returning:", output);
  return output;
}

将输出保存到常量中可以防止意外的副作用，并避免因执行两次相同代码而导致的（可能很大的）运行时增加， 并确保记录的值确实是正在返回的值。

最后，关于 TypeScript/JavaScript 中的打印调试说几句。 一些内置类型，包括 Map 和 Set，有非常无用的 toString() 方法。 这意味着如果你试图使用，比如说，console.log("map is " + map) 来调试，你可能会看到类似 "map is [object Map]" 这样无用的内容。 有两种方法可以改善这个问题：

  • 使用多个参数给 console.log()，而不是依赖 + 和 toString()：

    console.log("map is", map);

    这意味着 console.log() 负责显示 map 对象，它在展示其内部内容方面做得更好。

  • 使用 util.inspect() 将对象转换为字符串：

    import util from 'util';
console.log("map is " + util.inspect(map));

替换组件

如果你假设 bug 在某个模块中，而你恰好有一个满足相同接口的不同实现，那么你可以做的一个实验就是尝试替换为替代方案。 例如：

  • 如果你怀疑你的 binarySearch() 实现，那么用更简单的 linearSearch() 替代它。
  • 如果你怀疑 JavaScript 运行时，用不同的 web 浏览器或不同版本的 Node 运行。
  • 如果你怀疑操作系统，在不同的 OS 上运行你的程序。
  • 如果你怀疑硬件，在不同的机器上运行。

然而，你可能会浪费大量时间替换正常的组件，所以除非你有充分的理由怀疑某个组件，否则不要这样做。 正如我们在优先排序假设中讨论的，编程语言、操作系统或硬件应该在你的嫌疑人列表中排在非常靠后的位置。

一次只处理一个 bug

在你试图调试一个问题的同时发现其他问题并不罕见。 也许你注意到其他模块返回了错误的答案。 也许在你阅读自己的代码（实际上相当于自我代码审查）时，你注意到需要修复的明显错误。

维护一个 bug 列表。 这帮助你在调试过程中处理新出现的问题。 把它们写在 bug 列表上，以便之后回来处理。 bug 列表可以简单到纸质笔记本或文本文件。 对于团队软件开发，像 GitHub 的 Issues 标签这样的在线 bug 跟踪器是最佳方法。

不要从你正在处理的 bug 上分心。 思考新问题是否为你正在处理的 bug 提供了有用的数据——它是否引出了新的假设？ 但不要立即开始对新 bug 进行递归调试，因为你可能很难从心理上退回到原来的 bug。 在调试时也不要随意编辑你的代码，因为你不知道这些更改是否会影响你的调试实验。 让你的代码更改专注于一次仔细、受控地探测一个 bug。

如果新问题干扰了你调试的能力——例如，通过间歇性崩溃程序，使你无法可靠地运行实验——那么你可能需要重新调整修复 bug 的优先级。 放下当前的 bug（回退或注释掉你的实验探测，并确保该 bug 在你的 bug 列表上以便稍后修复），转而处理新的 bug。

先不要修复

试图做一个看起来能修复假设 bug 的实验，而不是仅仅探测，这种诱惑很强烈。 这几乎总是错误的做法。 首先，它导致了一种临时猜测和测试式的编程，产生糟糕的、复杂的、难以理解的代码。 其次，你的修复可能只是掩盖了真正的 bug，而没有真正消除它——治标不治本。

例如，如果你遇到了 RangeError，不要只是添加捕获异常并忽略它的代码。确保你理解为什么会抛出那个异常，并修复导致它的真正问题。

4. 重复

实验之后，反思结果并修改你的假设。 如果你观察到的结果与假设预测的不一致，那么拒绝该假设并提出新的假设。 如果观察结果与预测一致，那么细化假设以缩小 bug 的位置和原因。 然后用这个新的假设重复该过程。

保留审计跟踪

这是 Agans 九条调试规则之一：保留审计跟踪。

如果一个 bug 需要超过几分钟才能找到，或者需要研究-假设-实验循环的几次迭代，那么你需要开始写下来，因为你的大脑短期记忆会很快失去对什么有效什么无效的跟踪。

在文本文件中记录你做了什么、按什么顺序、以及结果如何。 包括：

  • 你目前正在探索的假设
  • 你目前正在尝试的测试该假设的实验
  • 你作为实验结果观察到的：
    • 这次测试是否通过
    • 程序输出，特别是你自己的调试消息
    • 任何堆栈跟踪

系统化调试技术很快就会超出你的大脑跟踪能力，所以早点开始写下来。 最小化测试用例和 delta 调试通常需要多次迭代才能找到答案。 如果你不写下你正在尝试哪个测试用例以及它是否通过，那么你将很难跟踪你正在做什么。

检查电源插头

如果你一直在对一个 bug 反复迭代但一切都不合理，考虑 Agans 的另一条规则：检查电源插头。 这意味着你应该质疑你的假设。 例如，如果你打开机器的电源开关，但机器没有启动，也许你不应该调试开关或机器——而是问机器是否插上了电源？ 或者电源插座本身是否有电？

编程中"检查电源插头"的一个例子是确保你的源代码和目标代码是最新的。 如果你的观察结果似乎都不合理，一个可能的假设是你正在运行的代码（目标代码）与你正在阅读的代码（源代码）不匹配。 为了测试这一点，从仓库中拉取最新版本，删除所有 JavaScript 输出文件（以 .js 结尾的文件），并重新编译你所有的 TypeScript 代码。

"检查电源插头"的另一个例子，当你调试一个失败的测试用例时，是仔细检查测试用例是否正确。 它是否提供了正确的输入，并检查了正确的输出？

调试的六个阶段：
1. 那不可能发生。
2. 那在我的机器上不会发生。
3. 那不应该发生。
4. 为什么会发生？
5. 哦，我明白了。
6. 那以前是怎么运行的？

如果你没有修复它，它就没有真正被修复

这是 Agans 的九条规则中的另一条。 在复杂系统中，有时 bug 会突然消失。 也许是你做了什么，但也许不是。 如果系统现在看起来运行正常，而你不知道 bug 是怎么被修复的……那么很可能它并没有被修复。 bug 只是再次隐藏了，被环境中的某些变化所掩盖，但准备好有朝一日再次露出丑陋的面目。 当我们稍后课程中讨论并发时，会看到一些这类棘手 bug 的例子。

系统化调试有助于建立信心，相信 bug 确实被修复了，而不仅仅是暂时隐藏。 这就是为什么你首先要复现 bug，这样你已经看到系统处于失败状态。 然后你在不修复的情况下理解 bug 的原因。 最后利用你对原因的了解来应用更改以修复 bug。 为了获得你已经真正修复它的信心，你想看到你的更改导致系统从失败状态转变为正常状态，并理解为什么。

修复 bug

一旦你找到了 bug 并理解了它的原因，第三步就是设计一个修复方案。 避免草草打上补丁就继续前进的诱惑。 问问自己这个 bug 是编码错误，比如拼写错误的变量或互换的方法参数，还是设计错误，比如规格说明不充分或接口不足。 设计错误可能表明你应该退后一步重新审视你的设计，或者至少考虑失败接口的所有其他客户端，看看它们是否也受到该 bug 的影响。

查找相关 bug 和新引入的 bug。 想想代码的其他地方是否可能出现类似的 bug。 如果我在这里发现了一个除以零的错误，我在代码的其他地方是否也这样做了？ 努力使代码免受未来此类 bug 的侵害。 还要考虑你的修复会产生什么影响。 它会破坏其他代码吗？

撤销调试探测。 在查找 bug 的过程中，你可能注释掉了代码、添加了打印语句或做了其他更改，以便探测程序的行为或使其更快地调试。 现在，在你将修复提交到版本控制之前，撤销所有这些更改。查看 git diff 的输出是确保你已移除所有探测的好方法。

创建回归测试。 在你应用修复后，将 bug 的测试用例添加到你的回归测试套件中，并运行所有测试以确保 (a) bug 已修复，且 (b) 没有引入新的 bug。

添加、提交、推送并反思。 通过添加、提交和推送来保存你的可运行代码。 然后反思。哪些调试策略最有效？ 你如何防止类似情况在未来发生？ 你现在应该感到一种新的拥有感，并对你的系统有更深入的理解。 如果不是，那可能表明你只是暂时掩盖了 bug 的症状，而不是其原因。

其他建议

获得新鲜视角。

这是 Agans 九条调试规则中的另一条。 向别人解释你的问题通常很有帮助，即使对方完全不知道你在说什么。 这有时被称为橡皮鸭调试或泰迪熊调试。 有一个计算机实验室在他们的帮助台旁边放了一只大泰迪熊，规定在你尝试找人类求助之前，必须先"告诉熊"。 这只熊独自处理了惊人数量的问题。 大声说出你期望代码为什么能正常工作以及它实际在做什么，可以帮助你自己意识到问题。

书面描述。

当泰迪熊没有帮助时，试着撰写一封（假装的）寻求帮助的电子邮件。 大多数人没有时间阅读关于你的 bug 的论文， 但大多数人也不会在没有足够细节或努力证明的情况下愿意提供帮助。 以你的审计跟踪为指导，将自己限制在 1-2 段，并尽量简洁而不牺牲重要细节。

首先描述症状。 你在最小化 bug 方面付出的努力将帮助你制作一个最小可复现示例来包含在内（你也可以用它在线提问）。 预期行为与实际行为有什么不同？ 如果抛出了运行时错误，你能从中获取什么信息？ 试着将你的程序想象成一个物理系统；描述哪里出了问题。

然后描述你的实验。 你已经测试了哪些假设？ 你看了哪些 StackOverflow 帖子？ 为什么它们不足以解决这个 bug？

最后，重读并修改。问问自己： 如果我从别人那里收到这个 bug 报告，我会有能力帮助他们吗？ 你能精简任何描述吗？ 你真的尝试了所有可用的调试策略并穷尽了所有假设吗？ 在以正式书面形式描述 bug 的过程中， 你可能会获得新的见解，发现新的假设来测试，甚至解决这个 bug。

你简洁的问题报告在向课程工作人员寻求帮助时也可能派上用场 （毕竟，在实验课时间可能很宝贵！） 并且在未来撰写 bug 报告或向同事寻求帮助时也是很好的练习。

寻求帮助。

编程很难，bug 不可避免。 6.102 的工作人员和同学通常知道你在说什么，所以他们更适合寻求帮助。 在这个课堂之外，你可以从其他团队成员、同事或 StackOverflow 获得新鲜视角。

睡一觉。

如果你太累了，你就不会是一个高效的调试者。 用时间换取效率。

总结

在本次阅读中，我们探讨了一些最小化调试成本的方法，以及如何进行系统化调试：

  • 避免调试
    • 通过静态类型、自动动态检查和不可变性等技术使 bug 不可能发生
  • 将 bug 限制在局部
    • 使用断言快速失败可以防止 bug 的影响扩散
    • 增量开发和单元测试将 bug 限制在你最近的代码中
      • 经常添加、提交和推送可运行的代码！
    • 模块化、封装和作用域最小化减少了你需要搜索的程序范围
  • 系统化地调试
    • 将 bug 复现为测试用例，并将其放入你的回归测试套件
    • 使用科学方法定位 bug：
      • 使用二分搜索和 delta 调试生成假设
      • 使用最小侵入性的探测，如打印语句、断言或调试器，来观察程序行为并测试你的假设预测
    • 深思熟虑地修复 bug

思考我们代码质量的三个主要衡量标准：

  • 免受 bug 侵害。我们正在努力预防它们并消除它们。
  • 易于理解。静态类型、const/readonly 声明和断言是对代码中假设的额外文档。变量作用域最小化使读者更容易理解变量的使用方式，因为需要查看的代码更少了。
  • 适应变化。断言和静态类型以自动可检查的方式记录假设，以便当未来的程序员更改代码时，那些假设的意外违反会被检测到。
