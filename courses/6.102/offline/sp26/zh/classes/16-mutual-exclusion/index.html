学习目标

本阅读将并发和 Promise 的概念结合在一起，在异步抽象数据类型的语境下——一种具有异步操作的 ADT，这些操作可能彼此并发运行，访问相同的共享（可变）表示。

我们将看到这如何增加并发 Bug 的风险，例如竞态条件和死锁，它们威胁着 ADT 努力保证的不变量和规约。

通过推理并发代码的交错，并利用互斥（代码独自运行而不交错的时间段），我们可以防御这些 Bug。

图书馆示例

作为一个贯穿始终的示例，让我们思考一个允许用户借书和还书的图书馆。首先，我们需要的类型来表示书籍和用户：

// Book represents a physical copy of a book.
// Equality operation is ===, safe for use in sets and maps.
class Book { ... }

// User represents a human patron of the library.
// Equality operation is ===, safe for use in sets and maps.
class User { ... }

操作已被省略，因为我们不会在用户或书籍上调用任何操作，只是将它们用于身份标识。

这是图书馆，及其两个关键操作 checkout 和 checkin：

// Library represents a mutable collection of books that can be borrowed by users.
// At any time, there is a set of books physically present at the library,
// and for each user, a set of books borrowed by that user.
// These sets are all disjoint because a book can't be in two places at once.
interface Library {

    /**
     * Check out every book in `books` so that `user` is now borrowing it.
     * Requires every book in `books` to be physically present at the library.
     */
    checkout(books: Array<Book>, user: User): void;

    /**
     * Check in every book in `books` so that it is physically in the library.
     * If any such book was previously borrowed by a user, it is now back in the library.
     */
    checkin(books: Array<Book>): void;

}

checkout 的这个初始规约相当薄弱，我们将对其进行迭代改进。 这个操作的设计在其他方面也有问题，这将揭示我们在并发编程世界中面临的一些挑战。

同步 ADT

让我们开始实现这个薄弱的规约，使用一个直接表示抽象中提到的集合的简单表示：

class MITLibrary implements Library {

    private inLibrary: Set<Book> = new Set();
    private borrowed: Map<User, Set<Book>> = new Map();

    // AF(inLibrary, borrowed) = the library such that 
    //    the books physically present is the set `inLibrary`,
    //    and the books borrowed by user u are borrowed.get(u)

    // Rep invariant:
    //   the sets of books of `inLibrary` and `borrowed` are all disjoint

    // Safety from rep exposure: 
    //   - all rep fields are private; 
    //   - the mutable Set and Map types in the rep are not taken 
    //     or returned by any of the public methods;
    //   - Book and User are aliased with clients, but are used
    //     only for their equality operation (which they specify 
    //     as safe for use in sets and maps).

    private checkRep(): void {
        // assert that every book in the rep appears exactly once
        const allBooks: Set<Book> = new Set(this.inLibrary);
        this.borrowed.values().forEach((borrowedBooks:Set<Book>) => {
            borrowedBooks.forEach((book: Book)=> {
                assert( ! allBooks.has(book) );
                allBooks.add(book);
            });
        });
    }

    public constructor() {
        this.checkRep();
    }

    /** @inheritdoc */
    public checkout(books: Array<Book>, user: User): void {
        // borrow the books
        for (const book of books) {
            this.inLibrary.delete(book);
            this.borrowedByUser(user).add(book);
        }

        this.checkRep();
    }

    /** @inheritdoc */
    public checkin(books: Array<Book>): void {
        for (const book of books) {
            // book is no longer borrowed, so remove it from all borrowed sets
            for (const borrowedBooks of this.borrowed.values()) {
                borrowedBooks.delete(book); // at most one of these sets has the book
            }

            // book is back in the library
            this.inLibrary.add(book);
        }

        this.checkRep();
    }

    /**
     * @returns mutable set of books borrowed by `user`,
     * creating the set if `user` hasn't borrowed before
     */
    private borrowedByUser(user: User): Set<Book> {
        let books = this.borrowed.get(user);
        if (books === undefined) {
            books = new Set();
            this.borrowed.set(user, books);
        }
        return books;
    }
}

异步方法

checkout 有一个问题，图书馆的读者很快就会发现：如果一本书目前不在图书馆怎么办？例如：

library.checkout([fellowship], bilbo);
// ... sometime later, Frodo comes along:
library.checkout([fellowship], frodo);

先是 Bilbo 借了《魔戒同盟》，现在 Frodo 也要借。按照当前的规约，这第二次调用实际上是非法的，因为它违反了所有请求的书必须实体存在于图书馆中的前置条件。但 Frodo 怎么会知道呢？即使我们给 Frodo 一个观察者操作来检查他想要的书是否在图书馆中从而避免违反前置条件，他仍然需要以某种方式等待，直到所有的书都归还。checkout 对客户来说是一个难以使用的操作。

让我们通过将 checkout 改为异步来解决这个问题。checkout 不会要求在调用时所有书都在图书馆中，而是等待它们被归还，然后借出。等待将通过返回一个 Promise 来实现：

/**
 * Check out every book in `books` so that `user` is now borrowing it.
 * If any of them is not in the library, waits until it is checked in,
 * resolving the promise only when all the books have been successfully borrowed by `user`.
 */
checkout(books: Array<Book>, user: User): Promise<void>;

现在我们可以设想 Frodo 和 Bilbo 各自运行在独立的异步函数中，与图书馆交互并等待 Promise：

await library.checkout([fellowship], bilbo);
... // Bilbo spends some time reading the book
library.checkin([fellowship]);
await library.checkout([fellowship], frodo);
... // Frodo spends some time reading the book
library.checkin([fellowship]);

我们如何实现异步的 checkout？这是我们可能尝试的草图：

public async checkout(books: Array<Book>, user: User): Promise<void> {

            // book is checked out right now
            // TODO -- wait somehow
        }

        this.inLibrary.delete(book);

操作的第一部分检查每本书是否在图书馆中。如果是，则立即进入第二部分，将它们全部借出并返回。

但如果其中一本当前已被借出，我们就会到达 TODO 部分。我们需要想办法等到那本书被归还。

做出并遵守承诺

当一本书缺失时，我们需要等待它被归还到图书馆。让我们创建一个代表该事件的 Promise。然后 checkout 可以 await 该 Promise，这就是它实现等待的方式。谁将 resolve 这个 Promise，向 checkout 发出可以继续的信号？这将发生在 checkin 操作体中，在书被归还的那一刻。

在我们深入之前，我们需要再次审视 Promise ADT。ADT 由其操作定义，那么 Promise 有哪些操作？到目前为止我们只见过 await，它充当观察者。

但创建者呢？我们目前使用的所有 Promise（用于定时器、文件 I/O 和网页加载）都是由底层库为我们创建的。现在我们处于一种情况，即我们自己的代码需要创建一个 Promise，该 Promise 将由我们自己代码内部的事件 resolve。不涉及时钟或 I/O 系统等外部设备。所以我们也需要能够创建 Promise。

Promise 是一个可变的东西——它的修改者操作在哪里？它的状态如何从 pending 变为 fulfilled 或 rejected？

这个问题的答案在于 Promise 有两个不同的客户端：Promise 的消费者，使用 await 来获取其值；以及承诺者，即为 Promise 计算值的代码。Promise 的设计使得只有承诺者应该能够访问改变 Promise 状态的 resolve() 和 reject() 修改者。

承诺者需要一个新的 Promise<T> 对象，加上其关联的修改者操作 resolve 和 reject。这可以通过工厂函数 Promise.withResolvers() 来实现，它返回一个包含三个属性的 记录类型：

  • promise:Promise<T> 是新的 Promise
  • resolve:(t:T)->void 是用值 t resolve Promise 的修改者
  • reject:(err:Error)->void 是用给定错误 reject Promise 的修改者

这种设计的一个重要结果是，只有承诺者——创建 Promise 的代码——才能访问 resolve 和 reject 修改者。这些修改者不是 Promise 对象上的公共实例方法。（Promise 类确实有名称诱人的 resolve() 和 reject() 方法，但事实证明这些是静态工厂方法，用于创建已经 resolve 或已经 reject 的 Promise——而不是 resolve 或 reject 现有 Promise 的修改者。）

更方便的管理方式是创建一个抽象数据类型 Deferred<T>，它将 Promise<T> 与其修改者捆绑在一起：

  • new Deferred<T>() 创建一个新的 Deferred<T> 对象
  • deferred.promise 是与 Deferred 对象关联的 Promise<T>
  • deferred.resolve(t:T) 用值 t resolve 关联的 Promise
  • deferred.reject(err:Error) 用给定错误 reject 关联的 Promise

所以 Deferred 具有承诺者所需的必要修改者。承诺者持有此对象以便稍后修改 Promise。承诺者将关联的 Promise 值传递给 Promise 的消费者，用于 await。

Deferred 不存在于标准的 Node 或 JavaScript 库中，但可以使用 Promise.withResolvers() 轻松实现。

异步方法做出承诺

让我们使用 Deferred 方法来做出承诺，因为它有一个很好的特性，即将 resolve/reject 修改者与 Promise 一起包装在单个对象中。这个 Deferred 对象将代表现实图书馆中一个熟悉的概念：预约一本书。当 checkin 最终看到书归还到图书馆时，它会查找该书的预约并调用 resolve() 来 resolve Promise，从而使等待中的 checkout 能够恢复。

多个用户可能同时等待预约同一本书，所以每本书需要一个预约队列，我们将用数组来表示：

private holds: Map<Book, Array<Deferred<void>>>;

当 checkout 想要等待一本书时，它创建一个 Deferred 对象，将其放入预约队列，并等待其 Promise。新代码以黄色高亮显示：

public async checkout(books: Array<Book>, user: User): Promise<void> {
    // wait for all the books to be returned
    for (const book of books) {
        if ( ! this.inLibrary.has(book) ) {
            // book is checked out right now, so
            // put ourselves on the hold queue and wait
            const hold = new Deferred<void>();
            this.holdsForBook(book).push(hold);
            await hold.promise;
        }
    }

    // borrow the books
    for (const book of books) {
        this.inLibrary.delete(book);
        this.borrowedByUser(user).add(book);
    }

    this.checkRep();
}

/**
 * @returns mutable hold queue for `book`,
 * creating the hold queue if it doesn't already exist
 */
private holdsForBook(book: Book): Array<Deferred<void>> {
    ... // similar to borrowedByUser() helper method
}

之后，当 checkin 看到书归还时，它找到预约并 resolve 它：

public checkin(books: Array<Book>): void {
    for (const book of books) {
        // book is no longer borrowed, so remove it from all borrowed sets
        for (const borrowedBooks of this.borrowed.values()) {
            borrowedBooks.delete(book); // at most one of these sets has the book
        }

        // book is back in the library
        this.inLibrary.add(book);

        // wake up the first person on the hold queue for this book (if any)
        const holds = this.holds.get(book);
        if (holds !== undefined) {
            const deferred = holds.shift();
            if (deferred !== undefined) {
                deferred.resolve();
            }
        }
    }

    this.checkRep();
}

让我们看看这在我们两个并发读书者 Bilbo 和 Frodo 的一种可能交错下是如何工作的：

await library.checkout([fellowship], bilbo);
... // Bilbo spends some time reading the book
library.checkin([fellowship]);
await library.checkout([fellowship], frodo);
... // Frodo spends some time reading the book
library.checkin([fellowship]);

  1. 假设 Bilbo 先调用 checkout。他拿到了书，checkout 立即返回，其 Promise 已 fulfilled，Bilbo 开始愉快地阅读。

  2. 现在 Frodo 调用 checkout，发现书不在图书馆，于是预约了它。Frodo 对 checkout 的调用返回了一个 Promise，Frodo 现在正在等待它（并且该 Promise 与预约的 Promise 绑定，因为这次 checkout 调用正在等待 await hold.promise 之后恢复）。

  3. 最终 Bilbo 调用 checkin，它首先将书放回图书馆，然后找到预约并 resolve 与该预约关联的 Promise。

  4. 这使得 Frodo 的 checkout 可以越过 await 完成将书借给 Frodo。

  5. Frodo 读完书，然后调用 checkin 将书归还到图书馆。

如果 Frodo 在借书竞赛中胜出，计算将以同样的方式演变，只是 Frodo 和 Bilbo 的角色互换：

  1. Frodo 借了书。

  2. Bilbo 预约了书并等待。

  3. Frodo 归还了书。

  4. Bilbo 完成了借书。

  5. Bilbo 归还了书。

竞态条件

但我们的图书馆并非一切安好。让我们看看这三个借书者会发生什么：

这里是一种可能的交错，没有问题：

  1. Bilbo 借了《双塔奇兵》。

  2. Frodo 看到《魔戒同盟》还在图书馆，预约了《双塔奇兵》，然后等待。

  3. Bilbo 归还了《双塔奇兵》并为 Frodo 释放了预约。

  4. Frodo 恢复执行，完成了两本书的借出。

  5. Gandalf 尝试借《魔戒同盟》，并预约了它。

  6. Frodo 归还了两本书，并为 Gandalf 释放了《魔戒同盟》的预约。

  7. Gandalf 完成了《魔戒同盟》的借出，阅读后归还。

但这里是另一种交错，结果就不那么好了（不同的步骤以黄色高亮显示）：

  1. Bilbo 借了《双塔奇兵》。

  2. Frodo 看到《魔戒同盟》还在图书馆，预约了《双塔奇兵》，然后等待。

  3. Gandalf 借了《魔戒同盟》。

  4. Bilbo 归还了《双塔奇兵》并为 Frodo 释放了预约。

  5. Frodo 恢复执行，在等待了两本书之后，完成了《魔戒同盟》和《双塔奇兵》的借出。

不幸的是，Frodo 在最后一步是错误的！当 Frodo 等待《双塔奇兵》时，Gandalf 趁机抢走了《魔戒同盟》。《魔戒同盟》已经不在图书馆了。

这个 checkout 实现有一个竞态条件，因为它对某些交错能正确工作，但对另一些则不行。如果 Gandalf 恰好在 Frodo 等待《双塔奇兵》期间借走了《魔戒同盟》，那么程序就会失败。并发程序的正确性不应取决于时间上的偶然性。这就是为什么调试竞态条件可能具有挑战性，因为只有某些交错可能暴露 Bug，这使得发现和复现变得困难。

修复竞态

这是修复我们刚才发现的竞态条件的一种自然方式：checkout 可以尽快借出每本书，而不是等到方法末尾。

public async checkout(books: Array<Book>, user: User): Promise<void> {
    for (const book of books) {
        if ( ! this.inLibrary.has(book) ) {
            // book is checked out right now, so
            // put ourselves on the hold queue and wait
            const hold = new Deferred<void>();
            this.holdsForBook(book).push(hold);
            await hold.promise;
        }
        // borrow the book right away
        assert(this.inLibrary.has(book));
        this.inLibrary.delete(book);
        this.borrowedByUser(user).add(book);
    }

    this.checkRep();
}

死锁

这里是一种可能的交错：

  1. Bilbo 借了《双塔奇兵》

  2. Frodo 看到《魔戒同盟》还在图书馆，立即将它标记为已借给自己。

  3. Frodo 预约了《双塔奇兵》，然后等待。

  4. Gandalf 立即将《王者归来》借给自己。

  5. Gandalf 预约了《双塔奇兵》，然后等待。

  6. Bilbo 归还了《双塔奇兵》并为 Frodo（预约队列中的第一个人）释放了预约。

  7. Frodo 恢复执行，立即将《双塔奇兵》借出。

  8. Frodo 预约了《王者归来》，然后等待。

现在我们卡住了。Frodo 在等待《王者归来》，这本书目前在 Gandalf 手中。但 Gandalf 在等待《双塔奇兵》，这本书在 Frodo 手中。他们都无法取得进展，直到对方释放预约。Frodo 和 Gandalf 陷入了"死亡拥抱"，它们将永远无法完成等待。

死锁发生在并发模块互相等待对方做某事时。死锁可能涉及两个以上的模块，例如 A 可能在等待 B，B 在等待 C，C 在等待 A。它们都无法取得进展。死锁的本质特征是这样的依赖循环。

交错与互斥

为了应对 checkout 中的竞态和死锁，我们需要更加悲观地思考。每次我们 await 一个 Promise，我们就放弃了控制权。其他异步代码可能在此期间交错。可能出什么问题？我们依赖什么？当我们重新获得控制权时，可能需要再次检查一些事情。

其次，我们需要延迟进行变更，直到一切就绪，然后一次性完成所有变更，而不会在变更进行到一半时失去控制权。

这引出了并发编程的两个重要思维习惯：

  • 危险的交错可能在哪里发生？ 在我的代码中，哪些地方其他并发运行的代码可能引起问题？

  • 交错绝对不能在哪里发生？ 我的代码中哪个部分需要运行而不被任何并发代码中断？

第一个问题帮助我们识别潜在的竞态条件，即我们需要防御并发 Bug 的地方。

第二个问题问的是我们应该在哪里建立一道墙来防御这些 Bug，通过利用或创建我们可以安全、独立地访问共享可变数据而不被其他并发代码干扰的时间段。

在单线程 TS/JS 编程模型中，交错问题实际上比其他并发模型更容易回答。任何 await 都是你的代码放弃控制权并允许并发代码运行的地方。在此期间，JS 运行时系统可能允许另一个 async 函数从其 await 处恢复。对于像 Library 这样的 ADT，这可能意味着已经在进行的异步操作可能恢复执行（例如 checkout 从 await 处恢复），或者异步客户端可能调用一个新的 ADT 操作（checkout 或 checkin）。

然而，在那些 await 点之间的代码是连续执行的，不会放弃控制权。如果你有一段完全不包含 await 的代码，那么你可以确信没有其他异步代码会与它交错。代码可能提前结束（返回或抛出异常），但如果没有，如果控制权从另一端干净地出来，那么你就知道它是在没有中断的情况下运行的。

这种性质被称为互斥，指的是一个代码区域中同一时间只有一个计算在运行，而其他可能访问相同共享数据的并发计算被排除在运行之外。互斥是防止竞态条件的基本思想。

重新设计 checkout

让我们用这个想法来重新设计 checkout 的实现。该函数将有两个部分：

  • 首先，它将使用预约队列和 await 来确保所有书都在图书馆中。由于我们需要等待一个复杂条件满足（多本书同时归还），我们需要保守处理，可能需要反复运行此部分。

  • 在确认所有书都已归还后，我们将一次性全部借出，在一个精心编写以保证互斥的部分中完成，这样在我们完成之前没有书会消失。

让我们也将遍历书籍的 for 循环改为 map/filter 操作，这将允许我们使用 Promise.all() 等操作来同时等待多个 Promise。作为起点，让我们命名一些有用的谓词函数，使代码更具可读性和 DRY：

const isInLibrary = (book: Book) => this.inLibrary.has(book);
const notInLibrary = (book: Book) => ! isInLibrary(book);

现在我们可以说我们正在尝试建立的条件是 books.every(isInLibrary)，而尚未可用的书列表可以通过 books.filter(notInLibrary) 计算。

让我们还定义一个函数来等待缺失的书，通过像之前一样预约它：

const waitForBook = (book: Book) => { // requires notInLibrary(book)
    const hold = new Deferred<void>();
    this.holdsForBook(book).push(hold);
    return hold.promise;
};

现在我们可以用单个表达式收集所有需要的 Promise，并同时等待它们：

await Promise.all(books.filter(notInLibrary).map(waitForBook));

例如，这行代码可能会预约《魔戒同盟》和《双塔奇兵》（目前从图书馆借出），直到两本书都在某个时刻被归还到图书馆之前不会恢复。但它不能保证当 await 最终恢复时两本书仍在图书馆中。正如我们在上面的竞态条件中看到的，可能《魔戒同盟》先被归还，然后在我们还在等待《双塔奇兵》时又被借出了。

所以我们需要保守处理，再次检查期望的条件，可能还需要等待更多时间，也许是为一组新的缺失书籍。让我们将所有这些代码组合到一个循环中：

// wait for all the books to be returned
while ( ! books.every(isInLibrary)) {
    await Promise.all(books.filter(notInLibrary).map(waitForBook));
}

一旦我们通过这个循环，我们就知道所有想要的书现在都已归还到图书馆，所以我们可以一次性完成借出。这是完整的代码：

public async checkout(books: Array<Book>, user: User): Promise<void> {
    const isInLibrary = (book: Book) => this.inLibrary.has(book);
    const notInLibrary = (book: Book) => ! isInLibrary(book);
    const waitForBook = (book: Book) => { // requires notInLibrary(book)
        const hold = new Deferred<void>();
        this.holdsForBook(book).push(hold);
        return hold.promise;
    };

    // wait for all the books to be returned
    while ( ! books.every(isInLibrary) ) {
        await Promise.all(books.filter(notInLibrary).map(waitForBook));
    }

    // borrow the books:
    // this section must be mutually exclusive, because its correctness depends
    // on this property that we just established:
    assert(books.every(isInLibrary));
    // ... and those books have to stay until we've borrowed them all, so
    // no awaits allowed here!
    for (const book of books) {
        assert(isInLibrary(book));
        this.inLibrary.delete(book);
        this.borrowedByUser(user).add(book);
    }
    // we've finished borrowing all the books, so end of mutual exclusion;
    // we can now await again.

    this.checkRep();
}

我们通过这个精心设计所做的，是使 checkout 的借出部分相对于 Library 的其他方法具有原子性。一个原子操作实际上是立即发生的——它不会将其内部步骤与其他操作的步骤交错，并且在整个操作完成之前，操作的效果对其他异步函数不可见，所以它永远不会看起来是半完成的。

互斥的其他技术

TypeScript/JavaScript 程序在单进程单线程中运行，使用协作式（非抢占式）并发在并发模块之间传递控制权。在这种背景下，我们可以通过观察 await 点来推理交错并保证互斥。

相比之下，在具有多个线程共享相同可变数据的低级系统中，情况要复杂得多。线程使用抢占式并发，意味着一个线程可以在计算的任意点中断另一个线程，而不仅仅是在 await 这样的几个特定位置。当你在任何地方都可能被中断时，推理交错就变得更加复杂，使用锁、互斥锁或信号量等技术来创建互斥是必不可少的。抢占式并发不在 6.102 的范围内，但你可以在 6.180 [原 6.033] 计算机系统工程和 6.181 [原 6.039] 操作系统工程中学习。

另一种常见的并发访问可变共享数据的方法值得一提：数据库。数据库系统广泛用于 Web 应用程序等分布式客户端/服务器系统。数据库通过使用事务来避免竞态条件，事务为对数据库的一系列读写提供互斥。你可以在 6.583 [原 6.814] 数据库系统中了解更多关于事务的信息。

顺便说一下，TypeScript/JavaScript 并不是唯一支持通过 async 和 await 实现协作式并发的语言。这种方法也存在于 Python、Swift、Rust 和 C# 中。

总结

  • 设计异步 ADT 需要防范竞态条件和死锁
  • 实现像 Deferred<T> 这样的类型允许承诺者将 Promise 和修改者操作作为单个对象创建，这对实现异步方法很有用
  • 利用 await 表达式之间代码中的互斥简化了交错推理
    • 在 await 处，控制权总是会失去，其他异步 ADT 操作可能恢复，或者异步客户端可能调用 ADT 操作

生产一个免受 Bug 侵害、易于理解并适应变化的并发程序需要仔细思考。构建并发软件显然对这三个目标都是挑战。我们可以将问题分为两大类。当我们问一个并发程序是否免受 Bug 侵害时，我们关心两个性质：

  • 安全性。并发程序是否满足其不变量和规约？安全性问的是：你能证明某些坏事永远不会发生吗？竞态条件威胁安全性。

  • 活性。程序是否持续运行并最终做你想做的事，还是卡在某处永远等待永远不会发生的事件？你能证明某些好事最终会发生吗？死锁威胁活性。

在单线程 TypeScript/JavaScript 中，使用 async 和 await，仔细推理交错（其他并发代码可以夺取控制权的地点）和互斥（没有其他并发代码可以干扰的地方）对于保证这两个性质是必要的。
