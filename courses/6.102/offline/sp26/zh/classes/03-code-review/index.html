代码审查

代码审查 is careful, systematic study of source code by people who are not the original author of the code. It’s analogous to proofreading a paper.

代码审查实际上有两个目的：

  • 改进代码。 Finding bugs, anticipating possible bugs, checking the clarity of the code, and checking for consistency with the project’s style standards.
  • 提高程序员的能力。 Code review is an important way that programmers learn and teach each other — about new language features, changes in the design of the project or its coding standards, and new techniques. In open source projects, particularly, much conversation happens in the context of code reviews (here’s an example from TypeScript’s repository).

代码审查在开源项目中被广泛实践，例如 Apache 和 Mozilla. Code review is also widely practiced in industry. In Google’s code review process, for example, you can’t push any code into the main repository until another engineer has signed off on it in a code review.

Why is code review widely used? There are many ideas out there for software development processes (some with buzzwords like Agile and Scrum). But code review is a practice with good evidence that it actually works. Hillel Wayne 收集了一些研究亮点，其中包括代码审查可以发现 70-90% 的软件缺陷，以及 Google 和 Microsoft 的绝大多数软件工程师认为它很有价值且值得做。

In 6.102, we’ll do code review on problem sets, as described in the 代码审查文档 中描述的方式对问题进行代码审查。

风格标准

Most companies and large projects have coding style standards. These can get pretty detailed, even to the point of specifying whitespace (e.g., how deep to indent) and where curly braces and parentheses should go. These kinds of questions often lead to 圣战 因为它们最终成为品味和风格的问题。

In 6.102, we have no official style guide. If you are new to JavaScript and TypeScript and want a recommendation, Idiomatic JavaScript 因其可读性而很有吸引力，而 Google TypeScript Style Guide 很适合 TypeScript 相关的考虑。

Visual Studio Code 有一个自动格式化工具（右键单击并选择 格式化文档），其默认规则类似于 Google 风格。

But we won’t dictate where to put your curly braces in this class. That’s a personal decision that each programmer should make. It’s important to be self-consistent, however, and it’s 非常 important to follow the conventions of the project you’re working on. If you’re the programmer who reformats every module you touch to match your personal style, your teammates will hate you, and rightly so. Be a team player.

但有一些规则非常合理，针对我们的 三大属性 in a stronger way than placing curly braces. The rest of this reading talks about some of these rules, at least the ones that are relevant at this point in the course, where we’re mostly talking about writing basic TypeScript. These are some things you should start to look for when you’re code reviewing other students, and when you’re looking at your own code for improvement. Don’t consider it an exhaustive list of code style guidelines, however. Over the course of the semester, we’ll talk about a lot more things — specifications, abstract data types with representation invariants, concurrency and thread safety — which will then become fodder for code review.

Don’t repeat yourself (DRY)

Duplicated code is a risk to safety. If you have identical or very similar code in two places, then the fundamental risk is that there’s a bug in both copies, and some maintainer fixes the bug in one place but not the other.

Avoid duplication like you’d avoid crossing the street without looking. Copy-and-paste is an enormously tempting programming tool, and you should feel a frisson of danger run down your spine every time you use it. The longer the block you’re copying, the riskier it is.

Don’t Repeat Yourself、 DRY for short, has become a programmer’s mantra.

在编程教育的这个阶段，你希望已经学到了许多消除重复代码的策略，包括但不限于：

  • 用命名良好的局部变量替换重复的表达式；
  • 用循环替换重复的代码块（在同一位置）；
  • 用辅助函数替换重复的代码块（在不同位置）。

The dayOfYear example is full of identical code. How would you DRY it out?

在需要的地方添加注释

优秀的软件开发人员在代码中写注释，并且做得审慎。好的注释应该使代码更容易理解、更安全（因为重要假设已被文档化）、更适应变化。

One kind of crucial comment is a specification, which appears above a function or above a class and documents the behavior of the function or class. In TypeScript, this is conventionally written as a documentation comment, starting with /** 开头，包含 @语法，如 @param 和 @returns for functions. Here’s an example of a spec:

/**
 * Compute the hailstone sequence.
 * See https://en.wikipedia.org/wiki/Collatz_conjecture#Statement_of_the_problem
 * @param n starting number of sequence; requires integer n > 0.
 * @returns the hailstone sequence starting at n and ending with 1.
 *         For example, hailstone(3) = [3, 10, 5, 16, 8, 4, 2, 1].
 */
function hailstoneSequence(n: number): Array<number> {
    ...
}

Specifications document assumptions. We’ve already mentioned specs a few times, and there will be much more to say about them in a future reading.

另一种关键的注释是指定从其他地方复制或改编的代码的来源或出处。这对执业软件开发人员至关重要，也是 6.102 协作政策 在你改编从网上找到的代码时的要求。这里有一个例子：

// reverse a string of digits
// see https://stackoverflow.com/questions/1611427/reversing-a-string-in-javascript
const digitsReversed = digits.split('').reverse().join('');

记录来源的一个原因是避免侵犯版权。Stack Overflow 上的小段代码通常属于公共领域，但从其他来源复制代码可能涉及专有代码或其他类型的开源许可证，这些许可证限制更多。记录来源的另一个原因是借用的代码可能存在 bug 或已过时； Stack Overflow 帖子 这段代码来自的 不 对包含非 ASCII（即非英语）字符的字符串不起作用！

有些注释是不好且不必要的。例如，将代码直接翻译成英文对理解没有任何帮助，因为你应该假设读者至少了解 TypeScript：

while (n !== 1) { // test whether n is 1   (don't write comments like this!)
   ++i; // increment i
   l.push(n); // add n to l
}

但晦涩的代码应该加注释：

const sum = n*(n+1)/2;  // Gauss's formula for the sum of 1...n

// here we're using the sin x ~= x approximation, which works for very small x
const moonDiameterInMeters = moonDistanceInMeters * apparentAngleInRadians;

It’s often good to divide your code into 段落，具有明确目的的行组，并以注释作为主题句开始每个段落，解释该目的：

// prepare the rocket
...
...
...

// launch the rocket
...
...
...

// enter orbit
...
...

一旦你开始以这种方式思考你的代码，你可能会意识到其中一些或所有这些段落应该成为辅助函数，然后注释可能会自然地变成命名良好的函数调用：

prepareRocket(...);

清晰的名称通常消除了对注释的需求。

避免魔法数字

There’s a computer science joke that the only numbers that computer scientists understand are 0, 1, and sometimes 2.

所有其他常量被称为 魔法数字 因为它们似乎凭空出现，没有任何解释。

解释数字的一种方法是用注释，但更好的方法是将数字声明为具有良好、清晰名称的命名常量。

dayOfYear 充满了魔法数字，这说明了一些应该避免它们的原因：

  • 数字不如名称易读。 在 dayOfYear, the month values 2, …, 12 would be far more readable as FEBRUARY、…、 DECEMBER。

  • 常量未来可能需要更改。 使用命名常量，而不是在各个地方重复字面数字，更适应变化。

  • 常量可能依赖于其他常量。 在 dayOfYear, the mysterious numbers 59 and 90 are particularly pernicious examples. Not only are they uncommented and undocumented, they are actually the result of a 手工计算 by the programmer – summing the lengths of certain months. This is less easy to understand, less ready for change, and definitely less safe from bugs. Don’t hardcode numbers that you’ve computed by hand. Use a named constant that visibly computes the relationship in terms of other named constants.

那些看起来恒定不变的常量呢，比如 π、三角形的内角和，或引力常数 G? Is it necessary to give names to fundamental constants of mathematics and physics that don’t depend on other constants? First, the number itself may be complex to express, so repeating it multiple times is not safe from bugs. Is it easy to tell which is right: 3.14159265358979323846 或 3.1415926538979323846? Second, even these numbers encode design decisions that might change in the future, such as the number of digits of precision, or the units of measurement. A named constant is more ready for change when those design decisions change.

如果你的代码中有大量魔法数字，这可能表明你需要退一步，将这些数字 视为数据 rather than named constants, and put them into a data structure that allows for simpler code. In dayOfYear, the lengths of the months (30, 31, 28, etc.) would be more readable, and far more DRY, if they were instead stored in a data structure like a list or map, e.g. monthLength[month]。

每个变量一个用途

在 dayOfYear 示例中，参数 dayOfMonth 被重复使用来计算一个非常不同的值——函数的返回值，它不是月份中的日期。

Don’t reuse parameters, and don’t reuse variables. Variables are not a scarce resource in programming. Introduce them freely, give them good names, and just stop using them when you stop needing them. You will confuse your reader if a variable that used to mean one thing suddenly starts meaning something different a few lines down.

Not only is this an ease-of-understanding question, but it’s also a safety-from-bugs and readiness-for-change question.

Function parameters, in particular, should generally be left unmodified. (This is important for being ready-for-change — in the future, some other part of the function may want to know what the original parameters of the function were, so you shouldn’t blow them away while you’re computing.) It’s a good idea to use const 来表示尽可能多的变量是个好主意，因为 const keyword says that the variable should never be reassigned, and the TypeScript compiler will check it statically. Unfortunately, TypeScript does not (yet) support declaring a function parameter as const，以防止它在函数体内被重新赋值。

使用好的名称

好的函数和变量名称应该长且具有自描述性。通常可以通过使代码本身更具可读性来完全避免注释，使用描述函数和变量的更好名称。

例如，你可以将

const tmp = 86400;  // tmp is the number of seconds in a day (don't do this!)

重写为：

const secondsPerDay = 86400;

一般来说，像 tmp, temp更清晰，而 data 这样的变量名很糟糕——是程序员极度懒惰的症状。每个局部变量都是临时的，每个变量都是数据，所以这些名称通常没有意义。最好使用更长、更具描述性的名称，使代码本身就清晰可读。

Follow the lexical naming conventions of the language. In both Python and TypeScript languages, classes typically start with a capital letter, and variable names and function names start with a lowercase letter. But the two languages differ in how multi-word phrases are rendered into a function or variable name. Python uses snake_case （下划线分隔短语中的单词），而 TypeScript 使用 camelCase （第一个单词后的每个单词首字母大写，如 startsWith 或 getFirstName）。

Java-like languages also use capitalization to distinguish global constants (const declarations outside of any function) from variables and local constants. ALL_CAPS_WITH_UNDERSCORES is used for global constants. But the local variables declared inside a function, including local constants like secondsPerDay 上面的局部常量，使用 camelCaseNames。

在任何语言中，函数名通常是动词短语，如 getDate 或 isUpperCase，而变量和类名通常是名词短语。选择简短的词语，简洁明了，但避免缩写。例如， message 比 msg更清晰，而 word 比 wd. Keep in mind that many of your teammates in class and in the real world will not be native English speakers, and abbreviations can be even harder for non-native speakers.

Avoid single-character variable names entirely except where they are easily understood by convention. For example, x 和 y 对于笛卡尔坐标来说有意义，而 i 和 j 作为 for loops. But if your code is full of variables like e, f, g更清晰，而 h, because you’re just picking them from the alphabet, then it will be incredibly hard to read. Putting a little effort into choosing good names is worth the investment, because your code will need to be read (by you and by other people) more often than it’s written, and modern code editors make it easy to autocomplete a name.

Effectively Naming Software Thingies has some excellent advice about naming. Robert Martin’s Clean Code （第 2 章）也强烈推荐。

We’re not saying you should never press the Tab key; only that your editor should never put a tab character into your source file in response to your pressing the Tab key. The reason for this rule is that different tools treat tab characters differently — sometimes expanding them to 4 spaces, sometimes to 2 spaces, sometimes to 8. If you run git diff ，或者在不同的编辑器中查看源代码，缩进可能会完全混乱。只需使用空格。始终将你的编程编辑器设置为在按 Tab 键时插入空格字符。 That’s the default for Visual Studio Code。

Put a semicolon at the end of each statement when you are writing in a C-like language like TypeScript (or JavaScript, or C, or C++, or Java). Even though TypeScript/JavaScript has “automatic semicolon insertion” that puts in missing semicolons automatically, it doesn’t always do what you expect. Be consistent and punctuate all your statements.

同样，始终在 if, while、 for statement. Even though C-like languages allow you to omit the curly braces when the body contains only one statement, 这种快捷方式可能导致 bug. Be consistent and put curly braces around all blocks of code, no matter how many statements they have.

避免特殊情况代码

Programmers are often tempted to write special code to deal with what seem like special cases – parameters that are 0, for example, or empty arrays, or empty strings. The countLongWords 示例通过特殊处理空 words 数组而落入这个陷阱：

if (words.length === 0) {
    console.log("0");
    return;
}
let n = 0;
longestWord = "";
for (let word of words) {
    if (word.length > LONG_WORD_LENGTH) ++n;
    if (word.length > longestWord.length) longestWord = word;
}
console.log(n);

开头的 if statement is unnecessary. If it were omitted, and the words 数组为空，那么 for 循环什么都不做， 0 is printed anyway. In fact, handling this special case separately has led to a possible bug – a difference in the way an empty array is handled, compared to a nonempty array that happens to have no long words on it.

积极抵制单独处理特殊情况的诱惑。 如果你发现自己在为一个特殊情况编写 if statement for a special case, stop what you’re doing, and instead think harder about the general-case code, either to confirm that it can actually already handle the special case you’re worrying about (which is often true!), or put in a little more effort to make it handle the special case. If you haven’t even written the general-case code yet, but are just trying to deal with the easy cases first, then you’re doing it in the wrong order. Tackle the general case first.

Writing broader, general-case code pays off. It results in a shorter function, which is easier to understand and has fewer places for bugs to hide. It is likely to be safer from bugs, because it makes fewer assumptions about the values it is working with. And it is more ready for change, because there are fewer places to update when a change to the function’s behavior is made.

Some programmers justify handling special cases separately with a belief that it increases the overall performance of the function, by returning a hardcoded answer for a special case right away. For example, when writing a sort algorithm, it can be tempting to check whether the size of the list is 0 or 1 at the very start of the function, since you can then return immediately with no need to sort at all. Or if the size is 2, just do a comparison and a possible swap. These optimizations might indeed make sense — but not until you have evidence that they actually would matter to the speed of the program! If the sort function is almost never called with these special cases, then adding code for them just adds complexity, overhead, and hiding-places for bugs, without any practical improvement in performance. Write a clean, simple, general-case algorithm first, and optimize it later, 只有 在它确实有帮助的情况下。

代码长度适当

Just as long, winding sentences and long, dense paragraphs make it harder to read natural language, the same thing is true of source code. When a unit of code is very long, it is often a bad code smell, and you should look for a way to restate it.

At the highest level, a long program should be divided into well-designed smaller modules. A program which is just one sequence of code, hundreds or thousands of lines long, with no abstractions at all (no well-named functions or classes), is 单体式的。顾名思义，它看起来和表现得像一块大石头——难以移动、难以改变、难以理解。

At the next level, each function should ideally be at most a “page” of code, so that a reader can easily see the whole function body on the screen at once. This is especially true for control flow – if a single loop or a single if/else statement exceeds the size of a screen, then it is much harder for a reader to trace the logic. Look for places where you can pull out well-named helper functions or other abstractions, or look for ways to simplify or shorten the control flow. For example, rather than a long nested if/else 语句直到函数末尾才返回，不如使用一系列较短的 if 语句，每个都立即返回。

在下一层，函数内部的代码，尝试按 段落来编写，如上文所述。

Finally, at the line level, keep your line lengths short (70-100 characters at most), so that the reader doesn’t have to scroll left or right. Sometimes a single statement needs to be longer than that, but you can use appropriate linebreaks and indentation not only to make it fit a typical window width, but also to make it more readable by grouping its subexpressions (as in the 空白字符示例 above). But you can also shorten a long statement by assigning some of its subexpressions to well-named variables, even though they are used only once.

重构

作为代码作者，代码审查的反馈通常需要你更改和改进代码，即使代码可能已经完全功能正常并正在工作。更改代码以改进它（在 SFB/ETU/RFC 方面）而不改变代码功能的过程称为 重构。

Some refactoring is small and localized, like improving a comment or renaming a local variable. But some refactoring can be substantial, like dividing up code into helper functions, or redesigning a function’s parameters. For bigger changes to a program, here are some steps for safe refactoring:

采取小步骤. Don’t just rewrite all your code at once and hope that it works; plan your change as a series of small steps. For example, when dividing long code into helper functions, introduce just one new function at a time, and check that everything is working before introducing the next one.

临时注释掉旧代码。 Particularly when a change is substantial, or if it involves logic like loops and if/then statements, it can help to comment out the original version (rather than deleting it outright) until the new version is working. That way, you have a working version right there in front of you to compare with the improved code you are trying to create.

使用静态检查来指导你的更改。 当你使用具有静态检查的语言（如 TypeScript）时，许多全局更改可以由类型检查器指导。例如，如果你要向一个在多个地方使用的函数添加新参数，则首先将参数添加到函数的 定义 of the function. The typechecker will then automatically point you to every use of the function, because they will all be erroneous (omitting the new parameter until you add it), so you can use its error messages to guide your editing.

每次更改后运行测试。 Every time you complete a small step, run your test suite to make sure you haven’t changed the behavior of the program. This is why it helps to keep each change small, because if a test is now failing, then there is only a small amount of code to look at to find the bug you just introduced.

每次小步骤后删除旧代码并提交到版本控制。 在一个小更改工作正常后，完成删除旧代码（你注释掉的）并立即将其放入版本控制。

总结

代码审查是一种通过人工检查来提高软件质量的广泛使用技术。代码审查可以检测代码中的多种问题，但作为入门，本阅读讨论了以下良好代码的一般实践：

  • Don’t Repeat Yourself (DRY)
  • 在需要的地方添加注释
  • 快速失败
  • 避免魔法数字
  • 每个变量一个用途
  • 使用好的名称
  • 使用空白和标点符号帮助读者
  • Don’t use global variables
  • 函数应该返回结果，而不是打印它们
  • 避免特殊情况代码
  • 代码长度适当

The topics of today’s reading connect to our three key properties of good software as follows:

  • 远离 bug。 一般来说，代码审查使用人工审查员来发现 bug。DRY 代码让你只需在一处修复 bug，而不必担心它在其他地方传播。用清晰的注释记录你的假设使得其他程序员不太可能引入 bug。快速失败原则尽早检测 bug。避免全局变量使得更容易定位与变量值相关的 bug，因为非全局变量只能在代码的有限位置更改。

  • 易于理解。 代码审查确实是发现晦涩或混乱代码的唯一方式，因为其他人在阅读它并试图理解它。使用审慎的注释、避免魔法数字、每个变量保持一个用途、使用好的名称以及良好使用空白字符都可以提高代码的可理解性。

  • 适应变化。 Code review helps here when it’s done by experienced software developers who can anticipate what might change and suggest ways to guard against it. DRY code is more ready for change, because a change only needs to be made in one place. Returning results instead of printing them makes it easier to adapt the code to a new purpose.

Code review is not the only software development practice with strong supporting evidence. Another is: 睡眠。
