接口

TypeScript 的 interface 是表达抽象数据类型的一种有用语言机制。 TypeScript 中的接口是一系列不带方法体的方法签名列表。 如果一个类在其 implements 子句中声明了该接口，并为接口的所有方法提供了方法体，则称该类实现了该接口。 因此，在 TypeScript 中定义抽象数据类型的一种方式就是使用接口。 该类型的实现就是实现该接口的一个类。

这种方法的一个优点是，接口可以为客户指定契约，仅此而已。 接口是客户程序员理解 ADT 所需阅读的全部内容。 客户不会无意中对 ADT 的表示产生依赖，因为表示并不存在于接口中（甚至不作为私有字段）。 实现被完全分离地保留在一个完全不同的类中。

另一个优点是，抽象数据类型的多种不同表示可以作为实现该接口的不同类，在同一程序中共存。 当抽象数据类型仅表示为一个没有接口的单一类时，就更难拥有多种表示。 在 MyString 示例（出自《抽象数据类型》）中，MyString 是一个单一类。 我们探讨了 MyString 的两种不同表示，但无法在同一程序中同时拥有该 ADT 的两种表示。

TypeScript 的静态类型检查允许编译器捕获实现 ADT 契约时的许多错误。 例如，省略某个必需的方法，或给方法错误的返回类型，都是编译时错误。 不幸的是，编译器不会替我们检查代码是否遵守了那些写在文档注释中方法的规约。

关于 TypeScript 中的接口

在语法上，TypeScript 的 interface 包含 ADT 的规约，即其公共方法签名和公共实例方法。 每个实例方法签名以分号结尾。

接口不包含关于表示的信息，因此它不应声明任何私有实例变量，也不应包含实例方法体。 它也不应包含任何抽象函数、表示不变量或防止表示暴露的论证，因为这些都依赖于拥有一个表示。

因为接口没有表示，TypeScript 不允许用 new 对其进行实例化。 表达式 new ArrayLike<number>() 是一个静态错误。 要创建 ArrayLike 类型的实例，你需要改为实例化一个为其提供表示的类，例如 new Array<number>()。

子类型

回顾一下，类型是一组值，带有相关的操作。 例如，TypeScript 的 ArrayLike 类型由一个接口定义，该接口具有 length 和 [..] 索引操作。

如果我们考虑所有可能的 ArrayLike 值，其中没有一个实际上是 ArrayLike 类型的对象：我们无法创建接口的实例。 相反，这些值可能是 string 对象，或 Array 对象，或任何提供 ArrayLike 所期望操作（即 length 和 [..] 索引）的类的对象。

子类型仅仅是超类型的一个子集：string 和 Array 都是 ArrayLike 的子类型。

“B 是 A 的子类型”意味着“每个 B 都是一个 A。” 就规约而言：“每个 B 都满足 A 的规约。”

这意味着，只有当 B 的规约至少与 A 的规约一样强时，B 才是 A 的子类型。 当我们声明一个实现接口的类时，TypeScript 编译器会自动强制执行这一要求的一部分：例如，它确保 A 中的每个方法都出现在 B 中，并具有兼容的类型签名。 类 B 无法在不实现 A 中声明的所有操作的情况下实现接口 A。

但是编译器无法检查我们是否在其他方面削弱了规约：加强某个方法对某些输入的前置条件，削弱后置条件，或削弱接口抽象类型向客户宣传的保证。 如果你在 TypeScript 中声明一个子类型——实现接口是我们当前的重点——那么你必须确保子类型的规约至少与超类型的一样强。

如何在 TypeScript 中声明子类型

要声明类 B 是接口 A 的子类型，请使用 implements：

class MyArray<Element> implements ArrayLike<Element> {
    ...
}

此声明要求 MyArray 实现（为……提供方法体）ArrayLike 中找到的所有操作，且其规约至少与 ArrayLike 中的规约一样强。 TypeScript 静态地检查类型，但人类程序员必须检查规约的其余部分。

注意，即使我们无法创建 ArrayLike 接口的实例，仍然可以用它来声明变量、参数和返回类型，只要它们最终用来自具体子类型类（如 MyArray）的对象初始化即可。

你也可以声明一个接口是另一个接口的子类型，使用 extends：

interface ReversibleArrayLike<Element> extends ArrayLike<Element> {
    // 继承现有 ArrayLike 操作的签名和规约，并添加新操作：

    /** 反转该数组，就地变更它。 */
    reverse(): void;
}

因为 ReversibleArrayLike 也是一个接口，它不提供任何 ArrayLike 操作的实现。 但它可以通过加强现有 ArrayLike 操作或添加新操作来加强类型的规约。 例如，这里 ReversibleArrayLike 添加了一个 reverse 操作。

TypeScript 中的结构化子类型

在 TypeScript 中，类型 B 成为另一个类型 A 的子类型还有一种方式：结构化子类型。 使用结构化子类型，B 不必在其声明中提到 A（没有 B implements A 或 B extends A）。 但如果 B 至少提供了 A 所需的所有操作——相同的公共方法和公共实例变量，且具有兼容的类型——那么 TypeScript 就会将 B 视为 A 的子类型。

结构化子类型很方便，在 TypeScript 中经常是必要的，但它在类型安全性上打开了一个漏洞，因为它允许 B 成为 A 的子类型，即使 B 具有不兼容的规约。 可变性和不可变性在这里提供了一个很好的例子，既展示了优点也展示了陷阱。 回顾一下，TypeScript 提供了一个 ReadonlyArray 接口，它具有 Array 的所有观测操作和生产操作，但省略了变更操作。 因此，Array 是 ReadonlyArray 的结构化子类型，所以 TypeScript 允许我们编写如下有用且良好的代码：

const readonlyArr: ReadonlyArray<number> = [ 1, 2, 3 ];

此声明中的初始化符 [ 1, 2, 3 ] 生成一个 Array 对象。 因为 Array 是 ReadonlyArray 的结构化子类型，我们可以然后将其赋值给一个 ReadonlyArray 类型的变量，此后将其视为不可变值。在 readonlyArr 上调用诸如 push() 之类的变更操作将导致静态错误：

readonlyArr.push(5);
// 静态错误：类型 'readonly number[]' 上不存在属性 'push'

此外，TypeScript 的静态检查将确保我们不会意外地以相反方式进行：

const arr: Array<number> = readonlyArr;
// 静态错误！ReadonlyArray *不是* Array 的结构化子类型，
// 因为它不提供 Array 的变更操作

这就是结构化子类型如何帮助我们的方式。但这是类型安全性上的漏洞。假设我们保留了对原始可变 Array 的一个别名：

const arr: Array<number> = [ 1, 2, 3 ];
const readonlyArr: ReadonlyArray<number> = arr;

现在我们可以使用其别名 arr 来变更 readonlyArr：

arr.push(4);
console.log(readonlyArr); // 输出 1,2,3,4

使用这个别名，我们已经破坏了 ReadonlyArray 最好的部分：它的不可变性！ 尽管 Array 是 ReadonlyArray 的结构化子类型，它并不是一个真正的子类型，因为 Array 契约不提供不可变性。

因此，结构化子类型很方便，但应谨慎使用。 此示例展示了它的一种常见用法——使用可变类型构造列表、映射或集合，然后将其赋值给 ReadonlyArray、ReadonlyMap 或 ReadonlySet，此后将其视为不可变。 重要的是丢弃所有使用原始可变类型的别名，以避免此处展示的风险。

示例：MyString

让我们重新审视 MyString。 使用接口而非类作为 ADT，我们可以支持多种实现：

/**
 * MyString 表示一个不可变的字符序列。
 */
interface MyString {

    // 我们现在将跳过这个创建操作
    // /**
    //  * @param s
    //  * @returns 表示 s 中字符序列的 MyString
    //  */
    // public constructor(s: string) { ... }

    /**
     * @returns 此字符串中的字符数量
     */
    length(): number;

    /**
     * @param i 字符位置（要求 0 <= i < 字符串长度）
     * @returns 位置 i 处的字符
     */
    charAt(i: number): string;

    /**
     * 获取 start（包含）与 end（不包含）之间的子字符串。
     * @param start 起始索引
     * @param end 结束索引。要求 0 <= start <= end <= 字符串长度。
     * @returns 由 charAt(start)...charAt(end-1) 组成的字符串
     */
    substring(start: number, end: number): MyString;
}

这是我们的第一个实现：

class SimpleMyString implements MyString {

    private a: Uint16Array;

    public constructor(s: string) {
        this.a = new Uint16Array(s.length);
        for (let i = 0; i < s.length; ++i) {
           this.a[i] = s.charCodeAt(i);
        }
    }

    /**
     * @inheritdoc
     */
    public length(): number {
        return this.a.length;
    }

    /**
     * @inheritdoc
     */
    public charAt(i: number): string {
        return String.fromCharCode(this.a[i]);
    }

    /**
     * @inheritdoc
     */
    public substring(start: number, end: number): MyString {
        const that = new SimpleMyString("");  // 创建一个暂时为空的对象
        that.a = this.a.slice(start, end);    // ... 并立即替换其数组
        return that;
    }
}

（注意，我们在 length、charAt 和 substring 的规约注释中使用了 @inheritdoc。这是一个标记，表示这些方法实现了 MyString 接口中相应的规约，TypeDoc 将从这些规约生成文档。）

这是优化后的实现：

class FastMyString implements MyString {

    private a: Uint16Array;
    private start: number;
    private end: number;

    public constructor(s: string) {
        this.a = new Uint16Array(s.length);
        for (let i = 0; i < s.length; ++i) {
            this.a[i] = s.charCodeAt(i);
        }
        this.start = 0;
        this.end = this.a.length;
    }

    /**
     * @inheritdoc
     */
    public length(): number {
        return this.end - this.start;
    }

    /**
     * @inheritdoc
     */
    public charAt(i: number): string {
        return String.fromCharCode(this.a[this.start + i]);
    }

    /**
     * @inheritdoc
     */
    public substring(start: number, end: number): MyString {
        const that = new FastMyString(""); // 创建一个暂时为空的对象
        that.a = this.a;                   // ... 并立即替换其实例变量 
        that.start = this.start + start;
        that.end = this.start + end;
        return that;
    }
}

客户将如何使用这个 ADT？ 这是一个示例：

const s: MyString = new FastMyString("good morning");
console.log("The first character is: " + s.charAt(0));

不幸的是，这种模式打破了抽象屏障——我们如此努力地在抽象类型与其具体表示之间构建的这道屏障。 客户必须知道具体表示类的名称。 因为 TypeScript 中的接口没有构造函数，客户必须直接调用某个具体类的构造函数。 该构造函数的规约不会出现在接口的任何地方，因此无法静态保证不同的实现甚至会提供相同的构造函数。

因此，我们可以将创建操作实现为工厂函数，而不是使用构造函数：

/**
 * @param s
 * @returns 表示 s 中字符序列的 MyString
 */
function makeMyString(s: string): MyString {
    return new FastMyString(s);
}

现在客户可以使用 ADT 而不会打破抽象屏障：

const s: MyString = makeMyString("good morning");
console.log("The first character is: " + s.charAt(0));

完全隐藏实现是一种权衡，因为有时客户希望选择具有不同特征的实现。

为什么使用接口？

接口在真实代码中经常使用。 并非每个类都与接口相关联，但有几个很好的理由让接口进入画面。

  • 同时为编译器和人类提供文档。 接口不仅帮助编译器捕获 ADT 实现错误，而且供人类阅读也比具体实现的代码有用得多。 这样的实现将 ADT 级别的类型和规约与实现细节交织在一起。
  • 允许性能权衡。 ADT 的不同实现可以提供具有非常不同性能特征的方法。 不同的应用可能更适合不同的选择，但我们希望以表示无关的方式编写这些应用的代码。 从正确性的角度来看，应该可以通过简单、局部的代码更改来加入任何关键 ADT 的新实现。
  • 具有有意不确定规约的方法。 有限集的 ADT 可以不确定转换为数组时获得的元素顺序。 某些实现可能使用较慢的方法实现，同时设法将集合表示保持为某种排序顺序，从而允许快速转换为排序后的数组。 其他实现可能通过不支持转换为排序数组来使许多方法更快。
  • 一个类的多个视图。 TypeScript 类可以实现多个接口。 例如，显示下拉列表的用户界面控件很自然地既可视为控件也可视为列表。 此控件的类可以实现这两个接口。 换句话说，我们并不总是仅仅因为选择了不同的数据结构而多次实现 ADT。 这些实现可能是各种不同类型的对象，可以视为该 ADT 的特殊情况。
  • 更可信和较不可信的实现。 多次实现接口的另一个原因可能是，构建一个你认为正确的简单实现很容易，而你可以更努力地构建一个更花哨、更可能包含错误的版本。 你可以根据被错误咬伤的严重程度来为应用选择实现。

子类化

实现接口是创建另一种类型的子类型的一种方式。 另一种你以前可能见过的技术是子类化。 子类化意味着将一个类定义为另一个类的扩展，即子类，以便：

  • 子类自动继承其超类的实例方法，包括它们的方法体
    • 子类可以用自己的方法体替换任何这些被继承的方法体，从而重写它们
  • 子类还继承其超类的私有表示
  • 子类还可以为自己的目的添加新的实例方法和表示字段

上面列表中的粗体部分显示了子类化与实现接口的不同之处。 接口既没有方法体也没有表示，所以在实现接口时不可能继承它们。

子类化是面向对象编程语言的一个常见特性。 你可能已经在 Python 中遇到过它，在 Python 中你可以编写 class SpottedTurtle(Turtle): ... 来将新类 SpottedTurtle 定义为类 Turtle 的子类。 TypeScript 用语法 class SpottedTurtle extends Turtle { ... } 提供相同的效果。

就像实现接口一样，子类化应当蕴含子类型关系。 如果 SpottedTurtle 是 Turtle 的子类，那么 SpottedTurtle 需要具有至少与 Turtle 一样强的规约，因为 TypeScript 将允许 SpottedTurtle 对象被用在任何可能期望 Turtle 的地方。

但与实现接口不同，子类不仅继承其超类的规约，还继承其表示——实现它的字段。 起初这似乎是个很棒的主意。 重用实现应当使我们的代码更 DRY，并更易于更改。

但 API 设计者多年来的经验揭示了使子类化在免于错误和易于更改方面面临微妙的挑战。 如果你感兴趣可以阅读更多，但本质上，继承表示意味着：

  • 超类与其所有子类之间的表示暴露
  • 超类与子类之间的表示依赖
  • 超类和子类可能无意中破坏彼此的表示不变量

设计安全的子类化意味着超类现在必须提供两个契约：一个用于与客户交互，一个用于子类。 这些问题在使用接口时根本不会出现。

重写与动态分派

然而，在编写 TypeScript 类时，我们在一个方面无法回避对子类化的思考。 每个 TypeScript 类自动是 Object 的子类，并自动继承诸如 toString() 之类的方法。 我们经常需要重写这个被继承的实现，用我们自己的实现替换它，以便我们的类能正确行为。

为了说明，让我们看一个更简单的例子：为我们的 FastMyString 类重写 toString() 方法。 Object 提供的默认 toString() 对于调试不是特别有用：

const fms: FastMyString = new FastMyString("hello");
fms.toString() → "[object Object]" // 没用！

当一个方法有多个实现时，例如当一个类重写一个像 toString() 这样已在其超类 Object 中有实现的方法，那么 TypeScript 必须确定在调用该方法时使用哪个实现。 这个过程称为方法的分派，TypeScript 的规则是动态分派——它使用适合对象动态类型的实现，而不是指向该对象的引用的静态类型。

让我们通过重写 toString() 来使这更好：

class FastMyString {
    ...
    public toString(): string {
      let s = "";
      for (let i = 0; i < this.length(); ++i) {
          s += this.charAt(i);
      }
      return s;
    }
}

在此更改后，我们得到：

const fms: FastMyString = new FastMyString("hello");
fms.toString() → "hello"

在此示例中，FastMyString 既是变量 fms 的类型，也是它指向的对象的类型。 但它们不必是同一类型。 变量可以是超类型，而对象本身来自子类型。 当我们使用 MyString 类型的变量来持有对 FastMyString 的引用时，我们已经这样做了。 但因为 Object 是 TypeScript 中所有类的超类型，我们也可以这样做：

const obj: Object = new FastMyString("hello");
obj.toString() → ?

但现在似乎存在一个歧义。 Object 有自己的 toString() 实现。 当我们调用 obj.toString() 时，它调用的是原始的 Object 实现，还是被重写的 FastMyString 实现？ 我们得到的是 "[object Object]" 还是 "hello"？

动态分派规则指出，运行时对象的类型决定了要调用的方法实现。 这种类型直到运行时才可知，因此有“动态”一词。 相比之下，obj 变量的类型在编译时就已可知。

使用动态分派，这是我们得到的结果：

const obj: Object = new FastMyString("hello");
obj.toString() → "hello"

……与我们从 fms.toString() 得到的结果相同。

动态分派规则的效果是，无论指向对象的引用是什么类型，它总是使用对象的动态类型进行方法分派。

静态检查使用静态类型

由于我们现在正在查看变量的静态类型与其指向的对象的动态类型不同的情况，值得重新审视静态检查能做什么和不能做什么。考虑这个示例：

const obj: Object = new FastMyString("hello");
obj.charAt(0) → ?

会发生什么？charAt 方法确实作为 obj 指向的 FastMyString 对象上的一个方法存在，所以这段代码在运行时理论上可能工作。 但 charAt 不是 Object 上的方法。由于 obj 的静态类型是 Object，TypeScript 编译器会将 obj.charAt(0) 视为静态类型错误，因此它甚至不会编译这段代码。

TypeScript 在编译时依赖表达式的静态类型，以确保方法调用在运行时始终可能。 因为 obj 的类型是 Object，在运行时它可能指向任何对象，包括 Object、Set、Date 或许多其他没有 charAt 方法的对象。 静态类型检查要求 TypeScript 只允许那些在运行时保证有操作可调用的表达式。 你不能使用超类型引用（这里是 Object）来调用只在子类型（FastMyString）上定义的方法。

泛型

TypeScript 类型系统（以及其他现代静态类型语言）的一个有用特性是泛型：一种其规约以待后续填充的占位类型表示的类型。

集合类型是这方面的好例子。 Set<T> 是某种其他类型 T 的元素的有限集的 ADT。 我们可以设计一个接口 Set<T> 来表示一整族集合 ADT，而不是为 Set<string>、Set<number> 等分别编写规约和实现。

注意，当我们声明 Set<T> 类型时，类型参数 T 是一个任意名称，就像函数声明中的参数是一个任意名称一样。 因此我们常常使用更具描述性的类型参数名称，例如 Set<Element>。 按照惯例，类型参数首字母大写，就像接口和类名一样。

这是 Set 接口 MySet 的一个简化版本：

/**
 * 一个可变的集合。
 * @template Element 集合中元素的类型
 */
interface MySet<Element> {

    // 观测操作示例

    /**
     * 获取集合的大小。
     * @returns 此集合中元素的数量
     */
    size(): number;

    /**
     * 测试成员关系。
     * @param e 一个元素
     * @returns 当且仅当此集合包含 e 时返回 true
     */
    has(e: Element): boolean;

    // 变更操作示例

    /**
     * 通过将 e 添加到集合中来修改此集合。
     * @param e 要添加的元素
     */
    add(e: Element): void;

    /**
     * 通过移除 e（如果找到）来修改此集合。
     * 如果集合中未找到 e，则无效果。
     * @param e 要移除的元素
     */
    delete(e: Element): void;

}

注意规约是如何基于我们对集合的抽象概念表达的；提及任何具有特定私有字段的特定集合实现的细节都是不合适的。 这些规约应适用于 MySet ADT 的任何有效实现。

我们还将需要一个创建操作：

// 创建操作示例
/**
 * 创建一个空集合。
 * @template Element 集合中元素的类型
 * @returns 一个新的集合实例，初始为空
 */
function makeMySet<Element>(): MySet<Element> { ... }

make 操作被实现为一个工厂函数。 客户将编写如下代码：
const strings: MySet<string> = makeMySet();
编译器将推断新的 MySet 应该是一个 string 对象的集合。

注意，在上面的方法签名中出现了一个 TypeScript 语法要求：像 makeMySet 这样的函数需要在参数列表之前独立声明其类型参数，这里显示为 function makeMySet<Element>。 上面的实例方法没有这个额外的 <...> 声明，因为类型参数 Element 已经由外围的类或接口 interface MySet<Element> 声明了。）

泛型函数本身也可以很有用，而不仅仅是在与 ADT 一起使用时。例如，回顾在规格说明阅读中讨论的空值合并运算符，用作断言一个值不是 undefined 的简写。 如果我们想把这个放进一个辅助函数中以避免每次都重复 assert.fail()，我们可以使用泛型：

/**
 * 断言一个值不是 undefined
 * @template T 待缩窄的类型
 * @param val 可能为 undefined 的值
 * @param message 如果抛出错误时显示的信息
 * @returns 已定义的值
 * @throws 如果该值是 undefined 则抛出错误
 */
function assertDefined<T>(val: T | undefined, message?: string): T {
  return val ?? assert.fail(message);
}

const temperatures = [99.4, 95.2, 100];
const firstTemp: number = assertDefined(temperatures[0]); // temperatures[0] 的类型为 number|undefined

泛型接口，非泛型实现。 让我们为一个特定的类型 Element 实现 MySet<Element>。 我们将实现一个数字集合：

    // ...

    /**
     * 测试成员关系。
     * @param e 一个元素
     * @returns 当且仅当此集合包含 e 时返回 true
     */

    /**
     * 通过将 e 添加到集合中来修改此集合。
     * @param e 要添加的元素
     */
    add(e: Element): void;

    // ...
}
/** 表示一个由数字 {0...9} 中取值的集合的可变集合 */
class DigitSet implements MySet<number> {

    private readonly digitInSet: Array<boolean> =
        [ false, false, false, false, false,
          false, false, false, false, false ];


    /**
     * 测试成员关系。
     * @param e 一个元素，必须是 {0...9} 中的整数
     * @returns 当且仅当此集合包含 e 时返回 true
     */
    public has(e: number): boolean {
        this.checkRep();
        return this.digitInSet[e];
    }

    /**
     * 通过将 e 添加到集合中来修改此集合。
     * @param e 要添加的元素，必须是 {0...9} 中的整数
     */
    public add(e: number): void {
        this.digitInSet[e] = true;
        this.checkRep();
    }
    // ...
}

枚举

有时 ADT 有一个小而有限的不可变值集，例如：

  • 一年中的月份：January, February, …
  • 一周中的天：Monday, Tuesday, …
  • 罗盘点：north, south, east, west
  • 线条绘制中的线帽：butt, round, square

像这样的类型可以用作更复杂类型（如 DateTime 或 Latitude）的一部分，或者用作改变方法行为的参数（如 drawLine）。

当值集小而有限时，将所有值定义为命名常量是合理的，这称为枚举。 TypeScript 有 enum 构造使这很方便：

enum Month { JANUARY, FEBRUARY, MARCH, ..., DECEMBER };

这个 enum 以与 class 和 interface 定义新类型名称相同的方式定义了一个新的类型名称 Month。 它还定义了一组命名值，我们将它们写成全大写，因为它们实际上是 public static readonly 常量。 所以现在你可以写：

const thisMonth = Month.MARCH;

这个想法被称为枚举，因为你显式地列出了集合的元素，而 TypeScript 正在为它们分配数字作为其默认表示值。

在枚举最简单的用例中，你需要的唯一操作是测试值之间的相等性：

if (day === Day.SATURDAY || day === Day.SUNDAY) {
  console.log("It's the weekend");
}

在那个意义上，使用枚举可能感觉就像你在使用原始 number 常量。 TypeScript 甚至支持在 switch 语句中使用它们：

switch (direction) {
    case Direction.NORTH: return "polar bears";
    case Direction.SOUTH: return "penguins";
    case Direction.EAST:  return "elephants";
    case Direction.WEST:  return "llamas";
}

但与 number 值不同，枚举有更多的静态检查：

const firstMonth: Month = Day.MONDAY; // 静态错误：MONDAY 的类型是 Day，而不是 Month

TypeScript 实际上提供两种枚举：数字枚举（其表示是数字）和 字符串枚举（其表示是字符串）。 默认是数字枚举，所以上面的 Month 枚举简单地使用一个数字来表示每个月，从 0 开始按顺序分配，所以 JANUARY 是 0，FEBRUARY 是 1，等等。 要改为获得字符串枚举，只需将枚举的每个成员初始化为一个不同的字符串值：

enum Direction {
  NORTH = "north",
  SOUTH = "south",
  EAST = "east",
  WEST = "west"
}

这在很大程度上是一个实现细节，因为我们正在讨论枚举的表示。但它影响为这些枚举自动生成的 toString() 操作。打印数字枚举的值只会打印其数字（所以 console.log(Month.FEBRUARY) 打印 1），但对于字符串枚举，它打印字符串值（console.log(Direction.EAST) 打印 east）。 因此，使用字符串枚举调试可能更容易。

Getter 和 setter

我们经常有没有参数的观测操作，比如我们 MyString 接口的这一个：

interface MyString {
    /**
     * @returns 此字符串中的字符数量
     */
    length(): number;

    // ...
}

如果我们反而想（在语法上）将此观测操作表示得如同它是一个实例变量，会怎样？ 然后客户可以省略括号，在类型为 MyString 的变量 s 上使用 s.length，就像我们对那些内置类型使用 Set.size 或 Array.length 一样。 在接口中声明此观测属性很直接：

interface MyString {
    /**
     * 此字符串中的字符数量
     */
    readonly length: number;

    // ...
}

（注意重要的 readonly——我们不想让客户试图通过给此属性赋值来调整字符串大小。）

但这不是牺牲了表示独立性吗？ 它不是通过强制我们在表示中拥有一个公共的 length 实例变量，来约束我们为 MyString 选择的表示吗？

在像 TypeScript 这样支持 getter 方法的语言中，答案是否定的。 使用关键字 get，我们可以定义一个 getter 方法，每当客户读取 length 实例变量时它就会被调用：

class FastMyString implements MyString {

    public get length(): number {
        return this.end - this.start;
    }

    // ... 
}

但 MyString 的不同实现可能选择直接将 length 表示为一个实例变量：

class SimpleMyString implements MyString {

    public readonly length;

    // ...
}

重要的是，FastMyString 和 SimpleMyString 可以决定该观测操作是由 getter 函数还是由变量实现，而不影响客户。 从客户的角度来看，length 看起来就像一个实例变量。

对于一个旨在看起来可重新赋值的公共实例变量，我们可以同时定义一个 getter 方法（观测操作）和一个 setter 方法（变更操作）。 setter 方法可以做任何必要的事情，使表示的其余部分与被重新赋值的值保持一致——甚至如果客户赋了一个坏值就抛出异常。

非面向对象语言中的 ADT

定义抽象数据类型的另一种方式是简单地作为一组对不透明数据类型进行操作的全局可访问函数。 这种模式在像 TypeScript 和 Python 这样的面向对象语言中很少见，但经常出现在像 C 这样的较老编程语言中。 这是 C 中一些文件 I/O 的示例：

FILE* f = fopen("out.txt", "w"); // 打开一个文件用于写入
fputs("hello", f); // 写入文件
fclose(f);  // 关闭文件

在此代码中，抽象数据类型是 FILE，表示一个打开的文件。 函数 fopen、fputs 和 fclose 是该类型的操作，接受 FILE 作为参数或将其作为返回值返回。 fputs 期望文件作为其第二个参数。

因为 C 不是面向对象的，所以没有类、方法、字段甚至 private 的概念，但表示独立性仍然实现了。 客户没有办法查看 FILE 值的内部。 使用 FILE 的唯一方法是将其传递给该类型提供的操作。

从这里得出的一个关键要点是，抽象数据类型的基本概念并不依赖于诸如类、接口或 public/private 访问控制等语言特性。 数据抽象是软件工程中普遍存在的一种强大设计模式。

总结

TypeScript 接口帮助我们将抽象数据类型的基本概念形式化为一组类型必须支持的操作。

这帮助我们的代码……

  • 摆脱 Bug。 ADT 由其操作定义，接口正是这样做的。 当客户使用接口类型时，静态检查确保他们只使用接口定义的方法。 如果实现类暴露了其他方法——或者更糟，有可见的表示——客户就不会意外地看到或依赖它们。 当我们有多种数据类型实现时，接口提供方法签名的静态检查。

  • 易于理解。 客户和维护者确切地知道去哪里找 ADT 的规约。 因为接口不包含字段或实例方法的实现，所以更容易将实现的细节排除在规约之外。

  • 为更改做好准备。 我们可以通过添加实现接口的类来轻松地添加类型的新实现。 如果我们避免构造函数而使用工厂函数，客户将只看到接口。 这意味着我们可以切换客户正在使用的实现类，而完全不改变他们的代码。

TypeScript 枚举允许用一个小而有限的不可变值集定义 ADT。与特殊整数值或特殊字符串的过时替代方案相比，枚举帮助使我们的代码：

  • 摆脱 Bug。 静态检查确保客户不能使用有限集之外的值，或混淆两个不同的枚举类型。

  • 易于理解。 命名常量不像整数字面量那样神秘，命名类型比 number 或 string 更能自我解释。

  • 为更改做好准备。 使用特定枚举的代码很容易通过搜索枚举的类型名来找到，以便在枚举更改时对其进行审查和更改。 （IDE 重构工具甚至可以自动进行其中一些更改。） 依赖于一组特定字符串或整数常量的代码更难与出于其他目的使用字符串和整数的代码区分开来。
