在 Star Battle 谜题中，一个 n×n 的网格被划分为 n 个区域。 为了解出这个谜题，玩家必须找到一种放置 2n 颗星的方式，使得每一行、每一列以及每个区域都恰好有 2 颗星，并且没有星星在垂直、水平或对角方向上相邻。 虽然其他尺寸的变体也是可能的，但在这个项目中我们将使用 10×10 的双星谜题。 我们还将假设有效的谜题有且仅有一个唯一解。

这个逻辑谜题由 Hans Enderbak 于 2003 年设计。 你可以在网上搜索到更多例子。 这是 Jim Bumgardner 的网站，提供 教程、一个 Web 应用，以及一页又一页的 Star Battle 谜题 PDF。

在这个项目中，你们小组将构建一个系统，通过网络发送谜题，并为玩家提供图形用户界面来解谜。

这个项目将锻炼你在课堂上学到的许多概念。 你将实现一个客户端/服务器架构；你将使用 ParserLib 来解析谜题；你还将开发自己的抽象数据类型来表示系统的不同方面。

最重要的是，你将在一个小团队中练习合作，运用我们本学期学到的软件工程技术。 几乎所有的软件工程工作都是在团队中完成的，所以在这个项目中，你将通过协作、有效沟通以及对队友工作的迭代改进，来练习构建一个软件系统。

设计自由度

在这个项目中，你有很大的设计自由度来选择你在代码中使用的接口、类和方法签名。 请明智地选择它们。 你将被要求使用规范、测试、抽象函数、表示不变量、安全性论证、checkRep 以及其他断言。

本讲义中的规范约束了你的解决方案必须做什么，但你会遇到许多本讲义中没有给出答案的设计问题。 你可以自由地提出自己的答案——只要合理、一致、防错、易于理解并且适应变化即可。 你可以随时向你的助教导师或在 Piazza 上寻求建议，但不太可能有一个唯一确定的答案。

在这个项目中，Didit 将只运行你自己的测试。 一如既往，正确性是你的责任，你必须依靠自己仔细的规范、测试和实现来保证正确性。

概述

在项目期间，课堂时间将被团队工作时间取代。 在这些时间里，你们团队应该聚在一起共同工作。

签到

你们团队将被分配一位助教导师，他将帮助你们进行设计，并在你们实现设计的过程中帮助你们保持进度。 在每次团队工作时间的课堂上，你们都必须与助教签到。 在这次签到中，每位团队成员应准备好：

  • 说明他们计划在下次签到之前完成什么
  • 说明有什么（如果有的话）正在阻碍他们的进展
  • 展示他们自己的项目工作副本已提交、已推送，并与远程仓库保持同步

利用签到来审查每个人的计划如何相互配合，并决定如何解决阻碍进展的问题。

协同工作

除了项目结束时的反思之外，项目的所有部分都应该提交到你们共享的仓库中。 对仓库的每次提交都应该有一条有用的提交信息，描述你所做的更改。

使用你在 Caesar 上练习过的代码审查技能，在项目中相互审查代码。 Caesar 不会加载你的项目代码，所以你们可以决定如何计划审查，可以是面对面讨论、通过邮件，或者使用 github.mit.edu 上的 pull request。 GitHub 的 pull request 功能要求你们团队使用 Git 分支。 如果你们想先在单独的练习仓库中尝试使用分支和 pull request，我们有一个可选的小组练习，关于用于代码审查的分支和 pull request。

我们也强烈鼓励你们尝试结对编程，即两个人在一台计算机上协作，一个人坐在另一个人旁边看着，或者通过视频聊天和屏幕共享来观看。 结对编程是一项需要练习的技能。 要有耐心：要预料到结对意味着你写代码的速度会更慢，因为它就像是实时的代码审查，但结果会更正确、更清晰、更易于修改。 你可以在网上找到大量关于如何组织结对编程的建议。

请注意，"结对编程"通常意味着只有一个键盘，一个人负责操作（打字），另一个人坐在后面（审查代码）。 所以你只编辑一个工作副本，并且只提交一次更改。 当多个人为一次提交做出贡献时，请在提交信息中提及他们。 你的助教将查看 Git 日志来了解每个人的贡献。

我们在课堂上使用 Constellation 所做的事情，是一种比普通结对编程更紧密的合作方式。 在项目期间使用 Constellation 是可能的，但不被鼓励，因为它会在两台计算机上进行相同的更改，需要仔细协调以避免合并冲突。 但如果你真的想使用 Constellation，那么在开始协作之前，请确保双方都处于干净状态，没有未提交的更改，并且与远程仓库完全同步。 协作之后，双方都应该将更改提交到本地仓库，然后推送并拉取，直到提交被合并且双方再次处于干净状态。 请注意，要成功地将 Constellation 和 Git 一起使用，你必须极其自律。 不要在未清理和合并的情况下离开 Constellation 协作。

一般来说，如果你们做到以下几点，协同工作会更轻松：

  1. 每次坐下来开始工作时都拉取代码
  2. 频繁地提交和推送
  3. 不要破坏构建！（不要提交无法编译的代码）

高层任务

  • 团队契约。 在开始之前，撰写并达成一份团队契约。 这应在项目启动当天的课堂时间结束前提交。

  • 理解问题。 仔细阅读本页的项目规范。

  • 设计。 你需要为系统的各个部分创建抽象数据类型，包括客户端和服务器端，以及一个用于解析谜题的语法。

    你的软件设计也许是项目中最重要的部分：一个好的设计将使实现和调试系统变得更加简单。 记得为类和方法编写清晰的规范；定义抽象函数和表示不变量，编写 checkRep，并记录防止表示暴露的安全性。

  • 迭代。 由于时间紧迫，关于如何迭代这个项目的规范由工作人员给出。 设计、测试和实现每个部分，始终朝着一个端到端的原型努力。 然后重新审视你的设计，改进规范，并测试和实现更多内容。 如此继续。

  • 测试。 你应该为系统的各个组件编写 Mocha 测试。 你的测试用例应该以有原则的方式开发，对输入和输出的空间进行划分，并且你的测试策略应该像我们一直以来所做的那样被记录下来。 你的程序的部分可能需要手动测试，这将在下文描述。

  • 实现。 编写实现代码使你的测试通过。 根据需要迭代设计和测试以使系统正常运行。

  • 反思。 每个人都要写一篇简短的评论，讲述你从这次项目经历中学到了什么，回答反思问题。 你的反思不得超过 300 字，并应提交到反思表格。

手动测试

不要依赖手动测试来构建一个正确的系统。

然而，如果你有不确定如何自动测试的规范，你可以记录手动测试来覆盖某些划分的部分。 在相关的 mocha 测试文件中，紧接在测试策略之后记录这些测试。

对于每个手动测试：给它一个描述性的名称，列出所覆盖的部分，并简要而精确地描述人类测试人员应遵循的每个步骤，以及每个步骤关于预期结果的断言。

例如，假设你正在测试 MIT 网站：

/*
 * 手动测试：导航到校历
 * 覆盖：page=home, type=static, type=redirect, data-source=registrar
 * 1. 浏览到 http://web.mit.edu => 断言头部包含今天的日期
 * 2. 点击 "education"
 * 3. 点击 "academic calendar" => 断言页面显示从上一个六月到下一个六月
 */

遵循与自动化测试相同的指导原则：先测试，设计少量测试，保持每个测试简短，并确保测试是在验证规范。

⭐️⚔️ 规范

设计、测试并实现一个客户端/服务器的 Star Battle 谜题图形界面。

你的系统只需要对具有唯一解的 10×10 双星谜题有效即可。

在你拥有一个完整的、可运行的端到端实现之前，你的设计自由度是有限的。 标记为 [暂时] 的项目是迭代 #0、迭代 #1 和集成期间的要求。 只有当你拥有了一个完整的、可运行的端到端系统之后，如果打破这些限制能够改善你的设计、启用新功能等，你才可以这样做。

规范：解析器

你的系统必须能够解析 puzzles 目录中提供的示例谜题，这些是带有 .starb 文件扩展名的纯文本文件。

这些提供的谜题是"已解出的"：文件标明了每个区域中星星的位置。

  • [暂时] 相同的语法和解析器还必须能够处理从服务器发送到客户端的"空白"谜题，这将在下文描述。

  • 你必须使用 ParserLib。

  • 除了示例中出现的内容之外，你接受或拒绝其他什么谜题文件格式完全由你决定，空白谜题的格式也由你决定。

  • 请注意，文件中的坐标是从谜题左上角开始的 1 索引（行，列）。

  • 与作业 3 不同，谜题不是递归的，所以你不应期望递归解析器或 AST。

规范：抽象数据类型

你的系统必须使用一个不可变的谜题 ADT，它能够表示有效的未解、部分已解和完全已解的谜题。 除此之外，其设计完全由你决定。

你的客户端网页必须使用另一个客户端 ADT 来管理其状态（例如，正在玩哪个谜题，使用谜题 ADT）和操作（例如，响应用户输入）。 其设计完全由你决定。

当然，你可以有其他被这些类型使用的 ADT，或者用于其他目的。

  • [暂时] 你必须在服务器和客户端上使用相同的不可变谜题 ADT。 只有客户端使用客户端 ADT。

  • 请注意，客户端和服务器没有共享内存，所以它们不共享谜题 ADT 的实例（也不共享上一节中解析器的实例）。 但你必须在系统的两部分使用相同的 ADT 类型（以及相同的解析器类）。

  • 与作业 3 不同，不要求每个谜题 ADT 实例（包括部分已解的谜题）都有可解析的字符串表示（解析器只需要处理"空白"和"已解出的"）。

规范：服务器

服务器必须在端口 8789 上接受 HTTP 请求，请求通过文件名（不带扩展名）标识 puzzles 子目录中的谜题。

它必须将"空白"谜题传输到客户端：不是单独列出星星的位置，而是将每个区域中的所有位置列为空。

  • [暂时] 服务器不得维护任何玩家或游戏状态。

  • 你必须使用 express。

  • 具体的 URL 和规范完全由你决定。

  • 除了发送空白谜题之外，不需要其他功能。

  • 特别是，与作业 4 不同，所要求的规范不包括多人游戏。 在获取一个谜题之后，你的客户端可能被设计为无需再次联系服务器即可继续运行。

规范：客户端

客户端网页必须：请求一个空白谜题，在屏幕上显示该谜题，允许用户在网格上的任意位置添加星星，显示这些星星，允许用户移除他们添加的星星，并在用户解出谜题时通知用户。

启动时，用户所需的任何指令都应显示在网页上。

客户端必须支持点击谜题来添加星星。

  • [暂时] 客户端只能使用 canvas 绘图，不得使用任何其他 HTML 元素进行绘图或交互。

  • [暂时] 客户端必须请求并运行 starb-client.ts 顶部 PUZZLE 常量指定的单个谜题。

  • [暂时] 点击已添加的星星必须将其移除。

  • 客户端可以自行判断谜题是否已解出，也可以请求服务器来判断。

  • 不需要其他交互或功能（例如，不要求标记空格，即使这会让解谜更有趣）。

  • 具体的图形展示完全由你决定（例如，你可以用背景颜色而不是轮廓线来表示区域，或者画笑脸而不是星星）。

  • 请记住，谜题文件使用的是（行，列）坐标，而不是（x，y）坐标。

规范：扩展

这个项目是一个练习团队合作的机会，也是一个展示你编写防错、易于理解和适应变化的代码的能力的机会。

但是，如果你已经有了一个能体现这些特性的可运行系统，我们鼓励你扩展它！ 你可以考虑的一些功能……

  • 在解谜过程中标记必须为空的格子。

  • 向服务器请求可用谜题列表并选择一个来解。

  • 用精彩的动画来庆祝成功解出谜题。

  • 请求提示，例如高亮显示星星或用户应该注意的格子。

  • 处理 10×10 双星谜题之外的其他变体。

  • …

确保你仍然满足所要求的规范，但只要你已经对一个完整的端到端系统进行了规范、测试和实现，你就可以打破 [暂时] 的要求。

任务划分

每位团队成员不仅必须对项目做出实质性贡献，而且每位团队成员都必须对项目的每个主要组件做出具体的贡献。

贡献包括编写规范、编写测试策略、编写测试、原型设计、编写内部文档、编写实现代码、修复缺陷以及提供代码审查反馈。 作为一对或整个团队一起完成的贡献也是很好的，只要每个人都参与其中。

由于项目时间紧迫，工作人员已经指定了你必须遵循的任务分解。 本节中的描述按时间倒序排列，因为迭代 #1的任务分配决定了迭代 #0中由谁做什么。

最后：集成、重构、继续迭代、扩展

当团队成员完成他们迭代 #1的任务后，每个人都应该一起将它们集成起来。 当你有了一个完整的、可运行的系统后，修改并重构它，使它尽可能地防错、易于理解和适应变化。

如果你发现需要进行更大幅度的重新设计，计划并对项目执行另一次迭代。 只有在时间允许的情况下，考虑实现一些上面建议的扩展或你自己的想法。

这些迭代 #0 任务应该由被分配的两位组员独立、并行地完成，从而产生两个不同的规范、测试策略、代码片段等。

而且这些任务应该快速完成：仔细阅读本讲义并理解项目规范后，在每个迭代 #0 任务上花费不超过一小时。 被分配到迭代 #1 工作的组员将……不断迭代！

这些任务几乎完全与规范和测试有关，这应该不足为奇。 即使是绘图原型，也是在提供你的谜题可能外观的视觉规范，同时探索一些你在项目中将使用的较新且不太熟悉的 JavaScript API。

每位组员应将他们的迭代 #0 工作提交到 iter0 下以其用户名为名的目录中：例如，alyssap 在 iter0/alyssap/ 中工作。 迭代 #0 之后，让那些文件留在原处，迭代 #1 及以后使用 src/ 和 test/。

  • 对于绘图原型：你可以通过编辑 example-page.ts、运行 npm run watch-example 并在 example-page.html 中查看来编写 iter0 代码。 但不要在那里提交：将你的工作复制并提交到 iter0 中你的用户名目录下，这样你就不会产生冲突。 如果你需要建议，请咨询你的助教导师。

交付物与评分

迭代 #0 进度签到

在迭代 #0 的签到中，每个人都应该至少完成其迭代 #0 任务中的四项中的两项，并计划在当天（4 月 28 日，周二）结束前完成任何剩余的任务。 一个组件的两项迭代 #0 任务必须在该组件迭代 #1 被分配的团队成员开始工作之前完成并提交到项目仓库。

请记住，这些东西中没有一个是接近最终版本的！ 在每项任务上花费不超过大约一个小时的时间，并让你的队友知道他们什么时候可以查看你的工作。

迭代 #1 进度签到

在迭代 #1 的签到中，每个人都应该对其迭代 #1 任务中的一项（4 月 30 日，周四）和然后两项（5 月 5 日，周二）取得实质性进展，并计划在当天结束前完成任何剩余的工作。 你应该展示尽可能多的你已运行的单个或相互连接的系统部分。

你应该已经初步完成（或者对于迭代 #0 中涉及的项目，完成第二稿）语法、规范、自动化和手动测试、数据类型定义、表示不变量、抽象函数、equalValue/toString 等，在适当的地方定义好。 再次提醒，这些东西中没有一个是最终版本！

如果你遇到了困难，请尽早寻求帮助。 宽限日（来自作业）不适用于项目截止日期。
