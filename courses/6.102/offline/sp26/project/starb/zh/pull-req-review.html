用于代码审查的分支与 Pull Request

使用分支进行代码审查

在 6.102 中，我们一直建议不要使用 Git 分支。 然而……

在更广泛的软件工程领域中，更改通常是在提交到大家都在开发的主分支之前接受代码审查，而不是之后。 让我们来看看在一个流行的基于 Git 的协作工具 GitHub 上是如何实现这一点的。

在 GitHub 上，一组可审查的项目更改称为pull request，通常缩写为 PR，因为你是在请求项目的维护者将你建议的更改拉入代码中。 当你本人就是这些维护者之一时，你可以通过创建分支来创建和使用 pull request：

  • 创建一个新的本地分支，并在该分支上提交你的更改

  • 将该本地分支推送到同名的远程分支（就像我们一直在推送和拉取本地 main 和远程 main 一样）

  • 使用 GitHub 用户界面创建 pull request

  • 将审查者指向该 PR，他们可以在其中添加总体评论或针对特定行的评论

  • 通过在本地分支上进一步提交并远程推送来回应所请求的更改，这会更新该 PR

  • 最后，使用 GitHub 用户界面将已审查的更改合并到 main 分支上，这将关闭该 PR 并合并代码，而无需运行本地 git 命令。

我们不推荐在你 6.102 的项目中对每个更改都使用 pull request，但如果团队中的每个人都想尝试这个流程，你可能会将它用于"iter1" 或后续的重大更改。 不要将 pull request 用于"iter0"，因为 iter0 的目的是快速原型，而不是仔细审查。

如果还有任何疑问的话：对于一个这种规模和范围的项目，不要过度依赖流程，重点关注清晰的沟通和频繁的同步，让整个团队保持一致。

团队热身练习

如果你团队的所有成员都对在项目中使用 Git 分支和 GitHub pull request 进行代码审查感到有信心，请使用以下练习作为团队热身，来练习这个流程并决定你们想如何使用 GitHub 的功能。

你们应该一起亲自做这个练习。 确保在进入下一步之前，每个人都完成了每一步。

步骤 0：创建一个练习仓库

（注意：仅在周四课堂项目启动后可用）

一位团队成员：让 Didit 创建一个热身练习仓库。

其他所有人：等待！

仓库创建后：每个人都应该前往 Didit，克隆热身仓库，cd 进入其中，运行 npm install，然后继续下面的步骤。

步骤 1：在分支上提出更改

切换到一个名为 warmup-«你的用户名» 的分支。

对应的命令是：git switch -c warmup-USERNAME   ← 创建新分支并切换到该分支

运行 git status 确认你已经在该分支上。

打开 src/«你的用户名».ts 并更新 greeting 常量。 保存、添加、提交并推送到你的分支。

推送命令是：git push -u origin warmup-USERNAME   ← 当远程不存在该分支时，将其推送到 origin 远程

当你推送时，github.mit.edu 会在控制台输出中建议你访问创建 pull request 的 URL！

在 github.mit.edu 上，创建一个 pull request，请求将你的更改从 warmup-«你的用户名» 分支合并到 main 分支。

转到列出开放 pull request 的标签页，等待每个人都创建好他们的请求。

步骤 2：练习在 main 上合并

现在我们将（1）模拟一些与分支上的工作并行发生的其他工作，（2）练习在 main 分支上合并。

切换回 main 分支，你会看到你在 «你的用户名».ts 中的更改已经不在你的工作副本中了！

对应的命令是：git switch main   ← 切换到已存在的分支而不创建新分支

打开 main.ts 并取消注释只属于你的那两行。 在本地添加并提交，确保在 main 分支上提交。

一旦每个人都提交了：推送、拉取并合并所有的更改！ 确保每个人的本地 SHA 都相同，且工作副本是干净的。

此时，npm run main 应该输出三行 MISSING。 确保每个人都明白为什么！

步骤 3：代码审查

每个人都在 main 分支上，本地 SHA 相同，工作副本干净……

将每个人的 pull request 分配给不同的团队成员。 你可以通过在 GitHub 用户界面中分配审查者（点击 PR 页面右侧审查者旁边的齿轮图标）来正式地进行分配，也可以口头约定。

访问你被分配的 PR 并提出修复或改进要求：例如，"请多用感叹号！！！"。 GitHub 提供了多种方式来实现这一点，包括：

  • 在对话标签页上，你可以留下评论或讨论该 PR
  • 在文件更改标签页上，你可以留下针对特定行的评论（悬停并点击蓝色的加号）
  • 这些针对特定行的评论可以成为审查的一部分，在其中你可以决定是否批准这些更改，也可以是属于不属于正式审查的单独评论

（上面的链接指向的是旧版本的 GitHub 文档，因为 github.mit.edu 运行的是旧版本的 GitHub Enterprise。）

步骤 4：回应代码审查

现在访问你自己的 PR 页面，看看别人对你提出了什么要求。

切换回你的本地 warmup-«你的用户名» 分支。 你会看到 main.ts 中的所有更改已经不在你的工作副本中了！

在 «你的用户名».ts 中做出你的审查者所请求的修复。

在 warmup-«你的用户名» 分支上添加、提交并推送。 在 github.mit.edu 上查看你的 pull request，确认它已经更新。

步骤 5：将分支更改合并到 main

现在回到你请求修复的那个 PR，看看（例如，在文件更改标签页上）修复是否已被你的队友推送。

点击对话标签页上的按钮，将他们的更改合并到 main 上！ 有不同的方式可以合并这些更改，目前使用默认选项即可。

切换回你的本地 main 分支并拉取，直到你拥有所有人的更改。

此时，npm run main 应该输出所有更新后的问候语！

一旦一个 PR 分支被合并，你就不需要再管它了。 在一个真实的项目中，你现在会回到步骤 1，为你计划处理的下一个交付物创建一个新分支。
