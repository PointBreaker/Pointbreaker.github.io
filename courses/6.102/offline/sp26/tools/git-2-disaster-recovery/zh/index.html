使用 Git 进行灾难恢复

学习目标

  • 了解如何使用 Git 命令查看和检索旧版本
  • 练习使用 Git 恢复代码的旧版本

为什么提交看起来像差异比较？

我们将提交定义为整个项目的快照，但如果你问 Git，它似乎不这么认为：

$ git show 1255f4e
commit 1255f4e4a5836501c022deb337fda3f8800b02e4
Author: Max Goldman <maxg@mit.edu>
Date:   Mon Sep 14 14:58:40 2015 -0400

    Change the greeting

diff --git a/hello.txt b/hello.txt
index c1106ab..3462165 100644
--- a/hello.txt
+++ b/hello.txt
@@ -1 +1 @@
-Hello, version control!
+Hello again, version control!

Git 假设我们的项目在每次提交中大部分内容不会发生变化，因此只显示差异会更有用。 在几乎所有情况下，这确实是对的。但我们也可以使用 Git 来显示仓库在某个特定提交时的完整状态，而不仅仅是差异。

我们可以通过在提交 ID 后输入冒号 : 并指定文件路径，来让 Git 显示某个特定提交时该文件的内容：

$ git show 3e62e60:hello.scm
(display "Hello, version control!")

我们也可以使用此命令来显示某个特定提交时某个文件夹的内容，只需指定该文件夹的路径即可。值得注意的是，我们可以在冒号后面不输入任何内容来显示整个仓库在某个提交时的状态：

$ git show 3e62e60:
tree 3e62e60:

hello.rb
hello.scm
hello.txt

由于空文件路径对应仓库的根目录，因此它会显示仓库中的所有文件。

使用 git show 是从灾难中恢复的最简单方法之一：让 Git git show 你某个已损坏文件在之前正常版本时的内容。

灾难恢复

正如《Version Control with Git》中建议的，GUI 程序可以让您更轻松地浏览仓库并查找从错误中恢复所需的数据。 VS Code 内置的版本控制 UI 在这方面也很有用（例如，资源管理器面板中的 TIMELINE 视图可以让你快速查看文件的历史记录），但我们仍然推荐使用命令行来运行 Git 命令。

在 6.102 中，你可以使用 GitHub 的网页界面来查看推送到 github.mit.edu 的提交。

  • 在仓库的摘要页面上，你可以看到当前 main 分支根目录下的文件和文件夹。

  • 点击 Commits 查看提交历史。

  • 点击提交消息或提交 ID，查看该提交引入的更改。

  • 然后点击最右侧的 Browse Files 按钮，浏览该旧版本的整个项目。

  • 浏览时，请注意左侧的 Tree: …提交 ID… 按钮，它提醒你正在查看仓库的旧版本。 通常，当你浏览仓库的最新版本时，这个按钮会显示 Branch: main。

git clone

与其在灾难性的工作丢失后再进行恢复，不如从一开始就防止灾难发生。 如果你定期添加、提交和推送你的工作，这些工作就会安全地存储在远程仓库中，你可以通过 git clone 将其检索到一个新的文件夹中。

需要强调的是，git revert 不会将整个仓库回退到旧版本：它通过在 HEAD 处创建一个新提交来反转旧提交的效果。 你也可以通过手动编辑当前版本来撤销旧提交引入的更改，然后提交你的编辑，从而达到完全相同的效果。

git show 和 git checkout

大多数时候，当我们犯了错误，我们不想撤销整个提交。例如，如果一个提交改进了三个不同的函数，而只有其中一个改进是错误的，我们只想撤销那一个。

通常，找到你需要的可用代码的最简单方法是让 Git 显示旧版本。 将鼠标悬停或点击以下示例中的每个步骤：

显示提交的差异

  1. git showrevision 会显示提交的差异。
    被删除的文本行显示为红色，以减号 - 开头；添加/修改的行显示为绿色，以加号 + 开头。
  2. 如果你 git show 的提交的差异内容超过一屏，它将分页显示（最初使用 more 命令，但现在更可能使用其继任者 less）。如果你在终端底部看到 : 提示符，说明正在分页…
  3. … 这意味着你可以按 space 向下翻页，或使用箭头键逐行查看。 （你可以按 h 获取更多关于使用 less 的帮助。） 按 q 退出 less 并返回命令提示符。

显示文件的旧版本

git showrevision:path/to/file 会输出文件的旧版本。

$ git show 1255f4e:hello.txt
Hello again, version control!
$ git show 41c4b8f:hello.txt
Hello, version control!

当你找到一个看起来正确的旧版本后，复制粘贴是最简单的恢复策略。

用旧版本替换文件

  1. git checkoutrevision--path/to/file 会用旧版本替换工作目录中的文件。 该命令中的 --（前后各有一个空格）和路径都很重要，不要忘记它们！
  2. 这个命令暂时不会创建提交，所以我们的历史没有改变…
  3. … 但它确实会将更改暂存！
  4. 我们可以查看已暂存的更改：我们正在通过删除 "again" 将 hello.txt 恢复到旧内容。
$ git checkout 41c4b8f -- hello.txt





$ git checkout 41c4b8f -- hello.txt
$ git lol
* b0b54b3 (HEAD, origin/main, origin/HEAD, main) Greeting in Java
*   3e62e60 Merge
|\
| * 6400936 Greeting in Scheme
* | 82e049e Greeting in Ruby
|/
* 1255f4e Change the greeting
* 41c4b8f Initial commit

$ git checkout 41c4b8f -- hello.txt
$ git status

Your branch is up-to-date with 'origin/main'.
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)

        modified:   hello.txt



$ git diff --staged
diff --git a/hello.txt b/hello.txt
index 3462165..c1106ab 100644
--- a/hello.txt
+++ b/hello.txt
@@ -1 +1 @@
-Hello again, version control!
+Hello, version control!

与 git revert 不同，此命令中的 revision 是我们想要的特定修订：文件将显示为该修订时的样子，包括该修订中的更改，不包括之后的任何更改。

你不应该使用不带 --path/to/file 的 git checkoutrevision 命令。 如果你这样做，你的 HEAD 将会指向那个旧提交，你将不再处于 main 分支上。 这被称为 分离的 HEAD，没有人想要这样。

如果有命令警告你 HEAD 处于分离状态，请在继续之前寻求帮助，以避免丢失工作。 如果你在分离 HEAD 的情况下工作而没有意识到，你所做的工作几乎总是可以恢复的，但必须小心操作。 请寻求帮助！

使用 GitStream 练习

GitStream 在多个练习页面同时打开时无法工作。

不要在多个标签页中打开练习。 如果练习无法工作，请关闭所有打开的 GitStream 页面，然后重试。

如果遇到问题，请寻求帮助。

GitStream → 练习 git log 和 git revert

请注意，GitStream 不会跟踪你是否已经完成了此练习。 要查看你已经完成了哪些 GitStream 练习，请查看 Omnivore。
