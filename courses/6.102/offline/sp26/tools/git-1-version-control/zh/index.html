使用 Git 进行版本控制

学习目标

  • 了解什么是版本控制以及我们为什么使用它

  • 练习作为独立程序员使用 Git

版本控制

版本控制系统是软件工程领域不可或缺的工具。 几乎所有项目——无论是严肃的还是爱好的、开源的还是专有的——都使用版本控制。 没有版本控制，协调一个程序员团队同时编辑同一项目的代码将会令人极度抓狂。

版本控制是指跟踪一个程序或文档的多个版本。 在你迄今为止的计算经验中，你可能已经使用过某种形式的版本控制：

  • Dropbox 有版本历史，保存文件的旧版本
  • Google Docs 有文档的版本历史
  • 文字处理软件和编辑器都有撤销功能，帮助你回到最近的编辑版本

你可能甚至自己实现过一些简单的版本控制，通过保存带有版本号的多个文件副本来实现。 让我们探讨在编程中这样做的一个场景，看看一个好的软件版本控制系统应该具备哪些特性。

不过，如果 Alice 不小心，这种方法可能会遇到麻烦。 想象一下，她开始在笔记本电脑上编辑hello.ts来创建"版本 5"。 然后她分心了，忘记了她的修改。 后来，她开始在台式机上创建一个新的"版本 5"，包含了不同的改进。 我们将这些版本称为"5L"和"5D"，分别代表"笔记本电脑"和"台式机"。

当需要上传修改到云端时，就有发生意外的机会！ Alice 可能将所有本地文件复制到云端，导致云端只包含版本 5D。之后 Alice 从云端同步到她的笔记本电脑，可能会覆盖版本 5L，丢失有价值的修改。 Alice 真正想要的是一个合并操作，基于两个版本 5 创建一个新版本。

至此，仅考虑一个程序员独立工作的场景，我们已经列出了版本控制方案应该支持的操作：

  • 回退到过去的版本
  • 比较两个不同的版本
  • 推送完整的版本历史到另一个位置
  • 拉取历史记录从那个位置
  • 合并从同一早期版本分叉出去的版本

仅仅上传新源文件并不是向他人传达一组修改的高级理念的好方法。 所以让我们添加一个日志，为每个版本记录是谁编写的、何时完成的，以及什么被修改了，以简短的人工编写消息的形式。

现在推送另一个版本变得更加复杂，因为我们需要合并日志。 合并日志比合并 TypeScript 文件容易，因为日志的结构更简单——但如果没有工具支持，Alice 和 Bob 仍然需要手动合并他们的日志！ 我们还希望强制日志和实际可用文件集之间的一致性：对于每个日志条目，应该能够轻松提取出在该条目创建时完整的文件集。

但有了日志，就能启用各种有用的操作。 我们可以只查看特定文件的日志：仅限于涉及修改某些文件的那些修改的日志视图。 我们还可以使用日志来确定每行代码是由哪个修改贡献的，或者更好的是，确定每行代码是由谁贡献的，这样当代码出问题时我们就知道该找谁抱怨了。 这种操作手动做会很繁琐；版本控制系统中的自动操作称为annotate（或者不幸的是，blame）。

多分支

有时让一部分开发者分开去开发一个分支是有意义的，一个平行的代码宇宙，比如说用来试验一个新功能。 其他开发者不想拉取新功能，直到它完成，即使在此期间创建了多个协调的版本。 即使单个开发者也可以发现创建分支是有用的，原因与 Alice 尽管独自工作却使用云服务器的原因相同。

一般而言，拥有多个共享位置来交换项目状态是有用的。 可能同时存在多个分支位置，每个由几位程序员共享。 通过正确的设置，任何程序员可以从任何位置拉取或推送到任何位置，创造了合作模式的极大灵活性。

令人震惊的结论

当然，事实证明我们在这里并没有发明任何新东西： Git为你做了所有这些事情，许多其他版本控制系统也同样如此。

传统的集中式版本控制系统，如CVS和Subversion，实现了我们上面设想的部分功能。 它们支持一个协作图——谁与谁共享什么修改——带有一个主服务器，以及只与主服务器通信的副本。

在集中式系统中，每个人必须向主仓库（通常缩写为repo）推送和从中拉取他们的工作。 修改被安全地存储在版本控制中的条件是它们在主仓库中，因为那是唯一的仓库。

相比之下，分布式版本控制系统，如Git和Mercurial，允许各种不同类型的协作图，团队和团队子集可以轻易地试验代码和历史的替代版本，在确定它们是好的想法时将版本合并在一起。

在分布式系统中，所有仓库都是平等的，由用户为它们分配不同的角色。 不同的用户可能向不同的仓库推送和从中拉取他们的工作，团队必须决定一个修改进入版本控制意味着什么。 一个程序员仓库中的修改是否需要与指定的协作者或服务器共享，然后团队其余成员才认为它是正式的？

版本控制术语

  • Repository（仓库）或 repo：本地或远程存储我们项目版本的地方
  • Working copy（工作副本）：我们可以处理的本地可编辑的项目副本
  • File（文件）：我们项目中的单个文件
  • Version（版本）或 revision（修订）：在某个时间点我们项目内容的记录
  • Change（修改）或 diff（差异）：两个版本之间的差异
  • Head：当前版本

版本控制系统的特性

  • 可靠：在需要时长期保存版本；允许备份
  • 多文件：跟踪项目的版本，而非单个文件
  • 有意义的版本：做了什么修改，为什么做这些修改？
  • 回退：恢复旧版本，全部或部分
  • 比较版本：查看改变了什么
  • 审查历史：针对整个项目或单个文件
  • 不仅限于代码：文本、图片、……

它应该允许多人协同工作：

  • 合并：合并没有从共同早期版本分叉的版本
  • 跟踪责任：谁做了那个修改，谁碰了那行代码？
  • 并行工作：允许一个程序员独立工作一段时间（不放弃版本控制）
  • 进行中的工作：允许多个程序员共享未完成的工作（不影响他人，不放弃版本控制）

Git

我们在 6.102 中使用的版本控制系统是Git。 它功能强大，值得学习。 但 Git 的用户界面可能非常令人沮丧。 Git 的用户界面是什么？

  • 在 6.102 中，我们将在命令行使用 Git。 命令行是一个生活事实，因其强大而无处不在。

  • 命令行可能使你很难看清仓库中正在发生什么。 你可能会发现SourceTree（右图所示）对 Mac 和 Windows 用户很有用。 在任何平台上，gitk都可以给你一个基本的 Git 图形界面。 用 Google 搜索可以找到其他建议。

关于 Git 工具的一个重要说明：

  • 像 VS Code 这样的编程编辑器通常内置了 Git 支持，带有有用的图标或高亮显示，展示（例如）你修改了哪些文件以及哪些文件还没有添加到仓库。 然而，我们不建议使用编辑器菜单或插件来运行 git 命令，如 add、commit 或 push。 如果你遇到问题，课程工作人员可能无法帮助你。

  • GitHub为 Mac 和 Windows 制作了桌面应用。 由于 GitHub 应用改变了某些 Git 操作的工作方式，如果你使用 GitHub 应用，课程工作人员将无法帮助你。

命令行

让许多学生学习 Git 更难的一件事是它是一个命令行程序。 如果你不熟悉命令行，这可能会令人困惑。

命令行是你计算机的一个界面，类似于 Mac Finder 或 Windows Explorer，只不过它是基于文本的。 正如其名称所示，你通过"命令"与之交互——每行输入以一个命令开头，后面跟着零个或多个参数，以空格分隔。

确保使用正确的命令行

在 MacOS 和 Linux 上，打开你的终端应用。

在 Windows 上，确保你打开的是Git Bash。

  • 不要使用 Windows 命令提示符；它有不同的命令语法，不是 Mac 和 Linux 中使用的 Unix shell 语法。
  • 也不要使用 Windows Subsystem for Linux；虽然它确实使用 Unix shell 语法，但在一些其他重要方面（比如文本文件的换行符约定）与 Unix shell 不同，这会在本课程中给你带来问题。

常用命令

你将需要在命令行中四处移动。以下是实现这一目的最重要的命令。

  • cd（代表"change directory"）

    更改当前目录。 如果你在一个名为hello的子目录所在的目录中，那么cd hello会进入那个子目录。

    使用cd ..移动到当前目录的父目录。

  • pwd（"print working directory"）

    打印当前目录，如果你不确定你在哪里。

    在配置良好的系统中，你的当前目录会作为系统准备接收命令时显示的提示符的一部分显示出来。 如果你的系统不是这样，请寻求帮助配置你的提示符。

  • ls（"list"）

    列出当前目录中的文件。

    使用ls -l获取关于文件的额外信息（"长"列表）。 使用ls -a（代表"all"）显示隐藏文件，即名称以句点开头的文件和子目录。

  • mkdir（"make directory"）

    在当前目录中创建一个新目录。 要创建一个名为goodbye的目录，使用mkdir goodbye。

  • 上箭头和下箭头

    使用上箭头将你刚才运行的命令放回命令行。 你现在可以编辑该命令来修正拼写错误，或者直接按回车再次运行它。

    使用上下箭头键浏览你的命令历史，这样你永远不需要重新输入一个长命令行。

  • Ctrl+A和Ctrl+E

    使用Ctrl+A将光标移到行首，或使用Ctrl+E将光标移到行尾。（如果你的键盘有 Home 或 End 键并且你的终端提示符能正确解释它们，它们也可能有效。）

    你可能会发现这些快捷键对编辑长命令很有用，可以避免按左右箭头键在整个命令中移动光标。

  • Ctrl+C

    你可能已经在 6.101（以前的 6.009）中熟悉了Ctrl+C，用于停止从命令行启动的正在运行的进程。不出所料，它在这里也会有用，特别是当我们开始部署小型 Web 服务器时。

    然而，Ctrl+C还有另一个用途！如果你在终端中输入了一个长命令后改变了主意，在没有按Enter或Return的情况下，按Ctrl+C会给你一个新的提示符并丢弃之前的输入，允许你快速取消命令，而不需要按住Backspace。

  • Tab 补全

    你可以使用Tab键自动补全文件或目录名称。

    例如，如果你想将目录更改为一个名为source的子目录，你可以在命令行输入cd s然后按Tab，如果只有一个以s开头的子目录，它将自动补全命令（cd source），或者列出所有以s开头的子目录。

Git 对象图

阅读：Pro Git 1.3：什么是 Git？

该阅读材料介绍了 Git 仓库的三个部分：.git 目录、工作目录和暂存区。

我们使用 Git 执行的所有操作——clone、add、commit、push、log、merge、……——都是对图数据结构的操作，该数据结构存储了项目中所有文件的版本以及描述这些修改的所有日志条目。 Git 对象图存储在你本地仓库的.git目录中。 远程仓库也有该图的一个副本：对于 6.102，该副本在 github.mit.edu 上，存储在某个 IS&T 数据中心。

使用git clone复制对象图

你如何将对象图从 github.mit.edu（或任何其他远程存储）获取到你的本地机器上，以便开始处理作业？ git clone复制该图。

假设你的用户名是bitdiddle，你运行：

git clone ssh://github.mit.edu/.../ps0-bitdiddle.git ps0

Git 执行几个步骤。 将鼠标悬停或点击每个步骤以更新下方图示：

  1. 创建一个空的本地目录ps0，以及ps0/.git。
  2. 连接到 github.mit.edu 并将对象图从ps0-bitdiddle.git复制到ps0/.git中。
  3. 检出（Check out）main分支的当前版本。

高亮步骤的图示：

我们还没有解释对象图中包含什么。 但在那之前，让我们理解git clone的第 3 步：检出main分支的当前版本。

对象图以方便快捷的格式存储在磁盘上，用于执行 Git 操作，但不是我们可以直接使用的格式。 在Alice 发明的版本控制方案中，hello.ts的当前版本就称为hello.ts，因为她需要能够正常编辑它。 在 Git 中，我们通过从对象图中检出文件来获取文件的普通副本。 这些是我们在 VS Code 中看到和编辑的文件。

我们上面还决定，支持版本历史中的多个分支可能是有用的。 多个分支对于从事长期项目的大团队至关重要。 为了在 6.102 中保持简单，我们将不使用分支，我们也不建议你创建任何分支。 每个 6.102 Git 仓库都有一个名为main的默认分支，我们所有的工作都将在main分支上进行。 （默认分支以前按惯例称为master。如果你在在线 Git 教程或 Stack Overflow 答案中看到它，只需将其替换为main即可。）

所以git clone的第 2 步为我们获取了对象图，第 3 步为我们获取了一个工作目录，其中包含我们可以编辑的文件，从项目的当前版本开始。

获取仓库历史

让我们终于深入那个对象图吧！

克隆一个有一些有趣历史的示例仓库：

git clone https://github.com/6031/ex05-hello-git hello-git

并确保你在它的目录中：

cd hello-git

以下是最有用的命令：

  • git lol

    显示仓库中所有提交的列表。它是git log加上几个选项的别名，是你按照入门说明时创建的。

  • git show

    显示仓库的最后一次提交。它会显示提交消息以及所有的修改。

长输出：如果git lol或git show产生的输出超过一页，你会在屏幕底部看到一个冒号（:）符号。 你将无法输入另一个命令！ 使用方向键或 Page Up/Page Down 上下滚动，按q退出输出查看器。 （你也可以按h查看查看器的其他命令，但滚动和退出是最重要的。）

提交 ID：每个 Git 提交都有一个唯一的 ID，就是你在git lol或git show中看到的十六进制数字。 提交 ID 是该提交内容的唯一加密哈希值。 每个提交，不仅仅是在你的仓库中，而是在所有 Git 仓库的宇宙中，都有一个唯一的 ID（以极高的概率）。

你可以通过 ID 引用一个提交（通常只需前几个字符）。 这在git show等命令中很有用，你可以查看特定的提交，而不仅仅是最新的那个。

你还会在github.mit.edu和Didit等工具中看到以 ID 标识的提交。

Git 项目的历史是一个有向无环图（DAG）。 历史图是存储在.git中的完整对象图的骨干，所以让我们先关注它一分钟。

历史图中的每个节点都是项目的一个提交（commit），也称为版本（version），也称为修订（revision）：在该时间点项目中所有文件的完整快照。 每个提交通过其提交 ID 标识，以十六进制数字显示。

除了初始提交，每个提交都有一个指向父提交的指针。 例如，提交1255f4e的父提交是41c4b8f：这意味着41c4b8f先发生，然后是1255f4e。

有些提交有相同的父提交。 它们是从一个共同的早期版本分叉出去的版本，例如因为两个开发者在独立工作。

一个提交可以有两个父提交。 这是一个将分叉的历史重新连接在一起的版本，例如因为这些开发者随后将他们的工作合并到了一起。

分支——记住main目前将是我们的唯一分支——只是一个指向提交的名字。

最后，HEAD指向我们当前的提交——几乎。 我们还需要记住我们正在处理哪个分支。 所以 HEAD 指向当前分支，分支指向当前提交。

使用git commit添加到对象图

我们如何向历史图中添加新的提交？git commit创建一个新的提交。

在某个平行宇宙中，git commit可能基于你工作目录的当前内容创建一个新的提交。 所以如果你编辑了hello.ts然后执行了git commit，快照将包含你的修改。

我们不在那个宇宙中；在我们的宇宙中，Git 使用仓库的第三个也是最后一个部分：暂存区（也称为索引（index），知道这个名字有用只是因为它有时会出现在文档中）。

暂存区就像一个原始提交，一个进行中的提交。 以下是我们如何使用暂存区和git add来构建一个新的快照，然后使用git commit将其固定下来：

修改hello.txt，git add hello.txt，git commit

  1. 如果我们还没有做任何修改，那么工作目录、暂存区和 HEAD 提交都是相同的。

获取仓库状态

Git 有一些方便的命令用于查看仓库的状态。

其中最重要的是git status。 随时运行它来查看哪些文件是：

  • 未跟踪的（untracked）（全新的，从未添加到 Git 中）；
  • 已修改但尚未暂存的；
  • 已修改且已暂存的。如果你git commit，只有已暂存的修改会被包含在提交中。

注意，同一个文件可能同时有已暂存和未暂存的修改，如果你在运行git add之后再次修改了文件。

当你有未暂存的修改时，你可以通过运行git diff查看修改内容（相对于最后一次提交）。 注意这不会包含已暂存（但未提交）的修改。 你可以通过运行git diff --staged查看已提交但尚未提交的已暂存修改。

频繁使用git status来跟踪你是否有未修改、未跟踪文件、未暂存修改或已暂存的修改；以及你的本地仓库中是否有尚未推送的新提交，这将在下面讨论。

使用git push和git pull发送与接收对象图

我们可以使用git push将新的提交发送到远程仓库：

git push origin main

将鼠标悬停或点击每个步骤以更新图示：

  1. 当我们克隆一个仓库时，我们获取了历史图的一个副本。
    Git 将我们克隆的来源记住为一个名为origin的远程仓库。
  2. 使用git commit，我们在main分支上向本地历史添加新的提交。
  3. 要将这些修改发送回origin远程，使用git push origin main。

我们使用git pull接收新的提交。 除了获取对象图的新部分，git pull还通过检出最新版本来更新工作副本（就像git clone开始时检出工作副本一样）。 如果远程仓库和本地仓库都已更改，git pull将尝试将这些修改合并在一起。

推送

在你做了一些提交之后，你会想把它们推送到远程仓库。 在 6.102 中，你应该只有一个远程仓库可以推送，叫做origin。 要推送到它，你运行命令：

git push origin main

命令中的origin指定你要推送到origin远程。 按照惯例，这是你克隆的远程仓库。

main指的是main分支，我们 Git 仓库中的默认分支。 在 6.102 中，我们不会使用main以外的分支。 我们所有的提交都将在main上，这是我们要推送的分支。

一旦你运行了这个命令，你将被提示输入密码，然后希望一切都能推送成功。 你会得到一行像这样的输出：

a67cc45..b4db9b0  main -> main
