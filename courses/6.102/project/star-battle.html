项目：Star Battle 星战谜题系统

本课程团队项目要求构建一个通过网络传输谜题并提供图形用户界面供玩家解决的 Star Battle 逻辑谜题系统。项目练习客户端/服务器架构、ParserLib 解析、抽象数据类型设计与团队协作。

Star Battle 谜题规则

在 Star Battle 谜题中，n×n 网格被划分为 n 个区域。玩家必须找到 2n 颗星的放置方式，使得每行、每列和每个区域恰好有 2 颗星，且没有垂直、水平或对角相邻的星。本项目使用 10×10 双星谜题，并假设有效谜题具有唯一解。

设计自由

本项目你有大量的设计自由，可选择在代码中使用的接口、类和方法签名。必须明智地选择。需使用规格、测试、抽象函数、表示不变量、安全性论证、checkRep 和其他断言。

本作业规格约束你的解决方案必须做什么，但许多设计问题未在此回答——你可自行作答，只需合理、一致、安全免于缺陷、易于理解且随时可变。

注意：Didit 仅运行你自己的测试。正确性由你负责，必须依靠自己仔细的规格、测试与实现来保证。

团队 Git

概述

分开工作

对于项目的几个部分，两名团队成员将独立完成该部分，在 iteration #0 中产生两种不同设计。第三名成员负责对这些设计进行迭代，在 iteration #1 中推进该部分。

检查会议

团队将分配一名 TA 导师帮助设计并保持进度。每次团队工作时间必须与 TA 检查。检查时每个成员应准备：

  • 说出自上次检查以来完成的工作
  • 说出到下次检查计划完成的工作
  • 说出阻碍进展的因素（如有）
  • 展示自己的项目工作副本已提交、推送并与远程仓库同步

协同工作

除最终反思外，项目的所有部分都应提交到共享仓库。使用 Caesar 练习的代码审查技能审查彼此代码。可选择使用 github.mit.edu 上的拉取请求（pull requests），这需要团队使用 Git 分支。

结对编程

强烈建议尝试结对编程——两人协作使用一台计算机。结对编程是实时代码审查，结果更正确、更清晰、更易变更。注意多人贡献提交时在提交消息中提及。

协作最佳实践

  1. 每次坐下开始工作时先 pull
  2. 频繁提交和推送
  3. 不要破坏构建！（不要提交无法编译的代码）

高层任务

  • 团队合同。开始前撰写并同意团队合同。
  • 理解问题。仔细阅读项目规格。
  • 设计。为系统各部分创建抽象数据类型，编写解析谜题的语法。
  • 迭代。设计、测试、实现每个部分，始终朝着端到端原型努力。
  • 测试。为系统各组件编写 Mocha 测试。
  • 实现。编写实现代码使测试通过。
  • 反思。个人撰写项目体验的简短评论。

⭐️⚔️ 规格说明

设计、测试并实现客户端/服务器 Star Battle 谜题 GUI。系统仅需支持 10×10 双星谜题且具唯一解。

标记为 [for now] 的项目在 iteration #0、#1 和集成期间是要求。仅当你拥有完整的端到端工作实现后，才可打破这些限制以改进设计或启用新功能。

规格：解析器

  • 系统必须能解析 puzzles 目录中提供的示例谜题（.starb 纯文本文件）。
  • 提供的谜题是"已解决"的：文件指示每个区域中星的位置。
  • [for now] 同一语法和解析器还必须处理从服务器发送到客户端的"空白"谜题。
  • 必须使用 ParserLib。
  • 文件中坐标为从左上角开始的 1 索引（行, 列）。
  • 与 PS3 不同，谜题非递归，不应期望递归解析器或 AST。

规格：抽象数据类型

  • 系统必须使用不可变的谜题 ADT，可表示有效的未解决、部分解决和完全解决的谜题。设计由你决定。
  • 客户端 Web 页面必须使用另一个客户端 ADT 管理其状态和操作。设计完全由你决定。
  • [for now] 必须在服务器和客户端使用相同的不可变谜题 ADT。仅客户端使用客户端 ADT。
  • 客户端和服务器没有共享内存，故不共享谜题 ADT 的实例。但必须在系统的两部分使用相同的 ADT 类型。
  • 与 PS3 不同，并非每个谜题 ADT 实例都需要有可解析的字符串表示。

规格：服务器

  • 服务器必须在端口 8789 接受 HTTP 请求，请求 puzzles 子目录中由其文件名（无扩展名）标识的谜题。
  • 必须向客户端传输"空白"谜题：每个区域中的所有位置列为空。
  • [for now] 服务器不得维护任何玩家或游戏状态。
  • 必须使用 express。
  • 除发送空白谜题外，不要求其他能力。
  • 与 PS4 不同，所需规格不包含多人游戏。

规格：客户端

  • 客户端 Web 页面必须：请求空白谜题、在屏幕上显示谜题、允许用户在网格任意位置添加星、显示这些星、允许用户移除已添加的星、并在用户解决谜题时通知用户。
  • 启动时应在 Web 页面上显示用户所需的任何说明。
  • 必须支持点击谜题添加星。
  • [for now] 客户端只能使用 canvas 绘图，不得使用任何其他 HTML 元素进行绘图或交互。
  • [for now] 客户端必须请求并播放 starb-client.ts 顶部的 PUZZLE 常量给出的单一谜题。
  • [for now] 点击已添加的星必须移除它。
  • 客户端可自行确定谜题已解决，或请求服务器确定。
  • 谜题文件使用（行, 列）坐标，非（x, y）坐标。

规格：扩展

如果系统展示了 SFB/ETU/RFC 属性，鼓励扩展：

  • 在解题过程中标记必须为空的单元格
  • 向服务器请求可用谜题列表并选择解决
  • 成功解决谜题时的庆祝动画
  • 请求提示（突出显示星或单元格）
  • 处理 10×10 双星以外的变体

测试要求

自动化测试

  • 不得使用 package.json 中包含的包以外的包。
  • 测试不得使用不合理的空间或时间。
  • 代码应使用 localhost 端口 8700-8799 在服务器与客户端间通信。
  • 名称中提及"Didit"的测试将在 Didit 上被排除运行。

Canvas 绘图测试

使用 WebOrNodeCanvas 类型定义解决浏览器与 Node 的 getContext 差异。在浏览器代码中定义辅助类型，在 Mocha 测试中导入 createCanvas 创建 Canvas 实例。

import type { Canvas, CanvasRenderingContext2D as NodeCanvasRenderingContext2D } from 'canvas';
type WebOrNodeCanvasRenderingContext2D = CanvasRenderingContext2D | NodeCanvasRenderingContext2D;
type WebOrNodeCanvas = Omit<HTMLCanvasElement | Canvas, 'getContext'> & {
    getContext(contextId: '2d'): WebOrNodeCanvasRenderingContext2D | null;
};

无浏览器依赖

在 Node 中运行的代码不得使用 DOM API。避免在导入时会立即运行的模块中使用 document。

Web 服务器测试

使用 fetch() 模拟客户端/服务器交互。示例：

import assert from 'assert';
import { WebServer } from '../src/web-server.ts';
import { StatusCodes } from 'http-status-codes';

describe('server', function () {
    it('covers /hello with valid greeting', async function () {
        const server = new WebServer();
        await server.start();
        const url = `http://localhost:${server.port}/hello/w0rld`;
        const response = await fetch(url);
        assert.strictEqual(await response.text(), "Hello, w0rld!");
        server.stop();
    });
});

手动测试

不要依赖手动测试构建正确系统。对于不确定如何自动测试的规格，可记录手动测试覆盖某些分区。每个手动测试：给出描述性名称，列出覆盖的部分，简要但精确地描述人类测试者应遵循的步骤及每步的断言。

Iteration #1

填写姓名规划系统不同模块的工作分配。要求每个成员做出几种不同种类的贡献。将 iteration #1 的组件分配，每人两个任务，使每行每列中任何人名至多出现一次。

Iteration #1 网格

Task 1Task 2
Person 1Puzzle ADTParser
Person 2DrawingServer
Person 3Client ADTInteraction

组件描述

  • Puzzle ADT：在客户端和服务器表示谜题的 ADT
  • Parser：用于从文件读取并从服务器发送到客户端的谜题解析器
  • Server：向客户端发送谜题的 HTTP 服务器
  • Client ADT：表示客户端状态的 ADT
  • Drawing：绘制谜题的函数或类型
  • Interaction：驱动客户端与服务器和用户交互的函数或类型

Iteration #0

在 iteration #1 之前，其他两名成员将为每个部分并行完成 iteration #0：

  • Puzzle ADT specs + t.s.：谜题 ADT 的规格与测试策略
  • Grammar："空白"和"已解决"谜题的单一语法
  • Drawing prototype：不同谜题组件的硬编码绘图
  • Web API + t.s.：客户端/服务器通信规格与测试策略
  • Client ADT specs + t.s.：客户端 ADT 的规格与测试策略
  • Integration t.s. + tests：整个客户端/服务器系统的手动测试计划

这些任务应独立、并行完成，产生两种不同的规格、测试策略等。每项任务不超过一小时。
