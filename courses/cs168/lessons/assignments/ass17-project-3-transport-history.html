工程合同

What you build
用 Fall 2022 Transport spec 与 PointBreaker/transport 的 2024 提交轨迹复建一个用户态 TCP socket 的心智模型，找出已闭合的不变量与尚未闭合的边界。
核心不变量
任意时刻，应用可读数据是唯一且连续的字节前缀；snd.una 之前已确认，snd.nxt 之前已发送，重传绝不创造新的逻辑字节。
Definition of Done
Correct：当前适用测试通过；Understand：能从事件解释状态变化；Evidence：保留最小 trace、失败注入和边界测试。
禁止捷径
不读取模拟器隐藏全局状态，不修改框架绕过协议，不把本教材伪装成提交实现。

依赖优先的实现路径

1 · 三次握手（历史 Stage 1）

Build
connect 初始化 TCB、绑定本地端点、发送 SYN(ISS) 并进入 SYN_SENT；合法 SYN+ACK 推进 snd.una/rcv.nxt、窗口与 ESTABLISHED。
Evidence
每个状态变化必须由一个可指认的 segment 与范围检查触发。

2 · 接收路径（Stage 2–3）

Build
acceptable_seg 先做窗口判定；RecvQueue 按模序号排序；只交付覆盖 rcv.nxt 的连续前缀，重叠片段裁掉已收部分。
Evidence
in-order、gap、reorder、overlap、wraparound 五类测试。

3 · 发送与流量控制（Stage 4–5）

Build
RetxQueue 保存占序号空间且需重传的 segment；available = advertised window − bytes in flight；ACK 累计弹出已确认项并更新窗口。
Evidence
已有在途数据时的新 send 是最关键的超发边界。

4 · 关闭状态机（Stage 6–7）

Build
被动 FIN→CLOSE_WAIT→LAST_ACK；主动 FIN→FIN_WAIT_1/2，交叉关闭→CLOSING，最终 TIME_WAIT。FIN 在前序数据清空后才发送且占 1 序号。
Evidence
ACK 先到、FIN 先到、同时到达三条轨迹。

5 · 重传与 RTT（Stage 8–9）

Build
只给 SYN/FIN/data 计时；超时重传不重复入队/推进 snd.nxt；对未重传包采 RTT，按 RFC 6298 更新 SRTT/RTTVAR/RTO，超时指数退避。
Evidence
丢一个包、连续超时、重传歧义、RTO 上下界。

最小 sanity check

先构造只含两个端点和一个可控故障的最小场景。预测每条消息、字段和状态变化，再运行一次；任何额外消息、无法解释的表项或越界状态都视为失败，即使最终输出碰巧正确。

你的历史实现：提交轨迹与代码审计

以下结论来自你提供的公开仓库与提交历史。它们服务于复盘，不复制完整实现，也不声称旧代码满足当前未发布/已变化的 spec。

  1. 2024-04-29：bytes/string 修复后完成 three-way handshake。
  2. 2024-04-30～05-01：从 in-order 接收推进到 out-of-order queue，随后实现发送、advertised window 与关闭。
  3. 2024-05-02：完成 retransmission，提交信息只写“passed 1 2 of stage 9”；最终提交修复 bytes-in-flight 入口条件。
  4. 复盘点一：maybe_send 虽计算 bytes_in_flight，但 payload 限制仍主要与完整 snd.wnd 比较；已有未确认数据时需要验证是否超出剩余窗口。
  5. 复盘点二：超时分支写的是 min(rto, MAX_RTO)，没有把 RTO 翻倍；这与历史 spec Stage 9 明确的 exponential backoff 不一致。
  6. 复盘点三：rx 路径留下大量 error 级调试日志。复建时应改成结构化 trace，并用 state/seq/ack/window 过滤，而不是在正常路径持续输出。

失败签名

  • 把普通整数比较用于 32 位回绕序号
  • 窗口上限未减去 bytes in flight
  • 重传再次推进 snd.nxt
  • 重传样本用于 RTT
  • 把历史 Project 2 直接称为 Fall 2026 Project 3
Hint 1 · Concept

先指出哪个协议不变量被破坏，不要直接添加特判。

Hint 2 · Structure

让每个输入事件只经过一次“验证 → 状态转移 → 输出”流水线；把可纯计算的部分提取成无副作用函数。

Hint 3 · Debug strategy

对边界前后各造一个输入，用 spy 记录所有发送动作，并在每次 mutation 后断言控制块/表项关系。

完成后的复盘

  1. 哪个状态是真正的 single source of truth？
  2. 哪些测试只证明输出，哪些测试能证明没有额外副作用？
  3. 如果消息延迟、重复、乱序或刚好落在边界，会破坏哪条假设？
  4. 今天重写时，你会先设计哪三个 helper / invariant？

能力门：不用翻代码，向未来的自己讲清一个正常轨迹、一个失败轨迹和一个恢复轨迹，并能从日志重建状态。
