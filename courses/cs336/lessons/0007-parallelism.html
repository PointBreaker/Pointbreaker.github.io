分布式训练并行

现代大模型不可能在一张 GPU 上训练。这一课系统讲解分布式训练的四种并行策略——data、tensor、pipeline、sequence——以及它们如何组合。统一主题：通过复制/分片来编排计算，避免数据搬运瓶颈。

为什么需要分布式训练

规模的力量

# 单卡是否能训练一个模型，不能只用参数量判断：
# 还要计入梯度、优化器状态、激活、临时 buffer 和通信 workspace。
#
# 例如常见 mixed-precision AdamW 预算可接近 18 bytes/parameter，
# 但具体值随 master weights、gradient dtype、optimizer 与 sharding 改变。
# 70B、405B 等规模通常需要同时分片模型状态、计算和激活。
#
# 理想训练时间 = 总训练 FLOPs / (GPU 数 × 单卡峰值 FLOP/s × MFU)
# 真实扩展还受通信、负载不均、batch size 与故障影响，不能假定线性加速。

统一主题

上一课（单 GPU）：通过 fusion/tiling 减少内存访问

这一课（多 GPU）：通过复制/分片减少跨 GPU 通信

核心权衡：计算 vs 内存 vs 通信——你可以选择重算、存内存、或存到另一张 GPU 然后通信。

通信原语

七种基本通信操作

操作输入输出描述
Broadcast1 个 GPU 有数据所有 GPU 有数据一对多
Scatter1 个 GPU 有大数据所有 GPU 各有一片分片分发
Gather所有 GPU 各有一片1 个 GPU 有大数据收集
Reduce所有 GPU 有数据1 个 GPU 有结果聚合（sum/max）
All-Gather所有 GPU 各有一片所有 GPU 有完整数据Gather 到所有
Reduce-Scatter所有 GPU 有完整数据所有 GPU 各有一片结果Reduce + Scatter
All-Reduce所有 GPU 有数据所有 GPU 有结果Reduce + Broadcast

关键等式

All-Reduce = Reduce-Scatter + All-Gather

# 直觉:
# Reduce-Scatter: 每个 GPU 得到最终结果的 1/N
# All-Gather: 把所有片拼起来，每个 GPU 都有完整结果

带宽分析

# All-Reduce 的每-rank 通信量（ring algorithm，忽略延迟）:
# 每个 rank 发送并接收约: 2 × (N-1)/N × data_size
# 近似: 2 × data_size（与 N 无关！）

# Reduce-Scatter:
# 每个 rank 发送并接收约: (N-1)/N × data_size
# 近似: data_size

# All-Gather:
# 每个 rank 发送并接收约: (N-1)/N × data_size
# 近似: data_size

Data Parallelism (DP)

核心思想

每个 GPU 持有完整模型，处理不同的数据片。梯度通过 all-reduce 同步。

# Data Parallelism 流程
for each GPU in parallel:
    # 1. 获取不同的数据片
    x_local = data[rank * batch_size : (rank+1) * batch_size]

    # 2. 前向传播（本地计算）
    loss = model(x_local)

    # 3. 反向传播（计算本地梯度）
    loss.backward()

    # 4. 同步梯度（通信！）
    all_reduce(gradients)  # 所有 GPU 得到平均梯度

    # 5. 更新参数（所有 GPU 同步更新）
    optimizer.step()

通信开销

# 每步通信: 对梯度做 All-Reduce
# 若梯度 payload 为 S bytes，N-rank ring 的每-rank 通信量约为:
#   2 × (N-1)/N × S
#
# 理想带宽时间下界约为 通信字节数 / 有效 collective 带宽。
# 不能直接用 900 GB/s NVLink 聚合峰值或单条 NIC line rate 相除：
# 实际值取决于拓扑、NCCL 算法、并发、协议效率和计算/通信 overlap。

Gradient Accumulation

当 batch size 太大，单 GPU 放不下时：

# DDP 示意：把一个大 batch 拆成多个 micro-batch
optimizer.zero_grad()
for micro_batch in micro_batches[:-1]:
    with model.no_sync():
        (model(micro_batch) / len(micro_batches)).backward()

# 最后一次 backward 不使用 no_sync()，触发 gradient bucket all-reduce
(model(micro_batches[-1]) / len(micro_batches)).backward()
optimizer.step()

Gradient Accumulation 的好处：

  • 模拟大 batch size（对训练稳定性重要）
  • 减少通信频率（每 N 个 micro-batch 通信一次）
  • 通信量不变（最终还是要同步所有梯度）

DDP vs FSDP

策略参数存储通信内存
DDP每个 GPU 完整副本All-Reduce 梯度高（冗余）
FSDP / ZeRO-3参数按组分片，需要时 All-Gather前向/反向 All-Gather + 梯度 Reduce-Scatter模型状态可近似 1/N；激活与临时 buffer 另算

Tensor Parallelism (TP)

核心思想

把模型的宽度切分到多个 GPU——每个 GPU 只持有参数的一部分。

# 标准 Linear 层: Y = X @ W
# W: (D_in, D_out)

# Tensor Parallel: 把 W 按列切分
# GPU 0: W_0: (D_in, D_out/2)  → Y_0 = X @ W_0
# GPU 1: W_1: (D_in, D_out/2)  → Y_1 = X @ W_1

# 需要 All-Gather 把 Y_0 和 Y_1 拼起来: Y = [Y_0, Y_1]

Megatron-LM 的切分策略

对于 Transformer 的 FFN 和 Attention，有特定的切分方式：

# FFN / SwiGLU:
# W_gate 与 W_up 按输出维切分（column parallel）
# 每个 rank 保留自己的中间分片，先在本地做 Swish(gate) * up
# W_down 按输入维切分（row parallel），最后合并各 rank 的部分和

# Attention 的切分:
# W_q, W_k, W_v 按 head 切分（每个 GPU 负责部分 head）
# W_o 按输入维切分，最后合并各 rank 的部分和
#
# 基础 Megatron TP 常用 All-Reduce 合并；配合 sequence parallel 时，
# 相邻区域可改用 Reduce-Scatter / All-Gather 组合。

通信模式

# Transformer block 的 TP 通信:
# 1. Attention:
#    - Q, K, V 计算: 无需通信（head 独立）
#    - W_o: All-Reduce

# 2. FFN:
#    - W_gate, W_up 和逐元素门控: 本地分片计算
#    - W_down 后: All-Reduce（或 sequence-parallel 变体中的 Reduce-Scatter）

# 总计: 每个 block 2 次 All-Reduce

TP 的代价：每个 Transformer block 都有 activation collectives，通常位于关键路径；框架可以尝试 overlap，但其低延迟、高带宽需求仍然很强。

TP 通常优先放在节点内高带宽域。跨节点 TP 并非不可能，但是否划算取决于网络拓扑、消息大小和实现。

切分示例（4 GPU）

# 假设 d_model = 4096, num_heads = 32
# 每 GPU: 8 个 head, d_model_per_gpu = 1024

# W_q: (4096, 4096) → 切成 4 份: 每 GPU (4096, 1024)
# W_k: (4096, 4096) → 切成 4 份: 每 GPU (4096, 1024)
# W_v: (4096, 4096) → 切成 4 份: 每 GPU (4096, 1024)
# W_o: (4096, 4096) → 切成 4 份: 每 GPU (1024, 4096)

Pipeline Parallelism (PP)

核心思想

把模型的深度切分到多个 GPU——每个 GPU 持有连续的几层。

# Pipeline Parallel: 4 GPU, 16 层
# GPU 0: layers 0-3
# GPU 1: layers 4-7
# GPU 2: layers 8-11
# GPU 3: layers 12-15

# 数据流:
# Input → GPU 0 → activations → GPU 1 → ... → GPU 3 → Output

Pipeline Bubble

朴素的 pipeline 有大量空闲时间——"bubble"：

# 朴素 pipeline (4 stages, 1 batch):
# Time →
# GPU 0: [====L0-3====]  idle   idle   idle
# GPU 1:  idle  [====L4-7====]  idle   idle
# GPU 2:  idle   idle  [====L8-11===]  idle
# GPU 3:  idle   idle   idle  [====L12-15==]

# 对理想化流水线，bubble time / useful compute ≈ (p-1) / m
# 若写成总时间占比，则约为 (p-1) / (m+p-1)
# p = pipeline stages, m = micro-batches
# 当 m >> p 时，bubble 可以忽略

1F1B Schedule（One Forward One Backward）

减少 bubble 的关键技术：

# 1F1B: 每个 stage 交替做 forward 和 backward
# 而不是等所有 forward 做完再做 backward

# 1F1B 在 warmup 后交替安排 forward/backward，
# 相比先做完全部 forward 再 backward，通常降低峰值 activation memory。
# 它仍有 warmup/drain bubble；bubble 大小取决于 stage 数、micro-batch 数、
# stage 是否均衡以及采用 GPipe、1F1B、interleaved 或 zero-bubble 等 schedule。

通信量

# Pipeline Parallel 的通信:
# 每对相邻 GPU 之间只传 activations
# 数据量: batch_size × seq_len × d_model × 2 (bf16)

# 例如: 一个 bf16 activation tensor，B=4, S=4096, D=8192
# = 4 × 4096 × 8192 × 2 bytes = 256 MiB

# 反向还要传 activation gradients；若叠加 TP/sequence sharding，张量大小会变化。
# P2P 通信可以与其他 micro-batch 的计算 overlap，但受 schedule 和依赖约束。

TP vs PP 的选择：

  • TP：每层都有 collective，对低延迟和高带宽敏感，通常放在节点内。
  • PP：只在 stage 边界传激活/梯度，常用于跨节点，但需要足够 micro-batches 控制 bubble。

实际中：常见做法是先按高带宽域选择 TP degree，再用 PP/FSDP 让模型装得下，最后用 DP 扩展吞吐；这只是经验起点，不是固定拓扑。

Sequence Parallelism (SP)

动机

Tensor parallel 主要切分矩阵乘法的宽度维；LayerNorm、Dropout 等逐 token 区域仍可能复制 activation。Megatron 的 sequence parallel 用序列维分片这些区域，以继续降低 activation memory。

核心思想

# 标准 TP 只切分宽度维度
# Sequence Parallel 额外切分序列维度

# 具体做法:
# 1. LayerNorm / Dropout 是逐 token 独立的 → 自然在序列维度并行
# 2. 在 row-parallel / column-parallel 区域之间用 Reduce-Scatter 与 All-Gather
# 3. 让非 TP 区域的 activation 也随 TP degree 分片

# 效果: 相关 activation 可近似减少到 1/N
#
# 注意：这不同于为超长上下文设计的 context parallel / ring attention；
# 后者会分片 attention 所需的序列上下文，并引入不同通信模式。

混合并行策略

3D / 4D 并行

实际训练大规模模型时，所有并行策略组合使用：

# 常见 3D 并行分解:
# - 数据并行 (DP): 复制训练任务，处理不同数据
# - 张量并行 (TP): 切分单层矩阵计算
# - 流水线并行 (PP): 切分层
# - 序列并行 (SP): 配合 TP 分片部分 activation

# 总 GPU 数 = DP_degree × TP_degree × PP_degree

并行策略选择

场景推荐策略原因
模型状态单卡可放下DDP / ZeRO-1实现简单，主要同步梯度或优化器状态
模型状态需要分片FSDP / ZeRO-3 或 TP+PP在参数通信、activation 通信和 bubble 间权衡
高带宽节点内域常用于 TP / EP这些策略的 collective 更频繁
超长上下文SP + context parallel 等分别解决非 TP activation 与 attention context 分片

实际配置示例

# 训练 70B 模型，16 节点 (128 GPU):
# TP = 8 (节点内)
# PP = 4 (4 个 stages)
# DP = 128 / (8 × 4) = 4 (数据并行)
# 总计: 8 × 4 × 4 = 128 GPU

# 仅参数 shard（未考虑 embedding tie、负载不均等）:
# 70B / (TP 8 × PP 4) ≈ 2.19B 参数/GPU
#
# 但不能据此宣布“放得下”：梯度、master weights、Adam moments 是否再按 DP 分片，
# 以及 activation、temporary buffers、pipeline schedule 都会改变峰值内存。

通信量对比

并行策略通信类型每步通信量频率
DDP梯度 All-Reducering 每 rank 约 2(N-1)/N × gradient bytes通常每步，按 bucket 触发
Tensor Parallel每 block 约 2 个 activation collectives与 micro-batch × sequence × hidden × dtype 及 TP degree 同阶每层
Pipeline ParallelP2P activation / gradient每边界每 micro-batch 各传前向 activation 与反向 gradientstage 边界
FSDP / ZeRO-32× parameter All-Gather + gradient Reduce-Scatter若参数/梯度 payload 为 P bytes，大 N 下每 rank 约 3P每 FSDP unit

统一视角：

  • DDP：复制参数，同步梯度
  • FSDP：分片模型状态，按需收集参数并分散梯度
  • TP：分片参数，同步激活
  • PP：分片层，传递激活

每种策略都在"计算冗余 vs 内存节省 vs 通信开销"之间做权衡。
