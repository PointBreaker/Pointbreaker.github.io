形式化验证基础

什么是形式化验证？

传统测试：运行程序，检查输出是否正确。只能证明存在 bug，不能证明没有 bug。

形式化验证：用数学方法证明程序满足规范。可以证明不存在特定类型的 bug。

# 例: 排序函数的规范

# 传统测试:
def test_sort():
    assert sort([3, 1, 2]) == [1, 2, 3]
    assert sort([]) == []
    assert sort([1]) == [1]
    # 测试通过 ≠ 所有输入都正确

# 形式化验证 (Lean 风格):
def sort (list : List Nat) : List Nat := ...

theorem sort_is_sorted (list : List Nat) :
  sorted (sort list) := by
  -- 证明: sort 的输出总是有序的
  ...

theorem sort_is_permutation (list : List Nat) :
  Permutation list (sort list) := by
  -- 证明: sort 的输出是输入的排列（没有丢元素）
  ...

Lean 定理证明器

Lean 是一个开源的编程语言和证明助手：

  • 可以写程序、定义数学概念、陈述定理、构造证明
  • 内核极小（trusted kernel），所有证明都被严格检查
  • Mathlib：最大的形式化数学库之一（包含数万条定理）
  • 被 AWS（Cedar 授权语言）、Google DeepMind（AlphaProof）等使用

形式化验证 vs 测试

维度测试形式化验证
保证部分覆盖数学证明
适用范围所有程序需要可形式化的规范
成本低高（需要专业知识）
发现 bug可以可以（在证明过程中）
证明无 bug不能能（对特定属性）

程序合成

什么是程序合成？

从高层规范自动生成程序。LLM 是程序合成的一种实现方式。

# 传统程序合成:
# 输入: 规范（如类型签名 + 示例）
# 输出: 满足规范的程序

# 例: 合成一个 reverse 函数
# 规范:
# - 类型: List A → List A
# - 示例: reverse [1, 2, 3] = [3, 2, 1]
# - 属性: reverse (reverse xs) = xs

# LLM 程序合成:
# 输入: "写一个函数反转列表" (自然语言规范)
# 输出: 代码

# 关键区别:
# 传统: 规范是形式化的，可以验证
# LLM: 规范是自然语言的，无法严格验证

LLM 用于程序合成

现代 LLM（如 Codex、DeepSeek-Coder）可以进行程序合成：

  • 从自然语言描述生成代码
  • 从类型签名推断实现
  • 从测试用例反推实现

LLM 程序合成的根本问题：LLM 生成的代码看起来正确，但无法保证正确。测试通过 ≠ 正确。形式化验证可以提供这种保证，但 LLM 目前还不能可靠地生成形式化证明。

Verification-Guided Generation

核心思想

将 LLM 的生成能力与形式化验证的保证能力结合：

# Verification-Guided Generation:
#
# 1. LLM 生成候选程序
# 2. 形式化验证器检查正确性
# 3. 如果不通过，反馈给 LLM 重新生成
# 4. 重复直到通过或超时

# 伪代码:
def verify_guided_generate(spec, max_attempts=10):
    for attempt in range(max_attempts):
        # LLM 生成
        code = llm.generate(spec)

        # 验证器检查
        result = verifier.verify(code, spec)

        if result.is_valid:
            return code  # 通过！

        # 不通过，反馈错误信息
        feedback = result.error_message
        llm.add_feedback(feedback)

    return None  # 所有尝试都失败

优势

  • 正确性保证：输出的代码被验证器证明是正确的
  • 错误反馈：验证器可以指出哪里错了，帮助 LLM 改进
  • 组合性：可以组合多个已验证的组件

挑战

  • 规范难题：如何形式化"写一个排序函数"这样的自然语言需求？
  • 验证成本：形式化验证可能非常耗时
  • LLM 生成证明：让 LLM 生成可验证的证明仍然很困难
  • 搜索空间：可能的程序空间巨大，LLM 可能找不到正确的

验证 LLM 输出

为什么需要验证 LLM？

LLM 在许多场景中被使用，其中错误代价很高：

  • 代码生成：bug 可能导致安全漏洞
  • 数学推理：错误推理导致错误结论
  • 法律/医疗：错误建议可能导致伤害
  • 金融：错误交易可能导致损失

验证方法

方法适用场景保证程度
形式化验证代码、协议、算法数学证明
符号执行有限状态系统路径覆盖
类型检查类型化语言类型安全
运行时监控任何系统运行时的部分保证

LLM 输出的形式化验证

# 例: 验证 LLM 生成的排序算法

# Step 1: LLM 生成代码
code = llm.generate("写一个快速排序")

def quicksort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[0]
    left = [x for x in arr[1:] if x <= pivot]
    right = [x for x in arr[1:] if x > pivot]
    return quicksort(left) + [pivot] + quicksort(right)

# Step 2: 形式化规范
# 规范 1: 输出是有序的
# 规范 2: 输出是输入的排列
# 规范 3: 时间复杂度 O(n log n) 平均

# Step 3: 验证
# 用 Lean/Coq/Isabelle 证明代码满足规范
# 如果验证通过 → 数学保证正确

未来方向

1. LLM + 证明助手

让 LLM 直接生成形式化证明，由证明助手验证：

  • LLM 生成证明步骤
  • 证明助手检查每一步
  • 错误反馈帮助 LLM 改进

2. 神经符号方法

结合神经网络（LLM）和符号推理（证明助手）：

  • LLM 负责"直觉"和"搜索"
  • 符号系统负责"验证"和"推理"
  • 两者互补，取长补短

3. 可验证的 AI 系统

构建可以数学证明其行为正确的 AI 系统：

  • 安全边界：证明 AI 不会做某些事
  • 鲁棒性：证明 AI 对扰动的稳定性
  • 公平性：证明 AI 不会对特定群体歧视

4. 形式化 LLM 行为

用形式化方法描述和验证 LLM 本身的行为：

  • LLM 的哪些行为是可以证明的？
  • 如何形式化"helpful, harmless, honest"？
  • 能否证明 LLM 不会产生某些输出？

关键洞察：LLM 和形式化验证是互补的技术。LLL 擅长生成（但不可靠），形式化验证擅长验证（但需要规范）。将两者结合，可以构建既强大又可靠的 AI 系统。
