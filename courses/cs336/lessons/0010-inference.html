推理优化

训练阶段追求稳定地消化大批量 token；推理阶段面对的是动态请求、自回归生成和持续增长的 KV cache。同一套模型权重没有改变，但 workload 改变了，因此性能瓶颈和优化目标也随之改变。

授课：Percy Liang 预计用时：80 分钟 难度：中等 → 困难

Spring 2026 官方来源：Lecture 10 trace · 课程日程

本页是中文学习导读；讲次主题、教师与材料版本以 Stanford 官方页面和讲义为准。

这一讲到底解决什么问题？

前面主要讨论如何高效训练模型；推理面对的是另一种 workload：请求到达时间不固定，生成必须逐 token 推进，KV cache 会随上下文增长，而且延迟与吞吐量往往互相牵制。

因此本讲不把“推理”视为一次更小的训练 forward，而是回答：prefill 和 decode 各在搬什么、算什么，系统怎样在用户延迟、总吞吐和显存容量之间做权衡？

30 秒知识地图

prefill / decode workload → arithmetic intensity → 权重与 KV traffic → 压缩数据（GQA / MLA / quantization）→ 减少必须执行的步骤（speculative decoding）→ 用 continuous batching 与 PagedAttention 管理动态请求。

推理的应用场景

  • 实际使用：chatbots、代码补全、批处理
  • 模型评估：跑 benchmark
  • Test-time compute：thinking models（o1/o3）
  • RL 训练：采样生成

关键指标

指标定义重要性
TTFTTime-to-first-token用户等待时间
Latency秒/token生成速度

推理的算术强度分析

Prefill vs Generation

阶段并行形态更可靠的 mental model
Prefill一次处理 prompt 中的大量 token，容易形成较大的 GEMM并行度高，因而更容易进入 compute-bound 区域；是否真的 compute-bound 仍取决于 shape、batch、精度和 kernel
Decode MLP每个请求一次生成一个 token，但可把多个请求组成 concurrent batchbatching 提高权重 reuse 和 arithmetic intensity，因此并非永远 memory-bound
Decode attention新 query 必须读取随 context 增长的 KV cache当 \(T=1\) 时 arithmetic intensity 很低，通常强烈受 memory bandwidth 限制

“decode 是 memory-bound”只是入口，不是终点。需要把 MLP 的权重复用与 attention 的 KV cache traffic 分开分析，才能知道 batching 对哪里有效。

Deep Dive · MLP 与 attention 的 arithmetic-intensity 推导

MLP 层的算术强度

# MLP 前向传播（SwiGLU）:
# 读 X (B×T×D), W_gate (D×F), W_up (D×F), W_down (F×D)
# 计算: U = X @ W_gate, G = X @ W_up, Y = Swish(G)*U @ W_down
# 写 Y (B×T×D)

FLOPs = 6 × B × T × D × F
Bytes = 4BTD + 6DF + 4BTD + 4BTD + 4BTF + 4BTD
      ≈ 4BTD + 4BTF + 6DF (忽略写入)

# 假设 B*T << D, F:
算术强度 ≈ B*T

# Prefill: B*T 很大 → compute-bound
# Generation: B*T = B（batch size）
#   B=1: 强度 = 1 → memory-bound
#   B=100: 强度 = 100 → 接近 compute-bound

Attention 层的算术强度

# Attention（FlashAttention 优化后）:
# 读 Q (B×T×D), K (B×S×D), V (B×S×D)
# 计算: Q @ K^T, softmax, @ V
# 写 Y (B×T×D)

FLOPs = 4 × B × S × T × D
Bytes = 4BSD + 4BTD + 4BTD ≈ 4BSD + 4BTD

算术强度 = S*T / (S + T)

# Prefill: T = S → 强度 = S/2 → 大 S 时 compute-bound
# Generation: T = 1 → 强度 ≈ 1 → memory-bound

# 在这个一阶模型里 B 同时缩放 FLOPs 与 KV bytes，因此不会像 MLP 那样
# 直接提高权重 reuse；真实实现仍受 paged layout、并行度和 kernel 影响。

核心洞察：

  • Prefill 并行度高：较大的 \(B\times T\) 更容易形成高效 GEMM，但不是无条件 compute-bound。
  • Decode MLP 可以受益于 batching：并发请求越多，权重被复用得越充分。
  • Decode attention 特别敏感于带宽：新 token 必须读取不断增长的 KV cache，batching 很难消除这项流量。
Reference · 理想化延迟与吞吐量核算示例 
Llama 2 13B 在 H100 上的理论性能:

# Batch size = 1:
# 内存: 参数 26GB (bf16) + KV cache ~0.5GB
# 延迟: ~13 ms/token（受内存带宽限制）
# 吞吐量: ~77 tokens/s

# Batch size = 64:
# 内存: 26GB + 32GB KV cache
# 延迟: ~20 ms/token（更慢）
# 吞吐量: ~3200 tokens/s（更高！）

# 权衡: 大 batch → 高吞吐、高延迟
#        小 batch → 低延迟、低吞吐

这些数字只用于展示 batch 带来的方向性权衡，不应当作特定 serving engine、精度或软件版本的性能承诺。

KV Cache 压缩

为什么 KV cache 是瓶颈？

KV cache 大小（每 token 每 layer）:
MHA: n_heads × d_head × 2 (K+V) × 2 (bf16)
= 64 × 128 × 2 × 2 = 32 KB/token/layer

100K 序列, 80 层:
= 32 KB × 100K × 80 = 256 GB！

大 batch 时 KV cache 远超模型参数大小

GQA（复习）

GQA 把 KV cache 缩小 n_heads / n_kv_heads 倍
Llama 2 70B: 64 Q heads, 8 KV heads → 8× 缩小

Multi-head Latent Attention (MLA)

DeepSeek-V2 的 MLA:
不存完整的 K, V 向量
存一个低秩压缩的 latent 向量 c (C=512 维)
需要时通过上投影恢复

KV cache: 512 + 64 (for RoPE) = 576 维
vs MHA: 64 × 128 × 2 = 16,384 维
压缩比: 28×！

Cross-layer Attention (CLA)

跨层共享 KV:
GQA 是共享 KV across heads
CLA 是共享 KV across layers

例如: 每 4 层共享一组 KV
KV cache 缩小 4×

Local Attention

部分层用 local attention（只关注附近 token）
KV cache 不依赖序列长度！

混合策略（character.ai）:
- 每 6 层有 1 层 global attention
- 其余 5 层用 local attention
- 有效上下文 = window_size × num_layers

量化

为什么量化对推理有效？

许多逐 token decode workload 对权重与 KV 的 memory traffic 很敏感
减少表示大小 → 减少数据搬运 → 可能降低延迟并提高吞吐

量化级别:
fp32 (4 bytes) → bf16 (2 bytes) → fp8 (1 byte) → int4 (0.5 byte)

int4 相对 fp32 可把权重表示压缩到约 1/8；实际加速取决于 kernel、量化元数据、batch、瓶颈位置和硬件支持，不能直接等同于 8×。

Post-training Quantization (PTQ)

# 训练后量化: 不需要重新训练

# 简单量化（per-tensor）:
scale = max(abs(x)) / 127  # int8
x_quantized = round(x / scale)

# 问题: outlier 会导致精度大幅下降
# LLM 中有 ~0.1% 的 outlier（值特别大的元素）

LLM.int8()

Dettmers et al. (2022):
1. 对大多数元素做 int8 量化
2. 对 outlier 保持 fp16
3. 矩阵乘法: outlier 用 fp16, 其余用 int8

效果: 几乎无损，但 15-23% 更慢（因为混合精度）

AWQ (Activation-aware Weight Quantization)

Lin et al. (2023):
关键洞察: 不是所有权重都同等重要
对应大 activation 的权重更重要

方法:
1. 分析 activation 找出重要权重 (0.1-1%)
2. 重要权重保持 fp16
3. 其余量化到 int3/int4

效果: 4× 内存降低, 3.2× 加速

Supplement · 模型剪枝与蒸馏

模型剪枝与蒸馏

Pruning：删除低价值结构

剪枝试图移除对输出影响较小的权重、通道、attention heads 或整个层。非结构化稀疏只减少非零元素，若硬件/库不能跳过稀疏位置，wall-clock 不一定变快；结构化剪枝更容易映射到 dense kernel，但通常更伤精度。

  • 目标：让实际矩阵形状或可执行稀疏模式变小，而不是只让 checkpoint 更容易压缩。
  • 验证：同时报告质量、显存、TTFT、inter-token latency 与吞吐；不能只报告参数量。

Distillation：让更快的学生模仿教师

Spring 2026 官方 trace 给出的 recipe 是：先定义更快的 student 架构，再用原模型的输出/中间分布初始化或训练它，最后通过蒸馏修复精度。蒸馏可以与 GQA、local attention、较浅网络或更窄 hidden size 组合。

loss = alpha * cross_entropy(student_logits, labels) \
     + (1 - alpha) * kl_div(student_logits / T, teacher_logits / T) * T**2

# 关键权衡：教师生成数据有成本；student 的架构必须真的对应更低推理开销。

投机解码 (Speculative Decoding)

核心思想

关键洞察：验证比生成快。

给定一个序列，大模型可以一次性评估多个 token（像 prefill）。但生成一个 token 需要一次完整的前向传播。

投机解码：用小模型（draft）快速猜几个 token，然后用大模型一次性验证。

算法

投机解码 (Leviathan et al., 2023; Chen et al., 2023)

1. Draft 模型（小）生成 γ 个 token: d₁, d₂, ..., dᵧ
2. Target 模型（大）一次性评估: p(x|prefix + d₁ + ... + dᵧ)
3. 逐个验证:
- 如果 p(d₁) > q(d₁) → 接受 d₁
- 否则 → 从修正分布采样
4. 如果 d₁ 被接受，继续验证 d₂，直到拒绝或全部接受
5. 至少生成 1 个 token（保证进度）

关键: 生成的分布和直接采样完全一样！（数学保证）

为什么能加速？

不使用投机解码:
生成 γ 个 token → γ 次大模型前向 → γ × T_large

使用投机解码:
1 次 draft 前向 + 1 次大模型前向
→ T_small × γ + T_large
→ 如果 draft 足够准 ≈ T_large（一次前向生成 γ 个 token）

实际加速: 2-3×（取决于 draft 质量和接受率）

Draft 模型的选择

  • 独立小模型：7B draft for 70B target
  • 蒸馏模型：从 target 蒸馏出小的
  • Medusa：给 target 加多个预测头
  • EAGLE：用 target 的特征做 draft

动态批处理

问题：推理的 batch 是动态的

训练: 固定 batch, 固定长度
batch_size × sequence_length × hidden_dim

推理: 请求动态到达，长度不一
请求 1: 已生成 10 tokens
请求 2: 刚到达，prefill 中
请求 3: 已生成 100 tokens

朴素方案: 等所有请求完成再返回
→ 先到的请求被后到的拖慢

Continuous Batching（迭代级调度）

Yu et al. (2022) - Orca
不是等整个 batch 完成，而是每步都可以加入/移除请求

每个 decode step:
1. 检查是否有新请求到达 → 加入 batch
2. 检查是否有请求完成 → 移除
3. 对所有活跃请求做一步 decode

效果: 吞吐量 10-20× 提升

Selective Batching

问题: 不同请求长度不同，不能组成规则 tensor

解决方案:
- Attention: 每个序列单独处理（或 padding）
- 非 attention: 拼接所有序列 [total_tokens, hidden_dim]

这样非 attention 部分仍然高效

PagedAttention

问题：KV cache 内存碎片

朴素 KV cache 分配:
每个请求预留 max_seq_len 的空间

问题 1: 内部碎片
大多数请求远不到 max_seq_len
预留的空间浪费

问题 2: 外部碎片
不同请求的 KV cache 大小不一
内存中出现不连续的空洞

PagedAttention（操作系统启发）

Kwon et al. (2023) - vLLM

核心思想: 像操作系统管理内存页一样管理 KV cache

  1. 把 KV cache 分成固定大小的 block（如 16 tokens）
  2. 每个请求有一个 "页表"（block table）
  3. 按需分配 block，不需要连续

效果:
- 内存利用率从 ~40% 提升到 ~96%
- 支持更大的 batch size
- 支持共享前缀（system prompt）

Copy-on-Write

多个请求共享 system prompt 的 KV cache
当某个请求需要修改时，才复制

类似操作系统的 fork()

Serving engines：把算法变成动态系统

系统官方 trace 强调的定位
vLLMPagedAttention 与通用高吞吐 serving 的常用默认选择
SGLangRadixAttention / prefix reuse，适合 agentic 与共享前缀工作负载
TensorRT-LLMNVIDIA GPU 上高度优化的 kernel、量化和多 GPU runtime
llama.cppCPU / 本地推理与紧凑量化生态

引擎名称不是性能保证。最终结果取决于模型结构、量化格式、batch 到达过程、prefix reuse、GPU 型号和调度策略，必须在真实请求分布上测 TTFT、吞吐与尾延迟。

超越 Transformer

State Space Models

Mamba, Jamba, etc.
用 O(1) 状态替代 O(n) KV cache
推理时不需要存储整个 KV cache

但: 不擅长 associative recall
混合架构（Transformer + SSM）是当前趋势

Diffusion Models for Text

非自回归生成
所有 token 同时生成，多步 refinement

优势: 并行生成，速度快
劣势: 文本质量目前不如自回归

总结

推理优化的四个方向

方向技术效果
减少 KV cacheGQA, MLA, CLA, local2-32× 内存节省
减少模型成本量化、结构化剪枝、蒸馏降低权重流量与计算量；收益需实测
投机解码draft model2-3× 加速
系统优化continuous batching, paged attention10-20× 吞吐

核心原则：

  • Prefill 的并行度通常更高，更容易利用矩阵计算单元，但仍需按实际 shape 判断瓶颈。
  • Decode MLP 可以通过 batching 提高权重复用；decode attention 仍特别受 KV cache 带宽影响。
  • 压缩、量化与 speculative decoding 分别减少数据量、表示成本或串行生成步骤。
  • Continuous batching 与 paging 把单个算法放进动态请求系统，收益必须用真实到达分布验证。

如果只能记住 5 件事

  1. Prefill 与 decode 是不同 workload，不能用同一个“compute-bound / memory-bound”标签概括全部推理。
  2. 较大的 \(B\times T\) 让 prefill 更容易形成高效 GEMM；decode MLP 也能通过 batching 提高权重复用。
  3. Decode attention 必须持续读取随 context 增长的 KV cache，因此通常特别受 memory bandwidth 限制。
  4. GQA / MLA、量化和 speculative decoding 分别减少 KV、权重表示或串行生成步骤。
  5. Continuous batching 与 PagedAttention 解决动态请求和 KV 内存管理；最终应同时测 TTFT、inter-token latency、吞吐与尾延迟。
