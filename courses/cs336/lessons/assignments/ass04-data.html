这个 Assignment 要你做什么？

一句话总结：从 Common Crawl 的原始 HTML 网页出发，构建一个完整的数据处理 pipeline：提取文本、过滤低质量内容、检测有害信息、去重，最终产出可用于训练 LM 的高质量语料。

Assignment 4 是数据工程的实战。你会理解为什么"数据质量"是 LLM 训练中最被低估的因素之一，以及如何系统性地处理互联网规模的数据。

如何开始？

0

理解数据格式

Common Crawl 数据存储为 WARC 格式。先下载一个小样本（几百 MB），手动查看几个文件的结构。理解 HTTP header、HTML body、metadata 的位置。

1

文本提取

从 HTML 中提取纯文本是第一步。关键挑战：

  • 移除 boilerplate（导航栏、页脚、广告）
  • 保留有意义的正文内容
  • 处理不同语言的编码问题
  • 决定保留还是丢弃表格、列表等结构
2

训练质量分类器

你需要一个模型来判断"这段文本是否适合训练 LM"。思路：

  1. 定义"高质量"参考语料（如 Wikipedia、Books）
  2. 定义"低质量"参考语料（随机网页、垃圾内容）
  3. 设计特征，训练二分类器
  4. 在验证集上评估 precision/recall
3

MinHash 去重

互联网数据有大量近似重复（模板、爬虫镜像）。MinHash + LSH 是标准方案：

  • 选择合适的 shingle 大小（n-gram 长度）
  • 选择 hash 函数数量和 band 数量
4

Pipeline 调优

整合所有步骤，调整阈值参数。最终评估指标通常是：在固定 token budget 下，下游 LM 的 perplexity。

常见陷阱

编码问题： 互联网数据有各种编码（UTF-8, Latin-1, GBK...），还有 mojibake（编码错误导致的乱码）。不处理会导致 tokenizer 行为异常。

内存效率： Common Crawl 是 TB 级别的数据。不能把所有文件加载到内存。学会用流式处理、分块读写、外部排序等技术。

去重参数选择： MinHash 的 band 数和 row 数直接影响 recall 和 precision。太宽松的去重等于没做，太严格会误删有价值的内容。

质量分类器的 bias： 如果你的"高质量"参考语料主要是英文 Wikipedia，分类器可能会歧视其他语言或文体（如口语化文本）。

过度过滤： 过滤太激进会导致数据多样性下降，模型在长尾任务上表现变差。要在"干净"和"多样"之间权衡。

数据处理与评估方法

Pipeline 调试技巧

  • 从小样本开始：先用 100 个文件调试，确认逻辑正确后再放大
  • 记录过滤统计：每个阶段记录被过滤了多少、为什么
  • 人工检查样本：随机抽取保留/丢弃的样本，人工判断是否合理
  • 可视化分布：文本长度、质量分数、语言分布的直方图

最终评估

数据处理 pipeline 的终极目标是提升下游 LM 的性能。评估方式：

  • 用你的语料训练一个小 LM，测量 perplexity
  • 对比 baseline（未过滤/未去重）的效果
  • 注意控制变量：训练配置、token 数、模型大小保持一致

数据工程是 LLM 训练中最"脏"也最重要的工作。 模型架构的改进容易被关注，但数据质量的提升往往带来更大的实际收益。

背景

在实现任何处理流程之前，先浏览原始数据、建立直觉总是有益的。Common Crawl 数据以三种格式发布：

  • WARC（"Web ARChive format"）文件：包含原始 CC 数据，包括页面 ID 和 URL、元数据与 HTTP 请求详情（如请求日期时间、服务器 IP 地址），以及页面的原始内容（如 HTML）。

  • WAT（"Web Archive Transformation"）文件：包含从 WARC 文件提取并以 JSON 对象形式导出的高层元数据。例如，对于 HTML 页面，包含该页面的链接列表和页面标题。

  • WET（"Web Extracted Text"）文件：包含从原始 HTML 页面抽取的纯文本。

# 下载对应的 WET 文件
$ wget https://data.commoncrawl.org/crawl-data/CC-MAIN-2025-18/segments/1744889135610.12/wet/CC-MAIN-20250417135010-20250417165010-00065.warc.wet.gz

完整任务

背景

从 HTML 抽取文本具有挑战性。通常，任何抽取流程都会寻找 HTML 中的可见内容（如 <p> 标签，这些标签本应包含文本块），但这仍可能抽取远超我们在浏览器中打开页面时感知到的"主体内容"的部分。例如，打开 StackOverflow 时，主体内容在问题和回答中，但菜单选项、指向 StackExchange 其他无关页面的链接、页脚、登录/注册链接——这些全是可见文本，却很难可靠地与主体内容区分开。

许多工具实现了文本抽取流程。本作业使用 Resiliparse 库执行文本抽取。Resiliparse 还能帮助解决一个更基础的问题：检测包含原始内容的字节串的文本编码。尽管网上大多数页面使用 UTF-8 编码（据 Wikipedia 称占 98.2%），你的文本抽取流程仍应能稳健处理其他编码。

提示：建议使用 FastWARC 库遍历 WARC 文件中的记录。以下类可能有用：

from fastwarc.warc import ArchiveIterator, WarcRecordType
问题 (3 分)

(a) 编写一个函数，从包含原始 HTML 的字节串中抽取文本。使用 resiliparse.extract.html2text.extract_plain_text 执行抽取。该函数需要字符串作为输入，因此你需要先将字节串解码为 Unicode 串。注意输入的字节串可能不是 UTF-8 编码，因此你的函数应能在 UTF-8 解码失败时检测编码。Resiliparse 提供了 resiliparse.parse.encoding.detect_encoding()，可能会有所帮助。

交付物：一个接受 HTML 字节串并返回抽取文本字符串的函数。实现适配器 run_extract_text_from_html_bytes，并确保通过 uv run pytest -k test_extract_text_from_html_bytes。

(b) 在单个 WARC 文件上运行你的文本抽取函数，将其输出与对应 WET 文件中的抽取文本对比。你注意到哪些差异和/或相似之处？哪种抽取看起来更好？

交付物：2–3 句话的回答，对比你自己函数抽取的文本与 WET 文件中的抽取文本。

查看解题提示

  • 先用 resiliparse.parse.encoding.detect_encoding() 检测字节串编码，再用对应编码解码为字符串；若检测失败可回退到 UTF-8 并设置错误处理策略（如 errors='replace'）。

  • 使用 resiliparse.extract.html2text.extract_plain_text 时，可查阅其文档了解可选参数（如是否保留链接、图片说明等）。

  • 用 FastWARC 遍历 WARC 记录时，筛选 WarcRecordType.RESPONSE 类型的记录以获取页面内容。

  • 自检方法：选取几条记录，分别打印你的抽取结果与 WET 中对应文本，逐段对比差异。

完整任务

exact_deduplication精确行去重任务 · 提示 · 验收
Handout 完整本土化可离线实施不含参考实现

完整任务

背景

网页包含大量重复内容。一些页面是彼此的精确副本——想想存档，或标准工具生成的默认页面，比如流行 Web 服务器的 404 页面。但大多数重复发生在更细粒度的层面。例如，考虑 Stack Overflow 上的所有问题页面。虽然每个页面都有独特内容（例如问题、评论、答案本身），但所有页面也有大量冗余，比如页眉、菜单选项和页脚，在渲染所有这些页面时都会以精确形式重复。在本节的第一部分，我们将处理这种精确重复，之后再看如何处理近似重复。

一种简单的精确重复去重方法是只保留文档中在语料库内唯一的行。这足以消除大部分冗余，比如我们上面提到的页眉和菜单选项。在更简单的情况下，当移除在其他地方精确重复的行时，我们通常会留下每个页面的唯一主要内容（比如 StackOverflow 上的问题和答案）。

为此，我们可以对语料库进行一次遍历，统计观察到的每行出现次数。然后，在第二次遍历中，通过仅保留其唯一行来重写每个文档。

天真地，用于保存计数器的数据结构可能占用与存储语料库中所有唯一行一样多的空间。一个简单的内存效率技巧是改用行的哈希作为键，使键具有固定大小（而不是依赖于行的长度）。你现在将实现这种简单的去重方法。

minhash_deduplicationMinHash + LSH 文档去重任务 · 提示 · 验收
Handout 完整本土化可离线实施不含参考实现

完整任务

背景

精确去重对于移除在多个网页间逐字重复的内容很有用，但不能处理文档内容略有不同的情况。例如，考虑软件许可证文档——许可证文档通常从模板生成，需要年份和软件作者姓名。因此，一个 MIT 许可项目的许可证文件包含的内容与另一个 MIT 许可项目大体相同，但它们不是精确副本。为了移除这种重复的、大部分模板化的内容，我们需要模糊去重。为了高效执行模糊文档级去重，我们将使用 minhash 与局部敏感哈希（LSH）。

为了执行模糊去重，我们将使用文档间的一种特定相似度概念：每个文档 n-gram 之间的 Jaccard 相似度。集合 \(S\) 和 \(T\) 之间的 Jaccard 相似度定义为：

\[ J(S, T) = \frac{|S \cap T|}{|S \cup T|} \]

要天真地执行模糊去重，我们可以将每个文档表示为一组 n-gram，计算所有文档对之间的 Jaccard 相似度，将超过特定 Jaccard 相似度阈值的对标记为重复。然而，这种方法对于大型文档集合（例如 Common Crawl）不切实际。此外，天真地存储一组 n-gram 会比文档占用更多内存。

MinHashing

为了解决内存问题，我们将 n-gram 文档表示替换为签名。特别是，我们希望构造签名，使得当我们比较两个文档的签名时，得到文档各自 n-gram 集合之间 Jaccard 相似度的近似值。Minhash 签名满足这些性质。要计算文档 n-gram 集合 \(S = \{s_1, \ldots, s_n\}\) 的 minhash 签名，我们需要 \(k\) 个不同的哈希函数 \(h_1, \ldots, h_k\)。每个哈希函数将一个 n-gram 映射到一个整数。给定哈希函数 \(h_i\)，文档 n-gram 集合 \(S\) 的 minhash 为：

\[ \text{minhash}(h_i, S) = \min(h_i(s_1), h_i(s_2), \ldots, h_i(s_n)) \]

文档 n-gram \(S\) 的签名是 \(\mathbb{R}^k\) 中的一个向量，其中每个元素 \(i\) 包含在随机哈希函数 \(h_i\) 下 \(S\) 的 minhash，即：

\[ [\text{minhash}(h_1, S), \text{minhash}(h_2, S), \ldots, \text{minhash}(h_k, S)] \]

事实证明，对于两个文档 n-gram 集合 \(S_1\) 和 \(S_2\)，集合之间的 Jaccard 相似度近似于具有相同 minhash 值的列的比例（证明见 Leskovec et al., 2014 的第 3.3.3 节）。例如，给定文档签名 [1, 2, 3, 2] 和 [5, 2, 3, 4]，n-gram 集合之间的 Jaccard 相似度近似为 \(2/4\)，因为这些签名的第二和第三列具有相同的 minhash 值。

局部敏感哈希（LSH）

尽管 minhashing 为我们提供了一种内存高效的文档表示，保留了任意文档对之间的预期相似度，我们仍然需要比较所有文档对以找到相似度最高的。LSH 提供了一种高效分桶可能具有高相似度的文档的方法。要将 LSH 应用于我们的文档签名（现在是 \(\mathbb{R}^k\) 中的向量），我们将签名分成 \(b\) 个带（band），每个带包含 \(r\) 个 minhash，其中 \(k = br\)。例如，如果我们有 100 元素的文档签名（由 100 个随机哈希函数生成），我们可以将其分成 2 个带各 50 个 minhash，或 4 个带各 25 个 minhash，或 50 个带各 2 个 minhash，等等。如果两个文档在某个带具有相同的哈希值，它们将被聚到同一桶中，并被视为候选重复。因此，对于固定数量的签名，增加带的数量会增加召回率并降低精确率。

对于上述的具体例子，假设文档 D1 的 minhash 签名为 [1, 2, 3, 4, 5, 6]，文档 D2 的签名为 [1, 2, 3, 5, 1, 2]。如果我们使用 3 个带各 2 个 minhash，则 D1 的第一带是 [1, 2]，D1 的第二带是 [3, 4]，D1 的第三带是 [5, 6]。类似地，D2 的第一带是 [1, 2]，D2 的第二带是 [3, 5]，D2 的第三带是 [1, 2]。由于第一带的哈希值匹配（两个文档都是 [1, 2]），D1 和 D2 将在第一带下被聚到一起。它们不会在任何其他带下被聚到一起，因为哈希值不匹配。然而，注意由于文档在至少一个带下被聚到一起，它们将被视为候选重复，无论其他带是否匹配。

一旦我们识别出候选重复，可以以多种方式处理它们。例如，我们可以计算所有候选重复之间的 Jaccard 相似度，将超过设定阈值的对标记为重复。

最后，我们在桶之间聚类重复文档。例如，假设文档 A 和 B 在一个桶中匹配且真实 Jaccard 相似度高于我们的阈值，文档 B 和 C 在另一个桶中匹配且真实 Jaccard 相似度也高于我们的阈值。那么，我们将文档 A、B 和 C 视为单个聚类。我们随机移除每个聚类中除一个以外的所有文档。

    total=len(lines),

pool.close()

# Flatten the list of ids and convert to numpy array
all_ids = [token_id for sublist in results for token_id in sublist]

问题描述

在你完成数据过滤与 tokenize 之后，现在要在处理好的数据集上训练一个语言模型，并以验证损失作为最终提交指标。

训练目标

  • 训练一个 GPT-2 small 形状的模型，在生成的数据上跑 200K iterations，并周期性地在 C4 100 domains 验证集上评估性能。

  • 作业的目标是通过构造最优数据来最小化验证损失，而不是通过修改模型或优化过程来降低损失。

  • 不要修改训练配置（除数据路径与 wandb 属性外），也不要修改训练脚本。

配置与启动

  1. 打开配置文件 cs336-basics/configs/experiment/your_data.yaml：

  • 将 paths.train_bin 指向你的 tokenized 训练数据文件。

  • 设置合适的 training.wandb_entity 与 training.wandb_project 用于日志记录。 2. 超参数位于 cs336-basics/cs336_basics/train_config.py，训练使用 2 块 GPU、data parallel、每设备 batch size 128。一次训练大约需要 7 小时，请预留足够时间。 3. 使用 cs336-basics/scripts/train.py 启动训练，命令如下：

uv run torchrun --standalone --nproc_per_node=2 scripts/train.py --config-name=experiment/your_data

调试与采样（可选）

  • 在测试数据时，可以将 training.save_checkpoints 设为 True，这样每次评估验证损失时都会保存一个 checkpoint：
uv run torchrun --standalone --nproc_per_node=2 \
  scripts/train.py --config-name=experiment/your_data \
  +training.save_checkpoints=True
  • checkpoint 会保存到 cs336-basics/output/your_data/step_N，之后可以用以下命令从模型中采样：
uv run python scripts/generate_with_gpt2_tok.py \
  --model_path cs336-basics/output/your_data/step_N

排行榜提交

  • 将你在验证集上取得的最佳验证损失提交到排行榜。

  • 排行榜通过向 github.com/stanford-cs336/assignment4-data-leaderboard 提交 PR 进行，详见该仓库的 README.md。

交付物

  • 记录到的最佳验证损失；

  • 对应的学习曲线；

  • 对你所做工作的描述（数据构造思路、过滤策略、迭代过程等）。

分值

本题共 2 分。

先修概念与准备：

  • 确认已完成 tokenize_data，tokenized 数据是以 np.uint16 序列化保存的整数 ID 数组，且每条文档后都附加了 <|endoftext|> 结束符。

  • 确认 cs336-basics/configs/experiment/your_data.yaml 中的 paths.train_bin、training.wandb_entity、training.wandb_project 均已正确设置。

实施顺序： 1. 先用小批量数据或较短训练验证流程是否能正常启动，排除路径与配置错误。 2. 正式启动 200K iterations 训练，利用 wandb 监控验证损失曲线。 3. 若需调试数据质量，开启 +training.save_checkpoints=True，在关键 step 保存 checkpoint 并用 generate_with_gpt2_tok.py 采样检查生成质量。

调试策略：

  • 若训练无法启动，优先检查 train_bin 路径是否指向实际存在的 tokenized 文件，以及 wandb 凭证是否配置正确。

  • 若验证损失异常高，回头审视过滤与质量分类器阈值是否过严/过松，或检查是否误引入了与验证集分布差异过大的数据。

  • 若训练时间紧张，可先用子集快速迭代过滤策略，再在最终数据上跑完整训练。

自检方法：

  • 对照作业目标确认没有改动模型架构、优化器超参数或训练脚本逻辑。

  • 确认最佳验证损失来自 C4 100 domains 验证集，并在学习曲线上标注对应 step。

  • 确保排行榜提交值与本地记录的验证损失一致。
