Lab 3：容错键值服务

从状态设计、实现步骤到故障注入的完整动手路线。

完成标准

本导读给出可独立实施的架构、状态、不变量和测试路线；官方 starter code 的函数签名、测试名与提交规则可能随学期变化，开始编码前请从官方课程表进入对应 Lab 核对。

前置准备

  • 通读依赖讲义，并用自己的话写出安全性与活性目标。
  • 先运行原始测试并保存基线；启用 Go race detector。
  • 禁止用固定 sleep 代替状态条件，禁止持锁执行阻塞 RPC/channel 操作。

分步实现

  1. Clerk 生成稳定 clientID 与递增 requestID；超时重试同一请求，并记住最近 leader 以优化下一次尝试。
  2. 服务端把 Get/Put/Append 统一封装为 Op 交给 Raft；为日志 index 建等待通道，但必须核对最终应用的 clientID/requestID。
  3. 状态机保存 KV 数据与去重表；重复请求直接返回缓存结果。去重更新与业务更新必须由同一条已提交日志原子驱动。
  4. 当 Raft state 超过阈值时编码 KV、去重表与 lastApplied 创建快照；恢复时在对外服务前装载。

状态设计清单

类别必须回答的问题
权威状态谁能修改？是否需要复制或持久化？
请求身份重复、迟到和跨重启请求如何识别？
完成条件何时可对客户端返回成功？
后台任务如何停止、重试并避免 goroutine 泄漏？

测试矩阵

  • 用单客户端建立串行 oracle。
  • 多客户端并发 Append 后检查每段恰好出现一次。
  • 隔离旧 leader 并让请求超时重试。
  • 在请求进行中持续重启服务器并触发快照。
go test -race ./...
go test -run TestName -count=20
go test ./... > test.log

调试方法

  1. 日志至少记录节点、term/config、index、request ID 和状态转换；不要只打印“failed”。
  2. 固定随机种子复现失败，再缩小到最短事件序列。
  3. 断言单调量：term、commitIndex、lastApplied 和配置号不得倒退。
  4. 测试结束确认 ticker、RPC 重试和等待通道全部退出。

自我验收

能够解释每一个锁、持久化点、重试循环和超时；能够画出一次正常执行与一次故障恢复；连续多轮竞态测试通过后再提交。本站不提供答案代码，避免破坏实验的学习目标。
