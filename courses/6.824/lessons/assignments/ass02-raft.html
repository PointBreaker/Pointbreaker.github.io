Lab 2：Raft

从状态设计、实现步骤到故障注入的完整动手路线。

完成标准

本导读给出可独立实施的架构、状态、不变量和测试路线；官方 starter code 的函数签名、测试名与提交规则可能随学期变化，开始编码前请从官方课程表进入对应 Lab 核对。

前置准备

  • 通读依赖讲义，并用自己的话写出安全性与活性目标。
  • 先运行原始测试并保存基线；启用 Go race detector。
  • 禁止用固定 sleep 代替状态条件，禁止持锁执行阻塞 RPC/channel 操作。

分步实现

  1. 2A：实现 follower/candidate/leader、随机选举超时、RequestVote 与空心跳；收到更高 term 原子更新 term、清空投票并降级。
  2. 2B：实现 Start、AppendEntries 前缀匹配、冲突截断、nextIndex/matchIndex 与多数提交；按索引单调发送 ApplyMsg。
  3. 2C：在可见 RPC 响应前通过 persist 保存 term、vote、log；重启后读取并恢复。所有旧 goroutine 回复必须核对 term 与角色。
  4. 2D：实现 snapshot/InstallSnapshot；保留 lastIncludedIndex/Term，原子保存状态与快照，处理日志完全落后于快照的 follower。

状态设计清单

类别必须回答的问题
权威状态谁能修改？是否需要复制或持久化？
请求身份重复、迟到和跨重启请求如何识别？
完成条件何时可对客户端返回成功？
后台任务如何停止、重试并避免 goroutine 泄漏？

测试矩阵

  • 选举：稳定网络恰好一个 leader，断开后多数侧产生新 leader。
  • 一致性：反复隔离旧 leader，其未提交项不能覆盖已提交项。
  • 恢复：随机 kill/restart，并在重启后继续提交。
  • 资源：检查 RPC 字节数、goroutine 泄漏与竞态。
go test -race ./...
go test -run TestName -count=20
go test ./... > test.log

调试方法

  1. 日志至少记录节点、term/config、index、request ID 和状态转换；不要只打印“failed”。
  2. 固定随机种子复现失败，再缩小到最短事件序列。
  3. 断言单调量：term、commitIndex、lastApplied 和配置号不得倒退。
  4. 测试结束确认 ticker、RPC 重试和等待通道全部退出。

自我验收

能够解释每一个锁、持久化点、重试循环和超时；能够画出一次正常执行与一次故障恢复；连续多轮竞态测试通过后再提交。本站不提供答案代码，避免破坏实验的学习目标。
